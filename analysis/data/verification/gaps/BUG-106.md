# Замечания верификаторов к BUG-106

Источник: data/verification/batch7.json

## Пробелы промпта (воспроизводящий агент)

1) Процитирована ошибка Vitest только для .js: «RolldownError: Parse failure… 3 errors» из ssrTransform/parseAstAsync. Для .ts модуль падает раньше, в плагине vite:oxc (transformWithOxc), с другим текстом: «Transform failed with 2 errors: [PARSE_ERROR] HTML comments are not allowed in modules». Фраза «Vite 8 разбирает модули parseAst» неполная: точек разбора две. Отчёт Mootant текст ошибки не показывает, и промпт не говорит, как его увидеть: нужно вручную подставить switched-тексты и запустить vitest.
2) Пункт критерия готовности «дополнить дифференциальный тест программой с /<!--[\s\S]*?-->/g» не ловит регрессию. Программы PROGRAMS не содержат синтаксиса модуля и исполняются как скрипт (transformWithOxc + vm.runInThisContext), поэтому такая программа на 170ec52 проходит (проверено: 2/2 зелёные). С export тест падает на «ожидаемой» стороне: test/helpers/apply-mutant.ts:61 тоже оборачивает replacement в скобки («${guard}(${replacement})»), а runInThisContext не исполняет export. Промпт не говорит, что applyMutant («the way the mutant switch will host it») нужно менять синхронно с render-mutant-range.ts. Утверждение «физически применённый мутант разбирается» верно только для дословной подстановки, не для хелпера репозитория.
3) test/core/instrument/instrumenter-version.test.ts фиксирует expect(INSTRUMENTER_VERSION).toBe(1). Требуемый подъём версии сломает этот тест, в промпте это не упомянуто.
4) Не описаны детали триггера, важные для исправления:
   - пробел, перевод строки или комментарий между «(» и литералом не помогают, так что «вставить пробел» — не исправление;
   - ломается и выражение, которое начинается с такого литерала, например «(/<!--x/g.source)»;
   - «(c ? 1 : (/<!--x/g))» тоже ломается;
   - скобки if(/while( не затронуты; «/<!-» (одно тире) не триггерит.
   Предложенный вариант (без скобок вокруг текста, начинающегося с /) проверен и разбирается.
5) Юнит-тест — прокси: он разбирает текст собственным oxc-parser Mootant (0.156.0). Если поднять oxc-parser до исправленной версии, тест станет зелёным без исправления для пользователей Vite 8.3.5 (rolldown 1.2.16 = oxc 0.156). Промпт об этом не предупреждает.
6) Не сказано, как собрать tgz для run.sh. В примере стоит /path/to/mootant.tgz, а по умолчанию в run.sh — путь, специфичный для этой машины. run.sh глушит вывод npm (--silent >/dev/null 2>&1 при set -e), поэтому сбой установки завершит скрипт молча. При этом здесь run.sh с vitest 5.0.5 на npm 10.9.9 отработал благодаря --legacy-peer-deps; на vitest 5.1.0 результат тот же.

## Скептик (refuted=false, severity=medium)

Опровергнуть BUG-106 не удалось ни по одному из пунктов (а)–(г). Находка подтверждена, серьёзность medium обоснована.

(в) Код прочитан верно. render-mutant-range.ts:91-95 берёт в скобки и replacement, и original: `${check} ? (${replacement}) : ` и `(${original})`. В createSwitchedFiles (create-switched-files.ts:74-104) разбор JS/TS не проверяется, проверяется только компиляция Svelte/Vue. parse-file.ts:77 вызывает parseSync с sourceType из get-parser-options.ts: для .js/.ts это 'unambiguous'. INSTRUMENTER_VERSION находится в instrumenter-version.ts:6.

Путь в Vite 8.3.5 проверен по коду пакета:
- .js: ssrTransformScript вызывает parseAstAsync(code) без опций (vite/dist/node/chunks/node.js:16494). Ошибка: «RolldownError: Parse failure… HTML comments are not allowed in modules».
- .ts: падает раньше, в плагине vite:oxc. transformWithOxc (node.js:7593-7618) всегда передаёт lang, поэтому sourceType не задан. Ошибка: «Transform failed with 2 errors: [PARSE_ERROR] HTML comments are not allowed in modules».
- Неточность промпта, на вывод не влияет: он называет только parseAst, а для .ts срабатывает oxc-трансформ. Это та же ошибка лексера oxc.

(б) Это не артефакт окружения. Ошибка детерминированная, тайминги, root и TERM на неё не влияют.
- Матрица разбора (scripts/parse-matrix.mjs) на oxc-parser 0.156.0 и 0.157.0 (latest) и на rolldown 1.2.16 (latest) совпала с промптом во всех 6 кейсах. `( /<!--x/g)` и `(\n/<!--x/g)` тоже падают. `if (/<!--/.test(s))` разбирается.
- Сквозной прогон выполнен на vitest 5.1.0 (не 5.0.5) + vite 8.3.5 (latest), установка без --legacy-peer-deps: 9/9 Error, 2 instrumentation-break, exit=1. Тот же проект на vite 7.3.1: 6 Killed, 3 Survived, score 66.67, exit 0, как в промпте.
- Фикстуры только с .ts и только с .js (e2e-v8-only-ts/-js) падают независимо друг от друга: 3/3 и 6/6 Error.
- Switched-текст я собрал упакованным dist/core/instrument/instrument-file.js. Обычный vitest на нём падает с указанной ошибкой.

(а) Ни задокументированным, ни задуманным это поведение не является.
- compatibility.mdx:40-43: «uses the project's installation of Vitest 5, its configuration and Vite plugins». Ограничений по мажорной версии Vite нет.
- У vitest 5.0.5 обязательный peer `vite: ^6.4.0 || ^7.0.0 || ^8.0.0`, поэтому npm/pnpm по умолчанию ставят 8.3.5. Сам Mootant разрабатывается на vite 8.3.5.
- В docs/content/mutators/regex-pattern.md:190 в качестве примера стоит именно `/<!--[\s\S]*?-->/g`.
- Диагностика instrumentation-break — это защитный механизм на случай поломки, а не задуманный результат для валидного кода.
- Исходный код проекта под тем же тулчейном проходит: plain vitest passes. Конструкцию `(/<!--` создаёт сам Mootant.
- Пример из vuejs/core реален: escapeHtml.ts:48 `/^(?:-?>)+|<!--|-->|--!>|<!-$/g` (проверено по raw GitHub). `mootant list` даёт для него replacement regex-pattern `/<!--|-->|--!>|<!-$/g`.
- Побочное утверждение тоже подтвердилось: источник с `return (/<!--/).test(s)` `mootant list` отвергает с parse-error, а Node выполняет этот код как ESM.

(г) Серьёзность не завышена, местами она даже недооценена. Почему не high/critical:
- ложных Killed/Survived нет;
- Error исключаются из score (cli.mdx:61-63);

Почему не low:

Тест-файл, который не загрузился, ничего не покрывает, и findBrokenFiles (run-dry-phase.ts:505-517) помечает все related-файлы.
