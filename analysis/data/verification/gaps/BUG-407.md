# Замечания верификаторов к BUG-407

Источник: data/verification/batch3.json

## Пробелы промпта (воспроизводящий агент)

1) Критерии готовности противоречат друг другу (самое важное). Скрипт промпта и run.sh жёстко прописывают node_modules/.cache/mootant/run-v3.json. Промпт при этом требует поднять CACHE_VERSION, а имя файла кэша — `run-v${CACHE_VERSION}.json` (core/cache/get-cache-path.ts:19). После правильного исправления файл станет run-v4.json, и скрипт под `set -eu` упадёт на `cp ... run-v3.json`. run.sh в этом случае завершится с кодом 1, то есть так же, как при «баг есть». Нужно указать run-v4.json или glob run-v*.json и поправить run.sh.
2) Не сказано, как получить .tgz в чистом клоне. dist/ в .gitignore, prepack-скрипта нет, поэтому нужно явно выполнить `pnpm install && pnpm build && pnpm pack`. Без сборки получится пакет без dist.
3) Подъём CACHE_VERSION сломает test/core/cache/cache-version.test.ts: там жёстко `toBe(3)` и `/run-v3\.json$/`. Это не упомянуто. Заодно: пример в JSDoc core/cache/get-cache-path.ts:11 уже устарел (run-v2.json).
4) `test:usage` описан как «проверка собранного пакета», а это knip. Скрипта, который проверяет собранный пакет, нет, так что указание «проверь, что pnpm build и test:usage его создают» сбивает с толку.
5) prepare-run-cache.test.ts назван местом, где проверяется штамп, хотя там его нет. Не сказано, что поле build сейчас типа number, а get-environment-key.test.ts передаёт числа: при переходе на хэш придётся менять тип в EnvironmentInput и тесты.
6) Не указаны версии, на которых проверялось (node 22.23.4, npm 10.9.9). Не сказано, что с vitest@5 (5.1.0) --legacy-peer-deps не нужен и баг воспроизводится так же.
7) Мелочи. Скрипт промпта не удаляет каталог из mktemp (нет trap). Не сказано, что баг «безопасный»: вердикты не становятся неверными, теряется только переиспользование кэша. Это полезно для приоритизации. Для pnpm стоит уточнить, что ключ сохраняется при переустановке из того же store и меняется при новом store (на другой машине или в CI без кэша store) — я проверил оба случая.

## Скептик (refuted=false, severity=low)

ОПРОВЕРГНУТЬ НЕ УДАЛОСЬ: баг настоящий. Код прочитан верно, это не артефакт окружения. Но серьёзность завышена: medium → low.

(в) Код прочитан верно.
- core/cache/prepare-run-cache.ts:164 — `build: (await stat(import.meta.filename)).mtimeMs`.
- core/cache/get-environment-key.ts:76 — штамп входит в digest; :47-50 — JSDoc поля (штамп нужен, чтобы пересборка невыпущенной версии не переиспользовала старые вердикты).
- Смена штампа меняет environment key, а через него ключи всех тестовых файлов и incremental-ключи (prepare-run-cache.ts:176-202).

(б) Не артефакт окружения.
- npm ставит текущее время безусловно: /opt/node22/lib/node_modules/npm/node_modules/pacote/lib/fetcher.js:426 `noMtime: true`. Root, TERM и нагрузка ни при чём.
- В tgz все mtime нормализованы pack'ом к 1985-10-26 08:15:00, поэтому для установки из архива штамп = время установки.
- Воспроизвёл на vitest@5 (5.1.0) без `--legacy-peer-deps`, скрипт /home/user/projects/verify-skeptic/BUG-407/seq.sh, 2 из 2 попыток:
  - same install 3/3 cached;
  - reinstalled 0/3;
  - old mtime back 3/3.
- Результат детерминирован: сравнивается точное mtime, тайминги не влияют.
- Копия проекта в другом каталоге (/home/user/projects/verify-skeptic/BUG-407/npm2): `npm ci` и восстановленный кэш дают 0/3; принудительно старый mtime даёт 3/3. Значит, в остальном ключ переносим, и mtime — единственное препятствие. Это соответствует замыслу get-portable-path.ts:4-7.
- Утверждение про pnpm подтверждено (/home/user/projects/verify-skeptic/BUG-407/pnpm1): после `rm -rf node_modules && pnpm install --offline` mtime не меняется (жёсткая ссылка из store, nlink=18), 3/3 cached.

(а) Не задуманное и не задокументированное поведение. Поле build по JSDoc только различает пересборки. Инвалидация при переустановке тех же байтов — побочный эффект: configuration.mdx:352-355 обещает переиспользование, пока не меняются мутируемый файл и то, что читают тесты. Но перенос кэша между установками или CI-прогонами нигде не документирован:
- readme.md:63-64 и getting-started.mdx:123-136 для CI советуют только `--since`/`--threshold`;
- кэш лежит в node_modules/.cache (get-cache-path.ts:5-7), то есть по соглашению одноразовый.

(г) Серьёзность завышена. Аргументы за low:
1. Влияет только на скорость, причём в безопасную сторону. Ложного переиспользования и неверных вердиктов нет, все мутанты просто прогоняются заново. На доверие к вердикту не влияет. После одного полного прогона кэш снова работает (проверено: touch даёт промах, следующий прогон — попадание).
2. Нужен кэш, переживший переустановку. Так бывает редко:
   - `npm ci` удаляет весь node_modules вместе с .cache/mootant (проверено);
   - обычный `npm install` и добавление другой зависимости mootant не перераспаковывают, mtime не меняется (проверено);
   - любая смена зависимостей меняет lockfile, а он по замыслу входит в ключ (prepare-run-cache.ts:120-124), так что кэш сбросится и без этого бага.
   
   Остаётся только недокументированный сценарий: тот же lockfile, свежая установка и явно восстановленный node_modules/.cache/mootant (CI-cache, Docker cache mount, кэш от коллеги).
3. У pnpm (на той же машине или с закэшированным store) бага нет. Не страдает и CI, где кэшируют весь node_modules целиком: tar сохраняет mtime.
4. По шкале этого же анализа medium стоит у находок с устаревшими или ложными вердиктами: BUG-402/403/410/419/602. BUG-407 явно ниже.

Почему не not-a-bug:
- npm — документированный способ установки (readme.md:75-78). В CI, который сохраняет кэш mootant между прогонами, кэш с npm не сработает ни разу.
- Промах молчаливый. При попадании печатается «Reused cached verdicts for 3 of 3 mutants» и «3 cached», при промахе про кэш ничего.
- mtime пакета из tgz вообще не годится как ID сборки. Предложенный хэш содержимого разумен.

Неточности промпта (опровержением не являются): репро на vitest@5.0.5 в npm 10.9.9 упирается в баг arborist, но на vitest@5.1.0 находка воспроизводится так же. Сценарий «установка у коллеги» не поддерживаемый.
