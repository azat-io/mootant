## Пробелы промпта (воспроизводящий агент)

1) Сквозная проверка опирается на фикстуру analysis/data/skips/fx1. Она есть только в ветке analysis/2026-11, в azat-io/mootant её нет. Текст test/root.test.js в промпт не вставлен. Её package.json указывает на несуществующий tgz и фиксирует vitest 5.0.5 (баг arborist в npm 10.9.9), поэтому npm install на месте не пройдёт. Не хватает: команды сборки пакета (pnpm build && pnpm pack) или запуска через `mootant list --skipped`, а также указания, как увидеть выживших (settings.timeouts=true даёт score 60% вместо 100%).
2) «Ожидаемое поведение» не говорит, выходы какого цикла считать, когда тест покидает несколько бесконечных циклов. getExitedLoops возвращает их все, а getRunningValue берёт только внутренний. Пример: for(;;){for(;;){if(a())return 1; if(b())break}}. Здесь a()→false должен остаться в пропуске: у внешнего цикла другого выхода нет, хотя у внутреннего есть. А b()→false нужно выдавать. Наивный подсчёт выходов внутреннего цикла даст ложные выдачи (их поймает hitLimit, но это лишние Timeout). Также не оговорено, что считать выходом: throw внутри try/catch в цикле, break из вложенного switch или цикла, labeled break/continue.
3) Совет «посчитать выходы в get-exited-loops.ts» не предупреждает о последствиях. getExitedLoops — публичный API: core/index.ts:13 → MutatorContext.syntax: SyntaxHelpers → types/syntax/syntax-helpers.d.ts:30-32. Кроме того, его используют advances-loop.ts:139 (loop-advance) и get-leave-now-value.ts:44 (O13). Безопаснее отдельный хелпер.
4) Не названы место определения правила (core/skips/skip-rules.ts:234-237, get-loop-running-skip.ts) и потребитель get-comparison-plan.ts:442-447 ('=='/'!='). Не сказано, что JSDoc у RunningValue и getRunningValue («keeps the loop running forever», «innermost one») тоже нужно править.
5) В доказательной части нерелевантна выборка unskip: в ней нет мутантов класса BUG-310. Прямое доказательство даёт физический прогон таких мутантов в core. Я его сделал: 4 из 5 завершаются и убиваются, 1 (find-lockfile.ts:33) реально бесконечен и станет Timeout через hitLimit.
6) Полезно было бы указать, что фикстура списка test/fixtures/list/source/catalog.ts содержит 2 теста выхода с одним выходом и ни одного с несколькими. Значит, при корректном исправлении expected-skipped.json не меняется, а файл служит регрессией.
7) Мелочи: строки абзаца документации (condition.md:40-43) не указаны. Текст репро-теста в промпте без JSDoc-комментария над findRoot (на суть не влияет).

## Скептик (refuted=false, severity=low)

ИТОГ. Факт верен и не зависит от окружения. Но это граница задокументированной консервативной эвристики, а не скрытый дефект. Эмпирика в промпте относится к другим мутантам, практическая польза почти нулевая. Поэтому серьёзность low, а не medium.

1. Воспроизведение (подтверждает факт; пункт (б) не применим).
- test/repros/BUG-310.test.ts в /home/user/wt/bug-repros: оба теста падают (vitest 5.0.5).
- Пакет tgz + vitest 5.1.0 (/home/user/projects/verify-skeptic/BUG-310/fx): `list --skipped` показывает `current.isRoot -> false` и `current.parent === null -> false` как `timeout loop-running`. С recommended все 3 мутанта root.js убиты. С `--preset strict` оба `false` выживают.
- Листинг статический и детерминированный, так что root, TERM, загрузка машины и npm ни при чём.

2. (а) Поведение задокументировано, но расходится с заявленным намерением.
- docs/content/mutators/condition.md:40-43: «The same goes for `false` in an `if` that leaves an endless loop, such as `if (done) break` in `while (true)`». Это общее правило для любого такого `if`, без оговорки про единственный выход; `if (done) break` — только пример.
- docs/content/mutators.md:40 определяет категорию timeout как «may loop forever», :46 — «not a proof». configuration.mdx:149,221,268-271: recommended оставляет такие мутанты в стороне. Пропуск виден в `--skipped` с причиной «false may keep the loop running forever».
- Однако types/config/preset-settings.d.ts:39-40 и core/presets/recommended.ts:5-9 обещают исключать только «mutants that only a timeout can kill». JSDoc get-running-value.ts:38-39 говорит «keeps the loop running forever». Для цикла с несколькими выходами оба утверждения неверны. Это реальное противоречие, поэтому находку не опровергаю.
- Тесты фиксируют только цикл с одним выходом: condition.test.ts:613-615, get-condition-constants.test.ts:403-410.
- `hasOtherExit` добавлен в df9ee04 (2026-10-30) только для one-way-counter (get-comparison-plan.ts:578-603). К loop-running его не применили ни для `false`, ни для `true`.

3. (в) Доказательства в промпте прочитаны неверно.
- «5 из 7 loop-running завершились (1.9–3.9 с)»: в core-run/joined.jsonl все 7 — тесты обычных циклов `→ true`/`!=` (find-this-class, infer-this-type ×2, get-slot ×2, parse-binary-paths, find-last-start). Ни один не является выходом из `for(;;)`.
  - По physical.jsonl все 5 убиты падением (TypeError «reading 'type'», «Node is not part of the runtime tree»), а не другим выходом.
  - В perf-run оба случая — `'property' in currentExpression → true`.
  - Предлагаемое исправление не меняет ни одного из этих мутантов.
- «30 из 131» — это записи пропусков: condition и comparison-operator дублируют один и тот же `→ false`. Уникальных мутантов 20 (из 100 уникальных loop-running) в 6 файлах, то есть 0.12% от 16 279 выдаваемых мутантов core.
- Проблема не специфична для `for(;;)`. В эквивалентной форме `while (current.parent !== null) { if (current.isRoot) break; … }` пропускается `current.parent !== null → true`, и под strict он выживает. В core 24 уникальных loop-running для тестов циклов с явным другим выходом. Исправление «только для if-выходов» сделает результат зависимым от формы записи цикла.

4. (г) Серьёзность завышена: физическая проверка всех 20 мутантов core (копия 170ec52, одноимённые тесты, phys-narrow.jsonl).
- 18 убиты обычными тестами за 0.9–3.1 с.
- 1 зацикливается по-настоящему, несмотря на второй выход: core/cache/find-lockfile.ts:33 `parent === directory → false`. Без lockfile цикл крутится на `/`, без hitLimit vitest висел до таймаута 300 с. Значит, «есть другой выход» не гарантирует завершения.
- 1 выжил, но он эквивалентен: core/syntax/is-timer-delay.ts:67 `key !== 'arguments' → false`. Для callee `index` равен null (types/syntax/node-slot.d.ts), поэтому `?.delay === null` всё равно даёт false.
- Итого: полезного сигнала 0, шума 1 неубиваемый мутант. Вред показан только на синтетической fx1, где оба выхода совпадают в одном узле.
- Довод промпта о цене подтверждается: под strict hitLimit ловит зацикливание find-lockfile быстро (13 мутантов, из них 2 timeout, 2.7 с, дважды одинаково).
