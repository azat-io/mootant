# Замечания верификаторов к BUG-100

Источник: data/verification/batch7.json

## Пробелы промпта (воспроизводящий агент)

1) Фикстуры сквозного прогона (collateral/flaky: 4+4 крошечных файла) и run.sh лежат только в локальной ветке experiment/bug-repros, в промпте они лишь описаны. Без этой ветки отдельная сессия сквозной прогон не повторит. Также не сказано, как собрать tgz для MOOTANT_TGZ (pnpm build + pnpm pack), а путь по умолчанию в run.sh привязан к этой машине. run.sh глушит вывод npm i, поэтому ошибка установки всплывёт как непонятная ошибка чтения report.json.
2) Встроенный код теста не проходит линт проекта:
   - prettier --check падает;
   - ESLint: id-length (d, r ×2), vitest/prefer-lowercase-title, unicorn/filename-case для BUG-100*.test.ts (два последних правила срабатывают и на файл из ветки).
   Если сессия «перенесёт тест» дословно, `pnpm test` не будет зелёным.
3) Не сказано, что flaky воспроизводится только без --fast. В --fast runCheckedDry уже повторяет упавший файл instrumented-прогоном, поэтому сбой поглощается, но появляется ложное unrepeatable-test. collateral воспроизводится в обоих режимах. Эту логику можно переиспользовать для направления (а).
4) Не сказано, что текущее поведение задокументировано и закреплено тестом: JSDoc findBrokenFiles :495-498 («every switched file counts as broken») и тест test/core/run/run-dry-phase.test.ts:466 «drops every switched file when the breakage reached no site» с проверкой phase.runs=3. Их придётся обновить. Не задана политика на случай, когда провал остаётся при исключении любого одного файла (как в тесте :466).
5) Формулировка «dryRun уже принимает files и related» вводит в заблуждение. Какие switched-тексты отдаются, определяет общий массив input.switched = context.files (core/run-mutants.ts:273, 298, 416). Адаптер Vitest перечитывает его на каждом dry run и инвалидирует удалённые файлы (adapters/vitest/run-dry.ts:26-28, 49-58). related лишь выбирает тест-файлы, а при заданных files они дополнительно фильтруются по related (run-dry.ts:231-246). Для бисекции нужно временно менять input.switched (splice с последующим восстановлением) синхронно с related. Юнит-тест моделирует «b подключён» через request.related, поэтому правка, которая сужает только related, пройдёт юнит-тест, но не сквозной прогон.
6) Кейс 2 требует diagnostics строго равным [], а «Ожидаемое поведение» допускает вариант «прогон явно сообщает о нестабильном тесте». Если сообщить об этом диагностикой, тест упадёт. Нужно уточнить, что такое сообщение идёт через report, или ослабить проверку.
7) Мелочи: диапазоны строк ±1 (см. citation_notes). У ссылок на BUG-101, BUG-902 и BUG-905 нет пояснения, где их искать.

## Скептик (refuted=false, severity=medium)

Итог: опровергнуть не удалось. Поведение реальное, детерминированное и не зависит от адаптера. Серьёзность medium обоснована, но это нижняя граница. Часть контраргументов снижает вес находки, ни один её не снимает.

1. Код прочитан верно. `findBrokenFiles` (core/run/run-dry-phase.ts:505-517): при пустом наборе улик строка 516 возвращает `new Set(related)`. `recoverFromFailures` удаляет все найденные файлы с одной и той же формулировкой (:285-296, текст на :289). `checkRealFailures` (:385-421) проверяет провал одним прогоном без switched-файлов. Номера строк в промпте точные.

2. (а) Задуманное поведение — да, и это главный контраргумент. В JSDoc (run-dry-phase.ts:495-498) сказано: «When they reached none, every switched file counts as broken». Отдельный тест закрепляет это поведение: test/core/run/run-dry-phase.test.ts:466 «drops every switched file when the breakage reached no site». Значит, это проектное решение, а не опечатка. Но пользователю оно не описано: cli.mdx:29-30 и compatibility.mdx:16-18 только требуют, чтобы тесты проходили без мутантов. Сообщение на :289 («Tests fail with the switched src/price.js and pass without it») утверждает причинную связь именно с этим файлом, хотя код её не проверял. Для невиновного файла это ложь.

   Для корректности фолбэк не нужен. После удаления файлов dry run повторяется, и оставшиеся провалы останавливают прогон (:304-319). Поэтому более узкий выбор виновных не может дать ложный вердикт.

3. (б) Это не артефакт окружения.
   - Юнит-репро в /home/user/wt/bug-repros (фейковый адаптер) падает в обоих кейсах.
   - Сквозные прогоны шли на vitest 5.1.0 + vite 8.3.5, а не на 5.0.5. Load average во время прогонов был около 2–3.
   - collateral: 14 из 14 мутантов `Error`, выброшены `[src/env.js, src/price.js]`, exit 1. Так было 2 раза из 2, и так же с `--fast`.
   - flaky-load: 12 из 12 `Error`, выброшены оба файла, 2 раза из 2. Повторный прогон с маркером: 9 Killed, 3 Survived.
   - На node:test collateral даёт то же самое: 14 из 14 `Error`. Значит, дефект в ядре.
   - Права root и TERM на результат не влияют.
   - Эксперименты лежат в /home/user/projects/verify-skeptic/BUG-100/.

4. (в) Дополнительные факты в пользу находки.
   - Я вставил отладочный вывод в свою копию dist. Уже в первом dry run ядро получает для test/env.test.js:
     - `covers: []`;
     - `errors: ["Cannot access 'globalThis' before initialization"]`;
     - `dependencies`, где есть src/env.js, но нет src/price.js. Поле `dependencies` описано в types/adapter/dry-file.d.ts:5-12 и заполняется в adapters/vitest/run-dry.ts:190,200.
   - Значит, вину можно сузить без дополнительных прогонов. Это дешевле бисекции, которую предлагает промпт.
   - Реальная причина пользователю не показывается нигде. В текстовом выводе (даже с `--verbose`) и в JSON нет ни имени упавшего тест-файла, ни текста ошибки.

5. (г) Что снижает вес находки.
   - Половина flaky не воспроизводится с `--fast`: там есть повтор с инструментированием (:201-213), прогон даёт exit 0, 9 Killed, 3 Survived. Однако режим по умолчанию — `fast: false` (configuration.mdx:318, core/config/resolve-run-settings.ts:38).
   - У этой половины та же корневая причина, что у BUG-902 (нет повторного instrumented-прогона), и она исправится тем же фиксом.
   - Половине collateral нужен другой дефект как триггер:
     - BUG-101: 0 привязок `globalThis` на 1466 файлов;
     - BUG-106: Vite 8/oxc, 4 файла из 1466;
     - BUG-905: только плагины.
     Все они редкие. Exit 1 в этом случае был бы и без BUG-100 — из-за мутантов самого виновного файла.
   - Ложных Killed или Survived нет. `Error` не входит в score (cli.mdx:62-63), exit 1 (cli.mdx:66, cli/report/build-run-report.ts:153) — сбой громкий.
   - После выбрасывания мутанты не запускаются вовсе, поэтому теряется только время dry-фазы (0.5–2 с в опытах). Фраза «часы» в analysis/bugs/instrumentation.md преувеличена.
   - Есть обходы: `mootant run src/price.js` даёт 6 Killed и 2 Survived; `--mutant x9z5` даёт Killed; при флаке помогает просто перезапустить прогон.

Почему medium, а не high: доверие к вердиктам не страдает, сбой виден сразу, триггеры либо редкие, либо совпадают с BUG-902.

Почему не low:
- срабатывает в режиме по умолчанию;
- одна флакующая `beforeAll` или один неудачно инструментированный модуль лишают вердиктов весь прогон, на больших проектах — сотни файлов;
- диагностика обвиняет невиновные файлы и прячет настоящую причину, хотя у ядра она есть (errors и dependencies). Это прямо вредит пользователям и агентам, на которых ориентирован Mootant;
- серьёзность согласуется с BUG-902 (medium), а BUG-100 — его вариант с бо́льшим ущербом.
