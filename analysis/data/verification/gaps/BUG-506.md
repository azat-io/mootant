# Замечания верификаторов к BUG-506

Источник: data/verification/batch4.json

## Пробелы промпта (воспроизводящий агент)

1) Указание про ESLint уводит от самого простого места исправления. unicorn/no-process-exit не трогает файлы с hashbang, а bin/mootant.js начинается с #!/usr/bin/env node: там process.exit() в unref-таймере после await run() линт пропускает (проверено). Промпт же говорит «только в process.on()». При этом не описан компромисс: bin/ не входит в coverage.include (adapters/**, cli/**, core/**), и юнит-тестом его не покрыть.
2) В блоке кода фикстуры нет package.json с "type": "module" (он есть только в ветке). Без него воспроизведение «с нуля» по тексту промпта падает на ESM-импорте. Не сказано и как поставить зависимости вне репозитория (mootant + vitest 5). run.sh опирается на node_modules и dist репозитория.
3) run.sh проверяет только код 124 за 40 с. Он не убеждается, что отчёт допечатан, не делает контрольного прогона без утечки и глушит stderr mootant. На перегруженной машине медленный, но не зависший прогон дал бы ложное REPRODUCED. Критерий «run.sh завершается с кодом 0» не проверяет обязательное предупреждение в stderr — его нужно тестировать отдельно.
4) Не определено, какой таймаут брать. Варианты: teardownTimeout из конфига Vitest пользователя (AdapterSession не передаёт его в cli/) или фиксированная константа mootant. Для адаптера node:test аналога нет. Формулировка «как vitest --run» двусмысленна.
5) Не сказано, что list тоже затронут: виснет, если хэндл оставляет код mootant.config.* (проверено: 30 с до SIGKILL, контроль 0.4 с), хотя run-list.ts упомянут. Также не сказано, что сценарий с globalSetup касается только run.
6) Нет подсказки, как тестировать выход в unit-тесте: шпион или мок на process.exit плюс фейковые таймеры, проверка, что таймер unref и что сохраняется process.exitCode.
7) Мелочь: Vitest, кроме «close timed out after 10000ms», печатает «Tests closed successfully but something prevents N Vite servers from exiting» и подсказку про reporter hanging-process. Это готовый образец текста предупреждения. Полезно и указание, что держит процесс: TCPServerWrap из globalSetup, Vitest-воркеров к этому моменту уже нет.

## Скептик (refuted=false, severity=medium)

Итог: находку опровергнуть не удалось. Код прочитан верно, баг воспроизводится на опубликованном пакете, поведение нигде не задокументировано. Серьёзность medium обоснована. По ходу проверки найден родственный и более опасный сценарий (п. 6).

1) (в) Код прочитан верно.
- bin/mootant.js:5 вызывает `run()`, и больше ничего не делает. В tarball mootant-0.1.0-170ec52.tgz файл package/bin/mootant.js идентичен.
- cli/index.ts:12-32 и cli/run-mutation.ts:73-75 и :93 только выставляют `process.exitCode`.
- `session.close()` вызывается в finally (core/run-mutants.ts:320-322). Внутри он лишь ждёт `vitest.close()` (adapters/vitest/start-vitest-session.ts:149-157).
- Заявление о Vitest проверено по его исходникам в /home/user/wt/base/node_modules/vitest (5.0.5). В dist/chunks/cac.CLrZKo1g.js:2369 стоит `if (!ctx.shouldKeepServer()) await ctx.exit()`. Метод `exit()` в cli-api.De07GUeT.js:13283-13300 ставит unref-таймер на `teardownTimeout` (по умолчанию 1e4, defaults.B1FCaFfh.js:64): тот печатает «close timed out…» и вызывает `process.exit()`. Программный `close()` (cli-api.De07GUeT.js:13216) выход не форсирует. Значит, раз mootant работает через программный API, за жизнь процесса отвечает он сам.
- Ссылки в промпте (:149-157, :12-32, :38-95, create-spinner.ts:149-152) указывают на нужные места.

2) (а) Поведение не задокументировано и не задумано.
- В readme.md и docs/content/** нет упоминаний зависаний, открытых хэндлов или teardown. В cli.mdx:59-68 сказано только «exit code is 1 when…»; compatibility.mdx про это молчит.
- В JSDoc cli/run-mutation.ts:26-28 («Never rejects… so piped output is never cut») видно сознательное решение использовать `exitCode` вместо `process.exit()`. Но это защита stdout от обрезки, а не намерение висеть. Предложенный в промпте unref-таймер с паузой этому решению не противоречит.
- Контраргумент: Jest по умолчанию тоже не делает принудительный выход. Однако он печатает «Jest did not exit…», а mootant молчит и при этом расходится с Vitest, поверх которого работает.

3) (б) Это не артефакт окружения. Эксперименты лежат в /home/user/projects/verify-skeptic/BUG-506/: пакет из tarball, установка через npm, vitest 5.1.0 вместо 5.0.5 из репозитория.
- Скрипты: run-one.sh, run-vitest.sh, probe.mjs.
- Фикстура leak — точная копия репро. На ней `vitest --run` завершается с кодом 0 за 10,9 с и предупреждением «close timed out after 10000ms».
- На leak mootant печатает отчёт на ~2 с, после чего `timeout 120` возвращает 124. Зонд `process.getActiveResourcesInfo()` 105 с подряд показывает единственный ресурс `["TCPServerWrap"]`.
- Повторы с таймаутами 60 с (с `--json`) и 45 с ×2 дают тот же результат.
- Контроль control (teardown закрывает сервер): mootant завершается с кодом 0 за 2,1 с.
- Хэндл живёт постоянно и от таймингов не зависит: load average 13–22 на результат не влияет. TTY нет (stdin=/dev/null), поэтому root и TERM ни при чём. Исходные данные анализа (data/cli/vt-handle.txt) сняты на vitest 5.0.5 — значит, воспроизводится на обеих версиях.

4) Код выхода действительно теряется. На фикстуре leak-threshold с `--threshold 100` JSON содержит `"passed": false`, но вместо кода 1 получаем 124. JSON при этом полный и парсится.

5) (г) Серьёзность: medium оправдан, хотя есть оговорки.
- Доверие к вердикту не страдает. Отчёт верный и печатается полностью. Сбой fail-closed: внешний таймаут даёт ненулевой код, ложного «зелёного» нет.
- Пользе для пользователя вред заметный. Джоб в CI висит до лимита (у GitHub Actions по умолчанию 360 мин), а CI с `--since`/`--threshold` — основной сценарий из документации. Инструмент агента отвалится по таймауту. Диагностики нет совсем, тогда как Vitest хотя бы подсказывает про hanging-process reporter.
- Триггер правдоподобен. Для таких случаев у Vitest есть отдельное сообщение и reporter, и проект, где `vitest run` проходит с 10-секундным предупреждением, под mootant виснет.
- Почему не high: нужна утечка в коде пользователя, о которой Vitest уже предупреждает, и вердикт не искажается.
- Мелкие преувеличения в промпте:
  - Для агента ожидание длится до таймаута инструмента, а не «бесконечно».
  - `mootant list` от globalSetup зависнуть не может: core/list-mutants.ts → prepareRun/loadConfig Vitest не запускает. `cli/run-list.ts` упомянут только для симметрии.

6) Родственный сценарий, которого нет ни в BUG-506, ни в analysis/bugs. Предложенный фикс его не покрывает.
- Пусть `vitest.close()` никогда не завершается и при этом ничто не держит event loop. Пример — teardown globalSetup, возвращающий `new Promise(() => {})` (фикстуры hang-teardown и hang-teardown-threshold).
- Тогда event loop опустевает прямо внутри `await session.close()` (core/run-mutants.ts:321), до `progress.finish()` и до печати отчёта. Процесс выходит с кодом 0 и пустым stdout — даже при `--threshold 100` и выжившем мутанте, с `--json` и без него.
- marks.txt показывает, что setup и teardown выполняются в PID mootant.
- Vitest в том же случае выходит с кодом 0, но результаты он печатает и `exitCode` выставляет до `close`. У mootant же получается тихий ложный «зелёный» (fail-open).
- Фиксу стоит ставить таймер до `close`, как Vitest ставит его до `await this.close()`, и/или ловить опустевший loop через `process.on('exit')`, выставляя код 1 с сообщением об ошибке. Рекомендую завести отдельный баг.
