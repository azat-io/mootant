## Пробелы промпта (воспроизводящий агент)

1) Ветка experiment/bug-repros есть только локально: на origin её нет (ls-remote показывает main и analysis/2026-11). Коммит b4efcf6 и путь worktree в промпте не указаны. Сессия из клона azat-io/mootant ветку не получит, выручает только то, что код теста и фикстуры приведён целиком.
2) Область бага занижена. Дело не в root, а в том, что у проекта свой Vite-сервер. Так же ломаются inline-проекты с общим root, но со своими plugins (типичный plugins: [vue()] на проект), test.mode/alias/css/browser, другими Vite-опциями, extends на другой файл, sharedViteServer: false, а также все file/directory-проекты. Проверено: plugins:[{name:'noop'}] и test.mode:'unit' дают ту же ошибку. Без этой оговорки сессия может чинить по признаку root. Правильный признак — project.vite !== vitest.vite либо «проект не прошёл configureVitest». В критерий готовности стоит добавить такие проекты и варианты 'packages/*' и 'packages/*/vitest.config.js'.
3) Не процитирована корневая причина в Vitest: inheritRootViteOverrides выбрасывает plugins (5.0.5 index.1TqnEahn.js:7119-7121), getOwnServerReason и VITE_AFFECTING_TEST_OPTIONS (7137-7181), attachProjectsFromEntries (7724-7737). Цитата cli-api показывает лишь место вызова hook. Путь в node_modules появляется только после pnpm install. В 5.1.0 чанки называются иначе, но баг воспроизводится и там.
4) «Третьим аргументом» нужно исправить на «вторым (viteOverrides)».
5) Подсказка про хук config, дописывающий плагин в inline-проекты, не покрывает строковые записи projects ('packages/*', '*/vitest.config.js') — по словам самого промпта, это самый частый случай. injectTestProjects добавляет новые проекты, а не настраивает существующие: есть риск дублей, об этом стоит предупредить.
6) Не сказано, где лежат интеграционные тесты с реальным Vitest: test/adapters/vitest/index.test.ts и фикстуры в test/fixtures/. Существующие многопроектные фикстуры (например, test/fixtures/cache-teardown) все с общим root.
7) Мелочи. Перед ошибкой CLI печатает строку «Some tests failed; running them again without mutants to check.». В смешанной конфигурации запуск только по путям проектов с общим сервером проходит. В package.json фикстуры нет зависимостей, поэтому для автономного воспроизведения Vitest должен лежать рядом или выше по дереву.

## Скептик (refuted=false, severity=high)

Опровергнуть не удалось. Я проверил все четыре направления: находка подтверждается, причём дефект шире, чем заявлено.

(а) Поведение не задокументировано и не задумано.
- readme.md:52-54 обещает «using your project's test configuration».
- В compatibility.mdx:40-54 перечислены неподдерживаемые режимы: browser mode, свои раннеры, другие пулы, viteModuleRunner:false. Проектов, монорепо и root в списке нет. Фраза «Any of these in one project stops the whole run» (:54) прямо предполагает, что проектов может быть несколько.
- configuration.mdx:124-130 («Project root») о монорепо ничего не говорит.
- JSDoc в adapters/vitest/create-mootant-plugin.ts:21 обещает: «Each Vitest project is configured for mootant's runner». Код нарушает собственный контракт.
- Changelog нет, TODO нет, коммитов о проектах нет.
- Единственная мультипроектная фикстура (test/fixtures/cache-teardown/vitest.config.ts:3-16) использует общий root, то есть этот случай тестами не покрыт.

(б) Это не артефакт окружения.
- Репро test/repros/BUG-508.test.ts в /home/user/wt/bug-repros (Vitest 5.0.5) упал 2 раза из 2.
- Независимая проверка на реальном пакете: /home/user/projects/verify-skeptic/BUG-508/mono, пакет из tgz, npm vitest@5 (это 5.1.0, а не 5.0.5), `projects: ['packages/*']`. `vitest --run` зелёный, а `mootant run packages` даёт exit 1 с «Tests fail without mutants… fails to load: The test runner did not report this file».
- Под root с TERM=linux так 3 раза из 3. Под nobody (setpriv, env -i, TERM=xterm-256color) — 2 раза из 2.
- Падение наступает за 2–3 с и детерминировано при load average около 25. Причина в логике резолва конфигурации Vitest, тайминги ни при чём.

(в) Код прочитан верно, неточность одна. Плагин передаётся не третьим, а вторым аргументом (viteOverrides) трёхаргументной формы createVitest(options, viteOverrides, vitestOptions): start-vitest-session.ts:91-117, строка :110. Это косметика. Точная причина:
- Vitest 5.0.5, index.1TqnEahn.js:7119-7121: inheritRootViteOverrides выбрасывает `plugins` из viteOverrides («keeping them would break isolation»).
- getOwnServerReason (:7152-7174) выдаёт проекту свой сервер, если задан test.root (VITE_AFFECTING_TEST_OPTIONS, :7137).
- Проекты из файлов и каталогов сервер никогда не делят (:7045).
- configureVitest берётся из project.vite.config (cli-api.De07GUeT.js:12410-12411).
- В 5.1.0 всё то же самое: index.Di8au7q4.js:7142-7144, cli-api.COfZo8lK.js:12954.

Пробник /home/user/projects/verify-skeptic/BUG-508/scripts/probe.mjs на смешанной конфигурации показал `configureVitest called for: ['b']`, а transform увидел только файлы packages/b. Значит, проект со своим root не настроен и не инструментирован.

Подтвердились все варианты из находки:

- pool:'vmThreads' в проекте со своим root даёт общее «fails to load» вместо ошибки checkProjectConfig. В проекте с общим root получается правильное «mootant needs the forks or threads pool».

Дефект шире заявленного. Так же падает любой проект со своим Vite-сервером и без своего root: с `test.alias`, с inline `plugins:[…]`, с `sharedViteServer:false` (варианты alias, inline-plugin и no-shared-server в mono/variants). Заголовок «со своим root» описывает частный случай. В критерий готовности стоит добавить и эти случаи, например проекты с собственным plugins:[vue()].

(г) Серьёзность high оправдана, но это нижняя граница high.

Против critical: отказ громкий. Запуск завершается с exit 1 до появления первого вердикта, ложных Killed или Survived нет, неверного score нет. Доверие к вердиктам не страдает.

За high:
- основная функция `mootant run` недоступна из корня для типовой монорепо-схемы Vitest и для всех проектов со своим сервером, и в документации об этом ни слова;
- сообщение вводит в заблуждение: утверждает, что тесты падают без мутантов, хотя `vitest --run` зелёный. Даже `--verbose` не подсказывает причину, и пользователь идёт «чинить» исправные тесты.

Что смягчает:
- обходные пути есть: запуск в каждом пакете (проверил, работает) или переписывание конфига на проекты с одним include;
- смешанная конфигурация работает частично. Если мутируемый код покрыт только проектами с общим сервером, всё проходит: `mootant run packages/b/src` в варианте mixed дал 100%.

Но обходные пути нигде не описаны и теряют настройки корневого конфига и общий отчёт. Если считать только вред для вердиктов, можно защитить и medium. С точки зрения пользы для пользователя это high.
