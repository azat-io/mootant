## Пробелы промпта (воспроизводящий агент)

1) Сквозная фикстура описана только словами: нет package.json, кода теста и конфига. Команда `npx mootant run --no-cache` без путей требует `run.paths` (иначе "mootant run needs paths"). Не сказано, где инкрементировать счётчик: в теле теста или при загрузке модуля. Я сделал в теле теста, файл `new URL('../.runs', import.meta.url)`.
2) Не предупреждено, что vitest 5.0.5 через npm 10.9.9 ломается (arborist edgesOut). Баг воспроизводится и на 5.1.0 (npm), и на 5.0.5 (pnpm).
3) Про кэш: в однофайловой фикстуре из промпта предупреждения cache-skipped не будет. После выброса единственного файла dry run пустой, и prepareRunCache возвращает null (core/cache/prepare-run-cache.ts:184-186). Цитируемый путь run-mutants.ts:515-526 виден только при втором, стабильном файле.
4) Критерий готовности неполон. Тест test/core/run/run-dry-phase.test.ts:373-403 'tries each test once outside fast mode and checks failures at once' явно закрепляет текущее поведение: 3 вызова dryRun, runs=3, точные progress-сообщения. Любой фикс его сломает (проверено патчем), его нужно переписать. Возможно, затронуты и счётчики runs в run-mutants.test.ts.
5) Не упомянуто, что после выброса уже есть второй инструментированный dry run (run-dry-phase.ts:300-308). Он идёт только по оставшимся файлам и поэтому не реабилитирует выброшенный. Сообщение "Running the dry run again without 1 file..." может сбить с толку.
6) Не упомянуто усиление через fallback findBrokenFiles (строка 516). Если флак-тест не задел сайтов, instrumentation-break получают ВСЕ переключённые файлы (e2e3: оба файла, 3 Error). Фиксу стоит покрыть и этот случай.
7) Предложенное переиспользование пути `--fast`/unrepeatable даёт неверные для режима без repeat тексты ("failed with each test run twice", unrepeatable-test "fails when each test runs twice"). Новые формулировки нужно придумать; промпт оставляет «или аналогичным».
8) В docs/content/guide нет описания instrumentation-break и обработки флаков. Нужно ли обновлять документацию, промпт не говорит.

(г) СЕРЬЁЗНОСТЬ. Что снижает:
- Нужен флаки-тест, то есть нарушено документированное предусловие.
- Отказ громкий: Killed/Survived не искажаются, Error исключён из score, повторный запуск всё лечит.
- Адаптер сохраняет Vitest retry (adapters/vitest/runner.ts:227-228, 619). Каталог retry: с `retry: 1` флак на уровне попытки поглощается, exit 0, killed 4.

Что усиливает:
1. two-files: флак до первого сайта → по :516 выброшены ОБА файла. Это касается и src/text.js, чей тест прошёл; весь прогон пропадает.
2. hook-retry: флак в beforeAll при `retry: 2` даёт то же самое. Retry не повторяет suite-хуки, а это типичные флаки: порт, БД, таймаут setup.
3. cached2: даже при тёплом кэше 4/4 «Reused cached verdicts» один флак в dry run (он идёт всегда) превращает вердикты в Error 4, exit 1.
4. Код instrumentation-break с severity error попадает в JSON и вводит в заблуждение CI и агентов: возможны ложные баг-репорты на mootant или исключение файла из проверки.

По шкале этого анализа medium обоснован: ложное самообвинение и красный CI в реалистичном сценарии (флаки есть почти в любом крупном проекте, а `--since` в CI рекомендует сама документация). Есть усиление до «весь прогон в Error», как у BUG-905 (medium). Но вердикты Killed/Survived молча не искажаются, а обходные пути есть, поэтому до high не дотягивает.

Замечание к «ожидаемому поведению»: если пропустить флаки-тест дальше, в фазе мутантов он будет давать ложные Killed — там флаки никак не обрабатываются. Поэтому при исправлении правильнее дать отдельное предупреждение о нестабильном тесте, а не тихо продолжать.
