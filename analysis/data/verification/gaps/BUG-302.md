## Пробелы промпта (воспроизводящий агент)

1) Готовый критерий не сходится с рекомендованной эвристикой, и промпт об этом молчит. Тесты-оракулы в test/core/generate/generate-file-mutants.test.ts требуют отсутствия duplicates для удалений под чистыми вызовами. Это идиомы 'a case swap with !== in a test' (:1299-1307), 'a case swap before includes' (:1319-1327), 'a case swap before endsWith' (:1329-1337), 'an awaited number in a comparison' (:1527-1539) и 'a push into an input' (:1701-1710). Значит, сессии нужно расширять список чистых методов и/или документировать случаи в идиомах через gaps/kept. Без этого «pnpm test зелёный» недостижим.
2) Не упомянут собственный дифференциальный оракул проекта, findUnsoundSkips. Идиома `function take(items,item){…splice…}; function f(items,item){ if (take(items,item)) save(item) }` на 170ec52 даёт owned: ['statement-removal save(item) -> ; (O19)'], а после гейта проходит. 3) Класс R4 описан слишком узко («владелец — константа или константа группы»). R4 ломается и с неконстантным toward-мутантом на левом операнде &&, который через short-circuit отключает эффект справа: `if (x > 1 && map.delete(key)) onRemove(key)` пропускается как R4 по comparison-operator, при этом 100% score, а удаление выживает. Владельцами O19 бывают и comparison-operator (`counter.next() === 3`), и тест-тернарник. Поэтому проверять нужно эффекты всего parent.test до O19 и до R4. Если закрыть только O19, тест падает с '(subsumed R4)'.
4) get-owner-constant.ts:35-41 указан как подозреваемое место, но правка внутри getOwnerConstant заденет return-value.ts:207-213. Там O19 корректен и при эффекте: `return !it.next().done -> true` — буквально тот же мутант, что у condition. Проверку надо ставить в местах вызова (statement-removal, get-branch-copy-skip).
5) Объём неясен: промпт называет тем же классом копии ветки тернарника (get-branch-copy-skip.ts, подтверждено: `map.delete(key) ? true : false`, `true -> false` пропускается как O19, копия выживает) и R5. Но критерий готовности и тесты покрывают только statement-removal.
6) Сквозная фикстура analysis/data/skips/fx1 отсутствует в upstream azat-io/mootant. Её содержимое в промпте не приведено (только названия тестов, без сигнатуры consume). По описанию фикстура восстанавливается легко, так что пробел мелкий.

## Скептик (refuted=false, severity=medium)

Опровергнуть не удалось. Находка подтверждается кодом, документацией и тремя независимыми экспериментами. Опровергнута только узкая часть про R4 (см. п. 4).

1. Код прочитан верно (в).
- core/mutators/statement-removal.ts:152-172: getForcedThenSkip проверяет только две вещи: что это `if` без `else` и что getOwnerConstant(test, false) не пуст. Эффекты в `parent.test` не проверяются.
- core/mutators/condition.ts:102-105: владелец подставляет литерал `{ text: String(value), node }` вместо всего теста, поэтому в `if (false)` вызов `map.delete(key)` не выполняется.
- get-owner-constant.ts:19-27 утверждает, что это «the same mutant under another name». Для теста с эффектом это неверно.
- skip-rules.ts:354-357: правило O19 имеет категорию owned и heuristic:false, то есть заявлено как точное.
- Ядро в /home/user/wt/bug-repros совпадает с 170ec52 (git diff по core, adapters, cli и types пуст). test/repros/BUG-302.test.ts падает 2 из 2: `[]` вместо `['onRemove(key) -> ;']`, получено `'onRemove(key) -> ; (owned O19)'`.

2. Это не задуманное поведение (а). Сам пропуск задокументирован (statement-removal.md:86, :205; condition.md:113-117), но только под посылкой «тот же результат»:
- docs/content/mutators.md:41: owned = «Has the same effect as a mutant that Mootant makes instead»;
- statement-removal.md:205: «Same result as a `true` or `false` of another mutator».
Для теста с эффектом обе формулировки ложны. Оговорка mutators.md:46-50 («not a proof») относится к правилам с heuristic:true, а у O19 стоит false.
Все тесты O19 используют чистые условия: test/core/mutators/statement-removal.test.ts:186-219 и get-branch-copy-skip.test.ts. При этом в соседних правилах проект явно учитывает эффекты:
- statement-removal.ts:290-318 (timer-delay): «Arguments with an effect keep the removal»;
- return-value.ts:152-163 (void-result): «no effect to remove».
Значит, здесь недосмотр, а не дизайн.

3. Окружение ни при чём (б). Решение статическое и детерминированное. Пакет tgz ставил через npm с vitest 5.1.0.
- `mootant list --skipped` даёт O19 для `onRemove(key)` и для `onItem()` («as logical-operator does»). То же с `--preset strict` и с `condition: 'off'` (тогда у файла 0 мутантов).
- `mootant run`: killed 5, score 100% (3 прогона).
- Физически удалённые операторы: все 4 теста проходят (2 прогона).
- Самое сильное доказательство: тот же код с семантически пустым `else {}`. O19 не срабатывает, и сам Mootant выдаёт `onRemove(key) -> ;` Survived и `onItem() -> ;` NoCoverage, score 71.43% вместо 100%.
- Варианты, где удаление тоже скрыто как O19: `await store.put()`, `(m = re.exec())`, `stack.pop() === name` (константа comparison-operator), `!stream.write()`, `lock.tryAcquire()`, группа `&&`. Копия ветки тернарника `map.delete(key) ? 'removed' : ''` → `'removed' -> ''` тоже пропускается как O19.

4. Где утверждение шире, чем на деле. R4 с перестановкой сравнения корректен: в `tries++ >= limit` «toward»-мутант `>` сохраняет вычисление операнда. R4 ломается, только когда «toward»-мутант отбрасывает эффектный операнд или обходит его коротким замыканием, например `c === Gt` → `true` в `!(c === Gt || this.fastForwardTo(Gt))` в htmlparser2.
