# Замечания верификаторов к BUG-601

Источник: data/verification/batch2.json

## Пробелы промпта (воспроизводящий агент)

1) Главное для исправления. Промпт говорит, что finally не выполняется «при смерти от сигнала», и умалчивает, что сам Vitest ставит в главном процессе свои process.once('SIGINT'|'SIGTERM'): Logger.addCleanupListeners() вызывается из setVitest(), файл node_modules/vitest/dist/chunks/index.1TqnEahn.js:8570-8585. Этот обработчик ставит exitCode=128+n и через setTimeout(…,1) вызывает process.exit(). Эмпирически vitest+SIGTERM даёт returncode 143 (exit), а не -15. Предложенный фикс (обработчики в CLI, ожидание session.close() и work.remove()) этот process.exit оборвёт, если слушатели Vitest не снять или не нейтрализовать.
2) Шаги проверки не изолированы. `ps | grep -F vitest` и `ls ${TMPDIR:-/tmp} | grep '^mootant-'` на общей машине неоднозначны: в /tmp уже лежало 127 чужих mootant-*, работали чужие vitest. Нужны `export TMPDIR=$(mktemp -d)` и фильтр по cwd фикстуры или по pid из worker/. Приватный TMPDIR упомянут только в критерии готовности.
3) `setsid … & pid=$!` работает только в шелле без job control. При set -m или в интерактивном шелле setsid форкается, `$!` указывает на уже завершившийся процесс, kill бьёт мимо, и баг ложно не воспроизводится (проверено).
4) Тайминг `sleep 6` хрупкий. Надёжнее ждать появления worker/<pid> или накопленного CPU у дочернего процесса; до срабатывания сторожа окно 20–40 с.
5) Область бага у vitest. Воркеры vitest в той же группе процессов, поэтому при Ctrl+C и при реальном закрытии терминала (SIGHUP группе переднего плана) они гибнут. Сирота появляется, только если сигнал получает один pid CLI (kill <pid>, менеджер процессов, CI). Фраза «SIGHUP (закрыли терминал…)» верна для node-test: это проверено закрытием pty. Тест должен слать сигнал pid'у CLI, а не группе. Ещё ловушка для теста: если CLI — лидер сессии pty (`script -c 'exec node…'`), ядро при его выходе шлёт SIGHUP группе и прячет сироту.
6) Формулировка «код выхода 128+сигнал» неоднозначна. Сейчас node-test и vitest+SIGHUP умирают от сигнала (в Node у child code=null, signal='SIG…'), а vitest+SIGTERM выходит через exit(143). Тесту нужно явно задать, что именно проверяется.
7) Для node:test фикстура дана словами: нет текста теста и конфига; восстанавливается легко, vitest в ней не нужен. TTY-варианты (Ctrl+C) заявлены в «Фактическом поведении», но шагов воспроизведения нет; для них нужен pty, например script + bash -i.
8) Ссылка на analysis/bugs/adapters.md в upstream azat-io/mootant ведёт в никуда: каталога analysis/ там нет.
9) Не пробел: установка с vitest@5.0.5 на npm 10.9.9 в чистом каталоге прошла, бага edgesOut не было.

КОНТРАРГУМЕНТЫ И ЗАВЫШЕНИЕ СЕРЬЁЗНОСТИ (г)
1. Строка «vitest+SIGHUP» получена через `kill -HUP <pid>` только главному процессу. При реальном закрытии терминала или обрыве SSH bash и ядро шлют SIGHUP всей группе задания. Fork-воркеры Vitest не detached, поэтому умирают: pty-тест чист 3 из 3.
   Для Vitest триггер остаётся только один — сигнал строго по pid (`kill <pid>`, pkill). Сирот не дают:
   - Ctrl+C;
   - `timeout` (шлёт сигнал группе);
   - закрытие терминала;
   - docker, systemd и CI (они убивают всё дерево).
   Через `npm run` при SIGTERM процессу npm сам mootant остаётся жив: dash не делает exec, умирает только sh. Сторож mootant продолжает работать, бесконечной сироты нет.
2. Для Vitest это поведение самого Vitest. Чистый `vitest run` с тем же зависанием после SIGTERM по pid оставляет такую же сироту (plaincase.py, batch2.log), так что регрессии относительно раннера нет.
   Специфичная для mootant часть — только node-test + SIGHUP. Обычный `node --test` при SIGHUP группе чист, а mootant из-за detached:true оставляет сироту. Это единственный реалистичный путь: закрыли вкладку терминала или оборвался SSH.
3. Нужны три условия одновременно:
   - Мутант синхронно вешает тест в цикле без сайтов мутантов, так что hitLimit не срабатывает. Мутанты, способные вызвать таймаут, по умолчанию выключены: readme.md:58-59, docs/content/guide/configuration.mdx:149, 268-271, 436-441.
   - Сигнал приходит, пока идёт этот юнит. Репро расширяет окно до 20 с. С дефолтным `{factor:3, constant:250}` (configuration.mdx:429-434) на той же фикстуре юнит живёт около 2 с плюс 2,5 с на подтверждение у vitest и около 1+1,5 с у node-test (замер out/default-*). Окно растёт на 250 мс за каждый тест файла и удваивается при подтверждении, поэтому сценарий редкий, но реальный.
   - Сигнал нужного типа (см. пункт 1).
4. На доверие к вердикту влияния нет: прерванный прогон не выдаёт отчёта, ни один вердикт не искажается. Ущерб сводится к двум вещам:
   - бесконечно крутящийся процесс, который занимает ядро CPU до ручного kill;
   - мусор в $TMPDIR размером десятки КБ (каталог mkdtemp с правами 0700).
5. Замечания к промпту:
   - `vitest@5.0.5` в npm 10.9.9 не ставится, нужен vitest@5;
   - SIGKILL (OOM, kill -9) обработчиками не лечится, предложенный фикс его не покрывает.

СЕРЬЁЗНОСТЬ: low. Дефект настоящий, но:
- срабатывает только при трёх условиях одновременно;
- вердикты не искажает;
- часть про Vitest совпадает с поведением самого Vitest и не достигается через Ctrl+C или закрытие терминала.
Ближе всего к medium подслучай node-test + SIGHUP (закрытие терминала или обрыв SSH): он специфичен для mootant, а процесс крутится до ручного kill. Его стоит исправить первым: добавить SIGHUP в track-process-group.ts:7.
