## Пробелы промпта (воспроизводящий агент)

1) Путь к пакету дан плейсхолдером `<path-to>/mootant.tgz`. Не сказано, где взять пакет: /home/user/artifacts/mootant-0.1.0-170ec52.tgz или `pnpm build && pnpm pack` на 170ec52. Не указана и версия Node для «Фактического поведения» (воспроизводится на 22.23.4 и 24.22.2).
2) Для контроля Vitest нет точных шагов. Нужны runner:'vitest', `npm i -D vitest@5` (с npm 10.9.9 не фиксировать 5.0.5: баг arborist edgesOut) и script `vitest --run`. Не предупреждено, что полный прогон контроля идёт около 4.5 мин: каждый из 3 мутантов тоже ждёт 65 с.
3) Нет различающего контроля `"test": "node --test --test-timeout=120000"`. С ним dry run проходит, и это прямо доказывает, что не читается именно опция {timeout}. Заодно это рабочий обходной путь, который в промпте не упомянут.
4) Не процитирован публичный контракт адаптера types/adapter/dry-run-request.d.ts:11-18: «on top of the test's own timeout». node-test его нарушает, это сильный аргумент в пользу бага. Кроме того, DryRunRequest и DryRunResult экспортируются публично (core/index.ts:18,20). Поэтому совет брать формулировку из `DryRunResult.hung` означает изменение публичного типа и противоречит разделу «Ограничения»; промпт этот компромисс не обсуждает.
5) test/adapters/node-test/get-dry-deadline.test.ts уже существует (один кейс), так что «новый тест» — это новый кейс в нём. Для интеграционного теста бюджеты уже передаются через DryRunRequest.timeouts (index.test.ts:248 передаёт {file:60_000, test:60_000}). Внедрять DRY_TIMEOUTS ядра не нужно, а подсказка «через внедряемые DRY_TIMEOUTS» уводит в сторону.
6) Путь (б) проверен на Node 22.23.4 и 24.22.2: ни события репортёра, ни TestContext таймаут не несут, остаётся только путь (а). Промпт не называет механизм обёртки. Рабочий вариант: в preload createRequire('node:test'), заменить экспорты и вызвать module.syncBuiltinESMExports(), чтобы ESM `import { it }` видел обёртку. Не перечислено и всё, что надо покрыть: t.test(), describe/suite, .only/.skip/.todo, test.it, хуки на контексте (t.before…), beforeEach/afterEach внутри попытки.
7) Не определено поведение для теста без явного timeout (в node:test по умолчанию Infinity). По семантике Vitest (`timeout > 0 ? timeout : Infinity`) бюджет стал бы неограниченным, и сторож для node:test по умолчанию отключился бы. Нужно явно сказать, что делать с тестом без timeout дольше 60 с: убивать, как сейчас, или нет. Например, «безопасный верхний предел» в критерии готовности задан неконкретно.
8) Сценарий с хуком описан одной фразой: нет ни шагов воспроизведения, ни фактического сообщения. А оно другое (строка 488: «…within 60 s plus the timeouts of its suite hooks»), и оно тоже ложно для node-test (проверено: exit 1 за 62 с).

## Скептик (refuted=false, severity=low)

Частично опровергнуто: основное поведение задокументировано и задумано, реальным остаётся только мелкий дефект сообщения. Серьёзность medium завышена, оцениваю как low.

1) (а) Поведение задокументировано и задумано. В docs/content/guide/compatibility.mdx:74-77 сказано: «Tests slower than 60 seconds need the `--test-timeout` flag of Node.js in a `node --test` or `tsx --test` command or in the adapter's `execArgv`, or `--timeout` in a `borp` command». Ограничение описано с первого коммита адаптера 9c27d69 (в readme: «tests slower than 60 seconds need `--test-timeout`»). Код последовательно реализует этот дизайн: JSDoc adapters/node-test/get-dry-deadline.ts:9-10 («grow by the `--test-timeout` of the project, the own timeout of tests and suites that mootant can see»), adapters/node-test/types/node-test-handle.d.ts:34-37, перевод `--timeout`/`-t` из команды borp в `--test-timeout` ради этого бюджета (adapters/node-test/resolve-command.ts:121-125), чтение флага в start-node-test-session.ts:196. Промпт документацию не упоминает, а его раздел «Ожидаемое поведение» ей прямо противоречит. По сути это запрос на снятие известного ограничения, а не ошибка в расчёте бюджета.

2) Эксперимент (/home/user/projects/verify-skeptic/BUG-603, Node 22.23.4, пакет 170ec52, load average ~42).
- A, точное воспроизведение: обычный `node --test` даёт exit 0 за 66,3 с; `mootant run` даёт exit 1 за 65,9 с с тем же сообщением, что в промпте.
- B, обход из документации (`node --test --test-timeout=120000` в scripts.test): dry run 1m 06s, мутант убит, exit 0.
- C, `nodeTestAdapter({ execArgv: ['--test-timeout=120000'] })`: dry run 1m 05s, exit 0.
Задокументированный обход в одну строку полностью снимает проблему. Неучтённого пути через NODE_OPTIONS нет: Node сам отвечает «--test-timeout= is not allowed in NODE_OPTIONS».

3) (б) Это не артефакт окружения. Таймер теста ждёт 65 с при бюджете 60 с, исход детерминирован. Нагрузка может только задержать тест или сторож, то есть скорее скрыть баг, чем создать ложное зависание; в B и C запас 115 с. Root, TERM=linux и баг npm не влияют (vitest не нужен).
(в) Код прочитан верно: ссылки path:строка в промпте точные (run-dry-phase.ts:106-114, :477-493, :489; get-dry-deadline.ts:17-28; vitest runner.ts:989-998). Контроль на Vitest не запускал, но по коду adapters/vitest/runner.ts:990-996 собственный таймаут теста там учитывается, асимметрия реальна. Вариант с хуком дольше 60 с отдельно не проверял; по коду путь тот же (бюджет файла плюс `--test-timeout`).

4) Реальный остаток дефекта. Сообщение в core/run/run-dry-phase.ts:489 («did not finish within 60 s plus its own timeout and the timeouts of its hooks») и в :488 («plus the timeouts of its suite hooks») для node-test ложно: собственный `timeout` теста и таймауты хуков не учитываются. Подсказки про `--test-timeout` нет ни в одном сообщении (grep по adapters/core/cli). Внутренний контракт types/adapter/dry-run-request.d.ts:11-17 («on top of the test's own timeout») node-test выполняет лишь частично. Пользователь с `{ timeout: 120_000 }` может искать несуществующее зависание.

5) (г) Серьёзность: low, а не medium. Вердикты не искажаются: прогон падает громко и рано (около минуты), называя тест и файл; с флагом вердикты корректны (в B и C мутант убит, score 100%). Условие срабатывания узкое: тест или хук дольше 60 с под node:test без `--test-timeout`, а мутационное тестирование такого файла и так стоит не меньше 65 с на каждый мутант. Обход задокументирован и проверен.

Рекомендация: переформулировать BUG-603 как low-дефект («сообщение о зависании для node-test обещает учёт собственного таймаута и не подсказывает задокументированный `--test-timeout`»), а чтение `options.timeout` у test()/describe()/хуков вынести в отдельное улучшение.
