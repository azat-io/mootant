# Замечания верификаторов к BUG-500

Источник: data/verification/batch4.json

## Пробелы промпта (воспроизводящий агент)

1) Фикстура и run.sh недоступны отдельной сессии. Ветка experiment/bug-repros (коммит 27abca7) локальная: в `git ls-remote origin` только main и analysis/2026-11. Конфиг, package.json и src/add.js в промпт встроены, а текста run.sh нет. При этом критерий «run.sh завершается с кодом 0» ссылается на файл, которого в клоне из GitHub не будет.
2) Ручные шаги молча предполагают собранный dist и установленные зависимости. На 170ec52 их нет: `node ../../../bin/mootant.js` падает с ERR_MODULE_NOT_FOUND. Нужно явно написать `pnpm install && pnpm run build`. Под pnpm 12.16.1 сборка в свежем экспорте падала на configDependencies без integrity; в bug-repros dist уже был собран.
3) Вердикт run.sh зависит только от кода выхода.
   - Без dist скрипт печатает «REPRODUCED: exit 1» на ERR_MODULE_NOT_FOUND — проверено, это ложноположительный результат. На Node < 22.18 без jiti он тоже вернёт 1.
   - dist пересобирается, только если его нет. После исправления устаревший dist даст ложный «не исправлено».
   - Стоит проверять текст ошибки в выводе и в критерии требовать `pnpm run build` перед run.sh.
4) Неполный список форм ошибки. Промпт называет только SyntaxError «Cannot use import statement outside a module» и ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. Конфиг без import (только export default) в commonjs-пакете падает с «Unexpected token 'export'» — проверено. Запасной путь, привязанный к тексту сообщения, этот случай пропустит. Надёжнее смотреть на type пакета или на класс SyntaxError.
5) Предупреждение Node не подавить перехватом ошибки. «Failed to load the ES module… Make sure to set "type": "module"» печатается в момент неудачного нативного import(), даже когда mootant ловит ошибку. Простой catch с переходом на jiti оставит в выводе это сбивающее с толку предупреждение. Тип пакета нужно определять до импорта, но промпт этого явно не говорит.
6) Неясны границы задачи.
   - Нужно ли убирать MODULE_TYPELESS_PACKAGE_JSON в пакете без type (это вывод npm 10 init)? Оно упомянуто в контексте, но не в ожидаемом поведении и не в критерии готовности.
   - Нужно ли поддерживать enum и прочий не-strippable синтаксис через jiti? Тоже не входит в критерий.
7) Подсказки для теста частично нерабочие.
   - Вариант «на исходниках через --experimental-strip-types» не работает: исходники импортируют './import-config' без расширения, и Node отвечает ERR_MODULE_NOT_FOUND (проверено).
   - Вариант «на собранном dist» требует сборки до `pnpm test`, а скрипт test (`pnpm run /^test:/`) её не делает.
   - Дочерний процесс не учитывается в v8-coverage, поэтому для 100% покрытия всё равно нужны in-process тесты с моками.
   - Утверждение, что внутри раннера Vitest баг скрыт, верно — проверено на vitest 5.1.0.
8) Окружение. Node 22.12, 22.18 и 26 на машине не установлены, их пришлось скачать с nodejs.org (SHA256 сверен). Промпт не говорит, откуда брать эти версии для проверки «поведение на Node без type stripping не меняется». Дешёвая замена — `node --no-experimental-strip-types` на 22.23.
9) Мелочь: те же ESM-примеры `import { defineConfig } from 'mootant'` без имени файла есть в docs/content/mutators.md и docs/content/mutators/*.md (около 20 страниц). Промпт называет только configuration.mdx.

## Скептик (refuted=false, severity=low)

Опровергнуть не удалось: дефект настоящий. Серьёзность, по-моему, завышена: low вместо medium.

ВОСПРОИЗВЕДЕНИЕ. Проверял на пакете, установленном из /home/user/artifacts/mootant-0.1.0-170ec52.tgz, а не на симлинке на репозиторий. Рядом поставлен jiti 2.7.0. Эксперименты лежат в /home/user/projects/verify-skeptic/BUG-500/ (base/, run-matrix.sh, vitest-cjs/, vitest-cjs-mts/).
- Пакет с "type": "commonjs" (вручную или из `npm init -y` npm 11.19.1). На Node 22.23.4, 24.22.1 и 26.13.0 (process.features.typescript=strip) выход 1: «Cannot load mootant.config.ts: Cannot use import statement outside a module». Node перед этим предупреждает и советует "type": "module" или .mjs. На 22.12.0 через jiti выход 0, мутанты выводятся.
- Пакет без поля type грузится, но на 22.23, 24 и 26 каждый запуск печатает MODULE_TYPELESS_PACKAGE_JSON.
- "type": "module" и CJS-пакет с mootant.config.mts работают везде.
- Конфиг с enum на 22.23, 24 и 26 даёт «TypeScript enum is not supported in strip-only mode»; на 22.12 с jiti работает.
- Если отключить type stripping (--no-experimental-strip-types или NODE_OPTIONS), тот же CJS-конфиг грузится через jiti. Значит, jiti установлен, но по умолчанию не используется.
- Проект из npm init (npm 11) с vitest 5.1.0: `vitest run` с vitest.config.ts в том же ESM-синтаксисе проходит, а `mootant run src` с конфигом из документации — выход 1. После переименования в .mts прогон проходит, порог 80 применяется. Без конфига тоже проходит.
- Ошибка детерминирована: 7 из 7 падений на трёх версиях Node. От нагрузки, root, TERM или бага npm не зависит.
- npm 11.19.1 действительно пишет "type": "commonjs" (npm 10.9.9 — нет). Это задуманное поведение npm, а не его баг. pnpm 12.16.1 пишет "type": "module".

КОД ПРОЧИТАН В НАХОДКЕ ВЕРНО:
- core/config/load-typescript-config.ts:16-18 при истинном process.features.typescript сразу возвращает importConfig, и запасного пути нет. jiti используется только в :19-30.
- core/config/import-config.ts:12 — нативный import(pathToFileURL(file).href).
- core/config/load-config.ts:51-60 отдаёт .ts в loadTypescriptConfig; :111-114 просто оборачивает сообщение, совета про .mts нет.
- Все ссылки path:line в промпте совпадают с кодом.

ЗАДОКУМЕНТИРОВАНО ЛИ? Нет.
- docs/content/guide/configuration.mdx:77-91 — главный пример с ESM-синтаксисом в .ts.
- configuration.mdx:121-122 и docs/content/guide/compatibility.mdx:26-28 требуют только Node 22.18+ или jiti. Про поле type и про .mts для CJS-пакетов ничего; .mts упомянут лишь в списке расширений (configuration.mdx:101).
- JSDoc в load-typescript-config.ts:5-14 показывает, что нативный импорт выбран сознательно. Но последствие для примера из документации нигде не описано и не обработано.
- Для тестов под tsx автор ту же ловушку с type обрабатывает и даёт совет: compatibility.mdx:70-72, adapters/node-test/check-typescript.ts:72. Значит, класс проблемы ему известен, и для конфига это недосмотр, а не задуманное поведение.
- Существующий тест (test/core/config/load-typescript-config.test.ts:33-44) идёт через модульный раннер Vitest во временном каталоге без package.json, поэтому такой случай поймать не может.

ПОЧЕМУ LOW, А НЕ MEDIUM:
1. Доверие к вердикту не страдает. Сбой происходит до запуска мутантов, выход 1, отчёта нет. Конфиг не игнорируется молча, ложных вердиктов не возникает. В этой же шкале medium стоят находки с молча неверными вердиктами (BUG-201, BUG-204, BUG-602), а этот дефект заметно мягче.
2. Обход в одно действие: переименовать в .mts (есть в документированном списке, :101), в .mjs (в примере нет аннотаций типов), перейти на JSON или поставить "type": "module". Предупреждение Node прямо называет причину — тип модуля.
3. Конфиг необязателен. Первый запуск в getting-started (getting-started.mdx:71-77) работает без него. «Падает на первом шаге» верно только для гайда по конфигурации, не для знакомства с инструментом.
4. Затронуты только пакеты с явным "type": "commonjs" при Node ≥22.18. Пакеты без type работают (лишь предупреждение), ESM-пакеты (pnpm init, шаблоны Vite) работают.
5. Побочные пункты слабее основного. Отказ на enum — известное ограничение strip-only режима Node, на которое намекает «strips types itself». Предупреждение MODULE_TYPELESS_PACKAGE_JSON — косметика.

ЗА MEDIUM, КАК ВЕРХНЮЮ ГРАНИЦУ:

- vitest.config.ts в том же синтаксисе в том же проекте работает, так что пользователь подвоха не ждёт.
