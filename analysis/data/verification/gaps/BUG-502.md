# Замечания верификаторов к BUG-502

Источник: data/verification/batch4.json

## Пробелы промпта (воспроизводящий агент)

1) Фикстура описана не полностью. Не сказано, где лежит тестовый файл и как он называется (я взял test/step.test.js с `import { getStep } from '../src/step.js'`), что нужен "type": "module", откуда ставить mootant (tgz /home/user/artifacts/mootant-0.1.0-170ec52.tgz или pnpm pack) и какую версию vitest. Для npm 10.9.9 нужен vitest@5 (поставился 5.1.0), точная 5.0.5 ломает arborist. Сработало с первой попытки, но пришлось угадывать.
2) Числа из промпта (~5 с, 99% CPU) получены на ненагруженной машине. При load ~30 на 4 CPU с ps выходит 7–11 с, а pcpu воркера 25–29% (это среднее за время жизни). Критерий лучше сформулировать так: после «dry run» прогресса нет, воркер постоянно в состоянии R, прогон не завершается за время, многократно превышающее время с ps (проверено до 200 с).
3) Нет предупреждения о сиротах. `timeout -s KILL` убивает всю группу процессов, и это скрыто спасает. Если убить только главный процесс mootant, зависший воркер vitest (vitest/dist/workers/forks.js) уходит к PID 1 и крутится бесконечно, его нужно добивать вручную. Кроме того, после KILL в TMPDIR остаются каталоги mootant-*. /tmp/nops — общий путь, лучше уникальный каталог.
4) wait-for-workers.ts:113 ошибочно отнесён к сторожу (см. citation_notes). Отдельной сессии стоит знать, что в этом сценарии работает только путь watchHeartbeats → stopHungWorker. Исправление в общей stopHungWorker закроет и уборку после WAIT_LIMIT: сейчас без ps она тоже не убивает воркеры и оставляет их живыми.
5) Совет опираться на state.spawns без оговорок: PID попадает туда, только если readProcessId достаёт приватный getter `fork` у Vitest (create-forks-pool.ts:113-120, «nothing is noted»), а run-plan.ts:61 очищает карту на каждом прогоне. Исправление только через spawns вернёт то же зависание, если Vitest перестанет отдавать процесс. Нужен запасной вариант, например /proc/<pid>/stat на Linux. Не сказано и то, что у stopHungWorker сейчас один параметр pid: придётся протаскивать spawns в три места вызова (run-plan, run-dry и waitForWorkers через runSpecifications).
6) Применимость к окружениям проверена лишь частично. Отсутствие ps я воспроизвёл через PATH, но сам состав node:*-slim и distroless запуском не проверял: docker нет, а доступ к GitHub ограничен azat-io/mootant. Поведение BusyBox я подтвердил запуском (1.36.1, сборка Ubuntu, не Alpine): `-p` отвергается с rc=1. В Ubuntu у procps Priority: required, так что Ubuntu-образы и раннеры GitHub не затронуты. Формулировку «типичные CI-образы» стоит сузить до Debian-slim, distroless и Alpine.
7) Мелочи окружения: для pnpm 12 нужен PATH=/home/user/tools/bin. Промпт не говорит, что ветка experiment/bug-repros уже лежит рабочей копией в /home/user/wt/bug-repros.

## Цитаты кода (воспроизводящий агент)

Все места открыты в /home/user/mootant (HEAD вне analysis/ совпадает с 170ec52), номера строк точные.

- wait-for-workers.ts:113 — `await Promise.all(leftover!.map(pid => stopHungWorker(Number(pid))))`. Строка верна, но в промпте она перечислена как место, где «watchHeartbeats … зовёт stopHungWorker», и это неточно. Это уборка оставшихся воркеров после WAIT_LIMIT 70 с, и вызывается она только после завершения runTestSpecifications (run-specifications.ts:41-42). В сценарии бага (синхронный цикл в тесте) этот путь не достигается.
- create-forks-pool.ts:66-68 — `let pid = readProcessId(worker); if (pid !== null) spawns.set(pid, spawned)`. Точно. state.spawns — та же карта (start-vitest-session.ts:74-87).

## Скептик (refuted=false, severity=medium)

ИТОГ: опровергнуть не удалось. Механизм и последствие подтверждены, ошибок прочтения кода нет. Но формулировка шире реального условия, поэтому оцениваю серьёзность как medium (верхняя граница), а не high.

1. Код прочитан верно.
- adapters/vitest/stop-hung-worker.ts:19-24 и :42-46: любая ошибка execFile('ps', ['-o','ppid=','-p',pid]) даёт null, сравнение null !== process.pid возвращает false, SIGKILL не посылается.
- watch-heartbeats.ts:53-63: после fired=true по тому же пульсу сторож повторно не срабатывает.
- Пул Vitest 5.1.0 (node_modules/vitest/dist/chunks/index.Di8au7q4.js:5877-5938) ждёт testfileFinished или error без таймаута на выполнение. Таймауты есть только на запуск и остановку (:5154-5155, :5858).
- Ссылки промпта сверены, все верны: run-plan.ts:74-75, run-dry.ts:69-70, wait-for-workers.ts:113, create-forks-pool.ts:66-68; тест stop-hung-worker.test.ts:48-64 с mockParent(null) и ошибкой 'gone'.

2. Воспроизведение.

  - С ps: 8,4 с и 10,7 с, вердикт Timeout и предупреждение worker-hang.
  - PATH со всеми утилитами, кроме ps: висит 150 с до KILL, воркер всё время в состоянии R.

- Это не артефакт нагрузки: путь детерминирован, контрольный прогон на той же машине завершается.

3. (а) Поведение не задокументировано и не задумано.
- docs/content/guide/getting-started.mdx:36-40 (Requirements) называет только Node.js и Vitest/node:test. В readme.md и docs/content 0 упоминаний ps или procps.
- JSDoc getParentPid (stop-hung-worker.ts:40): «null when the process is gone». Авторы приравняли ошибку ps к «процесса нет», случай отсутствия ps не рассматривали.
- wait-for-workers.ts:42 обещает «no worker outlives the run».

4. (б) Окружение реальное, это не артефакт root, TERM=linux или npm.
- Слои образов скачаны с mirror.gcr.io, листинги в images/.
- node:22-slim (22-bookworm-slim, сборка 2026-10-28): нет ни ps, ни procps.
- node:22-alpine (Alpine 3.24.3): /bin/ps -> /bin/busybox, BusyBox v1.37.0. Строка опций ps в бинарнике — «Zo:*aAdeflT», ключа p нет. По исходникам procps/ps.c (getopt32 "Zo:*aAdefl"+T) и libbb/getopt32.c:592-594 неизвестный ключ ведёт к bb_show_usage и xfunc_die, то есть к коду выхода 1. Запустить сам бинарник не дала политика песочницы, поэтому для Alpine доказательство статическое, но сильное.

5. (г) Почему не high: «вечно» верно не для любого синхронного цикла.
- core/runtime/install-mutant-runtime.ts:40-44 считает попадания в любое место мутанта и при превышении бросает MootantHitLimitError. Лимит на юнит — сумма max(100000, 100×hits) по загрузке и всем тестам файла (core/run/plan-isolated.ts:24-38, get-try-limits.ts:26, adapters/vitest/runner.ts:551).
- Эксперимент fixture-hits: мутант i+1 -> i-1 в функции шага, которую вызывает цикл теста. Без ps прогон завершился за 37,6 с и 58 с против 7,7 с с ps, вердикты те же (killed 1, timeout 1). Цикл через переключённый код без ps даёт замедление до hitLimit, а не вечное зависание.
- Единственное срабатывание сторожа в реальных данных анализа — analysis/data/tests/mutants/run-terminal.json: z2gry0wp7b1h, cli/terminal/fit-parts.ts:21, один мутант из 301. Это как раз цикл через переключённый код, то есть без ps была бы задержка, а не зависание.
- По умолчанию мутанты, которые могут вызвать таймаут, исключены (configuration.mdx:149, 268-271).
- Значит, нужны три условия одновременно: Vitest-адаптер; окружение без совместимого ps (не GitHub-hosted runner, не полный образ node:22, не macOS и не Windows); синхронное зависание, ни разу не проходящее через переключённый код (цикл в тесте или зависимости, regex backtracking и т. п.).
- Вердикты не искажаются: прогон либо даёт верные вердикты (медленнее), либо не даёт ничего. Обход простой: apt/apk add procps.

6. Почему не low.
- При срабатывании прогон теряется целиком, без какой-либо диагностики.
- Повторяется детерминированно при каждом перезапуске и расходует CI до лимита job.
- Затронуты официальные образы node slim и alpine, зависимость от ps нигде не описана.

Неточности промпта:
- Фраза «Мутант, который вешает тест (бесконечный синхронный цикл), ... останавливает сторожем» обобщает слишком широко: многие такие циклы останавливает hitLimit.
- Для Alpine статус «гипотеза» можно заменить на «подтверждено статически».
