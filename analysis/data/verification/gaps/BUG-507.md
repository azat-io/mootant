И надо определить, входит ли этот случай в объём задачи: критерий готовности покрывает только цепочку a.cjs -> b.cjs.
3) Дизайн исправления не описан. Переключённые тексты (VitestSessionState.files), served и mismatched живут в главном процессе, в состоянии Vite-плагина (adapters/vitest/types/vitest-session-state.d.ts). У воркера (runner.ts) есть только mutant runtime. Чтобы поставить patchModuleCompile в runner.ts, нужно доставить тексты в воркер и вернуть served/mismatched в главный процесс, например по аналогии с listDependencies в runner.ts:1182 или через out-records. Нужна и проверка mismatch (аналог resolveSwitchedText -> null).
4) Ветка experiment/bug-repros есть только локально, origin/experiment/bug-repros нет. Отдельной сессии придётся воссоздавать файлы по встроенному тексту. Текста хватает: у теста отличаются только комментарии, vitest.config.ts и package.json даны однострочно.
5) Для проверки CLI нужна сборка: bin/mootant.js импортирует ../dist/cli/index.js, а dist/ нет. Нужно 'pnpm build' или установка упакованного tgz. Точная команда ('mootant run src --no-cache' из каталога фикстуры) не указана.
6) Не сказано, куда класть фикстуру нового теста. В проекте принято test/fixtures/**: этот каталог игнорируют eslint, knip и cspell и исключает vitest.config.ts. Каталог test/repros/ не игнорируется и помешает требованию «pnpm test зелёный».
7) Полезно добавить эталон: под node:test та же цепочка даёт killed 7, survived 1, no coverage 0, 87.5%. Это готовый oracle для сравнения вердиктов.

## Скептик (refuted=false, severity=high)

Итог: опровергнуть находку не удалось. Баг настоящий и воспроизводится детерминированно. Серьёзность high оправдана, но находится на нижней границе. В описании есть две неточности, на суть они не влияют.

(а) Задокументировано или задумано? Нет.
- docs/content/guide/compatibility.mdx:34 обещает для `.cjs` «List and run mutants» без оговорок. Список ограничений Vitest (:45-57) про require()/createRequire молчит: в нём только вычисляемый import() (:56) и дочерние процессы и воркеры (:57). readme.md:70-72 отправляет за остальными ограничениями на эту же страницу. Код `never-served` в документации не описан вообще.
- Авторы знают, что require() обходит Vite (adapters/vitest/worker/list-dependencies.ts:21-23, adapters/vitest/runner.ts:1176-1188, `createRequire(import.meta.url).cache` на :1182), но используют это только для инвалидации кэша. Тестов, которые закрепляли бы NoCoverage для таких модулей, нет: test/adapters/vitest/index.test.ts:1600 и :1775 проверяют только кэш.
- В node:test для известного обхода есть отдельная причина с рецептом (adapters/node-test/run-dry.ts:23-24, :151-154). Под Vitest печатается общий текст core/run/run-dry-phase.ts:365: «no test imports it, or tests import a built copy, an external or a pre-bundled dependency». В этом случае он ложен: тест импортирует a.cjs, а тот загружает b.cjs через require().
- node:test тот же код переключает: patch-module-compile.ts:14-41 вызывается в install-module-hooks.ts:76.

(в) Неверное прочтение кода? По сути нет.
- В адаптере Vitest мутанты переключаются только в transform-хуке (adapters/vitest/create-mootant-plugin.ts:32-50). grep по adapters/vitest не находит `_compile`, `registerHooks` или `Module.prototype`.
- Мутант без достигнутых сайтов получает NoCoverage (core/run/get-final-status.ts:26-36, core/run/decide-results.ts:50).
- Неточность 1, в «Подозреваемых местах». core/run/read-test-imports.ts и rank-test-file.ts не выбирают тест-файлы для dry run. Они только ранжируют их и выбирают, какой файл предложить дописать (core/run-mutants.ts:465, rank-module-files.ts:43, rank-mutant-files.ts:52). Под Vitest файлы выбирает `vitest.getRelevantTestSpecifications()` с `config.related` (adapters/vitest/run-dry.ts:225-236) по графу статических импортов. Поэтому тест с require()/createRequire не выбирается. Для этой части исправления смотреть нужно туда.
- Неточность 2. Заголовок analysis/bugs/cli-env.md:76 («молча становятся NoCoverage») неверен. Предупреждение never-served печатается и в терминале, и в JSON (diagnostics, summary.totalWarnings=1). Сам промпт BUG-507 описывает это правильно.

(г) Завышена ли серьёзность? high оправдан, на нижней границе.
За high:
- Вердикт неверен систематически для каждого модуля, загруженного через require(), а не в редком крайнем случае.
- Реальный выживший (`age == 18`) скрыт как NoCoverage с "tests": 0 в JSON, а поиск таких выживших — главная польза мутационного тестирования.
- Score 37.5% вместо 87.5%.
- Типичная легаси-кодовая база (`"type": "commonjs"`, src/*.js с require; /home/user/projects/verify-skeptic/BUG-507/cjs-legacy): 18 из 24 мутантов NoCoverage, score 25%.
- Если тесты сами вызывают require() (globals: true; /home/user/projects/verify-skeptic/BUG-507/cjs-require-test): dry run 0 tests, 24 из 24 NoCoverage, score 0%.
- С --threshold CI падает ложно. Агент по JSON будет дописывать тесты к уже покрытому коду, а при require() в тестах безуспешно.
- Обойти настройкой нельзя: Vitest не пропускает require() через Vite. При этом документация обещает поддержку `.cjs`.

Смягчающие (почему не critical, и почему кто-то поставил бы medium):
- Ошибка пессимистичная: score занижается, ложных Killed нет, ложной уверенности не возникает.
- Сбой не молчаливый: never-served печатается для каждого файла, хотя названная причина ложная.
- Затронуты только модули, которые под Vitest загружает нативный require() (JS с синтаксисом CommonJS, createRequire). Проекты на TS и ESM, основная аудитория Vitest, не затронуты: их import обрабатывает Vite.
