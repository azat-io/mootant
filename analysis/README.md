# Анализ Mootant — ноябрь 2026

> Коммит `170ec52` (`main`). Ветка анализа: `analysis/2026-11` (меняется только
> каталог `analysis/`). Исходное задание: [`TASK.md`](TASK.md). Язык отчётов —
> русский, код и команды — как есть. Шкалы: серьёзность critical / high /
> medium / low; трудоёмкость S (до часа) / M (до дня) / L (несколько дней) / XL
> (больше недели).

## 1. Резюме

**Общее состояние:** ядро вердикта надёжно; слабые места — нештатные
ситуации, релиз и скорость.

- **Ядро** выдержало независимые проверки: switched-код без активного мутанта
  ведёт себя как исходный, с активным — как физически применённая мутация
  (аудит 123 867 мутантов в 9 проектах, сверка 422 + 1 105 мутантов, ufo 157
  из 157, `core/text` 127 из 127). Исключения узкие: BUG-106 (регулярка с
  `<!--` в Vite 8), BUG-102 (номера строк без source map), BUG-103 (имя
  функции через `?:`).
- **Доверие** подрывают места, где Mootant молча толкует нештатную ситуацию:
  `--since` проходит CI-гейт без проверки изменённых строк (BUG-305), сбой в
  юните даёт ложный Survived (BUG-900), а ошибка загрузки — ложный Killed,
  закреплённый в кэше (BUG-901), Vitest-адаптер не видит `require()` и
  вычисляемый `import()` (BUG-507, BUG-903), ключ кэша пропускает часть
  входов (BUG-402, 403, 410, 419). Ни одна из 43 перепроверенных находок не
  оказалась невоспроизводимой.
- **Принятию** мешают простые вещи: на npm заглушка 0.0.0 (BUG-653), agent
  skill нет (BUG-651), монорепо с `test.projects` не запускаются (BUG-508),
  поддержан только Vitest 5. Каждое, кроме Vitest 4 (L), чинится за день.
- **Скорость:** вопреки ощущению «уже быстрее Stryker», в режиме по умолчанию
  Mootant медленнее StrykerJS (perTest, конкурентность 3, те же файлы) на
  всех четырёх проектах — в 1,04–1,62 раза. Проигрыш даёт планировщик
  isolated-фазы, а не ядро. Прототип P1 (параллельные юниты, opt-in)
  ускоряет прогон в 1,34–1,75 раза при тех же вердиктах: с ним Mootant в
  1,4 раза быстрее Stryker на двух проектах и медленнее на 6,5 и 7,8% на
  двух других (§5).
- **Архитектура** реорганизации не требует: нужны правило группировки
  «модуль = концепт» и сужение публичного API до 1.0 (§4).

## 2. Топ-10 важнейших проблем (независимо от стоимости)

Отобраны тремя независимыми аналитиками с разными «линзами» (доверие,
принятие, сопровождение) и критиком, который сверил доказательства и выбросил
38 слабых или дублирующихся кандидатов (`data/synthesis/synthesis.json`).
Серьёзность и трудоёмкость — как у критика, кроме п. 9: его серьёзность
повышена по итогам замеров, обоснование — в самом пункте.

1. **Установить Mootant по документации нельзя** — critical, исправление S.
   `npm install -D mootant` ставит OIDC-заглушку `0.0.0` без `bin`, после неё
   `npx mootant run src` падает. Из GitHub пакет тоже не ставится: нет `dist/`
   и `prepare`. У тех, кто уже поставил заглушку, диапазон `^0.0.0` не включает
   0.1.0. → [BUG-653](bug-prompts/BUG-653.md), `06-ux-and-agents.md` §6.1.
2. **`--since` молча теряет мутантов изменённых строк, CI-гейт проходит** —
   high, M. Отбор по строкам идёт после правил пропуска. Если «владелец»
   пропуска стоит на неизменённой строке, изменённая строка остаётся без
   мутантов: «score none», exit 0 при любом `--threshold`, хотя полный прогон
   даёт 0% и exit 1. Масштаб: 357 строк в `core` и 268 в perfectionist. →
   [BUG-305](bug-prompts/BUG-305.md).
3. **Нештатный исход юнита превращается в вердикт** — high, M. Посторонний
   сбой (таймаут теста, не дошедшего до мутанта, упавший хук) мешает выполнить
   тесты, достигающие мутанта. Тогда юнит — «файл без улик», и итог — ложный
   Survived или NoCoverage без диагностики, хотя `--mutant <id>` даёт Killed.
   Обратная сторона: `crash` и `load-error` без достижения мутанта дают
   Killed, и `load-error` закрепляется в кэше. →
   [BUG-900](bug-prompts/BUG-900.md), [BUG-901](bug-prompts/BUG-901.md),
   BUG-206, [BUG-602](bug-prompts/BUG-602.md).
4. **Vitest-адаптер доверяет статическому графу Vite** — high, L. Модули из
   `require()`/`createRequire` не переключаются: их мутанты получают
   NoCoverage, хотя вручную 4 из 5 убиваются. Тест с вычисляемым `import()` не
   выбирается. Вердикт может зависеть от набора выбранных мутантов (`--mutant`,
   `--since`). В node:test тесты отбираются по фактической загрузке, и этих
   проблем нет, но в связке yarn PnP + node:test все мутанты молча получают
   NoCoverage при exit 0 ([BUG-820](bug-prompts/BUG-820.md)). →
   [BUG-507](bug-prompts/BUG-507.md), [BUG-201](bug-prompts/BUG-201.md),
   [BUG-903](bug-prompts/BUG-903.md), BUG-205.
5. **Монорепозитории с `test.projects` и своим `root` не запускаются** —
   high, M. При `projects: ['packages/*']` прогон падает с «Tests fail without
   mutants», хотя `vitest --run` зелёный. Плагин попадает только в корневой
   Vite-сервер. → [BUG-508](bug-prompts/BUG-508.md).
6. **Поддержан только Vitest 5 (вышел 2026-09-03)** — high, L. Проекты на
   Vitest 4 и 3 получают отказ на первом же запуске. Простое снятие проверки
   версии не помогает: адаптер завязан на API пула v5. → `07-compat-and-release.md`
   §7.1.5–7.1.6, `data/compat-experiments.md` M11.
7. **Agent skill, заявленный главным отличием, отсутствует** — medium, S.
   `npx skills add azat-io/mootant` отвечает «No skills found», пункт меню
   сайта «Agent skill» ведёт на 404, в README skill не упомянут. →
   [BUG-651](bug-prompts/BUG-651.md), [BUG-650](bug-prompts/BUG-650.md);
   черновик [`ux/SKILL.draft.md`](ux/SKILL.draft.md) проверен на CLI `skills`
   1.7.6.
8. **Кэш по умолчанию отдаёт устаревшие вердикты в обе стороны** — medium, L.
   Ключ не видит файлов за виртуальными модулями Vite, чтений через `fs` вне
   root, правок в `node_modules` без смены lockfile и tsconfig из `references`.
   Обратный дефект: в CI с `npm ci` кэш не срабатывает никогда (0 из 67), потому
   что ключ сборки — mtime файла. → [BUG-402](bug-prompts/BUG-402.md),
   [403](bug-prompts/BUG-403.md), [410](bug-prompts/BUG-410.md),
   [419](bug-prompts/BUG-419.md), [407](bug-prompts/BUG-407.md).
9. **Isolated-фаза плохо параллелится, поэтому Mootant медленнее Stryker** —
   high, L. Серьёзность повышена с medium (оценка критика синтеза до замеров)
   до high: в окне замеров при той же конкурентности Mootant медленнее
   Stryker на всех четырёх проектах (×1,04–1,62), хотя на двух из них тратит
   меньше CPU. Это прямо противоречит цели автора «заметно быстрее», а
   исправление (прототип P1) измерено и не меняет вердиктов. Причина —
   расписание. Контракт запрещает гонять один тест-файл дважды одновременно:
   воркер ждёт очереди и держит слот. На path-to-regexp весь раунд — одна
   цепочка из 339 юнитов, слоты заняты на 31%. Выжившие проходят раунды 1, 1,
   2, 4, 8 файлов, и каждый раунд ждёт свой самый долгий юнит. На
   perfectionist выжившие забирают 71% времени юнитов. Если мутантов
   покрывает один тест-файл (типично для `--since` на PR, одного модуля и
   цикла агента), раунд превращается в одну цепочку. → `04-performance.md`
   §4.5, `03-competitors.md` «Эмпирическая проверка», `00-baseline.md`
   (догфудинг: 85 юнитов × 10–13 с подряд).
10. **Тёплый прогон и перепроверка `--mutant` всегда платят старт раннера и
    dry run, а Timeout-мутанты гоняются заново** — medium, XL для полного
    решения. Dry run выполняется раньше, чем применяется кэш
    (`core/run-mutants.ts:411` до `:444`/`:489`): в тёплом прогоне — полный,
    в `--mutant` — тестов, связанных с файлом мутанта. Мутанты со статусом
    Timeout не кэшируются (`core/cache/create-run-cache.ts:313-319`). Тёплый
    прогон без изменений занимает 5,4–80,4 с: dry run — 7–92% этого времени,
    повтор Timeout-мутантов — до 86% (path-to-regexp). Перепроверка одного
    мутанта — 1,7–6,9 с. Прототип P3 сокращает тёплый прогон cheerio и
    fast-json-stringify до 0,5–0,7 с (×10,1 и ×9,3), но не срабатывает после
    правки мутируемого файла и при `time-limit`-тайм-аутах: на perfectionist
    (два таких Timeout) он, по коду, не помог бы, а замер там не снят (§7). →
    `04-performance.md` §4.5, прототип P3.

**Что проверено и проблемой не оказалось** (поэтому в топе нет): изоляция
isolated-пути (у каждого юнита свой процесс в обоих адаптерах), детерминизм
вердиктов, кроме зависящих от времени, слои (ядро не знает ни одного раннера,
копипасты 0,03–0,19%), эвристики «владения» и поглощения (на собственном коде
Mootant 0 ложных пропусков из 360 проверенных).

## 3. Топ-10 наиболее выгодных улучшений (польза / трудоёмкость)

У каждого улучшения указаны проблема, доказательство, польза, риск и проверка
(принцип 10 задания); трудоёмкость — в скобках после названия. Пункты 1, 2, 4,
5 и 10 закрывают проблемы 1, 7, 2, 3 и 9 из §2: они стоят в обоих списках
сознательно, потому что это и важная проблема, и выгодное действие.
Подробности — в отчётах по ссылкам и в bug-prompts.

1. **Опубликовать 0.1.0 и закрыть ловушки первого релиза** (S).
   - *Что сделать:* `"exclude": ["dist"]` в `tsconfig.json`, порядок шагов и
     права в `release.yml`, `npm pkg fix`, `.mootant/` в `.gitignore`, заметки к
     0.1.0 с советом поставить `mootant@latest` вместо `^0.0.0`, затем `npm
     deprecate mootant@0.0.0`.
   - *Проблема:* п. 1 §2 — документированная установка ставит заглушку 0.0.0.
   - *Доказательство:* [BUG-653](bug-prompts/BUG-653.md), воспроизведён
     независимо; после `pnpm build` краснеет `test:astro`, и повторный
     `release:check` падает (`00-baseline.md`); в `release.yml` GitHub Release
     создаётся до `npm publish`, а `id-token: write` выдан всему джобу
     (`07-compat-and-release.md` §7.4.4).
   - *Польза:* начинает работать первая команда из документации — у людей и у
     агентов.
   - *Риск:* релиз закрепит текущие контракты; планируемые ломающие правки 0.x
     (коды выхода, корень проекта) объявить в changelog.
   - *Проверка:* `npm init -y && npm i -D vitest@5 mootant && npx mootant
     --version` → `mootant/0.1.0`; `pnpm build && pnpm release:check` зелёный
     дважды подряд.
2. **Положить `skills/mootant/SKILL.md` и починить ссылку `/agent-skill`** (S).
   - *Проблема:* п. 7 §2 — `npx skills add azat-io/mootant` отвечает «No skills
     found», `/agent-skill` — 404.
   - *Доказательство:* `ux/skills-add-output.txt` (CLI `skills` 1.7.6),
     [BUG-651](bug-prompts/BUG-651.md), [BUG-650](bug-prompts/BUG-650.md).
     Черновик [`ux/SKILL.draft.md`](ux/SKILL.draft.md) CLI находит (`--list`) и
     ставит (`-y`); на ручном прогоне цикла агента по нему score вырос с 35 до
     48% за один проход.
   - *Польза:* ключевое отличие проекта начинает работать: один файл и рабочая
     ссылка вместо 404.
   - *Риск:* skill нужно держать в синхроне с CLI; оговорки черновика про `npx`
     и гранулярность игнора — обновить после BUG-652 и игнора по id.
   - *Проверка:* `npx skills add azat-io/mootant --list` показывает `mootant`;
     агент на `docs/demo` убивает выжившего и подтверждает это через `--mutant`.
3. **Кэш в CI: идентификатор сборки вместо mtime, CI-переменные вне `*`-хэша**
   (S).
   - *Проблема:* штамп сборки в ключе кэша — mtime файла пакета, а `npm ci`
     ставит файлам время установки, поэтому в CI кэш не срабатывает никогда
     ([BUG-407](bug-prompts/BUG-407.md)). Тесты, которые перечисляют
     `process.env` (RuleTester, запуск дочерних процессов), вдобавок теряют кэш
     из-за `GITHUB_RUN_ID` и подобных переменных
     ([BUG-701](bug-prompts/BUG-701.md)). Вердикты при этом не ложные: теряется
     только кэш.
   - *Доказательство:* `ux/ci-cache-check.txt`: после `npm ci` с восстановленным
     кэшем все 67 мутантов прогоняются заново, после `touch -d` — «Reused cached
     verdicts for 67 of 79»; `bench/repro/bug-701/`: с другим значением
     переменной из кэша берётся 1 вердикт из 5 вместо 5 из 5.
   - *Польза:* полный прогон `main` и проверки PR берут вердикты из кэша.
   - *Риск:* идентификатор должен меняться при каждой пересборке кода; из `*`
     исключать только идентификаторы прогона (`GITHUB_RUN_*`, `RUNNER_*`), иначе
     вердикты устареют.
   - *Проверка:* сценарий `ux/ci-cache-check.txt` без `touch` — «Reused cached
     verdicts for 67 of 79»; `bench/repro/bug-701/repro.sh` с другим
     `GITHUB_RUN_ID` — 5 из 5.
4. **`--since`: сразу диагностика, затем пропуск с владельцем — только если
   владелец запускается** (S, затем M).
   - *Проблема:* п. 2 §2 — изменённая строка остаётся без мутантов, CI-гейт
     проходит с «score none».
   - *Доказательство:* тест и сквозной сценарий в
     [BUG-305](bug-prompts/BUG-305.md); независимо воспроизведён (тест падает 3
     из 3), масштаб пересчитан: 357 строк в `core` и 268 в perfectionist.
   - *Польза:* шаг 1 (S) — предупреждение о строках только с пропущенными
     кандидатами, и гейт перестаёт молчать; шаг 2 (M) — мутант изменённой строки
     возвращается, и PR-гейт проверяет то, что действительно изменилось.
   - *Риск:* в PR станет немного больше мутантов; нельзя вернуть дубль, если
     владелец тоже отобран; без `--since` id и состав не должны меняться.
   - *Проверка:* тест из BUG-305; фикстура `data/skips/fx-since` даёт мутанта и
     exit 1 при `--threshold 80`; эталоны `test/fixtures/list` без `--since` не
     меняются.
5. **Нештатный исход юнита — не вердикт** (S, затем M).
   - *Что сделать:* сначала не кэшировать `load-error` и подтверждать `crash`
     повтором, затем исход «юнит неполон» → повтор → `Error` с диагностикой.
   - *Проблема:* п. 3 §2 — посторонний сбой даёт ложный Survived или NoCoverage,
     а `crash` и `load-error` — ложный Killed.
   - *Доказательство:* [BUG-900](bug-prompts/BUG-900.md) (сквозные прогоны на
     Vitest 5.0.5 и 5.1.0 и на node:test) и [BUG-901](bug-prompts/BUG-901.md)
     воспроизведены независимо; `--mutant <id>` на том же мутанте даёт Killed.
   - *Польза:* Survived снова значит «все покрывающие файлы прошли», score не
     растёт от нестабильности CI, полный прогон совпадает с `--mutant`.
   - *Риск:* лишний юнит на прерванный файл; на нестабильных сьютах больше
     `Error`; меняется контракт `IsolatedFacts` в обоих адаптерах.
   - *Проверка:* тесты из BUG-900 и BUG-901; согласие оракула не ниже 91,5%
     (Vitest) и 96,7% (node:test).
6. **Первый запуск без спотыканий** (S): `npx` в подсказках перепроверки,
   автоматический `.mootant/.gitignore`, проверка версии Node в `bin`.
   - *Проблема:* скопированная `re-check one: mootant run src --mutant 69kd`
     даёт `command not found` ([BUG-652](bug-prompts/BUG-652.md)); HTML-отчёт с
     исходниками легко попадает в коммит; на Node ниже 20.19 вместо сообщения о
     версии — стек `toSorted is not a function` (BUG-515).
   - *Доказательство:* журнал первого запуска (`06-ux-and-agents.md` §6.1): `git
     add -A` закоммитил `.mootant/report.html` на 4223 строки; BUG-652
     воспроизведён независимо, BUG-515 — на Node 18.20.8.
   - *Польза:* каждая подсказка работает при копировании и у человека, и у
     агента; отчёт с кодом не утекает в git; вместо стека — понятная ошибка о
     версии.
   - *Риск:* менеджер пакетов можно угадать неверно, поэтому в JSON отдавать ещё
     и массив аргументов команды; существующий `.gitignore` не перезаписывать.
   - *Проверка:* строка `re-check one:` запускается в bash как есть; `git
     status` чист после `--html`; `bin` на Node 18 печатает требуемую версию.
7. **Документация, которая калибрует доверие** (S): CI-рецепт для GitHub
   Actions, Troubleshooting, раздел «когда вердикту не верить» (CJS под Vitest,
   монорепо до BUG-508, контейнеры без `ps`, что не входит в ключ кэша), совет
   про `fetch-depth` при shallow-клоне.
   - *Проблема:* первый CI-конфиг ломается на деталях: клон глубиной 1 даёт
     `unknown git revision` без подсказки, кэш не переживает `npm ci`. Пределы
     вердикта не описаны: CJS под Vitest, что не входит в ключ кэша, «score
     none» проходит порог.
   - *Доказательство:* `06-ux-and-agents.md` §6.2 (`ux/ci-since-check.txt`: при
     `fetch-depth: 1` — `unknown git revision "origin/main"`) и §6.6 (D3, D8); в
     документации про CI — одна фраза без YAML
     (`docs/content/guide/getting-started.mdx:132-134`).
   - *Польза:* пользователь и агент знают, что перепроверить, ещё до исправлений
     кода; первый CI собирается по готовому рецепту.
   - *Риск:* документация отстаёт от кода: пункты убирать по мере исправлений,

## 5. Производительность: главное

**Методика.** Эксклюзивное окно замеров (4 vCPU Xeon 2,1 ГГц, 15 ГБ, Node
22.23.4): тяжёлых нагрузок, кроме замера, на машине не было. Mootant
`170ec52` из tarball; StrykerJS 10.1.1 с `coverageAnalysis: perTest` (для
node:test — tap-runner); у обоих конкурентность 3 и одинаковые файлы. Замеры
hyperfine: 3 прогона на точку, тест-сьюты — по 5. hyperfine мерил обвязку
замера, а она ждала сэмплер памяти с шагом 1 с, поэтому wall короткой точки
завышен на 0,2–1,0 с. Точки короче ~30 с (тест-сьюты, тёплый кэш,
`--mutant`, `--since`) и все коэффициенты с ними даны по elapsed GNU time тех
же прогонов; у длинных точек смещение меньше 1% (`bench/README.md`,
«Известные ограничения», п. 11; обвязка исправлена после окна). Стенд

трассы юнитов — в [`04-performance.md`](04-performance.md); сопоставление
наборов мутантов — в [`03-competitors.md`](03-competitors.md), «Эмпирическая
проверка».

     вместе с `killedBy`.
4. **Префорк процессов** без загрузки кода пользователя (L). После P1 слоты на
   path-to-regexp и cheerio заняты юнитами на 67–69%, остальное — старт и
   сворачивание форков (старт — 142–156 мс на юнит у Vitest). Прогноз после P1:
   ×1,2–1,4 на этих проектах, около 5% на perfectionist. Не прототипировалось.
   - *Риск / проверка:* средний — процесс не должен ничего грузить из кода
     пользователя до получения юнита; оракул физически применённых мутантов и
     сравнение `--json --all`.
5. **Кэш компиляции V8 в воркерах и процессах node:test**
   (`module.enableCompileCache`, `NODE_COMPILE_CACHE`; S). На perfectionist
   компиляция CJS (typescript, ESLint) — 15% CPU воркеров, ESM — ещё 3%.
   Прогноз: −10…−15% CPU воркеров на проектах с тяжёлыми зависимостями. Не
   прототипировалось.
   - *Риск / проверка:* низкий — кэш по содержимому, а модули проекта Vitest
     исполняет не через загрузчик Node; профиль `run` до и после, равенство
     вердиктов.
6. **Быстрый путь ширины строки для печатного ASCII** в текстовых отчётах
   (BUG-702; S). Измерено: `mootant list core` 7,78 → 6,28 с (×1,24). Diff:
   [`experiments/perf-display-width-ascii-fast-path.diff`](experiments/perf-display-width-ascii-fast-path.diff).
   - *Риск / проверка:* риска нет — меняется только вывод, и он совпадает байт в
     байт (`experiments/perf-display-width.md`).
7. **Перепроверка выживших без барьеров раундов** (S — крупнее пакеты файлов, L
   — потоковая очередь). Прогноз по трассам: без P1 −80…−140 с на perfectionist
   (≈×1,1–1,2), после P1 около 5%: раунды 4–6 уже заняты на 96–97%, это работа
   выживших. Не прототипировалось.
   - *Риск / проверка:* для вердиктов риска нет — меняется только расписание
     (`core/run/decide-evidence.ts:5-16`); `compare-verdicts --strict`.
8. **Калибровка тайм-аутов** (S–M; кэш `hit-limit` уже входит в п. 2). На
   perfectionist два `time-limit`-Timeout стоят 8–9% времени юнитов и
   повторяются в каждом тёплом прогоне (32 с из 80); более жёсткий `time-limit`
   — до −8% (не измерено).
   - *Риск / проверка:* снижение `time-limit` даёт ложные Timeout на шумной
     машине (BUG-204); точка `m-warm` стенда и сравнение вердиктов.

Ранги 9–12 (порядок тест-файлов, node:test без процесса на юнит, отсев
некомпилирующихся мутантов, выборка) дают малый или не оценённый выигрыш —
`04-performance.md` §4.4.

**Отрицательные результаты:**
- обрезка юнита до покрывающих тестов (P2) даёт ложные Survived на
  зависимых тестах: 3 из 12 на граничной фикстуре;
- ускорять dry run незачем: он стоит ×1,0–1,2 от обычного прогона тест-сьюта
  (на 4–25% дороже) и 1–5% холодного прогона; проблема в том, что он идёт
  всегда, в том числе в тёплом прогоне (ранг 2);
- кэш трансформаций Vite между прогонами даёт не больше 0,4–2,0 с CPU за
  прогон;
- сортировка юнитов раунда по стоимости (LPT) отброшена по коду: узкое место —
  цепочка одного файла;
- `--fast` не помогает, когда время съедают выжившие (perfectionist, ×1,00).

## 7. Что не успел или не смог проверить

**Не смог (ограничения окружения):**
- **Windows и macOS** — машин не было. Всё про них остаётся гипотезами по
  коду: BUG-511 (`stopProcessGroup` на Windows), BUG-421, BUG-512, пути и
  регистр.
- **Тесты внешних проектов под оракулом** — система разрешений запретила
  агенту-оракулу исполнять тесты склонированных репозиториев (defu, scule,
  nanoid, fastify-error). Поэтому оракул работал на фикстурах и на
  `core/text` самого Mootant. Сквозной прогон против физических мутаций на
  чужом коде есть только для ufo (157 из 157) — его делал агент
  инструментирования.
- **Закрытые хосты:** api.npmjs.org, arxiv.org, research.google,
  stryker-mutator.io и mootant.org были недоступны из сессии. Поэтому доли
  аудитории по версиям Vitest не посчитаны, статьи сверены по поисковой
  выдаче без полных текстов, а навигация сайта проверена только по исходникам
  `docs/`.
- **CI-workflow на GitHub не запускался:** доступа на запись к репозиторию у
  сессии не было. Черновик `ux/mootant-workflow.yml` проверен только
  actionlint и локальным прогоном шагов Mootant и конвертера; лимиты
  аннотаций взяты из документации.
- **BusyBox `ps` (Alpine)** — скачать внешний бинарь не разрешено. Поэтому
  BUG-502 для Alpine — гипотеза; для slim/distroless (без `ps`) подтверждён.

**Не успел (время и эксклюзивное окно замеров):**
- **Догфудинг `core/regex` и `core/run`.** `mootant run core/text` остановил
  на 42-й минуте внешний лимит времени фоновой задачи (таймаут я задал
  неверно); к этому моменту шёл раунд 5, а время съели последовательные
  хвосты выживших (`00-baseline.md`). Вместо `core/regex` и `core/run` агент
  раздела 5 прогнал до конца `core/git` и `cli/terminal`: 84,45% → 90,3% и
  88,7% → 93,7% после новых тестов.
- **Ярусы 4–6 стенда:** обычный кэш после правки без `--incremental`,
  `list` текстом против JSON на проектах, Stryker с `typescript-checker`,
  инкрементальный Stryker, `--no-cache`, command runner для node:test,
  догфудинг на стенде. План и скрипты готовы (`bench/README.md`,
  `bash analysis/bench/run.sh`).
- **P3 на perfectionist** не измерен из-за ошибки стенда: лог подготовительного
  прогона шёл в ещё не созданный каталог `snapshots/`, и точка не стартовала
  (исправлено после окна). По коду P3 там и не помог бы: два
  `time-limit`-Timeout не кэшируются, прогноз — около 80,4 с, как у базы.
- **Профили и трассы.** CPU-профили сняты только на perfectionist и
  path-to-regexp: cheerio и fast-json-stringify в окно не вошли. Трасс юнитов
  node:test нет, поэтому у fast-json-stringify загрузка и тесты на юнит не
  разделены.
- **Смещение коротких точек hyperfine.** Обвязка замера ждала сэмплер памяти
  с шагом 1 с, и wall hyperfine у точек короче ~30 с завышен на 0,2–1,0 с (до
  +97%). Эти точки и коэффициенты с ними пересчитаны по elapsed GNU time тех
  же прогонов. Обвязку исправили после окна (хелперам сразу после команды
  посылается SIGTERM; на `sleep 1.3` она теперь даёт 1,33 с), но стенд с ней
  не перемеряли (`bench/README.md`, «Известные ограничения», п. 11).
- **Полный I2 (весь тест-сьют против полностью switched-кода) на сьютах
  Mootant и perfectionist** — под нагрузкой не успели. I2 выполнен на ufo и
  defu и на фикстурах Vue и Svelte.
- **Независимая перепроверка** двумя агентами не проводилась для BUG-510,
  BUG-701, BUG-800, BUG-820, BUG-850 и BUG-851. BUG-850 и BUG-851
  подтверждены моими собственными прогонами `test:unit`. BUG-800 я
  воспроизвёл сам на чистой установке tarball (путь `run --html` выведен из
  кода). BUG-701 подтверждён агентом раздела 4 на фикстуре и perfectionist
  (`bench/repro/bug-701/`), BUG-510 — падающим тестом-воспроизведением
  (контрольный прогон — `data/repros-run.md`), BUG-820 — экспериментом M10
  (`data/compat-experiments.md`). У BUG-856 воспроизводящий агент остановлен ради
  окна замеров, а скептик подтвердил факты ручными мутациями. BUG-651
  независимый верификатор воспроизвёл частично: песочница не дала запустить
  `npx skills`, но отсутствие `SKILL.md` доказано; исходный запуск CLI —
  `ux/skills-add-output.txt`.
- **Проверка типов выживших.** Утверждение «29% мутантов Mootant на его
  строгом TS-коде не проходят `tsc`» — статический замер (TS 5.9
  LanguageService), без прогона против `typescript-checker` Stryker.
- **Пресет `strict` против Stryker** не запускался. 135 общих выживших
  вручную не разбирались, доля эквивалентных среди них неизвестна; выжившие
  «только у Mootant» разобраны выборкой — 74 из 111.
- **Шум облака.** Окно замеров эксклюзивное по тяжёлым нагрузкам, но в нём
  работали «бумажные» агенты (чтение и правка текста, CPU около 0). Разброс
  (σ/mean по elapsed GNU time): у точек длиннее 30 с — 0,2–6,6% (P1 —
  1,4–3,7%), у коротких — 2,2–10,4%, у тёплого прогона P3 — 8,8 и 17,4% (при
  0,5–0,7 с на прогон 0,1 с — это уже 15%). Для публичных цифр стоит
  повторить на выделенной машине.

**Сознательно не проверялось:** производительность на Node 20 и 24 (вердикты
на них проверены, скорость — нет) и браузерный режим Vitest (не поддерживается
по документации).
