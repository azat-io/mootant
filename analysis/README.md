## 1. Резюме

**Ядро Mootant надёжнее, чем можно было ожидать от версии 0.1: механизм
вердикта выдержал несколько независимых проверок.** Switched-код без активного
мутанта ведёт себя как исходный, а с активным — как физически применённая
мутация. Проверки: структурный аудит 123 867 мутантов в 9 проектах,
поведенческая сверка 422 мутантов по-тестово и 1 105 мутантов
модулей-ловушек, сквозные прогоны ufo (157 из 157) и `core/text` (127 из 127).
Изоляция isolated-пути реальная: у каждого юнита свой процесс. Вердикты
детерминированы, кроме зависящих от времени. Слои и ESLint-модель здоровые:
ядро не знает ни одного раннера, копипасты почти нет (0,03–0,19%). Эвристики
«владения» и поглощения на собственном коде Mootant дали 0 ложных пропусков из
360 проверенных.

**Доверие подрывает не механизм, а места, где Mootant молча толкует нештатную
ситуацию:**
- `--since` проходит CI-гейт с «score none», не проверив изменённые строки
  (BUG-305);
- посторонний сбой в юните даёт ложный Survived (BUG-900), а ошибка загрузки —
  ложный Killed, который закрепляется в кэше (BUG-901);
- Vitest-адаптер не видит `require()` и вычисляемый `import()` (BUG-507);
- кэш по умолчанию не замечает нескольких видов входов (BUG-402, 403, 410,
  419).

Почти у всех таких находок есть падающий тест и самодостаточный промпт. Ни одна
из 43 перепроверенных находок не оказалась невоспроизводимой.

**Принятию мешают простые вещи:**
- на npm лежит заглушка 0.0.0 (установка по README не работает — BUG-653);
- обещанного agent skill нет в репозитории (BUG-651);
- монорепозитории с `test.projects` не запускаются (BUG-508);
- поддержан только Vitest 5, вышедший два месяца назад.

Всё перечисленное, кроме Vitest 4, чинится за дни.

**Скорость: ощущение «уже быстрее Stryker» замеры не подтверждают.** В
эксклюзивном окне при одинаковой конкурентности (3) и одинаковых файлах
Mootant в режиме по умолчанию **медленнее** StrykerJS (perTest) на всех
четырёх проектах: в 1,04 раза (cheerio), 1,22 (path-to-regexp), 1,44
(eslint-plugin-perfectionist) и 1,62 (fast-json-stringify). При этом CPU он
тратит меньше, а пиковая память ниже в 1,5–2,7 раза. Значит, проигрыш — в
планировании: ядра простаивают. Время уходит не на тесты и не на dry run
(1–5% холодного прогона), а на isolated-фазу:
- юниты одного тест-файла идут строго по очереди: на path-to-regexp весь
  раунд — одна цепочка, слоты заняты на 31%;
- выжившие проходят все покрывающие файлы раундами с барьерами: на
  perfectionist выжившие забирают 71% времени юнитов, около 27 с на каждого;
- тёплый прогон платит dry run и каждый раз заново гоняет Timeout-мутантов,
  потому что кэш их не хранит (7–92% и 41–86% тёплого прогона).

В `--fast` Mootant уже в 2,4–3 раза **быстрее** Stryker на path-to-regexp и
cheerio при тех же вердиктах, но на perfectionist выигрыша нет. Прототип
параллельных юнитов (opt-in) ускорил path-to-regexp в **1,74 раза** при
совпадении всех 342 вердиктов, после чего режим по умолчанию быстрее Stryker
и там. Быстрый путь ширины строк ускорил текстовый `list` в 1,24 раза.
Подробности — §5 и `04-performance.md`.

**Архитектура** не требует реорганизации. Нужно правило группировки «модуль =
концепт» вместо «одна функция — один файл» (653 → 535 файлов в консервативном
варианте) и сужение того, что торчит наружу: 40 методов `context.syntax` в
плагинном API и 822 `.d.ts` в пакете при 62 нужных. Контракт адаптера
правильный по сути, но это вынесенный наружу внутренний API без версии.
Rstest при целевом контракте — M, Jest — L.

## 2. Топ-10 важнейших проблем (независимо от стоимости)

Отобраны тремя независимыми аналитиками с разными «линзами» (доверие,
принятие, сопровождение) и критиком, который сверил доказательства и выбросил
38 слабых или дублирующихся кандидатов (`data/synthesis/synthesis.json`).

1. **Установить Mootant по документации нельзя** — critical, исправление S.
   `npm install -D mootant` ставит OIDC-заглушку `0.0.0` без `bin`, после неё
   `npx mootant run src` падает. Из GitHub пакет тоже не ставится: нет `dist/`
   и `prepare`. У тех, кто уже поставил заглушку, диапазон `^0.0.0` не включает
   0.1.0. → [BUG-653](bug-prompts/BUG-653.md), `06-ux-and-agents.md` §6.1.
2. **`--since` молча теряет мутантов изменённых строк, CI-гейт проходит** —
   high, M. Отбор по строкам идёт после правил пропуска. Если «владелец»
   пропуска стоит на неизменённой строке, изменённая строка остаётся без
   мутантов: «score none», exit 0 при любом `--threshold`, хотя полный прогон
   даёт 0% и exit 1. Масштаб: 357 строк в `core` и 268 в perfectionist. →
   [BUG-305](bug-prompts/BUG-305.md).
3. **Нештатный исход юнита превращается в вердикт** — high, M. Посторонний
   сбой (таймаут теста, не дошедшего до мутанта, упавший хук) мешает выполнить
   тесты, достигающие мутанта. Тогда юнит — «файл без улик», и итог — ложный
   Survived или NoCoverage без диагностики, хотя `--mutant <id>` даёт Killed.
   Обратная сторона: `crash` и `load-error` без достижения мутанта дают
   Killed, и `load-error` закрепляется в кэше. →
   [BUG-900](bug-prompts/BUG-900.md), [BUG-901](bug-prompts/BUG-901.md),
   BUG-206, BUG-602.
4. **Vitest-адаптер доверяет статическому графу Vite** — high, L. Модули из
   `require()`/`createRequire` не переключаются: их мутанты получают
   NoCoverage, хотя вручную 4 из 5 убиваются. Тест с вычисляемым `import()` не
   выбирается. Вердикт может зависеть от набора выбранных мутантов (`--mutant`,
   `--since`). В node:test этих проблем нет: отбор идёт по фактической
   загрузке. → [BUG-507](bug-prompts/BUG-507.md), BUG-201, BUG-903, BUG-205,
   [BUG-820](bug-prompts/BUG-820.md).
5. **Монорепозитории с `test.projects` и своим `root` не запускаются** —
   high, M. При `projects: ['packages/*']` прогон падает с «Tests fail without
   mutants», хотя `vitest --run` зелёный. Плагин попадает только в корневой
   Vite-сервер. → [BUG-508](bug-prompts/BUG-508.md).
6. **Поддержан только Vitest 5 (вышел 2026-09-03)** — high, L. Проекты на
   Vitest 4 и 3 получают отказ на первом же запуске. Простое снятие проверки
   версии не помогает: адаптер завязан на API пула v5. → `07-compat-and-release.md`
   §7.1.5–7.1.6, `data/compat-experiments.md` M11.
7. **Agent skill, заявленный главным отличием, отсутствует** — medium, S.
   `npx skills add azat-io/mootant` отвечает «No skills found», пункт меню
   сайта «Agent skill» ведёт на 404, в README skill не упомянут. →
   [BUG-651](bug-prompts/BUG-651.md), BUG-650; черновик
   [`ux/SKILL.draft.md`](ux/SKILL.draft.md) проверен на CLI `skills` 1.7.6.
8. **Кэш по умолчанию отдаёт устаревшие вердикты в обе стороны** — medium, L.
   Ключ не видит файлов за виртуальными модулями Vite, чтений через `fs` вне
   root, правок в `node_modules` без смены lockfile и tsconfig из `references`.
   Обратный дефект: в CI с `npm ci` кэш не срабатывает никогда (0 из 67), потому
   что ключ сборки — mtime файла. → [BUG-402](bug-prompts/BUG-402.md),
   [403](bug-prompts/BUG-403.md), [410](bug-prompts/BUG-410.md),
   [419](bug-prompts/BUG-419.md), [407](bug-prompts/BUG-407.md).
9. **Isolated-фаза плохо параллелится** — medium, L. Контракт запрещает
   гонять один тест-файл дважды одновременно. Воркер ждёт очереди и держит
   слот. Выжившие проходят раунды 1, 1, 2, 4, 8 файлов, и каждый раунд ждёт
   свой самый долгий юнит. При `--since` на PR, на одном модуле и в цикле
   агента прогон превращается в одну цепочку. → `04-performance.md`,
   `00-baseline.md` (догфудинг: 85 юнитов × 10–13 с подряд).
10. **Тёплый прогон и перепроверка `--mutant` всегда платят старт раннера и
    полный dry run** — medium, XL для полного решения. Dry run выполняется
    раньше, чем применяется кэш (`core/run-mutants.ts:411` до `:444`/`:489`). На
    внешних проектах это 90–98% тёплого прогона. Цикл агента «тест →
    перепроверка» на большом проекте занимает минуты. → `00-baseline.md`,
    `04-performance.md`, прототип P3.

## 3. Топ-10 наиболее выгодных улучшений (польза / трудоёмкость)

Для каждого улучшения указаны проблема, доказательства, польза, риски и
проверка. Подробности — в отчётах по ссылкам и в bug-prompts.

1. **Опубликовать 0.1.0 и закрыть ловушки первого релиза** (S). *Проблема:*
   п. 1 топа проблем. *Что сделать:* `"exclude": ["dist"]` в `tsconfig.json`
   (иначе `test:astro` краснеет после `pnpm build`, см. `00-baseline.md`),
   порядок шагов и права в `release.yml`, `npm pkg fix`, `.mootant/` в
   `.gitignore`, заметки к 0.1.0 с советом поставить `mootant@latest` вместо
   `^0.0.0`, затем `npm deprecate mootant@0.0.0`. *Польза:* начинает работать
   первая команда из документации. *Риск:* релиз закрепит текущие контракты;
   планируемые ломающие правки 0.x (коды выхода, корень проекта) объявить в
   changelog. *Проверка:* `npm init -y && npm i -D vitest@5 mootant && npx
   mootant --version` → `mootant/0.1.0`; `pnpm build && pnpm release:check`
   зелёный дважды подряд.
2. **Положить `skills/mootant/SKILL.md` и починить ссылку `/agent-skill`** (S).
   *Проблема:* п. 7. *Доказательство:* `ux/skills-add-output.txt`; черновик
   `ux/SKILL.draft.md` CLI `skills` находит (`--list`) и ставит (`-y`). На
   ручном прогоне цикла агента score вырос с 35 до 48%. *Риск:* skill нужно
   держать в синхроне с CLI. *Проверка:* `npx skills add azat-io/mootant
   --list` показывает `mootant`; агент на `docs/demo` убивает выжившего и
   подтверждает это через `--mutant`.
3. **Кэш в CI: идентификатор сборки вместо mtime, CI-переменные вне `*`-хэша**
   (S). *Проблема:* 0 из 67 вердиктов из кэша после `npm ci`
   ([BUG-407](bug-prompts/BUG-407.md)). Любая переменная вроде
   `GITHUB_RUN_ID` сбрасывает кэш тестам, которые перечисляют окружение
   (BUG-701). *Польза:* полный прогон `main` и проверки PR берут вердикты из
   кэша. *Риск:* идентификатор должен меняться при каждой пересборке кода.
   *Проверка:* сценарий `ux/ci-cache-check.txt` без `touch` — «Reused cached
   verdicts for 67 of 79».
4. **`--since`: сразу диагностика, затем пропуск с владельцем — только если
   владелец запускается** (S, затем M). *Проблема:* п. 2. *Польза:* PR-гейт
   перестаёт молча пропускать непроверенные строки. *Риск:* в PR станет
   немного больше мутантов; без `--since` id и состав не должны меняться.
   *Проверка:* тест из [BUG-305](bug-prompts/BUG-305.md); фикстура
   `data/skips/fx-since` даёт мутанта и exit 1 при `--threshold 80`.
5. **Нештатный исход юнита — не вердикт** (S, затем M). Сначала не кэшировать
   `load-error` и подтверждать `crash` повтором, затем вердикт «юнит неполон» →
   повтор → `Error` с диагностикой. *Проблема:* п. 3. *Польза:* Survived снова
   значит «все покрывающие файлы прошли», score не растёт от нестабильности
   CI, полный прогон совпадает с `--mutant`. *Риск:* лишний юнит на
   прерванный файл; на нестабильных сьютах больше `Error`. *Проверка:* тесты из
   [BUG-900](bug-prompts/BUG-900.md) и [BUG-901](bug-prompts/BUG-901.md);
   согласие оракула не ниже 91,5% и 96,7%.
6. **Первый запуск без спотыканий** (S): `npx` в подсказках перепроверки
   ([BUG-652](bug-prompts/BUG-652.md)), автоматический `.mootant/.gitignore`
   (HTML-отчёт содержит исходники), проверка версии Node в `bin`. *Польза:*
   каждая подсказка работает при копировании и у человека, и у агента.
   *Проверка:* строка `re-check one:` запускается в bash как есть.
7. **Документация, которая калибрует доверие** (S): CI-рецепт для GitHub
   Actions (проверенный workflow — `ux/mootant-workflow.yml`), Troubleshooting,
   раздел «когда вердикту не верить» (CJS под Vitest, монорепо до BUG-508,
   контейнеры без `ps`, что не входит в ключ кэша), совет про `fetch-depth`
   при shallow-клоне. *Польза:* пользователь и агент знают, что перепроверить,
   ещё до исправлений кода. *Риск:* документация отстаёт от кода. *Проверка:*
   workflow зелёный на тестовом PR.
8. **Повторять упавшие тест-файлы dry run с инструментированием, прежде чем
   объявлять `instrumentation-break`** (M). *Проблема:* один нестабильный тест
   без `--fast` даёт `Error` всем мутантам файла, exit 1 и несохранённый кэш
   ([BUG-902](bug-prompts/BUG-902.md)). Невиновные файлы тоже выбрасываются
   ([BUG-100](bug-prompts/BUG-100.md)). *Риск:* лишний прогон упавших файлов,
   но только при провале. *Проверка:* тесты из промптов; фикстура `flakydry`
   проходит с exit 0.
9. **Контракт `--json` для агентов** (M): JSON и при ошибке, различимые коды
   выхода, чистый stdout ([BUG-509](bug-prompts/BUG-509.md)). Компактный
   построчный формат `--format agent` экономит 55–62% токенов против
   `--json`; TOON, наоборот, на 14–20% длиннее (`06-ux-and-agents.md` §6.4).
   *Риск:* смена кодов выхода ломает скрипты, поэтому делать её в 0.x как можно
   раньше. *Проверка:* stdout фикстуры BUG-509 парсится как JSON; на каждый код
   выхода есть тест.
10. **`run.parallelUnits` как opt-in** (M; прототип P1 —
    `experiments/perf-parallel-units.diff`). *Проблема:* п. 9. *Доказательство:*
    path-to-regexp — 92,9 ± 2,5 с → 53,5 ± 1,2 с (×1,74), вердикты совпали
    (342 из 342). Остальные проекты — в §5. *Риск:* тесты, рассчитанные на
    эксклюзивный файл, порт или БД, дают ложные Killed: на стресс-фикстуре 4–6
    расхождений из 13. Поэтому только opt-in, с подсказкой в отчёте, когда
    раунд был одной цепочкой. *Проверка:* `compare-verdicts --strict` — 0
    расхождений на стенде; контрактный тест, что при `false` юниты одного
    файла не перекрываются.

**До 1.0:**
- Публичный API: разделить на стабильный (конфиг, `defineConfig`,
  `Plugin`/`Preset`, минимальный `Mutator`) и экспериментальный (адаптерный
  контракт, `syntax`/`hints`). Отдавать плагинам курируемый `syntax`, а не 40
  внутренних методов. Публиковать только нужные `.d.ts`.
- Контракты: semver-политика «добавление мутатора в `recommended` — major,
  `strict` может меняться в minor», раздел changelog «влияет на score»,
  объявленные `schemaVersion`, схема id и коды выхода.
- Релиз: сборка и публикация в разных джобах, минимум прав, smoke-тест tarball
  на обоих адаптерах.
- Контракт адаптера: версия, проверка результатов (BUG-605), явные
  capabilities, отмена через `AbortSignal`, `adapter-kit`. Rstest — после его
  1.0 (M при целевом контракте), Jest — по спросу (L).
- Цикл агента: частичный dry run только для тест-файлов с изменившимися
  входами (XL) поверх P3.
- Windows и macOS: smoke-джоб или явное «не поддерживается» (гипотезы
  BUG-511, 421, 512).
- Проверка типов у выживших TS-мутантов: 29% мутантов Mootant на его
  собственном строгом коде не проходят `tsc`. Плюс `--format github`/SARIF.
- **Сознательно не делать:** команду `init` (работает без конфига), MCP-сервер
  до появления тёплого процесса, формат TOON, обрезку юнитов до покрывающих
  тестов (прототип P2 дал ложные Survived) и переиспользование воркеров между
  мутантами.

## 7. Что не успел или не смог проверить

**Не смог (ограничения окружения):**
- **Windows и macOS** — машин не было. Всё про них остаётся гипотезами по
  коду: BUG-511 (`stopProcessGroup` на Windows), BUG-421, BUG-512, пути и
  регистр.
- **Тесты внешних проектов под оракулом** — система разрешений запретила
  агенту-оракулу исполнять тесты склонированных репозиториев (defu, scule,
  nanoid, fastify-error). Поэтому оракул работал на фикстурах и на
  `core/text` самого Mootant. Сквозной прогон против физических мутаций на
  чужом коде есть только для ufo (157 из 157) — его делал агент
  инструментирования.
- **Реестр `skills`, api.npmjs.org, arxiv.org, research.google,
  stryker-mutator.io, mootant.org** были закрыты для сессии. BUG-651 поэтому
  воспроизведён частично (отсутствие `SKILL.md` доказано, но ответ реестра —
  нет). Доли аудитории по версиям Vitest не посчитаны. Статьи сверены по
  поисковой выдаче, без полных текстов.
- **BusyBox `ps` (Alpine)** — скачать внешний бинарь не разрешено. Поэтому
  BUG-502 для Alpine — гипотеза; для slim/distroless (без `ps`) подтверждён.

**Не успел (время и эксклюзивное окно замеров):**
- **Догфудинг `core/regex` и `core/run`.** `mootant run core/text` не
  завершился за 42 минуты из-за последовательных хвостов. Вместо этого
  агент раздела 5 прогнал до конца `core/git` и `cli/terminal`: 84,45% → 90,3%
  и 88,7% → 93,7% после новых тестов.
- **Ярусы 4–6 стенда:** обычный кэш после правки без `--incremental`,
  `list` текстом против JSON на проектах, Stryker с `typescript-checker`,
  инкрементальный Stryker, `--no-cache`, command runner для node:test,
  догфудинг на стенде. План и скрипты готовы (`bench/README.md`,
  `bash analysis/bench/run.sh`).
- **Полный I2 (весь тест-сьют против полностью switched-кода) на сьютах
  Mootant и perfectionist** — под нагрузкой не успели. На 4 других проектах
  I2 выполнен.
- **Независимая перепроверка** не проводилась для BUG-510, BUG-820 и
  BUG-850/851. BUG-850 и BUG-851 подтверждены моими собственными прогонами
  `test:unit`, BUG-800 я воспроизвёл сам. У BUG-856 воспроизводящий агент
  остановлен ради окна замеров, а скептик подтвердил факты ручными мутациями.
- **Проверка типов выживших.** Утверждение «29% мутантов Mootant на его
  строгом TS-коде не проходят `tsc`» — статический замер (TS 5.9
  LanguageService), без прогона против `typescript-checker` Stryker.
- **Прогон `strict`-пресета против Stryker** и разбор всех 135 общих выживших
  (оценена только выборка).
- **Шум облака.** Окно замеров эксклюзивное по тяжёлым нагрузкам, но в нём
  работали «бумажные» агенты (чтение и правка текста, CPU около 0). σ у
  hyperfine небольшие (1–6% среднего), но для публичных цифр стоит повторить
  на выделенной машине.

**Сознательно не проверялось:** производительность на Node 20 и 24 (вердикты
на них проверены, скорость — нет) и браузерный режим Vitest (не поддерживается
по документации).
