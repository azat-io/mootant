# BUG-602: процесс юнита, убитый извне, даёт мутанту ложный Killed

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (дубликат crash-части BUG-901). Статус:
> подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено обоими верификаторами на Vitest
> 5.1.0 и node:test (SIGKILL процесса isolated-юнита → `Killed`/`crash`,
> `diagnostics: []`, повтора нет; без убийства — `Survived`); скептик: не
> опроверг, но снизил до low — нужен внешний SIGKILL именно процесса юнита
> посреди юнита, а ложный вердикт не кэшируется и живёт один прогон;
> координатор признал находку дубликатом crash-части BUG-901 (та же ветка
> `crash → Killed`), отдельного исправления она не требует.

## Контекст

В режиме по умолчанию (без `--fast`) каждый покрытый мутант решается на
isolated-пути (`core/run/classify-mutants.ts:55`): юнит — один мутант в одном
тест-файле целиком, в воркере Vitest или в отдельном процессе Node.js
(node:test). Если процесс юнита не дописал end-запись и сторож его не
останавливал, адаптер сообщает `IsolatedFacts.incomplete: 'crash'`
(`adapters/vitest/build-isolated-facts.ts:31-45`,
`adapters/node-test/build-isolated-facts.ts:58-64`). Ядро превращает это в
`Killed` с причиной `crash` без повтора и без диагностики
(`core/run/read-isolated-unit.ts:42-44`). Ветка стоит раньше разбора проб и
`reached` (`:45-63`), поэтому неважно, что пробы, успевшие записаться, прошли
и дошли до мутанта.

Это верно, когда процесс уронил сам мутант. В фикстурах проекта законный
crash — именно `process.kill(process.pid, 'SIGKILL')`
(`test/fixtures/node-test/basic/src/guard.js:3`,
`test/fixtures/runner/test/probe.test.ts:16-21`). Но это ложно, когда процесс
убила инфраструктура: OOM killer, лимит памяти контейнера в CI, внешний
`kill -9`. Такой мутант засчитывается как обнаруженный и завышает score. Сам
mootant ложных crash не создаёт: процессы, которые останавливает сторож,
помечаются как `hang` (`adapters/vitest/run-plan.ts:73-78`,
`adapters/node-test/run-test-process.ts:133-138`). `process.exit()` в
node:test к crash тоже не ведёт: обработчик `exit` дописывает end-запись
(`adapters/node-test/preload/preload.ts:83-88`,
`adapters/node-test/preload/create-try-tracker.ts:277-300`). Что даёт
`process.exit()` под Vitest, не проверено.

Похожие сигналы ядро подтверждает. Таймауты `time-limit` и `hang` ждут повтора
(`core/run/get-unit-evidence.ts:22-28`) с удвоенными границами
(`core/run/plan-isolated.ts:23`). Юнит Vitest, который ни один воркер не
захватил, приходит без фактов (`adapters/vitest/run-isolated.ts:43-45`),
повторяется и при второй пропаже даёт `Error`
(`core/run/apply-isolated-result.ts:93-113`). А смерть процесса после захвата
юнита сразу даёт `Killed`: для crash подтверждения нет.

Насколько это тихо (проверено верификаторами):

- Текстовый отчёт печатает `killed 1` и `score 100%`, предупреждений нет, код
  выхода 0. В `--json --all` у `Killed` нет поля `cause`
  (`cli/report/slim-run-report.ts:75-86`). `"cause":"crash"` видно только в
  `--json --verbose` и в HTML-отчёте
  (`cli/html/client/render-mutant-panel.ts:296-299`).
- Кэш убийства crash не хранит (`core/cache/create-run-cache.ts:143-144`,
  фильтр `:313-320`), поэтому ложный `Killed` живёт один прогон: следующий
  прогон с кэшем даёт `Survived`.
- Сценарий редкий. По замеру скептика главный процесс mootant (~147 МБ)
  крупнее воркеров (~67 МБ). OOM killer обычно выбирает самый крупный
  процесс, и тогда прогон падает громко. Систематическая нехватка памяти
  ломает и dry run. Тихий ложный `Killed` остаётся для кратковременных событий
  и внешнего SIGKILL процесса юнита.

Задумано ли это. Crash как убийство описан в публичном типе
`types/run/try-cause.d.ts:12` («the worker died with the mutant active»).
`TryCause` экспортируется (`core/index.ts:33`) и входит в JSON-отчёт
(`types/report/run-report.d.ts:86`). То же правило записано в JSDoc
`core/run/apply-isolated-result.ts:20-26` и закреплено тестом
`test/core/run/apply-isolated-result.test.ts:54`. Но «with the mutant active»
никто не проверяет. В `readme.md` и `docs/content/**` слово crash не
встречается.

Связь с BUG-901 (другой промпт этого анализа, в клоне его нет). BUG-901: crash
и `load-error` без достижения мутанта засчитываются как `Killed`. Его
crash-часть — та же ветка и то же исправление: подтверждать crash повтором.
Координатор признал BUG-602 дубликатом этой части. BUG-602 добавляет сценарий,
где мутант уже достигнут (`reached: true`, пробы до смерти процесса прошли), и
воспроизведение на node:test. Если crash-часть BUG-901 уже исправлена в
`main`, проверь шагами 1 и 3, что исправление закрывает и этот сценарий, и
добавь на него тест. Иначе сделай исправление, описанное ниже: оно закрывает и
crash-часть BUG-901.

### Шаг 1. Падающий юнит-тест (fake-адаптер, сборка не нужна)

Сценарий: в `/t/c.test.ts` тест `c1` мутанта `m` не достигает, а `c2`
достигает и ничего не проверяет, поэтому обычный прогон оставляет `m` живым.
Без fast-режима (`isolate: true`) `m` идёт на isolated-путь в единственном
покрывающем файле. Первый isolated-прогон портится через `onIsolated`
(`call === 1`): юнит сообщает `incomplete: 'crash'`. В первом `it` записанные
пробы остаются и `reached` равно `true`: так адаптер Vitest описывает воркер,
убитый в более позднем тесте. Во втором `it` проб и `reached` нет: процесс
умер до первого теста. Повторы не портятся. Fake-адаптер —
`test/helpers/create-fake-adapter.ts` (`onIsolated` на `:26-30`, вызов на
`:433-445`, факты юнита на `:504-535`), состояние прогона —
`test/helpers/create-test-run.ts:53-101`. Файл временный, в коммит не входит
(см. «Ограничения»).

```bash
# в корне клона azat-io/mootant
pnpm install
mkdir -p test/repros
cat > test/repros/BUG-602.test.ts <<'EOF'
import { describe, expect, it } from 'vitest'

import type { IsolatedResult } from '../../types/adapter/isolated-result'
import type { MutantState } from '../../types/run/mutant-state'
import type { FakeWorld } from '../helpers/create-fake-adapter'

import { runIsolatedRounds } from '../../core/run/run-isolated-rounds'
import { getFinalStatus } from '../../core/run/get-final-status'
import { createTestRun } from '../helpers/create-test-run'

/**
 * Runs mutant `m` isolated outside fast mode in a test file whose first unit
 * fails as `spoil` says, for a reason that has nothing to do with `m`: `c1`
 * never reaches `m`; `c2` reaches it and checks nothing, so a plain run of the
 * tests lets `m` survive.
 *
 * @param spoil - What the first unit reports instead of its facts.
 * @returns State of `m` after the isolated rounds.
 */
async function runMutant(
  spoil: (
    facts: IsolatedResult['units'][number],
  ) => IsolatedResult['units'][number],
): Promise<MutantState> {
  let world: FakeWorld = {
    onIsolated: (result: IsolatedResult, _plan, call) =>
      call === 1 ? { units: result.units.map(spoil) } : result,
    tests: [
      { file: '/t/c.test.ts', id: 'c1' },
      { file: '/t/c.test.ts', covers: ['m'], id: 'c2' },
    ],
  }
  let { session, state } = await createTestRun(world, {
    mutants: ['m'],
    isolate: true,
  })
  await runIsolatedRounds(session, state)
  return state.mutants.get('m')!
}

describe('BUG-602: a unit process killed from outside kills the mutant', () => {
  it('does not kill a reached mutant whose unit process died once after its tests passed', async () => {
    // The process dies in a later test (the OOM killer, `kill -9`), as Vitest
    // reports it: no end record; the tries written before passed, and `c2`
    // reached the mutant (`reached: true`).
    let mutant = await runMutant(facts => ({ ...facts, incomplete: 'crash' }))

    expect(mutant.verdict?.cause).not.toBe('crash')
    expect(getFinalStatus(mutant)).toBe('Survived')
  })

  it('does not kill a mutant whose unit process died once before any test reached it', async () => {
    // The same death before any try was written: nothing reached.
    let mutant = await runMutant(facts => ({
      ...facts,
      incomplete: 'crash',
      reached: false,
      tests: [],
    }))

    expect(mutant.verdict?.cause).not.toBe('crash')
    expect(getFinalStatus(mutant)).toBe('Survived')
  })
})
EOF
pnpm exec vitest run test/repros/BUG-602.test.ts
# 2 failed, оба на expect(mutant.verdict?.cause).not.toBe('crash'):
#   AssertionError: expected 'crash' not to be 'crash'
```

Второй `it` по логике совпадает с первым тестом репро BUG-901 (отличаются
только название и комментарий): верификаторы BUG-901 видели, как тот падает с
этой ошибкой. Первый `it` (вариант BUG-602)
отличается только тем, что пробы и `reached` сохранены. По чтению кода он
падает так же: ветка `read-isolated-unit.ts:42-44` срабатывает раньше разбора
проб. Запуском он не проверен.

### Шаг 3. Сквозной сценарий (Vitest и node:test)

У мутанта `percent > 100` → `percent >= 100` (`src/price.js:2:7`,
`comparison-operator`) нет убивающего теста: случай `percent === 100` никто не
проверяет. Тест `waits` записывает pid своего процесса в `pids.txt` в корне
фикстуры и убивает себя `SIGKILL`, если он — второй процесс, загрузивший
тест-файл. Первый процесс — dry run, второй — isolated-юнит мутанта. Убийство
не зависит от мутанта и случается после того, как два первых теста прошли и
дошли до мутанта. Для mootant это то же, что SIGKILL извне: сигнал нельзя
перехватить. `cache: false` в конфиге выключает кэш. Фикстура и тест взяты у
воспроизводящего верификатора без изменений, кроме `package.json` (у него в
этом каталоге его не было).

Vitest:

```bash

cd "$FIX/vitest"
cat > package.json <<'EOF'
{ "name": "bug602", "private": true, "type": "module" }
EOF
cat > src/price.js <<'EOF'
export function applyDiscount(price, percent) {
  if (percent > 100) {
    throw new RangeError('percent must be at most 100')
  }
  return price - (price * percent) / 100
}
EOF
cat > test/price.test.js <<'EOF'
import { expect, it } from 'vitest'
import { appendFileSync, existsSync, readFileSync } from 'node:fs'

import { applyDiscount } from '../src/price.js'

it('takes a percent off', () => {
  expect(applyDiscount(200, 25)).toBe(150)
})

it('rejects more than 100 percent', () => {
  expect(() => applyDiscount(10, 101)).toThrow(RangeError)
})

it('waits', async () => {
  // Simulates an external kill of the second process that runs this file
  // (the first is the dry run), whatever mutant is active.
  let log = new URL('../pids.txt', import.meta.url)
  let pids = existsSync(log) ? readFileSync(log, 'utf8').split('\n').filter(Boolean) : []

    appendFileSync(log, process.pid + '\n')
    pids.push(String(process.pid))
  }
  await new Promise(resolve => setTimeout(resolve, 300))
  if (pids.indexOf(String(process.pid)) === 1) {
    process.kill(process.pid, 'SIGKILL')
  }
  await new Promise(resolve => setTimeout(resolve, 300))
})
EOF
```

Внешний SIGKILL вместо самоубийства даёт то же. Скептик убивал процесс юнита
точечно, без `sleep`. У Vitest он брал pid воркера из claim-файла юнита: файл
`claim/<hash>-<index>` в рабочем каталоге прогона `os.tmpdir()/mootant-*`
(`core/run/create-work-directory.ts:27`,
`adapters/vitest/worker/claim-unit.ts:28,37`). У node:test он искал процесс, в
окружении которого `MOOTANT_UNIT` с `"mode":"isolated"`
(`adapters/node-test/run-test-file.ts:48`,
`adapters/node-test/types/node-test-unit.d.ts:17`). Итог 3 из 3 на каждом
адаптере: `Killed`, `cause` `crash`, `diagnostics: []`, `runs.isolated` 1.
Его скрипты в промпт не включены.

Чего не делать. Прежняя версия промпта убивала процесс через `sleep 4` и
`pkill -KILL -f 'vitest/dist/workers/forks'` (для node:test —
`pkill -KILL -f 'test/price.test.js'`). Так нельзя:

- под нагрузкой `sleep 4` попадал в dry run (2 из 2), и итогом были `Error` и
  `instrumentation-break`, а не этот сценарий;
- командные строки dry run и юнита одинаковы (у node:test — один и тот же
  `node --import …/preload.js … test/price.test.js`);
- шаблон `pkill -f` задевает процессы других проектов на машине, а при запуске
  через `bash -c` совпадает с командной строкой самой оболочки и убивает её.

## Ожидаемое поведение

- Смерть процесса юнита (`crash`) сама по себе ничего не решает: юнит
  повторяется один раз, как при подтверждении таймаута. `Killed`/`crash` —
  только если повтор тоже падает. Если повтор дошёл до конца, решают его
  факты: здесь `Survived`.
- Мутант, который роняет процесс сам, по-прежнему убит: при повторе он уронит
  процесс снова. Сквозной тест `test/adapters/node-test/index.test.ts:435`
  (`src/guard.js | condition | true | Killed | crash | -`) остаётся зелёным.
- Шаг 1: оба `it` проходят. Шаг 3 после исправления, на обоих адаптерах:
  `kill.json` — `"status":"Survived"`, в `pids.txt` три pid (dry run, юнит и
  повтор), `control.json` — по-прежнему `Survived`. Это следует из чтения
  кода, запуском не проверено.
- Предупреждение о неподтверждённом crash — на усмотрение (см. «Что работает
  и что нет»); тест-воспроизведение его не проверяет.

## Фактическое поведение

Шаг 1: оба `it` падают (вывод выше). Мутант получает `Killed`/`crash` с первой
попытки, повтора нет.

Шаг 3 (у воспроизводящего верификатора по 2 из 2 на каждом адаптере, Vitest
5.1.0). В `control.json` — `"status":"Survived"` и `"diagnostics":[]`.
`kill.json` у Vitest (у node:test то же, кроме `"runner":"node-test"` и

### Что работает и что нет

Работает: подтверждение в `getUnitEvidence`. Вердикт `crash` при
`!request.confirming` → `'confirming'`, как у `hang`
(`core/run/get-unit-evidence.ts:22-28`). Дальше всё уже есть:

- `applyIsolatedResult` ставит запрос с `confirming: true`
  (`core/run/apply-isolated-result.ts:86-88`);
- повтор получает удвоенные границы (`plan-isolated.ts:23`): для crash они не
  нужны, но и не мешают;
- `previewIsolatedUnit` ведёт себя так же, потому что зовёт ту же функцию;
- первая попытка в кэш не попадёт. `applyIsolatedResult` отдаёт вердикт в кэш
  до `getUnitEvidence` (`:77-82`), но `crash` кэш отбрасывает
  (`core/cache/create-run-cache.ts:313-320`), а у упавшего юнита Vitest нет
  `inputs`: их получают только юниты с end-записью
  (`adapters/vitest/run-isolated.ts:48-58`);
- граница раундов сохраняется: подтверждение одно, как у таймаута. Обнови
  только текст JSDoc `core/run/run-isolated-rounds.ts:21-27`.

Верификатор BUG-901 проверил такую правку вместе с правкой `load-error`: тест
без `reached` (второй `it` шага 1) проходит. Из существующих тестов к crash
относится одно падение — `test/core/run/apply-isolated-result.test.ts:54`.
Второе, `test/core/run/run-isolated-rounds.test.ts:10`, вызвано правкой
`load-error`: в `run-isolated-rounds.test.ts` crash нет. Вариант с
`reached: true` (первый `it`) по чтению проходит так же, запуском не проверен.

Не работает:

- Проверка `facts.reached`, как у hook-error (`read-isolated-unit.ts:84`). В
  этом сценарии мутант достигнут (`reached: true`), и проверка ничего не
  изменит. К тому же у Vitest `reached` собирается только из записанных проб
  (`adapters/vitest/build-isolated-facts.ts:37`), а тест, во время которого
  умер процесс, не записан.
- Решение по сигналу или коду выхода. В прежней версии промпта был пункт:
  SIGKILL/SIGTERM не от сторожа сразу считать сбоем инфраструктуры. Но
  законный crash в фикстурах проекта — именно SIGKILL: `guard.js:3` ожидает
  `Killed | crash` в `test/adapters/node-test/index.test.ts:435`, а
  `probe.test.ts:16-21` ожидает `[0, 'crash', false, [false]]` в тесте
  адаптера `test/adapters/vitest/index.test.ts:596` (строка `:773`). Мутант,
  раздувший память, получит SIGKILL от того же OOM killer. По сигналу причину
  не отличить: он годится только для текста предупреждения.
- Вернуть `null` из `readIsolatedUnit` для crash. `null` становится `'none'`
  (`get-unit-evidence.ts:19-21`), и файл считается пройденным без улик
  (`core/run/decide-evidence.ts:23-25`). Законный crash (`guard.js`) потеряет
  убийство. Мутант без других улик станет `NoCoverage`: `survived` от
  crash-юнита не ставится (`core/run/get-final-status.ts:36`). Это по чтению
  кода. Для аналогичной правки `load-error` верификатор BUG-901 видел
  `expected 'NoCoverage' to be 'Survived'`.
- Правка только в `applyIsolatedResult`. Тогда `previewIsolatedUnit`
  (`core/run/preview-isolated-unit.ts:28-38`) продолжит считать crash
  убийством в живых счётчиках.

Вердикт при повторной смерти — `Killed`/`crash`, а не `Error`. Так описан
`TryCause` (`types/run/try-cause.d.ts:12`), так ждёт
`test/adapters/node-test/index.test.ts:435`, и так предлагает BUG-901. Для
сравнения (довод скептика): PIT считает падение minion обнаружением, StrykerJS
после двух повторов ставит `Error`, который в score не входит.

Предупреждение — необязательно. Код `worker-crash` уже есть
(`types/mutant/diagnostic.d.ts:29`; batch-путь —
`core/run/run-batch-phases.ts:126-137`). Предупреждение на каждую смерть
процесса сломает `test/adapters/node-test/index.test.ts:360-362`: там все
диагностики должны быть `worker-hang`, а в том же прогоне есть законный crash
`guard.js`. К тому же такое предупреждение будет шуметь на законных crash.
Если добавляешь предупреждение, давай его для crash, который повтор не
подтвердил. Для этого ядру нужно знать, что подтверждался именно crash, а
`IsolatedRequest.confirming` — булево поле с описанием «confirms a timeout»
(`types/run/run-state.d.ts:84-87`). По наблюдению верификатора, в Vitest 5.1
`ForksPoolWorker.on` передаёт подписку `ChildProcess`, так что `(code,
signal)` доступны; в этом репозитории не проверено. Новое поле в
`IsolatedFacts` — только необязательное: тип экспортируется для сторонних
адаптеров (`core/index.ts:1-4`).

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.

- Сообщения коммитов — Conventional Commits (commitlint).
- Тест из шага 1 нельзя копировать в `test/repros/` как есть. Этот каталог не
