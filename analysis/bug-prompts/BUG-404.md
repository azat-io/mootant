# BUG-404: кэш молча выключается из-за `mtime` не раньше старта прогона

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (заявлялась medium, понижена по итогам
> перепроверки). Статус: подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (в тесте шага 1 падают оба `it`: 3
> из 3 прогонов у верификатора, 2 из 2 у скептика; упакованный CLI с Vitest
> 5.1.0 при `mtime` +2 ч у `vitest.config.ts` или у `src/math.ts` даёт
> `totalCached: null` и `diagnostics: []` в обоих прогонах, а контроль без
> будущего `mtime` берёт из кэша 3 из 3); скептик: не опроверг, но понизил до
> low — вердикты не страдают (mootant просто гоняет мутантов заново), теряются
> время и объяснение, триггеры редкие; ценное в находке — `null` из
> `prepareRunCache` ничем не объясняется, а `DryFile.modified` для файлов
> окружения не учитывается.

## Контекст

Кэш вердиктов считает файл изменённым во время прогона, если его
`mtimeMs >= start` (`core/cache/find-changed-files.ts:20-33`, сравнение на
`:27`; `start` — `Date.now()` в начале `runMutants`,
`core/run-mutants.ts:172`). Так mootant не сохраняет вердикт, полученный на
старом тексте файла. Само правило задумано. Оно описано в JSDoc
(`core/cache/find-changed-files.ts:11-19`,
`core/cache/prepare-run-cache.ts:99-110`), а unit-тест проверяет, что конфиг с
будущим `mtime` выключает кэш
(`test/core/cache/prepare-run-cache.test.ts:281-285`).

`prepareRunCache` вызывается после dry run и применяет правило без сравнения
содержимого. Файлы окружения собираются на
`core/cache/prepare-run-cache.ts:121-128`:

- файлы адаптера. У Vitest это конфиги с их импортами, `.env`-файлы режима,
  globalSetup с модулями, которые главный процесс вычислил для него, и test
  environment, заданный путём
  (`adapters/vitest/get-cache-inputs.ts:47,128-162`). У node:test —
  `package.json`, `node.config.json`, файлы флагов `--env-file` и подобных,
  setup-файлы флагов и `tsconfig.json` при tsx
  (`adapters/node-test/get-node-cache-inputs.ts:20-29,51-62`);
- lockfile, `package.json`, `.env*`, `tsconfig*.json` и `jsconfig*.json` в
  корне.

Если «изменился» хоть один из них, функция возвращает `null` (`:139-141`).
Тест-файл, зависящий от такого файла, не получает ключа (`:171-175`). Если
ключа нет ни у одного тест-файла, функция тоже возвращает `null` (`:184-186`).
На `:184-186` `null` бывает и по другой причине: адаптер не сообщил
зависимостей ни одного тест-файла (`core/cache/get-test-file-keys.ts:41-44`).

При `null` `runMutants` работает без кэша (`core/run-mutants.ts:442-459`), не
вызывает `saveRunCache` (`:515`) и ставит `RunResult.cache: false` (`:552`).
Диагностики нет. Отчёты показывают только сам факт:

- `--json --verbose`: `summary.totalCached: null`
  (`cli/report/build-run-report.ts:161-164`). По типу это значит «кэш
  выключен» (`types/report/run-report.d.ts:130-133`). Обычный `--json` поля
  `totalCached` не печатает (`cli/report/slim-run-report.ts:27-51`);
- HTML: «cache: off» (`cli/html/client/render-overview.ts:94`);
- текстовый отчёт молчит. «N cached» печатается только при `totalCached > 0`
  (`cli/report/format-run-text-report.ts:196-199`), а строки «Reused cached
  verdicts …» (`core/run-mutants.ts:703-711`) просто нет.

Причину не видно нигде. Документация при этом обещает переиспользование по
содержимому: «reused while the mutated file and the files and environment
variables its tests read stay the same»
(`docs/content/guide/configuration.mdx:350-355`). JSDoc `RunResult.cache`
перечисляет для `false` только `--no-cache`, `run.cache: false` и адаптер без
поддержки кэша (`types/run/run-result.d.ts:92-96`).

Когда это срабатывает без настоящей правки:

- Часы файловой системы впереди часов процесса: WSL2 с проектом на `/mnt/c`,
  NFS/SMB, общие папки VM, архив с «будущими» датами. Кэш выключен не навсегда,
  а пока часы процесса не догонят `mtime`. У скептика при перекосе +4 с
  потерян один прогон, следующий сохранил кэш, третий взял из кэша 3 из 3.
  Кэш-файл не создаётся вовсе, только когда будущий `mtime` у файла окружения
  или ключа не остаётся ни у одного тест-файла. В проекте из двух пар
  «источник — тест» с будущим `mtime` у одного источника скептик получил из
  кэша 5 из 9 вердиктов, кэш-файл создан.
- Тест во время dry run перезаписывает файл окружения тем же содержимым,
  например `package.json` в тестах инструментов, которые правят и
  восстанавливают его.

Скептик считает оба триггера редкими. Например, при часах, синхронизированных
по NTP, перекос измеряется миллисекундами.

`saveRunCache` в похожей ситуации сравнивает содержимое. Файл с
`mtime >= start`, у которого есть хэш, считается изменённым, только если хэш
теперь другой (`core/cache/save-run-cache.ts:70-86`). Настоящая правка файла
окружения даёт предупреждение `cache-skipped` с путём через `getDisplayPath`
(`:87-93`). JSDoc обещает, что тесты, которые записывают обратно прочитанное,
сохраняют свои вердикты (`:17-21`). Публичный контракт `DryFile.modified`
говорит то же: `mtime` таких файлов ничего не значит, кэш сравнивает их
содержимое (`types/adapter/dry-file.d.ts:34-41`).

Перезаписанный тестом `package.json` в `DryFile.modified` попадает.
`trackInputs` относит туда файлы, которые код сначала прочитал, а потом
записал (`adapters/shared/track-inputs.ts:29-44,53`). Но `prepareRunCache`
проверяет файлы окружения на `:139`, раньше, чем исключает `modified` на
`:142-144`. Контроли скептика показывают разрыв:

- перезапись `package.json` тем же содержимым только под мутантом, то есть
  после `prepareRunCache`, кэш сохраняет;
- настоящая правка `package.json` под мутантом даёт `cache-skipped`;
- та же настоящая правка в dry run даёт `cache: false` без единой диагностики.

Сравнить содержимое в `prepareRunCache` сейчас не с чем. Хэши считаются после
dry run (`prepare-run-cache.ts:146-151`), и `saveRunCache` сравнивает именно с
ними. Для файла с будущим `mtime` нужен хэш, снятый до dry run. Это смена
дизайна, а не правка одной строки (см. «Подозреваемые места в коде»).

Собственные интеграционные тесты ждут 5 мс после записи фикстуры
(`test/adapters/vitest/index.test.ts:359-360`). `Date.now()` — целое число, а
`mtimeMs` дробный, и без паузы файл, записанный в миллисекунду старта,
считается изменённым. Это деталь тестов, а не пользовательский сценарий.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создайте
сами. Нужны:

- Node.js 22.12 или новее (этого требует Vitest 5,
  `docs/content/guide/compatibility.mdx:22-24`);
- pnpm 12. В CI стоит `latest-12`
  (`.github/actions/install-tools/action.yml:14`). pnpm 10 не читает
  `configDependencies` из `pnpm-workspace.yaml`. По наблюдению анализа, даже
  `pnpm --version` внутри репозитория у него зависает.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Тест создаёт во временном каталоге проект на Vitest. `node_modules/vitest` в
нём — ссылка на Vitest репозитория. Тест дважды гоняет `runMutants` из
исходников по `src` с включённым кэшем:

- первый `it` сдвигает `mtime` у `vitest.config.ts` на 2 часа вперёд. Второй
  прогон должен либо взять вердикты из кэша, либо объяснить отказ диагностикой
  `cache-skipped`;
- во втором `it` тест проекта перезаписывает `package.json` тем же
  содержимым. Второй прогон должен взять вердикты из кэша.

Файл временный и в коммит не входит (см. «Ограничения»). Именно этот код оба
верификатора запускали дословно.

```bash
# в корне клона azat-io/mootant (коммит 170ec52)
pnpm install --frozen-lockfile
mkdir -p test/repros            # на 170ec52 этого каталога нет
cat > test/repros/BUG-404.test.ts <<'EOF'
import { writeFile, realpath, mkdtemp, symlink, utimes, mkdir, rm } from 'node:fs/promises'
import { afterEach, expect, it } from 'vitest'
import { setTimeout } from 'node:timers/promises'
import { tmpdir } from 'node:os'
import path from 'node:path'

import type { RunResult } from '../../types/run/run-result'

import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

let roots: string[] = []

async function createProject(files: Record<string, string>): Promise<string> {
  let root = await realpath(await mkdtemp(path.join(tmpdir(), 'mootant-bug-')))
  roots.push(root)
  await mkdir(path.join(root, 'node_modules'))
  await symlink(
    await realpath(path.resolve(import.meta.dirname, '../../node_modules/vitest')),
    path.join(root, 'node_modules/vitest'),
  )
  for (let [file, text] of Object.entries({ 'package.json': '{ "type": "module" }', ...files })) {
    await mkdir(path.dirname(path.join(root, file)), { recursive: true })
    await writeFile(path.join(root, file), text)
  }
  await setTimeout(5)
  return root
}

function run(root: string): Promise<RunResult> {
  return runMutants({
    builtIns: createBuiltIns('vitest', vitestAdapter()),
    paths: ['src'],
    concurrency: 1,
    cwd: root,
  })
}

let files = {
  'vitest.config.ts': "export default { test: { include: ['test/**/*.test.ts'] } }\n",
  'src/math.ts': 'export function isAdult(age: number): boolean {\n  return age >= 18\n}\n',
  'test/math.test.ts': [
    "import { expect, it } from 'vitest'",
    "import { isAdult } from '../src/math'",
    "it('isAdult', () => {",
    '  expect(isAdult(30)).toBe(true)',
    '  expect(isAdult(5)).toBe(false)',
    '})',
  ].join('\n'),
}

afterEach(async () => {
  await Promise.all(roots.splice(0).map(root => rm(root, { recursive: true, force: true })))
})

it('reuses verdicts, or says why not, when the configuration has a future modification time', async () => {
  let root = await createProject(files)
  let future = new Date(Date.now() + 2 * 60 * 60 * 1000)
  await utimes(path.join(root, 'vitest.config.ts'), future, future)
  await run(root)

  let second = await run(root)

  let reused = second.results.some(entry => entry.cached)
  let explained = second.diagnostics.some(entry => entry.code === 'cache-skipped')
  expect(reused || explained).toBe(true)
}, 120_000)

it('reuses verdicts when a test writes package.json back unchanged', async () => {
  let root = await createProject({
    ...files,
    'test/math.test.ts': [
      "import { readFileSync, writeFileSync } from 'node:fs'",
      "import { expect, it } from 'vitest'",
      "import { isAdult } from '../src/math'",
      "it('isAdult', () => {",
      "  let file = new URL('../package.json', import.meta.url)",
      '  writeFileSync(file, readFileSync(file))',
      '  expect(isAdult(30)).toBe(true)',
      '  expect(isAdult(5)).toBe(false)',
      '})',
    ].join('\n'),
  })
  await run(root)

  let second = await run(root)

  expect(second.cache).toBe(true)
  expect(second.results.some(entry => entry.cached)).toBe(true)
}, 120_000)
EOF

pnpm vitest run test/repros/BUG-404.test.ts --coverage.enabled=false
```

В ветке анализа есть вариант этого теста на общем помощнике
`BUG-400-cache-project.ts`: конфиг через `defineConfig`, проверка через объект.
Падает он по той же причине. Код выше самодостаточен, помощник не нужен.

### Шаг 2. CLI на упакованном mootant

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому для CLI нужна
сборка. Vitest ставьте как `vitest@5` (сейчас это 5.1.0), а не `vitest@5.0.5`:
в npm 10.9.9 установка 5.0.5 падает с `Cannot read properties of null (reading
'edgesOut')`. Это баг arborist, не mootant. Флаг `--no-install` не даёт npx
пойти в реестр, если локальной установки нет.

Сценарии те же, что у верификатора: контроль, `mtime` +2 ч у `vitest.config.ts`
и `mtime` +2 ч у `src/math.ts` (зависимость единственного тест-файла). Каждый
сценарий начинается со свежих файлов и пустого кэша. Команды рассчитаны на одну
сессию shell. Скрипт собран по сценарию верификатора и в таком виде целиком не
запускался. Значения в «Фактическом поведении» взяты из отчёта верификатора на
том же проекте.

```bash
# в корне клона, после шага 1
CLONE="$PWD"
pnpm build
pnpm pack                        # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"    # *.tgz нет в .gitignore, не оставляйте его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"

APP="$(mktemp -d)"
cd "$APP"
echo '{ "name": "bug-404", "private": true, "type": "module" }' > package.json
npm i -D vitest@5 "$TGZ"

# Свежие файлы проекта (mtime — сейчас) и пустой кэш
fresh_project() {
  rm -rf node_modules/.cache/mootant
  mkdir -p src test
  printf "export default { test: { include: ['test/**/*.test.ts'] } }\n" > vitest.config.ts
  printf 'export function isAdult(age: number): boolean {\n  return age >= 18\n}\n' > src/math.ts
  cat > test/math.test.ts <<'EOF'
import { expect, it } from 'vitest'
import { isAdult } from '../src/math'
it('isAdult', () => {
  expect(isAdult(30)).toBe(true)
  expect(isAdult(5)).toBe(false)
})
EOF
  sleep 1
}
# run_mootant <метка>: полный JSON-отчёт в <метка>.json, stderr в <метка>.err
run_mootant() {
  npx --no-install mootant run src --json --verbose > "$1.json" 2> "$1.err"
}

fresh_project
run_mootant control-1
run_mootant control-2

fresh_project
touch -d '+2 hours' vitest.config.ts
run_mootant future-config-1
run_mootant future-config-2

fresh_project
touch -d '+2 hours' src/math.ts
run_mootant future-dependency-1
run_mootant future-dependency-2

node -e '
  const fs = require("node:fs")
  for (const file of process.argv.slice(1)) {
    const text = fs.readFileSync(file, "utf8")
    const report = JSON.parse(text.slice(text.indexOf("{")))
    const diagnostics = report.diagnostics.map(d => d.code + ": " + d.message)
    console.log(file, "totalCached=" + report.summary.totalCached,
      "diagnostics=" + JSON.stringify(diagnostics))
  }' control-1.json control-2.json future-config-1.json future-config-2.json \
  future-dependency-1.json future-dependency-2.json
grep -H . ./*.err                # «Reused cached verdicts …» есть только в control-2.err
ls node_modules/.cache/mootant   # после future-dependency-*: каталога нет
cd "$CLONE"
```

`touch -d '+2 hours'` — синтаксис GNU coreutils. На macOS поставьте `mtime`
иначе, например
`node -e 'const t = new Date(Date.now() + 7200000); require("node:fs").utimesSync(process.argv[1], t, t)' vitest.config.ts`
(тест шага 1 делает то же через `utimes`).

## Ожидаемое поведение

- Тест, который во время dry run перезаписал файл окружения тем же
  содержимым, кэш не выключает. Как и для зависимостей из `DryFile.modified`,
  содержимое сверяет `saveRunCache`, и второй прогон берёт вердикты из кэша.
- Если mootant всё-таки отказывается от кэша из-за `mtime` не раньше старта
  (файл окружения или зависимость, из-за которой ключа не осталось ни у одного
  тест-файла), результат говорит почему: предупреждение `cache-skipped` с
  путём файла, как в `saveRunCache`. В текстовом режиме CLI печатает его в
  stderr (`cli/run-mutation.ts:60-62`), в `--json` оно попадает в
  `diagnostics`.
- Настоящая правка файла окружения или зависимости во время прогона
  по-прежнему не даёт переиспользовать и сохранить вердикты, теперь с
  объяснением.
- По желанию, это смена дизайна (см. «Подозреваемые места в коде»): файл с
  будущим `mtime` и прежним содержимым кэш не выключает.

## Фактическое поведение

Шаг 1 (у верификатора 3 из 3 прогонов в клоне 170ec52, у скептика 2 из 2).
Оба теста падают с `AssertionError: expected false to be true`: первый на
`expect(reused || explained)` (строка 67 файла), второй на
`expect(second.cache)` (строка 89). Во втором прогоне первого теста
`cache: false`, ни одного вердикта из кэша, `diagnostics: []`.

Отладка верификатора:

- в первом тесте `findChangedFiles` возвращает `vitest.config.ts`: его `mtime`
  на 7 200 000 мс позже старта;
- во втором — `package.json`, записанный примерно через 400 мс после старта.
  Содержимое прежнее (`{ "type": "module" }`), `DryFile.modified` содержит
  `package.json`;
- если внутри `prepareRunCache` заменить результат `findChangedFiles` пустым
  множеством, оба теста проходят;
- если перенести цикл `:142-144` перед проверкой на `:139`, второй тест
  проходит, первый по-прежнему падает (правка откачена).

Шаг 2 (верификатор: упакованный mootant с 170ec52, Vitest 5.1.0 из npm):

| Сценарий | `totalCached`, прогон 1 | `totalCached`, прогон 2 | `diagnostics` | stderr прогона 2 |
| --- | --- | --- | --- | --- |
| `control` | 0 | 3 | `[]` | `Reused cached verdicts for 3 of 3 mutants.` |
| `future-config` | `null` | `null` | `[]` | только строки прогресса: dry run и `testing 3 mutants  3/3 test runs` |
| `future-dependency` | `null` | `null` | `[]` | то же |

В сценариях с будущим `mtime` кэш-файла
`node_modules/.cache/mootant/run-v3.json` нет после обоих прогонов, текстовый
отчёт о кэше молчит. Скептик получил то же на своём упакованном mootant:
`totalCached: null`, `diagnostics: []`, в `report.html` встроено
`"cache":false`.

Контроли скептика на исходниках (`runMutants` с адаптером Vitest, проект как в

## Подозреваемые места в коде

- `core/cache/prepare-run-cache.ts:137-144` — порядок проверок, главное место
  для сценария 2. `modified` собирается на `:137`, но файлы окружения
  проверяются на `:139-141`, раньше, чем `modified` исключаются из `changed` на

  - После переноса такой файл хэшируется в состоянии после dry run, как сейчас
    зависимости из `modified` (JSDoc `:102-105`). `saveRunCache` сверит его
    содержимое в конце прогона и при настоящей правке даст `cache-skipped`

    зависимость `a.test.ts`, а конфиг с будущим `mtime` в `modified` не входит.

    трогает, вердикты этого прогона сохранятся под новым содержимым. Для
    зависимостей из `modified` проект такой компромисс уже принял. Для файлов
    окружения реши явно и опиши в JSDoc.
- `core/cache/prepare-run-cache.ts:139-141`, `:184-186` и
  `core/run-mutants.ts:442-459` — `null` без причины, главное место для
  сценария 1. Нужна причина, которую `runMutants` превратит в предупреждение
  `cache-skipped` с путём файла через `getDisplayPath`
  (`core/run/get-display-path.ts:11-13`), как на `save-run-cache.ts:87-92`.
  Добавить предупреждение в `diagnostics` можно так же, как `runMutants` уже
  добавляет результат `saveRunCache` (`core/run-mutants.ts:515-530`).
  `prepareRunCache` из `core/index.ts` не экспортируется, так что форму его
  результата можно поменять: например, `{ cache, reason }` или готовая
  диагностика. Тогда поправь тесты, которые ждут `null`
  (`test/core/cache/prepare-run-cache.test.ts:240-247,283-285`). Различай
  причины `null`:
  - нет `cacheInputs` (`:116-118`). Это задокументированный случай «адаптер
    без поддержки кэша» (`types/run/run-result.d.ts:92-96`), предупреждения не
    нужно (`test/core/run-mutants.test.ts:1069-1074`);
  - файл окружения с `mtime >= start` (`:139-141`) — предупреждение с этим
    файлом;
  - ключа нет ни у одного тест-файла (`:184-186`). Если ключи потеряны из-за
    зависимостей с `mtime >= start` (`:171-175`), нужно предупреждение с таким
    файлом. Если адаптер не сообщил зависимостей
    (`core/cache/get-test-file-keys.ts:41-44`), дело не в `mtime`, реши
    отдельно.

  Если ключ потеряли не все тест-файлы, кэш работает для остальных.
  `saveRunCache` в похожем случае тоже молча забывает тест-файл
  (`save-run-cache.ts:94-98`), так что здесь предупреждение не обязательно.
- `core/cache/find-changed-files.ts:20-33` и `prepare-run-cache.ts:171-175` —
  сравнение по содержимому для файлов с будущим `mtime`. Оно нужно только для
  ветки «переиспользовать» в сценарии 1 и делается по желанию.
  - Эвристика «`mtime` позже текущего момента — значит, не правка во время
    прогона» не годится. Если часы ФС впереди часов процесса, правка во время
    прогона тоже даёт будущий `mtime`. А тесты проекта моделируют настоящую
    правку именно будущим `mtime` при прежнем содержимом
    (`test/core/cache/prepare-run-cache.test.ts:253-256,281-285`,
    `test/core/cache/save-run-cache.test.ts:169-170,179-180,208-209`).
  - Отличить перекос часов от правки можно только по содержимому, а для этого
    нужен хэш, снятый до dry run. Сейчас хэши считаются после него
    (`prepare-run-cache.ts:146-151`). Это смена дизайна: снять хэши в
    `runMutants` до `runDryPhase` (`core/run-mutants.ts:410-420`) и передать
    их новым входом в `prepareRunCache`.
  - `AdapterSession.cacheInputs()` по контракту вызывается один раз после
    последнего dry run (`types/adapter/adapter-session.d.ts:35-40`). Тип
    публичный (`core/index.ts:15`). У node:test список файлов готов уже при
    старте сессии (`adapters/node-test/start-node-test-session.ts:154-162`).
    У Vitest он собирается в `cacheInputs()` и включает модули, которые главный
    процесс вычислил для globalSetup
    (`adapters/vitest/get-cache-inputs.ts:147-158`). Доступен ли он целиком до
    dry run, не проверялось. Файлы корня (`prepare-run-cache.ts:121-128`)
    известны и без адаптера.
  - Если делаешь это, перепиши `:249` и `:281-285` в
    `test/core/cache/prepare-run-cache.test.ts` на настоящую смену содержимого
    после раннего хэша.
- Документация и JSDoc. В `prepare-run-cache.ts:91-111` опиши порядок,
  `modified` для файлов окружения и причины `null`. В
  `types/run/run-result.d.ts:92-96` добавь ещё один случай `cache: false`,
  теперь с предупреждением. Проверь `types/report/run-report.d.ts:130-133`. По
  желанию допиши в `docs/content/guide/configuration.mdx:350-359`, что файл с
  `mtime` не раньше старта прогона выключает кэш на этот прогон и mootant об
  этом предупреждает.

## Критерий готовности

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  `prepareRunCache` внутренний, в `core/index.ts` он не экспортируется. Публичны
  `AdapterSession` и `DryFile` (`core/index.ts:15,30`), а через
  `AdapterSession.diagnostics` (`types/adapter/adapter-session.d.ts:46`) — и
  `Diagnostic`. Не меняй момент вызова `AdapterSession.cacheInputs()` (контракт
  «once after the last dry run», `types/adapter/adapter-session.d.ts:35-40`)
  без описанного компромисса.
- Сообщения коммитов — Conventional Commits (commitlint).
- Код диагностики — существующий `cache-skipped` с `severity: 'warning'`, новый
  код не вводи. `Diagnostic.code` — закрытое объединение
  (`types/mutant/diagnostic.d.ts:10-33`). Новый код меняет `types/` и
  JSON-отчёт, а тест шага 1 принимает только `cache-skipped`. Сообщение
  называет файл через `getDisplayPath`, как `save-run-cache.ts:89-92`, и
  говорит, что вердикты не переиспользованы и не сохранены. Например: «Verdicts
  were neither reused nor cached because vitest.config.ts was modified at or
  after the start of the run.» Это пример, а не требование.
- Правило «`mtime >= start` значит правка во время прогона» задумано (JSDoc
  `find-changed-files.ts:11-19`, `prepare-run-cache.ts:99-110`). Не ослабляй
  его без сравнения содержимого. Настоящая правка во время прогона по-прежнему
  не должна давать сохранить или переиспользовать вердикт.
- Тест шага 1 нельзя копировать в `test/repros/` как есть. На нём ESLint даёт 10
  ошибок (`unicorn/filename-case` для `BUG-404.test.ts`, `perfectionist`,
  `no-await-in-loop`, `vitest/require-top-level-describe`), есть и замечания
  prettier. Каталог `test/repros/` не исключён ни из ESLint, ни из knip, cspell

  `knip.config.ts:5`, `cspell.config.ts:44`, `vitest.config.ts:18`,
