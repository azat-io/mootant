# BUG-800: плагинный мутатор со своим правилом пропуска роняет `list --skipped` и `run --html`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён (воспроизведён
> координатором на чистой установке tarball 170ec52 независимо от нашедшего
> агента). Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено координатором для `list` (`list src`
> — exit 0, `list src --skipped` — `Error: Cannot read properties of undefined
> (reading 'heuristic')`, exit 1), путь `run --html` выведен из кода и запуском
> не проверялся; скептик: не привлекался — баг не входил в Workflow
> перепроверки `verify-mootant-bugs`, итогового решения координатора по
> серьёзности нет, поэтому оставлена заявленная medium.

## Контекст

Плагины Mootant устроены как правила ESLint: мутатор возвращает замены, и
замена может нести `skip: { rule, reason }`. Такая замена не становится
мутантом, а `mootant list --skipped` показывает её с причиной
(`types/mutator/replacement.d.ts:25-30`). Поле `skip.rule` имеет тип
`SkipRuleId = keyof typeof skipRules` (`types/mutant/skip-note.d.ts:26`,
`types/mutant/skip-rule-id.d.ts:1,7`), то есть закрытое множество из 95
встроенных правил (реестр `core/skips/skip-rules.ts:9`). По имени тип не
экспортируется, но достижим из публичного `Replacement` (`core/index.ts:25`),
поэтому он — часть плагинного API.

Плагин на JavaScript (или на TypeScript с приведением типа) может передать
своё имя правила, и ядро его нигде не проверяет:

- `addReplacement` отдаёт замену с `skip` в `skip()` и возвращается раньше
  проверки цели `validateReplacement`
  (`core/generate/collect-candidates.ts:278-285`; проверка — `:286-304`).
  `skip()` копирует `note.rule` как есть (`:228`), и только если пропущенные
  кандидаты запрошены (`:212-233`, условие `input.skipped` — `:217`).
- Без `--skipped` такая замена просто исчезает. Для пропуска это задуманное
  поведение (`types/mutator/replacement.d.ts:25-29`), но о неизвестном правиле
  автор плагина не узнаёт.
- С `--skipped` кандидат доходит до `listSkipped`
  (`core/generate/generate-file-mutants.ts:318-389`), и строки `:376-377`
  читают `skipRules[candidate.rule].heuristic`. Для неизвестного правила
  `skipRules[candidate.rule]` — `undefined`, отсюда `TypeError`. CLI
  перехватывает его (`cli/run-list.ts:41-45`) и печатает
  `Error: Cannot read properties of undefined (reading 'heuristic')` с exit 1,
  не называя ни плагин, ни мутатор, ни правило, ни файл. По коду так же и с
  `--json`: исключение возникает до форматирования отчёта.

Пропущенных кандидатов перечисляет и `mootant run` с HTML-отчётом:
`skipped: html !== null` (`core/run-mutants.ts:198`), а `html` включают и флаг
`--html`, и `run.html` в конфиге (`core/run/get-html-path.ts:24-37`,
`types/config/run-config.d.ts:28-33`). Перечисление
(`core/run-mutants.ts:192-201`) идёт раньше выбора тестового раннера (`:229`).
Значит, по коду `run --html` падает тем же сообщением
(`cli/run-mutation.ts:83-94`) ещё до запуска тестов, а проект с `run.html` в
конфиге падает на каждом `mootant run`. Запуском это не проверялось.

TypeScript-плагин без приведения типа такую ошибку не совершит, но тогда он
вообще не может описать свой пропуск: только чужим встроенным `rule`, с чужими
категорией и флагом `heuristic`.

## Ожидаемое поведение

Один из двух вариантов, на выбор мейнтейнера. Архитектурный разбор
рекомендует сначала дешёвый вариант 2, а вариант 1 — как расширение API до
1.0.

1. Ядро принимает собственные правила пропуска плагинов. Например,
   `Plugin.skipRules?: Record<string, SkipRule>` с неймспейсом плагина
   (`acme/my-rule`), как у мутаторов и пресетов, и
   ``SkipRuleId = BuiltInSkipRuleId | `${string}/${string}` ``.
   `list --skipped` и HTML-отчёт показывают такой пропуск с его `heuristic` и
   `category` из закрытого множества `SkipCategory`
   (`types/mutant/skip-category.d.ts:9-16`). Незарегистрированное правило
   обрабатывается как в варианте 2.
2. Ядро проверяет `skip.rule` при получении замены: в `addReplacement`,
   независимо от `--skipped`, чтобы `list` и `list --skipped` давали одинаковые
   диагностики. Вместо `TypeError` выдаётся понятная диагностика
   `mutator-error` с id мутатора и именем правила. Так ядро уже поступает с
   невалидной целью замены (`core/generate/collect-candidates.ts:291-302`:
   `createMutatorError` с текстом `Mutator "<id>" …`). Учти: диагностика
   уровня `error` даёт exit 1 и у `list` (`cli/run-list.ts:38-40`), и у `run`
   (`cli/report/build-run-report.ts:151-152`). Невалидные цели уже ведут себя
   так. Если это слишком жёстко для замены, которая и так не стала бы мутантом,
   выбери уровень `warning` и обоснуй.

В обоих вариантах для правила из реестра ничего не меняется: пропущенная
замена не становится мутантом, а мутанты и их id не зависят от `--skipped`
(инвариант из JSDoc `generateFileMutants`,
`core/generate/generate-file-mutants.ts:221-224`).

## Фактическое поведение

```
$ npx mootant list src; echo "exit=$?"
… мутанты встроенных мутаторов; в сводке строка «mutants N in 1 file» …
exit=0                     # замены плагина нет ни среди мутантов, ни в диагностике
$ npx mootant list src --skipped; echo "exit=$?"
Error: Cannot read properties of undefined (reading 'heuristic')
exit=1
```

Число мутантов N в первой команде не зафиксировано; для бага оно неважно.
По коду так же падают `list src --skipped --json`, `run src --html` и
`run src` при `run.html` в конфиге. Запуском это не проверялось.

## Подозреваемые места в коде

- `core/generate/generate-file-mutants.ts:375-377` (`listSkipped`, `:318-389`)
  — место падения: `skipRules[candidate.rule]` читается без проверки. Простое
  `?.` в `:377` — не исправление. В `:376` распаковывается `undefined`, и
  кандидат остаётся без `category`, а отчёты считают и показывают пропуски по
  категориям из закрытого множества (`cli/report/build-list-report.ts:232-242`,
  `cli/report/format-text-report.ts:91`,
  `cli/html/client/render-skipped-summary.ts:57`). К тому же ошибка автора
  плагина по-прежнему была бы видна только с `--skipped`.
- `core/generate/collect-candidates.ts:278-285` (`addReplacement`) и `:212-233`
  (`skip()`) — замена с `skip` никогда не проверяется, `rule` копируется как
  есть (`:228`). Это естественное место для проверки (вариант 2): до ветки
  `input.skipped`, с диагностикой через `createMutatorError` (`:465-480`), как
  для невалидной цели (`:286-304`).
- `core/generate/validate-replacement.ts:49-84` проверяет только узел и
  `focus` (сигнатура `(tree, node, focus)`) и для пропущенных замен вообще не
  вызывается. Одной правки здесь недостаточно: нужно менять и вызов в
  `addReplacement`.
- `types/mutant/skip-rule-id.d.ts:1,7`, `types/mutant/skip-note.d.ts:22-26`
  — закрытый тип. Для варианта 1 его нужно расширить, а реестр плагина донести
  до генерации. `listSkipped` читает модульный `skipRules` (импорт в
  `core/generate/generate-file-mutants.ts:43`). Правил плагина не несут ни
  `GenerateFileInput` (`:50-94`), ни `RegisteredMutator`
  (`types/mutator/registered-mutator.d.ts:6-22`). `Plugin`
  (`types/config/plugin.d.ts:8-18`) знает только `mutators` и `presets`. Форму
  плагина проверяет `validatePlugin` (`core/plugins/validate-plugin.ts:19-25`),
  регистрирует его `createMutatorRegistry`
  (`core/plugins/create-mutator-registry.ts:22-35`).
- `core/run-mutants.ts:192-201` (`:198`) — тот же путь для `run --html` и
  `run.html`.
- Другое обращение `skipRules[…]` — `core/mutators/missing-await.ts:252` —
  читает только правила встроенного мутатора, менять его не нужно.
- Неизвестные id мутаторов в конфиге отклоняет `prepareRun`
  (`core/config/prepare-run.ts:113-121`), а не `validate-config`. Для правил
  пропуска ближе аналог из `collect-candidates.ts`: ошибка конкретного
  мутатора, а не всего конфига.

## Критерий готовности

- Выбран вариант 1 или 2, и он назван в описании PR.
- Новый unit-тест в `test/core/generate/generate-file-mutants.test.ts` (см.
  набросок). Если проверка ляжет в `addReplacement`, добавь тест и в
  `test/core/generate/collect-candidates.test.ts`. Тест падает до исправления
  (`TypeError … 'heuristic'`) и проходит после. Он проверяет конкретный

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let`, строгий ESLint (`@azat-io/eslint-config` с
