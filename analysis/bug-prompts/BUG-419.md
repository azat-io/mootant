# BUG-419: кэш не видит `tsconfig`, подключённый через `references` вне корня проекта

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест падает 7 из 7 под
> нагрузкой; скептик повторил сценарий 4 раза на pnpm/Vitest 5.0.5 и npm/Vitest
> 5.1.0, включая CLI из tarball: с кэшем score 50, с `--no-cache` 16.67);
> скептик: не опровергнуто, medium на нижней границе — при переключении в
> обратную сторону кэш даёт ложный Killed и завышает score, но затронут только
> Vitest и только `tsconfig` из `references` не в корне проекта (опции прямо в
> `tsconfig.json`, через `extends` и solution-style `tsconfig.json` в корне кэш
> сбрасывают).

## Контекст

Кэш mootant переиспользует вердикт, пока не изменились мутируемый файл и файлы,
которые читают его тесты (`docs/content/guide/configuration.mdx:352-355`).
Единственное оговорённое исключение — изменения, которые видят только дочерние
процессы, воркеры и сеть (`:357-359`). `tsconfig` же читает Vite в главном
процессе и по нему трансформирует TypeScript: `useDefineForClassFields` (и
`target`, от которого зависит его умолчание), `experimentalDecorators`, `jsx*`,
`verbatimModuleSyntax` и другие поля. Если ближайший к файлу `tsconfig.json` —
solution-style (`"files": []` и `references`, как в шаблонах `create-vite`),
Vite берёт настройки из того файла `references`, который включает
трансформируемый файл.

Как это устроено в Vite 8.3.5 (версия из lockfile на 170ec52; строки
`node_modules/vite/dist/node/chunks/node.js` после `pnpm install`):
TypeScript-модули трансформирует плагин `vite:oxc` (`:7665`, вызов на `:7690`)
через `transformWithOxc` (`:7593-7607`). Он передаёт в `transformSync` из
`rolldown/utils` кэш `TsconfigCache` (`:4`, `:7523-7531`), tsconfig
разрешается нативно, а результат содержит `tsconfigFilePaths` — файлы tsconfig,
которые повлияли на трансформацию. В `transformWithOxc` они идут только в
`ensureWatchedFile` (`:7607`). `tsconfigFilePaths` возвращает и
`resolveTsconfig` из `rolldown/experimental` (импорт на `:16`, вызов в
устаревшем `transformWithEsbuild` на `:7364-7367`); по проверке верификатора,
для файла репро это `[packages/web/tsconfig.app.json]`. Полный список полей, которые
нативный путь берёт из tsconfig, чтением не проверен. В `transformWithEsbuild`
их 11 (`:7349-7361`), среди них ещё `alwaysStrict`, `importsNotUsedAsValues` и
`preserveValueImports`.

Mootant включает tsconfig в ключ двумя способами:

- корень проекта: все файлы корня с именами `tsconfig*.json`, `jsconfig*.json`
  и `.env*` (`core/cache/prepare-run-cache.ts:125-127`). Это только
  `readdir(root)`, без подкаталогов;
- каталог каждой зависимости тестового файла: `tsconfig.json` в этом каталоге и
  выше, до первого существующего (пути отсутствующих тоже входят), и вся цепочка
  `extends` найденного (`adapters/shared/list-tsconfig-files.ts:17-42`,
  `adapters/shared/read-tsconfig-extends.ts:24-47`). Для Vitest это делает
  `collectDependencies` (`adapters/vitest/collect-dependencies.ts:147-153`).
  Замысел записан в JSDoc: файлы, которые «may decide how a loader, such as Vite
  or tsx, transforms» (`adapters/shared/list-tsconfig-files.ts:6-11`,
  `adapters/vitest/collect-dependencies.ts:60-62`).

`references` из tsconfig не читается нигде в `adapters/`, `core/` и `cli/`.
Поэтому файл, на который ссылается solution-style `tsconfig.json`, попадает в
ключ, только если его и так находит одно из двух правил: он лежит прямо в корне
проекта и называется `tsconfig*.json` или `jsconfig*.json`, либо сам оказался
ближайшим `tsconfig.json` каталога зависимости или файлом из цепочки `extends`.
В пакете монорепозитория (`packages/web/tsconfig.json` →
`packages/web/tsconfig.app.json`) смена такой настройки меняет код, который
выполняют тесты, но не ключ, и кэш возвращает старые вердикты. Mootant при этом
печатает только «Reused cached verdicts for N of M mutants.»
(`core/run-mutants.ts:703-711`), предупреждения об устаревании нет.
`--no-cache` сохранённые вердикты не обновляет (`configuration.mdx:357-359`),
поэтому устаревшие записи живут, пока не удалён каталог
`node_modules/.cache/mootant`.

## Воспроизведение

Ветки `experiment/bug-repros` из анализа в публичном репозитории нет, каталога
`test/repros/` на 170ec52 тоже нет: файлы ниже создайте сами. Нужны Node.js
22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:23-24`) и pnpm 12: в CI стоит `latest-12`
(`.github/actions/install-tools/action.yml:14`). pnpm 10 не читает
`configDependencies` из `pnpm-workspace.yaml`, и даже `pnpm --version` внутри
репозитория у него зависает. Команды шага 2 рассчитаны на одну сессию shell: они
используют переменные `TGZ` и `FIX`.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Тест создаёт во временном каталоге монорепозиторий. В корне нет
`tsconfig*.json`, `packages/web/tsconfig.json` — solution-style со ссылкой на
`./tsconfig.app.json`, где и лежат опции. В `node_modules` проекта стоит
симлинк на Vitest репозитория. Тест прогоняет мутанты `packages/web/src` с
кэшем, переключает `useDefineForClassFields` с `true` на `false` и сравнивает
прогон с кэшем с прогоном без кэша. Поле поверх аксессора в `math.ts` — ошибка
TypeScript TS2610, поэтому там стоит `@ts-expect-error` (Vite типы не
проверяет). Пример искусственный; реалистичный триггер — подъём `target`
(шаг 2).

Файлов два. Первый — общий помощник репро кэша `BUG-400-cache-project.ts`:
BUG-419 берёт из него `createCacheProject`, `writeProjectFiles`, `runProject`,
`listVerdicts` и `removeCacheProjects`, а `MATH_SOURCE`, `VITEST_CONFIG` и
`countCached` нужны другим репро. Второй — сам тест. Оба временные и в коммит не
входят (см. «Ограничения»).

import {
  writeFile,
  realpath,
  mkdtemp,
  symlink,
  mkdir,
  rm,

import { setTimeout } from 'node:timers/promises'

import path from 'node:path'

import type { RunResult } from '../../types/run/run-result'

import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

/**
 * Projects created by the running test file, removed by `removeCacheProjects`.
 */
let projects: string[] = []

/**
 * Template of the cache reproductions (BUG-402 and later): `isAdult` has the
 * survivors `age > 18` and `age >= 17` while no test asks about 18 or 17, and
 * `age == 18` is killed by `isAdult(30)`.
 */
export const MATH_SOURCE = [
  'export function isAdult(age: number): boolean {',
  '  return age >= 18',
  '}',
  '',
].join('\n')

/**
 * Configuration of Vitest of the reproductions.
 */
export const VITEST_CONFIG = [
  "import { defineConfig } from 'vitest/config'",
  '',
  "export default defineConfig({ test: { include: ['test/**/*.test.ts'] } })",
  '',
].join('\n')

/**
 * Creates a project in a temporary directory with a `node_modules` of its own,
 * where a link to the repository's Vitest stands for the installed one, so
 * the cache file of every reproduction is private.
 *
 * @param files - Texts by path relative to the root.
 * @returns Real path of the project.
 */
export async function createCacheProject(
  files: Record<string, string>,
): Promise<string> {
  let root = await realpath(
    await mkdtemp(path.join(tmpdir(), 'mootant-repro-')),
  )
  projects.push(root)
  await mkdir(path.join(root, 'node_modules'), { recursive: true })
  await symlink(
    await realpath(
      path.resolve(import.meta.dirname, '../../node_modules/vitest'),
    ),
    path.join(root, 'node_modules/vitest'),
  )
  await writeProjectFiles(root, { 'package.json': '{ "type": "module" }', ...files })
  return root
}

/**
 * Writes files of a project, creating their directories.
 *
 * @param root - Root of the project.
 * @param files - Texts by path relative to the root.
 */
export async function writeProjectFiles(
  root: string,
  files: Record<string, string>,
): Promise<void> {
  for (let [file, text] of Object.entries(files)) {
    let absolute = path.join(root, file)
    await mkdir(path.dirname(absolute), { recursive: true })
    await writeFile(absolute, text)
  }
  // Files modified in the millisecond a run starts count as changed during it.
  await setTimeout(5)
}

/**
 * Runs the mutants of a project with Vitest.
 *
 * @param root - Root of the project.
 * @param options - Paths and whether to use the cache.
 * @param options.cache - Whether to use the cache; on when omitted.
 * @param options.paths - Paths to mutate; `src` when omitted.
 * @returns Result of the run.
 */
export function runProject(
  root: string,
  options: { paths?: string[]; cache?: boolean } = {},
): Promise<RunResult> {
  return runMutants({
    builtIns: createBuiltIns('vitest', vitestAdapter()),
    paths: ['src'],
    concurrency: 1,
    cwd: root,
    ...options,
  })
}

/**
 * Lists the verdict of every mutant of a run by its replacement.
 *
 * @param result - Result of a run.
 * @returns Status by `<file>: <replacement>`.
 */
export function listVerdicts(result: RunResult): Record<string, string> {
  return Object.fromEntries(
    result.results.map(entry => [
      `${entry.mutant.file}: ${entry.mutant.replacement}`,
      entry.status,
    ]),
  )
}

/**
 * Removes the projects of the running test file.
 *
 * @returns Promise of the removal.
 */
export async function removeCacheProjects(): Promise<void> {
  await Promise.all(
    projects.splice(0).map(root => rm(root, { recursive: true, force: true })),
  )
}

/**
 * Counts the mutants of a run whose verdict came from the cache.
 *
 * @param result - Result of a run.
 * @returns Number of cached verdicts.
 */
export function countCached(result: RunResult): number {
  return result.results.filter(entry => entry.cached).length
}

### Шаг 2. CLI на упакованном mootant

Сквозная проверка, как у пользователя: npm, Vitest 5.1.0 и Vite 8.3.5, пакет
`packages/web` с `tsconfig.json` как в шаблоне create-vite (ссылки на
`tsconfig.app.json` и `tsconfig.node.json`). Меняется только `target` в

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому для CLI нужна

## Ожидаемое поведение

- Шаг 1: тест проходит. В прогоне с кэшем после смены `tsconfig.app.json`
  вердикты те же, что без кэша: `packages/web/src/math.ts: value / 2` и
  `packages/web/src/math.ts: 3` (замена литерала `2`) — `Killed`.
- Шаг 2: после подъёма `target` прогон с кэшем не переиспользует вердикты
  тестов пакета (строки «Reused cached verdicts…» нет) и даёт тот же score, что
  `--no-cache`: 16.67.
- В общем случае смена любого `tsconfig`, который Vite применяет к модулю через
  `references`, меняет ключ тестовых файлов, зависящих от этого модуля. Это
  касается ссылки на файл и на каталог, в том числе за пределы каталога пакета,
  и цепочки `extends` у файла по ссылке.

Контрольные опыты скептика на том же проекте. «Шаг 1» — `useDefineForClassFields`
`true` → `false` (опыт E1). «Обратно» — `false` → `true` (E2) или только
`target` ES2020 → ES2022 без явного `useDefineForClassFields` (E6); результаты
E2 и E6 совпали. Пометка «кэш» значит, что вердикт взят из кэша.

| Мутант | Шаг 1, с кэшем | Шаг 1, без кэша | Обратно, с кэшем | Обратно, без кэша |
| --- | --- | --- | --- | --- |
| `value / 2` | Survived, кэш | Killed | Killed, кэш | Survived |
| `3` (литерал `2`) | Survived, кэш | Killed | Killed, кэш | Survived |
| `1` (`stored = 0`) | Survived, кэш | Survived | Survived, кэш | Survived |
| `;` (тело сеттера) | Killed | Killed | NoCoverage | NoCoverage |
| `0` (`return this.stored`) | Killed | Killed | NoCoverage | NoCoverage |
| `6` (`value = 5`) | Killed, кэш | Killed | Killed, кэш | Killed |

Свежий dry run видит новую семантику, поэтому мутанты, у которых сменилось
покрытие (`;` и `0`), пересчитываются. Вердикты мутантов с теми же
покрывающими тестами берутся из кэша по старому ключу и остаются такими и в
следующих прогонах с кэшем. В обратную сторону ошибка оптимистичная: ложный
Killed завышает score и может пропустить `--threshold`.

Шаг 2 (Vitest 5.1.0, Vite 8.3.5):

```
r1.json:"score":83.33
r2.json:"score":50
r3.json:"score":16.67
```

Второй прогон печатает в stderr «Reused cached verdicts for 4 of 6 mutants.».
С кэшем `value / 2` и `value * 3` — Killed (Killed 3, Survived 1, NoCoverage
2), без кэша — Survived (Killed 1, Survived 3, NoCoverage 2).

## Подозреваемые места в коде

- `adapters/shared/list-tsconfig-files.ts:17-42` — обходит только `extends`
  (цикл `:29-36` через `readTsconfigExtends`). Сюда нужен обход `references`.
- `adapters/shared/read-tsconfig-extends.ts:57-91` — `readExtends` разбирает
  `tsconfig` как JS-выражение через `oxc-parser` (JSON с комментариями и
  висячими запятыми) и берёт только `extends`. Разбор естественно обобщить на
  `references` — массив объектов с полем `path`. По правилу «одна функция —
  один файл» чтение ссылок ляжет в отдельный модуль рядом.
- `adapters/vitest/collect-dependencies.ts:147-153` — вызов, через который идёт
  репро: каждый каталог зависимостей тестового файла добавляет
  `listTsconfigFiles(directory, input.tsconfigs)`. Сам вызов менять не нужно.
- `core/cache/prepare-run-cache.ts:125-127` — корневое правило. Оно объясняет,
  почему solution-style `tsconfig.json` в корне (одно приложение create-vite)
  уже обрабатывается. Общие входы сессии Vitest
  (`adapters/vitest/get-cache-inputs.ts:43-60`) tsconfig не добавляют.
- `adapters/node-test/collect-node-dependencies.ts:67-71` и
  `adapters/node-test/get-node-cache-inputs.ts:59` — тот же
  `listTsconfigFiles` для node:test с tsx. Бага там нет. tsx 4.23.15 (из
  lockfile) читает один tsconfig на процесс: `TSX_TSCONFIG_PATH` или ближайший
  `tsconfig.json` от `process.cwd()` (встроенный get-tsconfig). У файлов из
  `extends` он отбрасывает `references`. Обход `references` даст node:test
  только лишнюю инвалидацию, вердиктам она не вредит.

### Где теряется файл

Для каталогов `packages/web/src` и `packages/web/test` функция
`listTsconfigFiles` поднимается до `packages/web/tsconfig.json`, находит его и
дальше идёт только по `extends`. У solution-style файла `extends` нет. Поэтому
для `packages/web/src` список — `packages/web/src/tsconfig.json` (отсутствует)
и `packages/web/tsconfig.json`, без `tsconfig.app.json`. Корневое правило
подкаталоги не читает. Контрольные опыты скептика это подтверждают: опции прямо
в `packages/web/tsconfig.json` (E3) и в файле, который он расширяет через
`extends` (E4), кэш сбрасывают; solution-style `tsconfig.json` в корне (E5) —
тоже, через корневое правило. Дыра ровно в `references`.

### Как чинить

1. Нужно: настоящий обход `references` в `listTsconfigFiles`, для найденного
   `tsconfig.json` и транзитивно для каждого файла по ссылке. Для репро он
   добавляет в ключ тот же `packages/web/tsconfig.app.json`, что и вариант из
   п. 2, который верификатор проверил запуском, поэтому репро он чинит; сам
   обход ещё не написан и не проверен.
   - `path` каждой ссылки разрешается от каталога ссылающегося файла. Путь на
     `.json` — это сам файл, иначе берётся `<path>/tsconfig.json`. Так делает
     TypeScript: `resolveConfigFileProjectName` в
     `node_modules/typescript/lib/typescript.js:135394-135399` (TypeScript 6.0.3
     из lockfile).
   - У каждого файла по ссылке — своя цепочка `extends` (`readTsconfigExtends`).
   - Множество посещённых файлов защищает от циклов, каждый путь входит в список
     один раз.
   - Файлы под `node_modules` можно не включать, как это делает
     `readTsconfigExtends` (их представляет lockfile).
   - Сопоставлять `include` и `files` ссылок с файлом не нужно. Включать все
     файлы по ссылкам консервативно: правка `tsconfig.node.json` из create-vite
     лишь сбросит кэш тестов пакета.

   Не проверено чтением, следует ли rolldown вложенным `references` (ссылкам
   файла по ссылке); транзитивный обход консервативен. Не проверено и то, нужно
   ли читать `references` у файлов из цепочки `extends`; более широкий обход
   добавит лишь лишние инвалидации.
2. Не подходит: добавлять все `tsconfig*.json` из каталога найденного
   `tsconfig.json` (как корневое правило). Репро это чинит (проверено
   верификатором), но не покрывает ссылки за пределы каталога
   (`../shared/tsconfig.lib.json`) и ссылки на каталог (`./src` →
   `src/tsconfig.json`), а их требует критерий готовности.
3. Не проверено, как дополнительный источник: брать список у самого Vite —
   `tsconfigFilePaths` из `transformSync` или `resolveTsconfig` rolldown (см.
   «Контекст»). Это API rolldown, а `resolveTsconfig` ещё и из
   `rolldown/experimental`. Vitest 5 допускает и Vite 6 и 7 (`"vite": "^6.4.0 ||
   ^7.0.0 || ^8.0.0"` в `peerDependencies` файла
   `node_modules/vitest/package.json`); есть ли там эти функции, не проверено.
   Поэтому основным решением остаётся обход `references` на стороне ключа.
4. node:test: либо принять лишнюю инвалидацию, либо включать обход
   `references` параметром только из Vitest-адаптера. Выбор опишите в коммите.

## Критерий готовности

- Unit-тесты обхода `references` в
  `test/adapters/shared/list-tsconfig-files.test.ts`, а если чтение ссылок
  вынесено в отдельный модуль — и его тест рядом с
  `test/adapters/shared/read-tsconfig-extends.test.ts`. До исправления падают и
  после проходят тесты на то, что в список попадают:
  - файл по ссылке на файл (`{ "path": "./tsconfig.app.json" }`);
  - `tsconfig.json` по ссылке на каталог (`{ "path": "./src" }` →
    `src/tsconfig.json`);
  - файл по ссылке за пределы каталога
    (`{ "path": "../shared/tsconfig.lib.json" }`);
  - цепочка `extends` файла по ссылке.
- Отсутствующая ссылка и цикл ссылок (A → B → A, ссылка на себя) не вызывают
  ни исключения, ни зацикливания, и каждый путь встречается в списке один раз.
  Поведение для отсутствующей ссылки выберите и закрепите тестом.
  Консервативный вариант — включать её путь, как функция уже включает пути
  отсутствующих `tsconfig.json` («missing files included»,
  `adapters/shared/list-tsconfig-files.ts:15`): тогда появление файла меняет
  ключ. Тест, который проверяет только отсутствие исключения и зацикливания,
  может проходить и до исправления (сейчас `references` просто игнорируется).
  Это допустимо; тест, который проверяет состав списка для цикла, падает до
  исправления.
- Существующие ожидания `listTsconfigFiles` и `readTsconfigExtends` для
  конфигов без `references` не меняются.
- Новый код покрыт на 100% (порог для `adapters/**`, `vitest.config.ts:8-16`),
  в том числе ветки разбора, если они появятся: `references` не массив, элемент
  без строкового `path`, файл, который нельзя прочитать или разобрать.
- Интеграционный тест в `test/adapters/vitest/index.test.ts` внутри
  `describe('vitest adapter with the cache', …)` (`:1440`), по образцу «runs
  mutants again after a change of a file loaded outside Vite» (`:1600-1636`).
  Он падает до исправления и проходит после.
  - Фикстура — новый каталог в `test/fixtures/` с раскладкой шага 1: в корне
    нет `tsconfig*.json`; `packages/web/tsconfig.json` — solution-style со

  - Помощник `run()` (`:373-391`) жёстко задаёт `paths: ['src']` (`:385`).
