# BUG-304: R6 считает константы `return ok` поглощёнными мутантом инициализатора или записи `ok`, хотя `ok` читается ещё где-то

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.
> Перепроверено независимо: воспроизведено (тест шага 1 падает 2 из 2 у обоих
> верификаторов; на сквозной фикстуре с упакованным mootant и Vitest 5.1.0
> `mootant run` даёт killed 9, score 100 %, а физически подставленные
> `return true` и `return false` проходят все 6 тестов; найдены ещё два
> триггера — чтение через вызов и источник-запись `ok = …`); скептик: не
> опроверг, medium ближе к нижней границе (по 2 мутанта на случай, пропуск
> виден в `list --skipped`), но правило заявлено доказательным
> (`heuristic: false`), `strict` его не отключает, а такой же перенос в
> `missing-await` условие «единственная ссылка» явно проверяет, так что здесь
> упущение, а не замысел.

## Контекст

Для булева возвращаемого значения `return-value` выдаёт константы `true` и
`false`. Правило `solitary` к булеву результату не применяется
(`core/mutators/return-value.ts:170-171`), поэтому скрыть константы может
только `getConstantSkip` (`core/mutators/return-value.ts:202-239`). Константа
пропускается по правилу `R6` (категория `subsumed`, `heuristic: false`,
`core/skips/skip-rules.ts:322-325`; у `solitary` на `:302-305` —
`heuristic: true`), если работающий мутант «двигает» к ней сам результат или
**значение, присвоенное возвращаемой локальной переменной**. Источники — это
`target` плюс `getAssignedValues` (`:219-222`), то есть инициализатор и правые
части записей `=` в той же функции (`getAssignedValues`, `:508-517`, поверх
`getLocalRanges`, `:349-365`). Для каждого источника вызывается
`getTowardMutant` (`:225-236`), причина пропуска собирается по шаблону на
`:232`.

Довод о субсумпции — в JSDoc `core/mutators/shared/get-toward-mutant.ts:36-50`
(строки 42-44): «Such a mutant changes the decision only where forcing it
changes it, and to the same value, so it subsumes the candidate». Он верен,
только если решение наблюдается лишь в точке форсирования, то есть если
локальную переменную читает только этот `return`. Если `ok` читается ещё
где-то (ветка `if (!ok)`, вызов `log(ok)`), мутант инициализатора меняет и это
чтение. Тест убивает его через это чтение и возвращаемое значение не
проверяет. Константа выжила бы, но в отчёте её нет. В примере ниже
`mootant run` показывает 100 %, а с двумя скрытыми мутантами было бы 9 из 11
(≈ 81,8 %).

Это не задуманное поведение:

- `subsumed` в документации — «Is caught by any test that catches another
  mutant» (`docs/content/mutators.md:42`). Оговорка «A category is Mootant's
  decision, not a proof» (`:46-54`) перечисляет правила с флагом `heuristic`,
  `solitary` и ограничения схемы, но не `R6`. Строка `R6` в таблице
  `docs/content/mutators/return-value.md:170` приводит только прямое сравнение
  (`cart.total >= 50` → `true`).
- При таком же переносе с инициализатора локальной переменной на `return`
  правило `missing-await` (`isReturnedLocal`,
  `core/mutators/missing-await.ts:152-179`) явно требует единственную ссылку:
  `binding.references.length !== 1` (`:162`). JSDoc
  `core/mutators/return-value.ts:191-195` показывает, что расширение `R6` на
  локальные переменные задумано, но без этого условия.

Обхода практически нет. `coarseMutants` (и `strict`, который его включает,
`docs/content/mutators.md:58-60`) выключает только `applySolitaryRule`
(`core/generate/generate-file-mutants.ts:258-259`); `--preset strict`
константы не возвращает (проверено прогоном). Документация обещает возврат
`R6`, «when the other mutant doesn't run, for example because its mutator is
off» (`docs/content/mutators/return-value.md:182-183`), но «другой мутант» не
один. В примере после выключения comparison-operator `R6` находит
logical-operator («as logical-operator does»), и константы возвращаются, только
если выключить оба мутатора (проверили оба верификатора).

Масштаб (по данным скептика). Нужны булева возвращаемая локальная переменная
с работающим «владельцем» в инициализаторе или записи `=`, другое наблюдаемое
чтение и тесты, не проверяющие возврат. На случай приходится по 2 мутанта.
Пропуск виден в `mootant list --skipped` и в HTML-отчёте (переключатель
Skipped). Шаблон частый: валидатор с отчётом (пример ниже), уведомление об
изменении
(`let changed = store.value !== next; if (changed) { …; onChange(next) } return changed`:
все 6 мутантов убиты, `changed -> true/false` скрыты по `R6`, физически оба
выживают), cache hit/miss (TS-вариант `const hit = cache.has(key) && …` даёт
тот же `R6`). В `core/` самого Mootant 13 `R6`-пропусков на локальных
переменных, и все безвредны: прочие чтения там стоят только в колбэках
`walkTree` и не наблюдаемы. Существующие тесты ошибочное поведение не
закрепляют: в `test/core/mutators/return-value.test.ts` (164 теста, на 170ec52
зелёные) во всех случаях `R6` через локальную переменную её читает только
`return`.

## Воспроизведение

Нужны Node.js `^20.19.0 || >=22.12.0` (поле `engines` в `package.json`) и
pnpm 12: pnpm 10 не читает `configDependencies` из `pnpm-workspace.yaml` и
зависает.

### Шаг 1. Unit-тест (сборка не нужна)

В анализе тест лежал в `test/repros/BUG-304.test.ts` ветки
`experiment/bug-repros`, которой в чистом клоне нет. Создай этот файл
временно, только чтобы увидеть падение. В таком виде его не коммить (см.
«Ограничения»). Хелперы `test/helpers/list-mutant-texts.ts` и
`test/helpers/list-skipped.ts` есть в 170ec52. `listMutantTexts` возвращает
выданные мутанты одного мутатора как `original -> replacement`. `listSkipped`
прогоняет весь конвейер со всеми встроенными мутаторами, как
`mootant list --skipped`, и возвращает пропуски мутатора как
`original -> replacement (category rule)`.

```ts
import { describe, expect, it } from 'vitest'

import { listMutantTexts } from '../helpers/list-mutant-texts'
import { listSkipped } from '../helpers/list-skipped'

/**
 * A local that a branch reads before the function returns it: the
 * comparison-operator mutants of its initializer are killed through the
 * `report` call, so they say nothing about whether a test reads the returned
 * value.
 */
let validate = [
  'export function validate(input, report) {',
  '  let ok = input.length > 2 && input.length < 10',
  '  if (!ok) {',
  "    report('invalid')",
  '  }',
  '  return ok',
  '}',
]

describe('BUG-304: R6 takes a mutant of a local read elsewhere for a subsumer of the returned constants', () => {
  it('keeps the constants of a returned local that a branch also reads', () => {
    expect(
      listMutantTexts('return-value', validate, { file: 'example.js' }),
    ).toStrictEqual(['ok -> true', 'ok -> false'])
  })

  it('does not skip the constants as subsumed', () => {
    expect(
      listSkipped('return-value', validate.join('\n'), { file: 'example.js' }),
    ).toStrictEqual([])
  })
})
```


сборка. В npm-фикстуре ставь `vitest@5` (сейчас это 5.1.0), а не
`vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает в arborist с

## Ожидаемое поведение

Значения, присвоенные локальной переменной (инициализатор и правые части
`=`), служат источниками `R6`, только если переменную не читает ничего, кроме
этого `return`. В примере `validate` выводятся `ok -> true` и `ok -> false`, и
`mootant run` показывает их как Survived. Если выражение стоит прямо в
`return` или переменную читает только `return`, `R6` остаётся. Оба случая
верификаторы проверили как контроль. При сравнении прямо в `return` `R6`
указывает на мутант в самом `return`. Для переменной, которую читает только
`return` (пример `isAdult` у скептика), `R6` корректен: подставленные
константы физически убиваются.

Что считать «другим чтением» (уточнения верификатора; пункты с пометкой «не
проверялось» выведены чтением кода):

1. Готовое условие из `missing-await` (`binding.references.length !== 1`,
   `core/mutators/missing-await.ts:162`) здесь не подходит.
   `Binding.references` — это «reads and write targets»
   (`types/syntax/binding.d.ts:23-27`), а у `R6` записи `=` — законные
   источники. С таким условием сломается существующий тест
   `test/core/mutators/return-value.test.ts:670-675`
   (`let ok = check(); if (a) ok = a > 2; return ok`: две ссылки — цель записи
   и `return`), а он обязан сохранить `R6`.
2. Цель простого `=` (`left` у `AssignmentExpression` с `operator === '='`)
   — не чтение.
3. Составная запись (`||=`, `&&=`, `??=` и т. п.) — чтение: она читает текущее
   значение. Тест `:677-683` (`let ok = check(); ok ||= a > 2; return ok`,
   константы выдаются) должен остаться зелёным. Готовый `isWriteTarget`
   (`core/syntax/is-write-target.ts:31-45`) считает целью записи левую часть
   любого присваивания и операнд `++`/`--`, поэтому одного его мало.
4. Чтения во вложенных функциях (колбэк, замыкание) — тоже чтения.
   `references` собираются обходом всей программы
   (`core/hints/analyze-scopes.ts:257-281`), так что они там есть. Фильтр
   `getEnclosingFunction`, которым `getLocalRanges` отбирает записи
   (`core/mutators/return-value.ts:359-363`), для поиска чтений не годится.
5. Второй `return` той же переменной — тоже другое чтение: тест может убить
   мутант инициализатора через другой `return` (вывод из определения; не
   проверялось).
6. Ссылки вне runtime-дерева (например, в аргументах логирующего вызова; такие
   записи `getLocalRanges` отбрасывает через `isRuntimeNode`) — реши сам и
   зафиксируй тестом. Группа «leaves names and writes outside the runtime tree
   out» (`test/core/mutators/return-value.test.ts:773-801`) должна пройти без
   правок.

Где ставить проверку:

- В пути `R6`: в `getAssignedValues` (`core/mutators/return-value.ts:508-517`,
  её вызывает только `getConstantSkip`, `:221`) или в самом
  `getConstantSkip`. Если у переменной есть другое чтение, источник один —
  сам `target`.
- Не в `getLocalRanges`, если не учитывать `solitary`. Эту функцию вызывает
  и `solitary` (`:170-171`), а там составная запись `sum += x` чтением
  считаться не должна. Тест `:91-94` и первый случай группы `:803-858`
  (`:804-817`) ждут, что `sum -> 0` пропущен, и с такой политикой упадут (по
  чтению кода; не проверялось). Корневая причина та же, что у BUG-301
  (`solitary`, итоговая серьёзность low), и общий помощник «есть ли другие
  чтения» уместен. Но составные записи два правила должны трактовать
  по-разному: доказательному `R6` нужна консервативная политика, а скептик
  BUG-301 для эвристики `solitary` предлагает записи, в том числе составные,
  чтением не считать.

Цена: если считать чтения в замыканиях, часть из 13 `R6`-пропусков в `core/`
самого Mootant (прочие чтения в колбэках `walkTree`), вероятно, вернётся как
лишние мутанты. Это шум, а не ложный вердикт. Сколько именно вернётся, не
проверено.

## Фактическое поведение

Шаг 1 (суть сообщений Vitest, не дословный лог; одинаково у обоих
верификаторов):

```
× keeps the constants of a returned local that a branch also reads
  expected [] to strictly equal [ 'ok -> true', 'ok -> false' ]
× does not skip the constants as subsumed
  expected [ 'ok -> true (subsumed R6)', 'ok -> false (subsumed R6)' ] to strictly equal []
```

Шаг 2, `npx mootant list src/validate.js --skipped`: `mutants 9`, в секции
`skipped:` обе константы. Раскладка приблизительная: колонки выравниваются, а
стрелка (`->` или `→`) зависит от терминала (`cli/report/format-text-report.ts`,
`cli/report/format-file-groups.ts`). Текст причины для `true` верификатор
видел дословно, для `false` он собран по шаблону
`core/mutators/return-value.ts:232`.

```
skipped:

src/validate.js
  6:10  return-value  ok -> true   subsumed  R6
        it makes the result true, as comparison-operator does on some inputs
  6:10  return-value  ok -> false  subsumed  R6
        it makes the result false, as comparison-operator does on some inputs
```

В `--json` у обеих констант `"rule": "R6"`, `"category": "subsumed"`,
`"heuristic": false` и `"by"` с `mutator: "comparison-operator"`, `line: 2`,
`column: 12`, то есть `input.length > 2` (поля —
`cli/report/build-list-report.ts:149-172`).
`mootant run src/validate.js --no-cache` даёт killed 9, survived 0,
score 100 % (на копии фикстуры анализа — три прогона подряд). Мутант-владелец
`>= 2` убивает тест для `'ab'`. С физически подставленными `return true` и
`return false` `vitest --run` оба раза даёт 6 passed.

Что ещё видели верификаторы (сквозными прогонами `mootant list --skipped`):

- `--preset strict` — `R6` остаётся.
- Выключен только comparison-operator — `R6` остаётся, «as logical-operator
  does». Выключены comparison-operator и logical-operator — `ok -> true` и
  `ok -> false` снова выдаются. Каким способом выключали мутаторы, в отчёте не
  записано.
- Чтение через вызов (`log(ok); return ok`) и источник-запись
  (`ok = a > 2; if (!ok) report(); return ok`, TS) дают тот же ложный `R6`.
  Голый `log(ok)` с нестроковым первым аргументом — обычный, не логирующий
  вызов (`core/syntax/is-logging-call.ts:31-32`, `:49-58`). Точный текст этих
  файлов не сохранился.
- Контроли. То же сравнение прямо в `return` даёт `R6` с `by` на самом
  `return`, это корректно. `let ok = a > 0 && b; return ok` с `b: boolean`
  даёт `R6`, тоже корректно: переменную читает только `return`. Тот же код
  без типов (`.js` или `.ts` без аннотаций) `R6` не даёт вовсе, а даёт
  `ok -> undefined (subsumed solitary)`: значение не булево.

## Подозреваемые места в коде

- `core/mutators/return-value.ts:219-237` — `sources` и цикл по ним: значения,
  присвоенные локальной переменной, становятся источниками `R6` без проверки
  других чтений.
- `core/mutators/return-value.ts:508-517` (`getAssignedValues`) —
  единственный вызов из `getConstantSkip` (`:221`), естественное место для
  проверки «переменную читает только этот `return`». Для не-`Identifier`
  функция уже возвращает `[]` (`:509-511`), так что цепочки членов `R6` через
  локальную переменную не затрагивает.
- `core/mutators/return-value.ts:349-365` (`getLocalRanges`) и `:378-391`
  (`getLocalBinding`) — проверяют только вид объявления, runtime-дерево и ту
  же функцию, другие чтения не смотрят. `getLocalRanges` вызывает и
  `solitary` (`:170-171`), см. «Где ставить проверку».
- `types/syntax/binding.d.ts:23-27` (`references`: чтения и цели записей по
  всему файлу, без объявляющего идентификатора) и `:41-47` (`writes`).
- `core/hints/analyze-scopes.ts:257-281` — ссылки собираются обходом всей
  программы, поэтому в `references` есть и чтения во вложенных функциях.
- `core/syntax/is-write-target.ts:31-45` (`isWriteTarget`) — готовая проверка
  «узел — цель записи». Целью она считает и составное присваивание, поэтому
  для `R6` нужна доработка (см. п. 3 «Ожидаемого поведения»).
- `core/mutators/missing-await.ts:152-179` (`isReturnedLocal`) — образец:
  `binding.references.length !== 1` (`:162`), родитель ссылки через
  `syntax.getContextSlot(reference).parent` (`:177`). Там у переменной не
  бывает записей (`const` или никогда не записываемый `let`), поэтому хватает

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, один экспорт на файл (локальные
  функции рядом допустимы: в `core/mutators/return-value.ts` один экспорт и
  13 локальных функций), JSDoc на каждую функцию, `let` вместо `const` там,
  где так принято в проекте, строгий ESLint (`@azat-io/eslint-config`),
  cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.

  `Binding.writes` уже есть.

  «Где ставить проверку»).
- Тест-воспроизведение из анализа нельзя копировать как есть в `test/repros/`:
  перепиши его в стиле проекта. Строгий ESLint (`eslint.config.ts`:
