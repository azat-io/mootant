# BUG-508: проекты Vitest со своим Vite-сервером (свой `root`, `projects: ['packages/*']`, свои `plugins`) не настраиваются — dry run падает

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: high. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест падает 2 из 2; на
> независимой фикстуре `projects: ['packages/*']` с упакованным mootant и
> Vitest 5.1.0 `vitest --run` зелёный, а `mootant run packages` завершается с
> exit 1 — под root и под nobody); скептик: не опровергнуто, high на нижней
> границе — отказ громкий (exit 1 до первого вердикта, ложных Killed и Survived
> нет), но `mootant run` из корня не работает для типовой схемы монорепо,
> сообщение «Tests fail without mutants» ложное, а затронут любой проект со
> своим Vite-сервером, не только со своим `root`.

## Контекст

Для каждого проекта Vitest mootant ставит свой раннер воркеров, свой пул forks,
`isolate: true`, отключает перемешивание и запись снапшотов
(`adapters/vitest/configure-project.ts:22-56`), а неподдерживаемые настройки
отлавливает через `checkProjectConfig` (`:30-34`). Всё это делается из хука
`configureVitest` Vite-плагина mootant
(`adapters/vitest/create-mootant-plugin.ts:53-55`). Мутанты подменяются в хуке
`transform` того же плагина (`:32-52`). JSDoc плагина обещает: «Each Vitest
project is configured for mootant's runner when Vitest starts» (`:20-21`).

Плагин передаётся в `createVitest` **вторым** аргументом, `viteOverrides`
(`adapters/vitest/start-vitest-session.ts:110`, весь вызов — `:91-117`).
Сигнатура в Vitest 5.0.5: `createVitest(options, viteOverrides?,
vitestOptions?)` (`node_modules/vitest/dist/node.d.ts:372`). Третий аргумент —
потоки stdout/stderr. Третьим плагин стоял бы только в устаревшей перегрузке с
`mode` (`:376`). `viteOverrides` попадают в корневой Vite-сервер, а проект со
своим Vite-сервером их плагинов не получает. Ниже цитаты по Vitest 5.0.5 из
`node_modules/vitest/dist/chunks/` (эти файлы появляются только после
`pnpm install`; в lockfile закреплена 5.0.5):

- Проекты из файлов и каталогов (`projects: ['packages/*']`,
  `['packages/*/vitest.config.ts']`) сервер никогда не делят
  (`index.1TqnEahn.js:7031-7055`, отладочное сообщение «file and directory
  projects never share the server» на `:7045`). От `viteOverrides` они ничего не
  наследуют: наследование есть только у inline-записей (`:7302-7312`).
- Inline-проект получает свой сервер, если `getOwnServerReason` находит причину
  (`:7152-7181`, вызов на `:7007`). Причины: `sharedViteServer: false`;
  `extends` указывает не на объявляющий конфиг; любой ключ верхнего уровня,
  кроме `test`, `extends`, `define` и пустого `plugins` (`:7159-7167`), то есть
  свой `plugins: [vue()]`, `resolve` и т. п.; унаследованный `browser`;
  `test.alias`, `test.browser`, `test.css`, `test.mode`, `test.root` (список
  `VITE_AFFECTING_TEST_OPTIONS`, `:7137-7143`); `test.deps.optimizer` и
  `test.deps.moduleDirectories`.
- Такому inline-проекту `inheritRootViteOverrides` передаёт `viteOverrides` без
  `plugins` (`:7119-7132`; комментарий «`plugins` are already initialised,
  keeping them would break isolation» и деструктуризация — `:7120-7121`).
- `attachProjectsFromEntries` создаёт для него новый Vite-сервер (`:7673-7739`,
  ветка `:7724-7737`). Проекты, которые делят корневой сервер, получают
  `vitest.vite` (`:7693`, `:7708-7714`, `:6769-6776`).
- Хуки `configureVitest` Vitest берёт из Vite-конфига самого проекта:
  `project.vite.config.getSortedPluginHooks("configureVitest")`
  (`cli-api.De07GUeT.js:12411`; весь вызов хуков — `:12410-12425` в методе
  `_attachProjectServers`, который начинается на `:12403`).

В Vitest 5.1.0 чанки называются иначе, код тот же:
`index.Di8au7q4.js:7142-7144` (`inheritRootViteOverrides`), `:7175`
(`getOwnServerReason`), `:7696` (`attachProjectsFromEntries`),
`cli-api.COfZo8lK.js:12954` (вызов `configureVitest`). Баг воспроизводится на
обеих версиях.

В итоге проект со своим сервером не настроен: у него штатный раннер и пул
Vitest, `checkProjectConfig` для него не вызывается. И он не инструментирован:
`transform` mootant нет в конвейере его сервера, поэтому мутанты не
подменяются. Тест теряется так. mootant узнаёт результаты только из out-файлов,
которые пишет его раннер в воркерах. `readDryResult` помечает тест-файл без
out-файла как незагрузившийся (`adapters/vitest/run-dry.ts:203-207`, текст «The
test runner did not report this file.» — `:263`). Исполняет ли этот файл при
этом штатный раннер Vitest, анализ не проверял. Затем `checkRealFailures`
повторяет dry run без мутантов (`core/run/run-dry-phase.ts:385-421`, сообщение
«Some tests failed; running them again without mutants to check.» — `:395`),
получает тот же результат и останавливает прогон с «Tests fail without
mutants; fix them first» (`:411-420`).

Последствия. Самая распространённая схема монорепо, `test.projects:
['packages/*']`, из корня не работает совсем. mootant сообщает, что тесты
падают без мутантов, хотя `vitest --run` зелёный, и даже `--verbose` не
подсказывает причину. Так же ломаются inline-проекты со своим `root`,
`extends: true` вместе с `root`, конфиги в пакетах, проекты со своими
`plugins`, `test.alias` или `test.mode`, а также `sharedViteServer: false`.
Неподдерживаемую настройку в таком проекте (`pool: 'vmThreads'`)
`checkProjectConfig` не ловит (`adapters/vitest/check-project-config.ts:22-24`):
вместо понятной ошибки выходит то же «fails to load». Работают только проекты,
которые делят корневой сервер (например, только `include` и `name`), и запуск
mootant из каталога пакета. Документация об ограничении молчит. `readme.md:53-54`
обещает «using your project's test configuration». В списке неподдерживаемого
(`docs/content/guide/compatibility.mdx:40-54`) нет ни проектов, ни монорепо, а
фраза «Any of these in one project stops the whole run» (`:54`) прямо
предполагает несколько проектов. Единственная многопроектная фикстура тестов,
`test/fixtures/cache-teardown/vitest.config.ts:3-17`, использует общий сервер,
поэтому этот случай тестами не покрыт.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создайте
сами. Нужны Node.js 22.12 или новее (Vitest 5 требует
`^22.12.0 || ^24.0.0 || >=26.0.0`, `docs/content/guide/compatibility.mdx:23-24`)
и pnpm 12 (`contributing.md:98`; в CI стоит `latest-12`,
`.github/actions/install-tools/action.yml:11-15`). Шаги 2–4 рассчитаны на одну
сессию shell: они используют переменные `TGZ`, `FIX` и `V`.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Тест фикстуры назван `*.check.ts`, чтобы корневой Vitest репозитория его не
подхватывал. У фикстуры нет своих зависимостей: Vitest берётся из
`node_modules` клона выше по дереву. Все файлы временные и в коммит не входят
(см. «Ограничения»).

```bash
# в корне клона azat-io/mootant
pnpm install
mkdir -p test/repros/BUG-508/pkg/src test/repros/BUG-508/pkg/test

cat > test/repros/BUG-508/package.json <<'EOF'
{
  "name": "bug-508-fixture",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "vitest --run"
  }
}
EOF

cat > test/repros/BUG-508/vitest.config.ts <<'EOF'
export default {
  test: {
    projects: [
      {
        test: {
          include: ['test/**/*.check.ts'],
          root: './pkg',
          name: 'pkg',
        },
      },
    ],
  },
}
EOF

cat > test/repros/BUG-508/pkg/src/add.ts <<'EOF'
export function add(a: number, b: number): number {
  return a + b
}
EOF

cat > test/repros/BUG-508/pkg/test/add.check.ts <<'EOF'
import { expect, it } from 'vitest'

import { add } from '../src/add'

it('adds', () => {
  expect(add(2, 3)).toBe(5)
})
EOF

cat > test/repros/BUG-508.test.ts <<'EOF'
import { describe, expect, it } from 'vitest'
import path from 'node:path'

import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

/**
 * Project whose only Vitest project has a root of its own, `pkg`, as
 * `projects: ['packages/*']` gives every package of a monorepo.
 */
let root = path.resolve(import.meta.dirname, 'BUG-508')

describe('BUG-508: Vitest projects with a root of their own', () => {
  it('runs the mutants of a project whose root is not the root of the run', async () => {
    /*
     * `npx vitest --run` in the fixture passes. mootant's plugin reaches only
     * the projects that share the root Vite server (`configureVitest` is not
     * called for `pkg`), so `pkg` keeps Vitest's own runner and pool, writes
     * no out files, and the dry run stops the run with "Tests fail without
     * mutants; fix them first (1 test file): pkg/test/add.check.ts: fails to
     * load: The test runner did not report this file."
     */
    let result = await runMutants({
      builtIns: createBuiltIns('vitest', vitestAdapter()),
      paths: ['pkg/src'],
      concurrency: 1,
      cache: false,
      cwd: root,
    })

    expect(
      result.results.map(
        verdict => `${verdict.mutant.replacement} ${verdict.status}`,
      ),
    ).toContain('a - b Killed')
  }, 60_000)
})
EOF

# без mootant, Vitest клона: зелёный (1 passed)
(cd test/repros/BUG-508 && node ../../../node_modules/vitest/vitest.mjs --run)
# с mootant: падает
pnpm exec vitest --run test/repros/BUG-508.test.ts
```

В анализе фикстура проверялась командой `npx vitest --run` из её каталога.
Здесь Vitest вызывается по пути: так `npx` не пойдёт искать его в реестре.
`test/helpers/create-built-ins.ts` есть в репозитории на 170ec52.

### Шаг 2. CLI на упакованном mootant: `projects: ['packages/*']`

`bin/mootant.js` импортирует `../dist/cli/index.js` (`bin/mootant.js:3`),
поэтому для CLI нужна сборка. Ставьте `vitest@5` (сейчас это 5.1.0), а не
`vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает с `Cannot read properties of
null (reading 'edgesOut')`. Это баг arborist, а не mootant. На этой фикстуре
скептик воспроизвёл баг независимо.

```bash
# в корне клона, после шага 1
pnpm build
pnpm pack                        # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"    # *.tgz нет в .gitignore, не оставляйте его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"

FIX="$(mktemp -d)"
cd "$FIX"
mkdir -p packages/a/src packages/a/test packages/b/src packages/b/test

cat > package.json <<'EOF'
{
  "name": "mono-508",
  "private": true,
  "type": "module",
  "workspaces": ["packages/*"],
  "scripts": {
    "test": "vitest --run"
  }
}
EOF

cat > vitest.config.ts <<'EOF'
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    projects: ['packages/*'],
  },
})
EOF

cat > packages/a/package.json <<'EOF'
{ "name": "@m/a", "private": true, "type": "module" }
EOF

cat > packages/a/src/add.ts <<'EOF'

EOF

cat > packages/a/test/add.test.ts <<'EOF'

cat > packages/b/test/mul.test.ts <<'EOF'

# обходной путь: из каталога пакета работает
(cd packages/a && "$FIX/node_modules/.bin/mootant" run src --no-cache)
```

### Шаг 3. Варианты конфигурации на тех же пакетах

Конфигурации вариантов взяты у скептика, результаты «сейчас» приведены по
данным обоих верификаторов (таблица в «Фактическом поведении»). Варианты лежат
внутри `$FIX`, поэтому Vitest и mootant находятся в `$FIX/node_modules`.
Бинарники вызываются по полному пути.

```bash
# в той же сессии shell, после шага 2
V="$FIX/variants"
variant() {  # $1 — имя варианта; его vitest.config.ts читается из stdin
  mkdir -p "$V/$1"
  cp -R "$FIX/packages" "$V/$1/"
  cat > "$V/$1/vitest.config.ts"
}

variant shared <<'EOF'
export default {
  test: {
    projects: [
      { test: { name: 'a', include: ['packages/a/test/**/*.test.ts'] } },
      { test: { name: 'b', include: ['packages/b/test/**/*.test.ts'] } },
    ],
  },
}
EOF

variant pkg-configs <<'EOF'
export default { test: { projects: ['packages/*/vitest.config.ts'] } }
EOF
echo "export default { test: { name: 'a', include: ['test/**/*.test.ts'] } }" \
  > "$V/pkg-configs/packages/a/vitest.config.ts"
echo "export default { test: { name: 'b', include: ['test/**/*.test.ts'] } }" \
  > "$V/pkg-configs/packages/b/vitest.config.ts"

variant extends-root <<'EOF'
export default {
  test: {
    projects: [
      { extends: true, test: { name: 'a', root: './packages/a' } },
      { extends: true, test: { name: 'b', root: './packages/b' } },
    ],
  },
}
EOF

variant mixed <<'EOF'
export default {
  test: {
    projects: [
      { test: { name: 'a', root: './packages/a' } },
      { test: { name: 'b', include: ['packages/b/test/**/*.test.ts'] } },
    ],
  },
}
EOF

variant alias <<'EOF'
export default {
  test: {
    projects: [
      { test: { name: 'a', include: ['packages/a/test/**/*.test.ts'], alias: { '@x': '/nonexistent' } } },
    ],
  },
}
EOF

variant inline-plugin <<'EOF'
export default {
  test: {
    projects: [
      { plugins: [{ name: 'noop' }], test: { name: 'a', include: ['packages/a/test/**/*.test.ts'] } },
    ],
  },
}
EOF

variant no-shared-server <<'EOF'
export default {
  test: {
    sharedViteServer: false,
    projects: [
      { test: { name: 'a', include: ['packages/a/test/**/*.test.ts'] } },
    ],
  },
}
EOF

variant vmthreads-root <<'EOF'
export default {
  test: {
    projects: [
      { test: { name: 'a', root: './packages/a', pool: 'vmThreads' } },
    ],
  },
}
EOF

variant vmthreads-shared <<'EOF'
export default {
  test: {
    projects: [
      { test: { name: 'a', include: ['packages/a/test/**/*.test.ts'], pool: 'vmThreads' } },
    ],
  },
}
EOF

for spec in shared:packages pkg-configs:packages extends-root:packages \
  mixed:packages mixed:packages/b/src alias:packages/a/src \
  inline-plugin:packages/a/src no-shared-server:packages/a/src \
  vmthreads-root:packages/a/src vmthreads-shared:packages/a/src; do
  v="${spec%%:*}"
  p="${spec#*:}"
  echo "== $v: mootant run $p"
  (
    cd "$V/$v"
    "$FIX/node_modules/.bin/vitest" --run > /dev/null 2>&1
    echo "vitest exit $?"
    "$FIX/node_modules/.bin/mootant" run "$p" --no-cache
    echo "mootant exit $?"
  )

```

Пути для mootant здесь выбраны так: `packages` для вариантов с двумя
проектами, `packages/a/src` для вариантов только с проектом `a`. С какими путями
запускали варианты верификаторы, не записано. На исход это не влияет: упасть
должен тест-файл проекта `a`. Воспроизводящий агент дополнительно проверил на
раскладке шага 1 inline-проект с общим root и `test.mode: 'unit'`. Результат
тот же: «fails to load».

### Шаг 4. Пробник: для каких проектов Vitest вызывает `configureVitest`

Пробник воспроизводящего агента. Плагин передаётся в `createVitest` в той же
форме, что и в `adapters/vitest/start-vitest-session.ts:91-117`.

```bash
# в той же сессии shell, после шага 3
PROBE="$(mktemp -d)"
cat > "$PROBE/probe.mjs" <<'EOF'
// Usage: node probe.mjs <vitest node entry (file path)> <project root>
import { pathToFileURL } from 'node:url'
let [entry, root] = process.argv.slice(2)
let { createVitest, version } = await import(pathToFileURL(entry).href)
let called = []
let probe = {
  name: 'probe',
  enforce: 'pre',
  configureVitest({ project }) {
    called.push(project.name)
  },
}
// same shape as adapters/vitest/start-vitest-session.ts:91-117
let vitest = await createVitest(
  { watch: false, cache: false, reporters: [], root },
  { plugins: [probe] },
  {},
)
console.log('vitest', vitest.version ?? version)
console.log('projects:', vitest.projects.map(p => `${p.name} (root=${p.config.root}, sameServer=${p.vite === vitest.vite})`))
console.log('configureVitest called for:', called)
for (let p of vitest.projects) {
  console.log(`  ${p.name}: pool=${p.config.pool} runner=${p.config.runner ?? '(default)'} plugins=${p.vite.config.plugins.map(x => x.name).filter(n => n === 'probe').length ? 'has probe' : 'no probe'}`)
}
await vitest.close()
EOF
node "$PROBE/probe.mjs" "$FIX/node_modules/vitest/dist/node.js" "$V/mixed"
```

## Ожидаемое поведение

- Каждый проект из `vitest.projects` настраивается через `configureProject`,
  делит он корневой Vite-сервер или нет: раннер, пул, `isolate`, снапшоты,
  `checkProjectConfig`, предупреждения `config-overridden`. И каждый
  инструментируется: `transform` mootant подменяет мутанты в конвейере его
  сервера.
- Шаг 1: dry run проходит, мутант `a + b` → `a - b` получает Killed.
- Шаг 2: `npx mootant run packages --no-cache` проходит dry run, все мутанты
  Killed, score 100%. Так уже сейчас работает вариант `shared` с теми же
  пакетами.
- Шаг 3: все варианты, кроме `vmthreads-*`, проходят dry run, все мутанты
  Killed. Это касается и `mixed` с путём `packages`. `vmthreads-root` даёт ту же
  ошибку `checkProjectConfig`, что сейчас `vmthreads-shared`: «mootant needs the
  forks or threads pool; project "a" uses the vmThreads pool.»
- Если какой-то вид проектов mootant поддержать не может, он останавливается до
  dry run с ошибкой. В ней названы проект и причина (свой Vite-сервер и почему)
  и сказано, что делать, например запускать mootant из каталога пакета. Ложного
  «Tests fail without mutants» быть не должно.

## Фактическое поведение

Шаг 1 (2 из 2 прогонов, Vitest 5.0.5 из lockfile):

```
Error: Tests fail without mutants; fix them first (1 test file):
  pkg/test/add.check.ts: fails to load: The test runner did not report this file.
```

Шаг 2. `npx vitest --run` зелёный. `mootant run packages` сначала печатает
«Some tests failed; running them again without mutants to check.», затем
завершается с exit 1 и «Tests fail without mutants; fix them first … fails to
load: The test runner did not report this file.» По коду
(`core/run/run-dry-phase.ts:411-420`, `formatFailures` на `:434`) для этой
фикстуры в заголовке ожидается «(2 test files)» и по строке на
`packages/a/test/add.test.ts` и `packages/b/test/mul.test.ts`. Дословный вывод
CLI в анализе не сохранён. Прогон падает за 2–3 с и детерминированно: под root
3 из 3, под nobody (`env -i`, `TERM=xterm-256color`) 2 из 2, при load average
около 25. Значит, причина в резолве конфигурации Vitest, а не в таймингах.
`--verbose` причину не подсказывает. Запуск из `packages/a` проходит.

Шаг 3:

| Вариант | Почему у проекта свой сервер | `mootant run` сейчас |
| --- | --- | --- |
| шаг 2 (`packages/*`) | каталог-проекты | exit 1, «fails to load» |
| `shared` | сервер общий | 2 Killed, score 100% |
| `pkg-configs` | конфиги в пакетах | exit 1, «fails to load» |
| `extends-root` | `test.root` | exit 1, «fails to load» |
| `mixed`, путь `packages/b/src` | у `b` сервер общий | score 100% |
| `mixed`, путь `packages` | у `a` — `test.root` | по чтению кода — «fails to load» на тестах `a`; верификаторы этот путь не приводят |
| `alias` | `test.alias` | exit 1, «fails to load» |
| `inline-plugin` | `plugins` | exit 1, «fails to load» |

| `vmthreads-root` | `test.root` | общее «fails to load» вместо ошибки `checkProjectConfig` |
| `vmthreads-shared` | сервер общий | «mootant needs the forks or threads pool; project "a" uses the vmThreads pool.» |

Шаг 4. На смешанной схеме (`a` со своим `root`, `b` на общем сервере) оба
верификатора получили `configureVitest called for: [ 'b' ]`. Воспроизводящий
агент — этим пробником на аналогичной фикстуре, скептик — своим пробником на
`mixed`. Пробник скептика с `transform` видел только файлы `packages/b`.
Значит, проект `a` не настроен и не инструментирован. Именно эта пара
«пробник + `$V/mixed`» не запускалась. Строки `projects:` и `pool=… runner=…
plugins=…` в анализе не сохранены.

Обходные пути есть, но нигде не описаны: запуск mootant в каждом пакете или
переписывание конфига на проекты с общим сервером (только `include`). В обоих
случаях теряются настройки корневого конфига и общий отчёт.

## Подозреваемые места в коде

### Где теряется

- `adapters/vitest/start-vitest-session.ts:110` — плагин передаётся только во
  `viteOverrides`, то есть попадает только в корневой Vite-сервер. Сразу после
  `createVitest` (`:118-122`) проверяется лишь `state.error`. Прошёл ли каждый
  проект из `vitest.projects` через `configureVitest`, никто не проверяет.
- `adapters/vitest/create-mootant-plugin.ts:32-55` — `transform` и
  `configureVitest`. Они работают только в тех серверах, в Vite-конфиге которых
  есть этот плагин.
- `adapters/vitest/configure-project.ts:22-56` — настройка проекта, включая
  `checkProjectConfig` (`:30-34`).
- Vitest: `getOwnServerReason`, `inheritRootViteOverrides`, файловые проекты,
  `_attachProjectServers` (ссылки в «Контексте»).
- `adapters/vitest/run-dry.ts:203-207` и `core/run/run-dry-phase.ts:385-421` —
  здесь ненастроенный проект превращается в «fails to load», а затем в ложное
  «Tests fail without mutants».

### Как чинить (направление по чтению кода, запуском не проверено)

- Каждому проекту нужны оба слоя: (1) `configureProject` вместе с
  `checkProjectConfig` и (2) подмена мутантов в конвейере его Vite-сервера.
  Одного `configureProject` мало. Тесты пойдут по исходному тексту, файл не
  попадёт в `served`, и, по чтению кода, вместо ложной остановки получатся
  ложные NoCoverage с `never-served` (`core/run/run-dry-phase.ts:360-367`).
- Признак «проект не настроен». Запоминайте в `VitestSessionState` проекты, для
  которых вызван `configureVitest` (тип в
  `adapters/vitest/types/vitest-session-state.d.ts`, помощник тестов в
  `test/helpers/create-vitest-session-state.ts`), и после `createVitest`
  сравнивайте их с `vitest.projects`. По чтению кода равносилен признак
  `project.vite !== vitest.vite`: у проектов на корневом сервере `vite` — это
  `vitest.vite` (`index.1TqnEahn.js:6769-6776`, `:7693`, `:7708-7714`), а
  пробник шага 4 печатает его как `sameServer`. Признак по `root`
  (`project.config.root !== vitest.config.root`) **неверен**. Он пропустит
  проекты со своим сервером и общим root: `plugins`, `test.alias`,
  `test.mode`, `sharedViteServer: false`, файл-конфиг проекта в корневом
  каталоге. Typecheck-only проекты `configureProject` намеренно не трогает
  (`adapters/vitest/configure-project.ts:27-29`), считать их ошибкой не нужно.
- Доставка плагина в проекты со своим сервером. Подсказки, которые не работают
  или работают частично:
  - Хук `config` корневого плагина, дописывающий плагин в inline-проекты, не
    покрывает строковые записи `projects` (`'packages/*'`,
    `'packages/*/vitest.config.ts'`), а это самый частый случай. Кроме того,
    непустой `plugins` сам переводит inline-проект на отдельный сервер
    (`index.1TqnEahn.js:7159-7167`). Так проекты, которые сейчас делят
    корневой сервер, получат лишние Vite-серверы.
  - `injectTestProjects` (есть в контексте `configureVitest`,
    `cli-api.De07GUeT.js:12414`) добавляет новые проекты
    (`index.1TqnEahn.js:7741-7745`), а не настраивает существующие, так что
    есть риск дублей. К тому же `configureVitest` mootant вызывается только
    для проектов с его плагином. В конфигурациях, где таких проектов нет вовсе
    (шаги 1 и 2), он не вызывается ни разу.
  - Публичного способа добавить плагин во все проекты у `createVitest` нет:
    `VitestOptions` содержит только `packageInstaller`, `stdin`, `stdout` и
    `stderr` (`node_modules/vitest/dist/chunks/plugin.d.C8mmycim.d.ts:2303-2308`).

  Рабочий способ доставить `transform` в серверы таких проектов анализ не нашёл
  и не проверял. Это основная инженерная часть задачи.
- Запасной вариант. Если какой-то вид проектов поддержать нельзя, проверка после
  `createVitest` останавливает прогон с понятной ошибкой (см. «Ожидаемое
  поведение»), а ограничение описывается в `docs/content/guide/compatibility.mdx`
  рядом с `:45-54`.
- Что, видимо, править не нужно (не проверено): `vitest.invalidateFile` уже
  обходит серверы всех проектов (`cli-api.De07GUeT.js:13183-13195`), а входы
  кэша учитывают Vite-конфиг каждого проекта
  (`adapters/vitest/get-cache-inputs.ts:84`, `:130-133`).

### Тестовые помощники

- Интеграционные тесты с настоящим Vitest лежат в
  `test/adapters/vitest/index.test.ts`, фикстуры — в `test/fixtures/` (например,

  `expectAgreement` требует, чтобы среди эталонных вердиктов были и `killed`, и
  `survived` (`:204-206`): заложите в фикстуру хотя бы одного выжившего или
  сравнивайте вердикты напрямую.
- `runReferenceMutants` (`test/helpers/run-reference-mutants.ts:120-188`) по

  фикстуры нужен `separate: true` (`:145-154`): каждая копия запускается своим

  со своим `vitest.config.ts`.
- `test/helpers/classify-verdict.ts:14-16` сводит NoCoverage к `survived`.
  Поэтому совпадения с эталоном мало, отдельно проверяйте отсутствие

- `test/adapters/vitest/start-vitest-session.test.ts` подменяет `vitest/node`

## Критерий готовности

- Появляется интеграционный тест (в `test/adapters/vitest/index.test.ts` или в
  новом файле в `test/adapters/vitest/`) на новой фикстуре в `test/fixtures/`.
  Он падает до исправления и проходит после. Фикстура (одна или несколько)
  покрывает как минимум:
  - inline-проект со своим `test.root`;
  - каталог-проект из `projects: ['packages/*']` без своего конфига;
  - проект с конфигом в пакете (`packages/*/vitest.config.ts`);
  - проект с общим root, но своим сервером: непустой `plugins`, например
    `plugins: [{ name: 'noop' }]`;
  - проект, который делит корневой сервер (только `include`).

  Каталог-проект и проект с конфигом можно получить одним `projects:
  ['packages/*', …]`, если у `packages/a` конфига нет, а у `packages/b` есть
  `vitest.config.ts`. Такая конфигурация запуском не проверялась, поэтому
  сначала убедитесь, что `vitest --run` в фикстуре зелёный. Тест проверяет:
  dry run проходит; нет диагностик `never-served` и `instrument-error`; вердикты
  совпадают с `runReferenceMutants(…, { separate: true })`; в каждом проекте
  есть хотя бы один Killed и нет NoCoverage у мутантов, которые тесты убивают
  вручную.
- В проекте со своим сервером неподдерживаемая настройка (`pool: 'vmThreads'`
  при своём `test.root`) **теперь** даёт ошибку `checkProjectConfig`: «mootant
  needs the forks or threads pool; project "a" uses the vmThreads pool.». Сейчас
  вместо неё выходит общее «fails to load». Это покрыто тестом.
- Молча ненастроенных проектов нет. Каждый проект из `vitest.projects` (кроме
  typecheck-only) либо настроен и инструментирован, либо mootant
  останавливается до dry run с ошибкой, где названы проект и причина. Ветка с
  ошибкой покрыта тестом, например в `start-vitest-session.test.ts` с поддельным
  `vitest/node`. Если для какого-то вида проектов остаётся только ошибка, это
  описано в `docs/content/guide/compatibility.mdx` (раздел Vitest, `:40-54`).
- Временный тест из шага 1 проходит (`pnpm exec vitest --run
  test/repros/BUG-508.test.ts`). После проверки каталог `test/repros/` удалён.
- Шаги 2 и 3 повторены целиком после исправления: новые `pnpm build` и
  `pnpm pack`, свежий каталог `FIX`, чтобы npm не сверял новый tarball со
  старым lockfile. Результат соответствует «Ожидаемому поведению»: в шаге 2 все
  мутанты Killed и score 100%, в шаге 3 `vmthreads-root` даёт ошибку
  `checkProjectConfig`, а остальные варианты проходят. Шаг 4 для проверки
  исправления не годится: пробник показывает поведение самого Vitest со своим
  плагином, без mootant, и после исправления его вывод не меняется.
- Проверки проекта зелёные при запуске по отдельности: `pnpm test:unit` (с
  порогом покрытия 100%), `pnpm test:js`, `pnpm test:types`, `pnpm test:usage`,
  `pnpm test:spelling`, `pnpm test:format` и остальные `test:*`. `pnpm
  test:astro` запускайте без `dist/` (см. «Ограничения»). Падения, которые
  зависят от окружения (см. «Ограничения»), сверьте с прогоном на нетронутом
  коде.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.

- Тест из шага 1 нельзя копировать в `test/repros/` как есть. Этот каталог не
