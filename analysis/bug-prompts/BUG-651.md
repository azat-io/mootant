# BUG-651: `npx skills add azat-io/mootant` не находит skill — в репозитории нет `SKILL.md`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium (в анализе была high). Статус:
> подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено частично — песочница не дала
> запустить `npx skills`, но без исполнения внешнего кода подтверждено, что
> `SKILL.md` нет ни в дереве 170ec52, ни в истории upstream, ни в npm-пакете, а
> логика поиска `skills@1.7.6` на этом дереве находит 0 skill; скептик: не
> опроверг, но снизил до medium — на вердикты, score и коды выхода skill не
> влияет, отказ громкий (exit 1 с сообщением), обходной путь — документированный
> `--json` «for scripts and agents», а пакет ещё не опубликован (BUG-653).

## Контекст

Mootant позиционируется как «Mutation testing tool that ships with an agent
skill for finding and fixing weak tests» (`package.json:4`; тот же текст — в
`docs/pages/index.astro:17` и `docs/public/manifest.webmanifest:4`).
Документация предлагает поставить skill командой `npx skills add
azat-io/mootant`: раздел «Let an agent fix them» в
`docs/content/guide/getting-started.mdx:136-145` (команда — `:142`) и блок
«Ships with an agent skill» на главной `docs/components/Skill.astro:22-41`
(команда — `:39`); сессия агента — `docs/components/skill-session.ansi`. Ещё
упоминания: `docs/components/Hero.astro:30`, `docs/components/HowItWorks.astro:20`
и пункт меню «Agent skill» → `/agent-skill` в `docs/components/Header.astro:15`.
Страницы `/agent-skill` нет (это BUG-650). Сайт `https://mootant.org`
(`astro.config.ts:24`) деплоится на каждый push в `main`
(`.github/workflows/docs.yml:3-6`), так что обещание публичное.

CLI `skills` (vercel-labs/skills; ниже ссылки на `dist/cli.mjs` пакета
`skills@1.7.6`) работает так:

- Для записи `owner/repo` он клонирует репозиторий GitHub. Без клона он читает
  только репозитории владельцев vercel, vercel-labs, heygen-com и remotion-dev
  и репозиторий `zapier/connectors` (`cli.mjs:3956`, `:5454-5491`). npm-пакет
  он не читает.
- `SKILL.md` он ищет в `discoverSkills` (`cli.mjs:1381-1464`):
  - в корне и в его непосредственных подкаталогах;
  - до глубины 3 — в `skills/` (и в `skills/.curated|.experimental|.system`),
    в каталогах агентов (`.agents/skills`, `.claude/skills`, …,
    `cli.mjs:1257`), в путях из `skills.sh.json` (`cli.mjs:1094`, `:1116-1124`)
    и из `.claude-plugin/marketplace.json|plugin.json` (`cli.mjs:1037-1063`);
  - если ничего не нашлось — рекурсивно до глубины 5, пропуская
    `node_modules`, `.git`, `dist` и `build` (`cli.mjs:1250-1256`,
    `:1357-1367`, `:1452`).
- Файл принимается, если во frontmatter есть строковые непустые `name` и
  `description` (`parseSkillMd`, `cli.mjs:1312-1356`). `metadata.internal: true`
  скрывает skill (`cli.mjs:1348`).
- Если не найдено ничего, CLI печатает «No valid skills found…» и выходит с
  кодом 1 ещё до обработки `--list` (`cli.mjs:5866-5870`).

На 170ec52 в репозитории нет ни одного `SKILL.md` в любом регистре. Нет и
`skills/`, `.agents/`, `.claude/`, `.claude-plugin/`, `skills.sh.json`. По
проверке верификаторов их нет ни в одном коммите upstream и нет в npm-пакете
(`package.json:45-48`: `"files": ["./bin", "./dist"]`).

Поэтому обещанный skill недоступен, хотя в позиционировании проекта это его
главное отличие. Само мутационное тестирование при этом работает. JSON-отчёт
задокументирован «for scripts and agents» (`docs/content/guide/cli.mdx:99`,
раздел `:114-135`), и агент может повторить цикл из `skill-session.ansi` без
skill. Но готовых правил у него не будет: что делать с эквивалентными
мутантами и ignore-комментариями, почему нельзя `--fast`, какие ловушки есть
в assertion.

Образец раскладки у автора — `azat-io/ghostwriter`: файл
`skills/ghostwriter/SKILL.md` и проверка skill в CI
(`scripts/lib/skill-validation.js`). Проверка смотрит frontmatter, совпадение
`name` с именем каталога, длину меньше 500 строк, `description` до 1024
символов и то, что ссылки ведут на существующие файлы. CI-джоба запускает
`pnpm test:skill`. Это проверили верификаторы на коммите ghostwriter
`f0881dd`; при редактировании промпта не перепроверялось.

### Шаг 2. CLI `skills` на локальном клоне

Этот шаг не зависит от того, куда ушёл upstream `main`. Запускай из пустого
временного каталога, а не из клона: `add` без `--list` ставит skill в текущий

включает `--yes` (`cli.mjs:5791-5798`).

```bash

timeout 120 npx -y skills@1.7.6 add "$CLONE" --list --full-depth </dev/null; echo "exit=$?"
```

Путь должен быть абсолютным или начинаться с `./` или `../`, иначе CLI
разберёт его как удалённый источник, например `owner/repo` (`isLocalPath`,
`cli.mjs:134-136`).

Ниже черновик из анализа (`analysis/ux/SKILL.draft.md` в ветке анализа, к

````markdown
---
name: mootant
description: >-
  Finds weak tests with Mootant mutation testing and writes the tests that are
  missing. Use when the user asks to find gaps in tests, improve or harden
  tests, kill surviving mutants, raise the mutation score, or check the tests of
  changed code in a JavaScript or TypeScript project tested with Vitest 5 or
  node:test.
license: MIT
compatibility: >-
  Needs mootant installed in the project, Node.js 22.12+ with Vitest 5 or
  Node.js 20.19+ with node:test, and tests that pass.
---

# Mootant

Mootant makes small changes to the code, called mutants, and runs the tests
that reach them. A mutant that **survives** marks code whose behavior no test
checks. Your job: for each survivor, write the smallest test that passes on the
current code and fails on the mutant, then let Mootant confirm the kill.

## Before you start

1. `npx mootant --version` must print `mootant/0.1.0` or later. If Mootant is
   missing, ask the user before adding it (`npm install -D mootant`, or the
   project's package manager).
2. The tests must pass as they are; Mootant runs them without mutants first and
   stops otherwise.
3. Pick a small scope: the paths the user named, the code of the current
   branch (`--since main`, or the base branch), or one directory. A whole
   project can take minutes to hours.
4. `.mootant/` must be in `.gitignore`: it holds source code.

## 1. Find the mutants to act on

```sh
mkdir -p .mootant
npx mootant run src/cart --json > .mootant/mutants.json
```

- stdout holds only JSON; progress goes to stderr.
- Exit code 1 **with empty stdout**: the run stopped (failing tests, bad
  option, unknown id). Read stderr, fix the cause, run again.
- Exit code 1 **with JSON**: errors or a score below `--threshold`. The JSON is
  still valid.
- `mutants` lists only `Survived`, `NoCoverage` and `Error`. Per mutant:
  - `id`, `file`, `line`, `column`, `mutator`, `scope` (enclosing function)
  - `before` / `after`: the source lines without and with the change; `…`
    marks text cut from a long line
  - `testFiles`: where to add the test: an object of test files, likeliest
    first, each with the number of its tests that reach the mutant
  - `test`: a covering test to start from (`file`, `name`; `line` only when
    the runner reports it, Vitest does, `node:test` does not)
  - `recheck`: the command that runs this mutant alone
  - `message`: the reason of an `Error`
- Add `--verbose` for `original`, `replacement` and every covering test
  (`coveredBy`). Do not read a large report at once: take one file at a time,
  for example `jq '[.mutants[] | select(.file == "src/cart.ts")]'`.

## 2. Decide what each mutant needs

Read the code around `file:line` and compare `before` with `after`. Ask: is
there an input the code can get for which a caller sees a different result,
return value, thrown error or side effect?

- **No such input**: the mutant is likely equivalent. Write no test. Tell the
  user and suggest an ignore comment with the reason; do not add it yourself
  unless asked:
  `// mootant-ignore-next-line <mutator>: <why it cannot change behavior>`.
  The comment turns off every mutant of that mutator on the line, so kill the
  others on the line first and name them to the user.
- **Survived**: a test runs the code but does not check this difference.
  Usually an assertion is too weak or a boundary value is missing.
- **NoCoverage**: no test runs this code. Write a test that calls it. When
  `testFiles` is empty, create a test file next to the existing ones, named the
  way the project names them.
- **Error**: the mutant broke compilation or the runner. It is not a gap in the
  tests; report `message`.

What usually kills a mutator (each page at
`https://mootant.org/mutators/<mutator>` has a section "Kill a surviving
mutant"):

| Mutator                                   | Test                                                    |
| ----------------------------------------- | ------------------------------------------------------- |
| `comparison-operator`, `number-literal`   | The value at the boundary and right next to it          |
| `arithmetic-operator`                     | Inputs where the operators differ: not 0, 1 or equal    |
| `logical-operator`, `condition`           | Each operand alone deciding the result, both branches   |
| `return-value`, `boolean-literal`         | The exact returned value, not `toBeTruthy()`            |
| `statement-removal`, `method-call`        | The effect of the call: state, output, thrown error     |
| `string-literal`, `regex-*`               | The exact text; strings that the changed pattern splits |
| `optional-chaining`                       | `null` or `undefined` where the code allows it          |
| `missing-await`                           | The result after `await`, rejections included           |
| `object-property`, `array-element`        | The removed property or element itself                  |

## 3. Write the test

- Add it to the first file of `testFiles`, the likeliest one (or to the file of
  `test`), in the style of that file; reuse the setup of `test`.
- Assert exact values (`toBe`, `toEqual`), never only `toBeDefined()`,
  `toBeTruthy()` or a length. For errors, check the type or shape as well:
  `toThrow('text')` also passes when `undefined` is thrown; use
  `toThrow(TypeError)` or `rejects.toMatchObject({ message: 'text' })`.
- Name the test after the behavior, not the mutant id. One behavior per test.
- Do not change the source code to kill a mutant, and do not weaken, skip or
  delete existing tests, unless the user asks. Do not use snapshots: Mootant
  never writes them, so a new snapshot fails.

## 4. Confirm the kill

1. Run the new test with the project's runner, such as
   `npx vitest run test/cart.test.ts`. It must pass on the current code.
2. Run the mutant again with the `recheck` command, prefixed with `npx` and
   without `--fast`, which `recheck` repeats from a fast run:
   `npx mootant run src/cart --mutant q31p780qv6yk`. Repeat `--mutant` for
   several ids. Expect `killed`; with `--json`, `mutants` is empty.
3. Still `survived`: the test does not reach the line or does not observe the
   difference. Run the recheck with `--verbose` to see the covering tests.
4. An id stays the same while other code changes. It changes when the mutated
   text, its enclosing function or the file path changes; then run step 1
   again. Never use `--fast` to confirm a kill: its kills may be false.

## 5. Report

Run the scope once more (cached verdicts make it fast) and tell the user:

- killed mutants: id, file:line, the test you added
- mutants you judged equivalent, with the reason and the suggested comment
- mutants left, and why
- the score before and after
````

   `"testFiles": { "test/discount.test.ts": 3, … }`). Поэтому `testFiles[0]`
   даёт `undefined`. Ключи идут от самого вероятного файла.
2. «1. Find the mutants to act on», пункт `testFiles`: добавлено, что это
   объект.
3. «4. Confirm the kill», шаг 2: добавлено «without `--fast`». `recheck`
   повторяет `--fast` исходного прогона: `cli/run-mutation.ts:52-58` передаёт

   `--fast`. Сам черновик запрещает подтверждать kill с `--fast`.

Что ещё стоит знать, правя текст.

## Критерий готовности

- В git ровно один `SKILL.md` — `skills/mootant/SKILL.md`: команда
  `git ls-files | grep -iE '(^|/)skill\.md$'` печатает только его.
- Из пустого временного каталога
  `timeout 120 npx -y skills@1.7.6 add <абсолютный путь к клону> --list </dev/null`
  завершается с кодом 0 и печатает «Found 1 skill» и `mootant`. На 170ec52 та
  же команда печатает «No skills found» и выходит с кодом 1. Проверяй на
  рабочей копии до пуша: локальный путь CLI читает с диска, коммит не нужен.
  Если песочница не даёт запустить `npx skills`, так и напиши в отчёте; тогда
  опора — тест ниже, он проверяет те же условия, что `parseSkillMd`.
- Появляется тест, который падает на 170ec52 и проходит после исправления.
  Имя — например, `test/skills/mootant.test.ts`; имя и стиль — как у остальных
  тестов проекта. Тест читает `skills/mootant/SKILL.md` и проверяет:
  - frontmatter разбирается. Новая зависимость не нужна: в devDependencies
    уже есть `@astrojs/markdown-remark`. Версия 7.3.5 из lockfile
    реэкспортирует `parseFrontmatter(code)` → `{ frontmatter, content }`
    (`dist/index.d.ts:14` пакета);
  - `name === 'mootant'`, совпадает с именем каталога и подходит под
    `/^[a-z0-9-]{1,64}$/u`;
  - `description` — непустая строка не длиннее 1024 символов;
  - `metadata?.internal !== true`;
  - файл короче 500 строк;
  - все относительные ссылки ведут на существующие файлы;
  - каждая команда `mootant …` из блоков кода разбирается экспортированной
    `parseArguments` (`cli/parse-arguments.ts:243`) без `kind: 'error'`.
    Перед проверкой убери `npx` и перенаправление `> …`;
  - если `references/` генерируется из `docs/content/mutators/*.md` — что
    он не устарел.

  `parserOptions` (`cli/parse-arguments.ts:64`) не экспортирован. Не
  экспортируй его ради теста: по замечанию верификатора это заденет knip (не
  проверено). `parseArguments` уже учитывает `allowNegative: true` (`:251`:
  `--no-cache`, `--no-html`, `--no-incremental`, `--no-color`) и
  `strict: true` (`:252`: неизвестный флаг даёт `kind: 'error'`). Флаги,
  упомянутые в тексте, проверь глазами или так же через `parseArguments`.
  Учти, что строковым флагам нужно правдоподобное значение (`--threshold 80`),
  а `--skipped` для `run` даёт ошибку: он относится только к `list`.
- В тексте skill нет `testFiles[0]`, а перепроверка идёт через `npx` и без
  `--fast`.
- Желательно: на собранном пакете из шага 4 команды skill выполняются на
  `docs/demo` как написаны: `npx mootant --version`,
  `npx mootant run src --json` и команда из `recheck` одного мутанта с
  префиксом `npx`.
- Каждый скрипт по отдельности зелёный (оговорки об окружении — в
  «Ограничениях»):
  - `pnpm test:format` — Prettier проверяет и `**/*.md` (`package.json:70`);
  - `pnpm test:spelling` — cspell проверяет все файлы, кроме перечисленных в
    `cspell.config.ts:38-46`, и `skills/` в этот список не входит;
  - `pnpm test:usage`, `pnpm test:js`, `pnpm test:types`, `pnpm test:unit`;
  - `pnpm test:astro` — после `rm -rf dist`.
- Если правишь документацию (`--skill mootant`), то в обоих местах:
  `getting-started.mdx:142` и `Skill.astro:39`.
- Страница `/agent-skill` (BUG-650) в этот критерий не входит. Если делаешь её

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip, Prettier для
  Markdown.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига). Поведение CLI ради skill не меняй: `npx` в `recheck` — отдельная
  задача (BUG-652).
- Текст skill — на английском, коротко, без обещаний сверх того, что делает
  CLI.
- Сообщения коммитов — Conventional Commits (commitlint).
- Теста-воспроизведения из анализа для этого бага нет. Если по образцу других
  багов захочется положить проверку в `test/repros/`, так нельзя: этот каталог
  не исключён ни из ESLint, ни из knip, cspell или tsc. Исключён только
  `test/fixtures/**` (`eslint.config.ts:15`, `knip.config.ts:5`,
  `cspell.config.ts:44`, `vitest.config.ts:18`, `tsconfig.json:2`). Тест пиши
  в стиле проекта под строгий ESLint: имена файлов, `describe`/`it`, порядок
  импортов, JSDoc у констант и функций (пример — `test/cli/parse-arguments.test.ts`).
  Фикстуры, если понадобятся, клади в `test/fixtures/**`.
- Ставь skill (`skills add` без `--list`) только во временном каталоге, не в
  клоне: `.agents/` не в `.gitignore`. Временные каталоги, tarball,
  `.agents/` и `skills-lock.json` в коммит не входят.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: 14 ошибок
  `ts(2322)` в `docs/components/*.astro` (по данным базовой линии анализа).
  Причина: `tsconfig.json` включает `**/*.ts` и не исключает `dist/`. После
  сборки в программу попадает `dist/types/html/inline-script.d.ts` (копия
  `types/html/inline-script.d.ts`) с `/// <reference types="vite/client" />`,
  и объявления `*.svg` из Vite конфликтуют с SVG-компонентами Astro. В CI
  джоба Astro пакет не собирает, поэтому там она зелёная. После `pnpm build`
  проверяй `test:unit`, `test:js`, `test:types` и остальные скрипты по
  отдельности, а `test:astro` запускай после `rm -rf dist`.
- Известные зависимости `test:unit` от окружения, не связанные с этим багом:
  - 4 теста в `test/cli/run-list.test.ts` и `test/cli/run-mutation.test.ts`
    ждут Unicode-символы и падают при `TERM=linux`
    (`cli/terminal/is-unicode-supported.ts:13`); запускай с
    `TERM=xterm-256color`;
  - тест «skips test files it cannot read»
    (`test/adapters/node-test/score-node-test.test.ts:98`) падает под root;
  - при заданном `NODE_OPTIONS` покрытие ветвей не достигает 100% в
    `adapters/node-test/start-node-test-session.ts:119,167`; запускай с
    `env -u NODE_OPTIONS`.
