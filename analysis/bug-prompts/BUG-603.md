# BUG-603: node:test — сообщение о зависании в dry run ложно обещает учёт собственного `timeout` теста и хуков

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (заявлялась medium). Статус: подтверждён.
> Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено на Node 22.23.4 и 24.22.2 (тест с
> `{ timeout: 120_000 }` на 65 с проходит в `node --test`, а `mootant run` через
> 61–66 с даёт exit 1 с сообщением `core/run/run-dry-phase.ts:489`; `before`-хук
> на 65 с — то же с сообщением `:488`; с `--test-timeout=120000` dry run
> проходит); скептик: частично опроверг — предел 60 с и обход через
> `--test-timeout` задокументированы
> (`docs/content/guide/compatibility.mdx:74-77`), поэтому итог low: дефект —
> ложный текст сообщения без подсказки про `--test-timeout`, а чтение
> `{ timeout }` из опций `test()` и хуков — отдельное улучшение.

## Контекст

Dry run запускает тесты без мутантов под сторожем, потому что таймауты раннера
не прерывают синхронный цикл. Бюджеты ядра —
`DRY_TIMEOUTS = { file: 60_000, test: 60_000 }`, «on top of the test runner's
own timeouts» (`core/run/run-dry-phase.ts:106-114`). Контракт адаптера обещает
то же: попытка может идти `timeouts.test` мс «on top of the test's own
timeout», работа файла вне попыток — `timeouts.file` мс
(`types/adapter/dry-run-request.d.ts:11-18`). Если адаптер остановил зависший
воркер и вернул его в `DryRunResult.hung`
(`types/adapter/dry-run-result.d.ts:8-13`), ядро обрывает весь `mootant run`
(`core/run/run-dry-phase.ts:477-493`) одним из двух сообщений:

```ts
// core/run/run-dry-phase.ts:486-490
throw new Error(
  hung.name === null ?
    `Tests hang without mutants: ${display} did not finish loading or its suite hooks within ${DRY_TIMEOUTS.file / 1000} s plus the timeouts of its suite hooks, and its worker was stopped.`
  : `Tests hang without mutants: "${hung.name}" in ${display} did not finish within ${DRY_TIMEOUTS.test / 1000} s plus its own timeout and the timeouts of its hooks, and its worker was stopped.`,
)
```

Для Vitest это правда: адаптер прибавляет к бюджету попытки собственный таймаут
теста (`timeout = test.timeout > 0 ? test.timeout : Infinity`) и таймауты его
хуков (`adapters/vitest/runner.ts:989-998`,
`adapters/vitest/worker/get-hook-budget.ts:49-84`). node-test-адаптер
прибавляет только `--test-timeout` из флагов Node: срок — время последней
записи процесса плюс `--test-timeout` плюс `timeouts.test`, пока идёт попытка,
иначе `timeouts.file` (`adapters/node-test/get-dry-deadline.ts:17-28`). Флаг
читает `adapters/node-test/read-test-timeout.ts:8-20` в
`adapters/node-test/start-node-test-session.ts:196`, срок передаёт
`adapters/node-test/run-dry.ts:85-86`. Каждая новая запись процесса сдвигает
`watch.last`, сторож проверяет срок раз в 50 мс
(`adapters/node-test/run-test-process.ts:99-115`, `:133-139`). Опцию
`{ timeout }` у `test()`, `it()`, `describe()` и хуков адаптер не видит: запись
`open` попытки — `{ seq, kind, occurrence, name }`
(`adapters/node-test/preload/create-try-tracker.ts:272`), а ни `TestContext`,
ни события репортёра таймаута не несут (проверено верификатором на Node 22.23.4
и 24.22.2). JSDoc `adapters/node-test/get-dry-deadline.ts:9-10` так и пишет:
оба бюджета растут на `--test-timeout`, «the own timeout of tests and suites
that mootant can see».

Ограничение задокументировано и задумано: «Tests slower than 60 seconds need
the `--test-timeout` flag of Node.js in a `node --test` or `tsx --test` command
or in the adapter's `execArgv`, or `--timeout` in a `borp` command»
(`docs/content/guide/compatibility.mdx:74-77`). `--timeout` и `-t` команды
borp адаптер переводит в `--test-timeout`
(`adapters/node-test/resolve-command.ts:121-125`). Дефект — в сообщении. Под
node:test оно утверждает, что учтены собственный таймаут теста и таймауты
хуков, хотя они не учтены, и не подсказывает `--test-timeout`: ни одно
сообщение в `adapters/`, `core/` и `cli/` этот флаг не упоминает. Пользователь,
чей тест с `{ timeout: 120_000 }` проходит в `node --test`, через минуту
получает exit 1 и ищет зависание, которого нет. Совет «увеличь таймаут теста»
ему тоже не поможет: `{ timeout }` node-test-адаптер не видит, помогает только
`--test-timeout`. Вердикты при этом не искажаются: прогон падает громко, с
именем теста и файла, а с `--test-timeout` всё работает.

## Воспроизведение

Автоматического теста-воспроизведения нет: в ветке анализа
`experiment/bug-repros` (в публичном репозитории её нет) для BUG-603 не было ни
теста, ни фикстуры. Ниже фикстуры верификаторов: исходники дословно, в
`package.json` нет только `devDependencies`, их добавляет `npm i`. Фикстура A —
та же, что в исходном анализе, верификатор прогнал её как есть. Всё создаётся во
временных каталогах и в коммит не входит (см. «Ограничения»).

Проверялось только на Linux: Node 22.23.4 (все фикстуры) и 24.22.2 (фикстура
A), npm 10.9.9. node:test-адаптер поддерживает и Node 20.19+, там не проверено.
Контролю D на Vitest 5 нужен Node 22.12+
(`docs/content/guide/compatibility.mdx:22-24`). Для сборки mootant нужен pnpm
12 (в CI — `latest-12`, `.github/actions/install-tools/action.yml:14`). По
наблюдению анализа pnpm 10.28 не понимает `configDependencies` из
`pnpm-workspace.yaml` и внутри репозитория зависает даже на `pnpm --version`.
Команды рассчитаны на одну сессию shell с переменными `TGZ`, `BUG` и `A`.

### Шаг 1. Собрать и упаковать mootant

`bin/mootant.js` импортирует `../dist/cli/index.js` (`bin/mootant.js:3`),
поэтому нужна сборка.

```bash
# в корне чистого клона azat-io/mootant
pnpm install
pnpm build
pnpm pack                          # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"      # *.tgz нет в .gitignore, не оставляй его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"
```

### Шаг 2. Фикстура A: тест со своим `{ timeout: 120_000 }`

```bash
BUG="$(mktemp -d)"
A="$BUG/node"
mkdir -p "$A/src" "$A/test" && cd "$A"
cat > package.json <<'EOF'
{ "name": "bug603", "private": true, "type": "module", "scripts": { "test": "node --test" } }
EOF
cat > src/price.js <<'EOF'
export function isFree(price) {
  return price <= 0
}
EOF
cat > test/slow.test.js <<'EOF'
import { it } from 'node:test'
import assert from 'node:assert/strict'

import { isFree } from '../src/price.js'

it('waits 65 s, then checks', { timeout: 120_000 }, async () => {
  await new Promise(resolve => setTimeout(resolve, 65_000))
  assert.equal(isFree(0), true)
})
EOF
echo "export default { run: { paths: ['src'], runner: 'node-test', cache: false } }" > mootant.config.js
npm i -D "$TGZ"

node --test; echo "plain exit=$?"              # exit 0 за ~65 с
npx mootant run src; echo "mootant exit=$?"    # exit 1 за 61–66 с
```

### Шаг 3. Контроли (по желанию)

Каждый из трёх мутантов `src/price.js` тоже ждёт 65 с, поэтому полный прогон
контроля, прошедшего dry run, длится около 4,5 мин. С одним мутантом — около
2,3 мин: добавь `--mutant fmk4` (так скептик запускал контроли B и B′ на
170ec52, мутант убит, score 100%). Если id у тебя другой, возьми его из
`npx mootant list src`.

**B — различающий контроль и задокументированный обход.** Тот же тест, но с
`--test-timeout` в команде. Dry run проходит, значит адаптер читает флаг, но не
опцию `{ timeout }`.

```bash

```

**B′ — то же через `execArgv` адаптера.** `scripts.test` остаётся
`node --test`, а `mootant.config.js` такой:

```js

  run: {
```

Через `NODE_OPTIONS` флаг не передать: Node отвечает
`--test-timeout= is not allowed in NODE_OPTIONS` (наблюдение скептика).

**C — `before`-хук на 65 с со своим `{ timeout: 120_000 }`** (сообщение
`core/run/run-dry-phase.ts:488`). `after`-хук и `beforeEach`/`afterEach` дольше
60 с не проверялись.

```bash

EOF
npm i -D "$TGZ"
node --test; echo "plain exit=$?"              # exit 0 за ~65 с
npx mootant run src; echo "mootant exit=$?"    # exit 1 за ~62 с
```

**D — контроль Vitest.** Тот же тест на Vitest 5 проходит dry run: адаптер
Vitest учитывает собственный таймаут теста.

## Ожидаемое поведение

Сам обрыв теста или хука дольше 60 с под node:test без `--test-timeout` —
задокументированное ограничение (`docs/content/guide/compatibility.mdx:74-77`),
а не ошибка. Ожидается:

- Сообщение о зависании под node:test не утверждает, что учтены собственный
  `timeout` теста и таймауты хуков. Оно называет фактически применённый бюджет
  (60 с плюс `--test-timeout`, если он задан) и подсказывает задокументированный
  обход: `--test-timeout` в команде `node --test` или `tsx --test` либо в
  `nodeTestAdapter({ execArgv })`, `--timeout` в команде `borp`.
- То же для сообщения о файле вне тестов: загрузка и хуки наборов,
  `core/run/run-dry-phase.ts:488`.
- Под Vitest сообщение остаётся верным по смыслу: там собственный таймаут и
  таймауты хуков действительно входят в бюджет.
- С `--test-timeout=120000` в команде или в `execArgv` dry run проходит, как и
  сейчас.

Отдельное улучшение, а не часть этого бага: node-test учитывает явный
`{ timeout }` теста, набора и хука, как Vitest. Тогда фикстура A проходит dry
run, а `docs/content/guide/compatibility.mdx:74-77` нужно переписать.

## Подозреваемые места в коде

- `core/run/run-dry-phase.ts:486-490` — оба текста обещают учёт собственного
  таймаута и таймаутов хуков при любом адаптере; JSDoc `:106-113` говорит то
  же. Главное место исправления. В `core/` сейчас нет ни одного упоминания
  Vitest или node:test, поэтому текст для конкретного раннера должен прийти из
  адаптера.
- `types/adapter/dry-run-result.d.ts:8-13` (`hung`) и
  `types/adapter/dry-run-request.d.ts:11-18` (`timeouts`, «on top of the test's
  own timeout») — контракт, который node-test выполняет лишь частично. Оба типа
  публичные: их экспортирует `core/index.ts:18`, `:20`, а это точка входа `"."`
  в `exports` `package.json`.
- `adapters/node-test/get-dry-deadline.ts:17-28` (JSDoc `:9-10`),
  `adapters/node-test/read-test-timeout.ts:8-20`,
  `adapters/node-test/types/node-test-handle.d.ts:34-37` (`testTimeout`),
  `adapters/node-test/start-node-test-session.ts:196`,
  `adapters/node-test/run-dry.ts:85-86` — откуда берётся бюджет node-test.
  Здесь адаптер знает фактический `--test-timeout` и может сам сформулировать
  бюджет и подсказку. Запись `hung` node-test собирает в
  `adapters/node-test/build-dry-file.ts:114` и кладёт в результат в
  `adapters/node-test/run-dry.ts:140-142`; у Vitest —
  `adapters/vitest/run-dry.ts:71`.
- `adapters/node-test/preload/create-try-tracker.ts:233-276` — `open`, его
  вызывает корневой `beforeEach` в
  `adapters/node-test/preload/preload.ts:74-76`. Запись `open` (`:272`) идёт без
  таймаута; сюда его пришлось бы добавить при улучшении.
- `adapters/node-test/preload/create-report-reader.ts:40-78` — читает только
  `test:start`, `test:pass` и `test:fail`.
- `docs/content/guide/compatibility.mdx:74-77` — документированное ограничение.
- Для сравнения: `adapters/vitest/runner.ts:989-998`,
  `adapters/vitest/worker/get-hook-budget.ts:49-84`.

### Направление исправления

Минимум, который закрывает BUG-603, — правдивое сообщение с подсказкой.

- Адаптер даёт свою часть фразы, ядро её печатает. Готовый образец есть в том
  же типе: `DryRunResult.unserved` (`types/adapter/dry-run-result.d.ts:15-22`).
  Адаптер передаёт окончание фразы (node-test — константу `REQUIRED_ESM`,
  `adapters/node-test/run-dry.ts:23-24`, `:151-154`), а ядро без него печатает
  общий текст (`core/run/run-dry-phase.ts:347-365`). Так же может работать
  необязательное поле у записи `hung`: node-test кладёт в него фактический
  бюджет и подсказку про `--test-timeout`, Vitest — нынешнюю формулировку, а
  без поля ядро печатает нейтральный текст. Это добавление в публичный тип. Оно
  ничего не ломает, но меняет `types/`, поэтому компромисс опиши (см.
  «Ограничения»). Имя поля и формулировку выбери сам; этот вариант не
  проверялся.
- Нейтральный текст в ядре без подсказки убирает ложь, но пользователь
  node:test так и не узнает, что помогает только `--test-timeout`. Общий совет
  «увеличь таймаут теста» уводит его к `{ timeout }`, который не работает.
  Поэтому одного нейтрального текста мало.
- Брать формулировку из `DryRunResult.hung` — тоже изменение публичного типа,
  делай его осознанно, как описано выше.
- Ядро печатает `DRY_TIMEOUTS` (`core/run/run-dry-phase.ts:488-489`), даже когда
  тест подменяет бюджеты через `shortenDryRuns`
  (`test/helpers/shorten-dry-runs.ts`). Учитывай это в проверках точного текста.

Улучшение — отдельная задача, для закрытия BUG-603 оно не требуется. Если
берёшься учитывать явный `{ timeout }`:

- Путь через события репортёра или `TestContext` не работает. На Node 22.23.4 и
  24.22.2 у `TestContext` нет поля с таймаутом, в событиях `test:enqueue`,
  `test:dequeue`, `test:start` и `test:pass` его тоже нет (проба верификатора).
- Рабочий путь (проба верификатора в собственном `--import`-preload на тех же
  версиях): взять экспорты через `createRequire(…)('node:test')`, заменить их
  обёртками, которые читают `options.timeout`, и вызвать
  `syncBuiltinESMExports()` из `node:module`. Тогда ESM-импорт
  `import { it } from 'node:test'` в тестах видит обёртку; обёртка `it` видела
  `options.timeout = 120000`. Preload mootant грузится первым `--import` или
  `--require` (`adapters/node-test/preload/preload.ts:25-29`) и уже держит
  `node:module` как `moduleApi` и свой `require` (`:4`, `:73`). Как сопоставить
  таймаут с попыткой (`open` знает только `context.fullName`), не проверено.
- Покрыть всё, через что задаётся таймаут: `test` и `it`, `describe` и `suite`,
  их `.only`, `.skip`, `.todo`, свойства `test.it`, `test.describe` и т. п.,
  `t.test()`, хуки на контексте (`t.before`, `t.beforeEach`, …),
  `before`/`after`/`beforeEach`/`afterEach` модуля, в том числе
  `beforeEach`/`afterEach` внутри попытки. По
  `node_modules/@types/node/test.d.ts` (`TestOptions.timeout`,
  `HookOptions.timeout`) таймаут по умолчанию — `Infinity`, а без явного
  значения подтест наследует таймаут родителя.
- Тест без явного `timeout` сохраняет нынешний бюджет: 60 с плюс
  `--test-timeout`. Семантику Vitest `timeout > 0 ? timeout : Infinity`
  (`adapters/vitest/runner.ts:990`) переносить нельзя: в node:test таймаут по
  умолчанию `Infinity`, и сторож отключился бы для всех тестов без явного
  таймаута. Отдельный «безопасный верхний предел» не нужен: без явного таймаута
  поведение не меняется.
- Бюджеты в тестах задаются через `DryRunRequest.timeouts` (обёртка
  `shortenDryRuns`). Внедрять в тесты `DRY_TIMEOUTS` ядра не нужно.
- После улучшения перепиши `docs/content/guide/compatibility.mdx:74-77` и JSDoc
  `adapters/node-test/get-dry-deadline.ts:9-10`.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  `DryRunRequest` и `DryRunResult` публичные (`core/index.ts:18`, `:20`). Новое
  необязательное поле — добавление, а не поломка, но его всё равно опиши. Смысл
  существующих полей не меняй.
- Не ослабляй сторож: тест node:test без явного `timeout` должен по-прежнему
  останавливаться через 60 с плюс `--test-timeout`.
- Держи `core/` независимым от раннера: сейчас в нём нет упоминаний Vitest или
  node:test.
- Теста-воспроизведения для BUG-603 в анализе нет. Если пишешь тест по
  фикстурам из «Воспроизведения», не клади их как есть в `test/repros/`, а
  перепиши в стиле проекта. Каталог `test/repros/` не исключён ни из ESLint, ни
  из knip, cspell, Vitest и `tsc`; исключён только `test/fixtures/**`
  (`eslint.config.ts:15`, `knip.config.ts:5`, `cspell.config.ts:44`,
  `vitest.config.ts:18`, `tsconfig.json:2`). Строгий ESLint
  (`@azat-io/eslint-config` с perfectionist и vitest, `eslint.config.ts:6-12`)
  проверяет имена файлов, `describe`/`it` и порядок импортов. Фикстуры клади в
  `test/fixtures/**`, для node:test — рядом с `test/fixtures/node-test/stuck`.
  Tarball и временные каталоги в коммит не входят.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`, по
  наблюдению анализа 14 ошибок `ts(2322)` в `docs/components/*.astro`.
  `tsconfig.json:2-4` включает `**/*.ts` и не исключает `dist/`. После сборки

  `test:js`, `test:types` и остальные `test:*` по отдельности, а `test:astro`
  запускай после `rm -rf dist`.
