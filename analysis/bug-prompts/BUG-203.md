# BUG-203: необработанная ошибка, которую конфигурация Vitest велит игнорировать, всё равно убивает мутанта

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест на Vitest 5.0.5 падает
> как описано: `vitest run` с мутантом даёт exit 0, а вердикт Mootant —
> `['Killed', 'stray-error']`; на фикстурах с нуля с упакованным mootant и
> Vitest 5.1.0 ложный `Killed (stray-error)` повторился 3 из 3 по умолчанию и
> 2 из 2 с `--fast` для обеих настроек, а контроль без настроек согласован с
> Vitest); скептик: не опроверг, medium — нижняя граница: ошибка оптимистичная
> (ложный `Killed` завышает score), но обе настройки редки
> (`dangerouslyIgnoreUnhandledErrors` примерно в 0,1% конфигов Vitest на
> GitHub, `onUnhandledError` обычно узко фильтрует по сообщению).

## Контекст

Воркер-раннер Mootant для Vitest сам подписывается на `unhandledRejection` и
`uncaughtException` процесса (`adapters/vitest/runner.ts:1249-1267`,
`process.on` на `:1261-1262`, вызов из конструктора раннера на `:483`) и
записывает каждую такую ошибку как stray-ошибку текущей попытки или юнита
(`onStray`, `:665-686`). На isolated-пути stray-ошибка в попытке, которая
достигла мутанта, — убийство с причиной `stray-error`
(`core/run/classify-try.ts:34-38`; по тестам —
`core/run/read-isolated-unit.ts:46-63`, на уровне юнита — `:93-105`).
Исключение одно: тесты и тест-файлы, у которых stray-ошибки были уже в dry run
(`core/run/read-dry-run.ts:48-50`, `:71-74` → `read-isolated-unit.ts:48`,
`:96`).

Проваливают ли такие ошибки прогон, в Vitest решают две настройки.
`dangerouslyIgnoreUnhandledErrors` меняет только код выхода
(`node_modules/vitest/dist/chunks/cli-api.De07GUeT.js:13199`). Фильтр
`onUnhandledError` отбрасывает ошибку, для которой вернул `false`: она не
попадает в необработанные ошибки прогона и не печатается (`:10868`). Mootant
эти настройки не читает: ни одного из двух слов нет в `adapters/`, `core/`,
`cli/`, `types/`, `docs/` и `test/`. Поэтому обычный `vitest run` такого
проекта с физически вписанным мутантом проходит (exit 0), а Mootant пишет
`Killed`. Это ложное убийство в режиме по умолчанию. Ошибка оптимистичная: она
завышает score и прячет как раз ту дыру в тестах, которую проект скрыл
настройкой. На фикстуре шага 2 score 66.67 вместо 33.33 у ручной проверки. В
нестабильном эксперименте скептика шум при teardown, которого не было в dry run
(`read ECONNRESET`), при `dangerouslyIgnoreUnhandledErrors` убил двух
посторонних выживших и поднял score с 40 до 80, хотя `vitest run` завершался с
exit 0.

Документация обещает обратное: «runs your tests. If they still pass, the mutant
survives» (`readme.md:27-29`), «using your project's test configuration»
(`readme.md:53-54`), «its configuration»
(`docs/content/guide/compatibility.mdx:42-43`). В списке неподдерживаемых
настроек Vitest (`compatibility.mdx:47-54`) этих двух нет.

Номера строк Vitest в этом промпте даны для версии 5.0.5 из `pnpm-lock.yaml`.
`npm i -D vitest@5` сейчас ставит 5.1.0: там тот же код лежит в
`cli-api.COfZo8lK.js:11349` (фильтр) и `:13745` (код выхода), поведение то же.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создайте
сами. Нужны Node.js 22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:23-24`) и pnpm 12: в CI стоит
`latest-12` (`.github/actions/install-tools/action.yml`), а pnpm 10 не читает
`configDependencies` из `pnpm-workspace.yaml:1-2`, и даже `pnpm --version`
внутри репозитория у него зависает. Команды шага 2 рассчитаны на одну сессию
shell: они используют переменные `PACK`, `TGZ`, `FIX` и функцию `show`.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Без `dist/` адаптер берёт воркер-раннер из исходника `runner.ts`
(`adapters/vitest/get-runner-path.ts:12-15`). Тест фикстуры назван
`*.check.js`, а `test/fixtures/**` исключён из корневого Vitest
(`vitest.config.ts:18`), так что корневой прогон фикстуру не подхватит. Все
файлы временные и в коммит не входят (см. «Ограничения»).

```bash

pnpm install
mkdir -p test/fixtures/repros/BUG-203/src test/fixtures/repros/BUG-203/test test/repros

cat > test/fixtures/repros/BUG-203/package.json <<'EOF'
{
  "name": "bug-203",
  "private": true,
  "type": "module"
}
EOF

cat > test/fixtures/repros/BUG-203/vitest.config.js <<'EOF'
export default {
  test: {
    include: ['test/**/*.check.js'],
    dangerouslyIgnoreUnhandledErrors: true,
  },
}
EOF

cat > test/fixtures/repros/BUG-203/src/events.js <<'EOF'
export function emitLater(listener) {
  setTimeout(() => {
    if (listener) {
      listener()
    }
  }, 0)
  return true

EOF

cat > test/fixtures/repros/BUG-203/test/events.check.js <<'EOF'
import { expect, test } from 'vitest'

import { emitLater } from '../src/events.js'

test('emits without a listener', async () => {
  expect(emitLater(undefined)).toBe(true)

cat > test/repros/BUG-203.test.ts <<'EOF'
import { writeFile, readFile, mkdtemp, cp, rm } from 'node:fs/promises'
import { describe, expect, it } from 'vitest'
import { execFile } from 'node:child_process'
import { createRequire } from 'node:module'
import { tmpdir } from 'node:os'
import path from 'node:path'

import type { Mutant } from '../../types/mutant/mutant'

import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { applyMutant } from '../helpers/apply-mutant'
import { runMutants } from '../../core/run-mutants'

/**
 * Fixture project with `dangerouslyIgnoreUnhandledErrors: true`: forcing the
 * `if (listener)` test to `true` makes the timer call `undefined`, an uncaught
 * error that Vitest reports and, by that setting, does not fail the run for.
 */
let root = path.join(import.meta.dirname, '../fixtures/repros/BUG-203')

/**
 * Runs plain `vitest run` on a copy of the fixture with the mutant applied.
 *
 * @param mutant - Mutant to apply.
 * @returns Exit code of Vitest.
 */
async function runPlain(mutant: Mutant): Promise<number> {
  let directory = await mkdtemp(path.join(tmpdir(), 'bug-203-'))
  try {
    await cp(root, directory, { recursive: true })
    let file = path.join(directory, mutant.file)
    await writeFile(file, applyMutant(await readFile(file, 'utf8'), mutant))
    let vitest = createRequire(import.meta.url).resolve('vitest/package.json')
    let bin = path.join(path.dirname(vitest), 'vitest.mjs')
    return await new Promise(resolve => {
      execFile(process.execPath, [bin, 'run', '--root', directory], error => {
        resolve(error === null ? 0 : Number(error.code ?? 1))
      })
    })
  } finally {
    await rm(directory, { recursive: true, force: true })
  }
}

describe('BUG-203: an unhandled error that the Vitest configuration ignores kills the mutant', () => {
  it('lets dangerouslyIgnoreUnhandledErrors keep the mutant alive', { timeout: 300_000 }, async () => {
    let result = await runMutants({
      builtIns: createBuiltIns('vitest', vitestAdapter()),
      concurrency: 2,
      paths: ['src'],
      cache: false,
      cwd: root,
    })
    let source = await readFile(path.join(root, 'src/events.js'), 'utf8')
    let forced = result.results.find(
      ({ mutant }) =>
        source.slice(mutant.start, mutant.end) === 'listener' &&
        mutant.replacement === 'true',
    )!
    await expect(runPlain(forced.mutant)).resolves.toBe(0)

    // Actual: `Killed` with cause `stray-error`.
    expect([forced.status, forced.cause]).toStrictEqual(['Survived', null])
  })
})
EOF

pnpm exec vitest run test/repros/BUG-203.test.ts
```

Что делает тест. `runMutants` с одним адаптером Vitest (`concurrency: 2`,
`paths: ['src']`, `cache: false`) решает мутантов фикстуры. Среди них тест
находит мутанта `if (listener)` → `if (true)` по условию
`source.slice(mutant.start, mutant.end) === 'listener' && mutant.replacement === 'true'`.
Затем `runPlain` копирует фикстуру во временный каталог, вписывает туда мутанта
хелпером `applyMutant` (`test/helpers/apply-mutant.ts:52-62`, так, как его
разместит переключатель мутантов) и запускает обычный `vitest run --root
<копия>` через `vitest.mjs` установленного пакета. Тест ждёт код выхода 0, а
затем `['Survived', null]` для `[status, cause]`. Хелперы
`test/helpers/apply-mutant.ts` и `test/helpers/create-built-ins.ts` есть в
170ec52.

### Шаг 2. CLI на упакованном mootant: обе настройки и оба вида ошибки

Фикстура взята из анализа. `emitLater` при мутанте `listener` → `true` бросает
из таймера (`uncaughtException`). `settle` при мутанте `value !== null` →
`false` оставляет отказ промиса без обработчика (`unhandledRejection`,
«settled late»): тест шага 1 этот случай не покрывает. `bin/mootant.js`
импортирует `../dist/cli/index.js`, поэтому для CLI нужна сборка. Ставьте
`vitest@5` (сейчас это 5.1.0), а не `vitest@5.0.5`: в npm 10.9.9 установка
5.0.5 падает с `Cannot read properties of null (reading 'edgesOut')`. Это баг
arborist, не mootant.

```bash

pnpm pack                        # пишет mootant-0.1.0.tgz в корень клона

TGZ="$PACK/mootant-0.1.0.tgz"

FIX="$(mktemp -d)"
mkdir -p "$FIX/src" "$FIX/test"
cat > "$FIX/package.json" <<'EOF'
{ "name": "vt-unhandled", "private": true, "type": "module", "scripts": { "test": "vitest run" } }
EOF
cat > "$FIX/vitest.config.js" <<'EOF'
import { defineConfig } from 'vitest/config'
export default defineConfig({
  test: {
    include: ['test/**/*.test.js'],
    dangerouslyIgnoreUnhandledErrors: true,
  },
})

export function emitLater(listener) {
  setTimeout(() => {
    if (listener) {
      listener()
    }

export function settle(value) {
  let failed = Promise.reject(new Error('settled late'))

    failed.catch(() => {})

EOF
cat > "$FIX/test/events.test.js" <<'EOF'

EOF

npm i -D vitest@5 "$TGZ"
npx vitest run; echo "exit=$?"   # без мутантов: 2 passed, exit=0
npx mootant run src --json --all --verbose --no-cache > default.json
npx mootant run src --json --all --verbose --no-cache --fast > fast.json
show default.json
show fast.json

# ручная проверка двух мутантов (GNU sed): вписать, прогнать vitest, вернуть файл
cp src/events.js "$PACK/events.js"
sed -i 's/if (listener)/if (true)/' src/events.js
npx vitest run; echo "exit=$?"   # exit=0: «Errors 1 error», но «Test Files 1 passed»
cp "$PACK/events.js" src/events.js
sed -i 's/if (value !== null)/if (false)/' src/events.js
```

## Ожидаемое поведение

Вердикт Mootant совпадает с обычным `vitest run` того же проекта с вписанным
мутантом:

- `dangerouslyIgnoreUnhandledErrors: true`: Vitest печатает «Unhandled Errors …
  Uncaught Exception … TypeError: listener is not a function», но завершается с
  кодом 0 (`Test Files 1 passed`, `Errors 1 error`). Значит, `listener` →
  `true` и `value !== null` → `false` — `Survived` с `cause: null`.
- `onUnhandledError() { return false }`: Vitest об ошибке не печатает ничего и
  завершается с кодом 0. Вердикт тот же — `Survived`.
- В `--fast` итог тот же, и проигнорированная ошибка не делает batch-попытку
  сомнительной: у мутанта `isolatedBecause: "batch-survivor"`, как сейчас у
  `listener` → `false` (`t824tj2rg579`), а не `"doubtful"`.
- Сводка шага 2 для обоих конфигов: `totalKilled: 2`, `totalSurvived: 4`,
  `score: 33.33`.
- Без этих настроек или с фильтром, который эту ошибку не отбрасывает,
  `vitest run` с мутантом завершается с кодом 1, и Mootant по-прежнему даёт
  `Killed (stray-error)`. Исключение тестов и файлов, у которых stray-ошибки
  были уже в dry run, сохраняется. В варианте скептика тест сам делает
  `Promise.reject(new Error('noise from a third-party lib'))`, и мутант
  `listener` → `true` уже сейчас `Survived`.

## Фактическое поведение

Шаг 1: проверка `runPlain(...)` → `0` проходит, тест падает на последнем
`expect`. Суть диффа Vitest:

```
- [ "Survived", null ]
+ [ "Killed", "stray-error" ]
```

Шаг 2, данные анализа (Vitest 5.0.5; у скептика на 5.1.0 для `listener` →
`true` так же):

- `dangerouslyIgnoreUnhandledErrors: true`, по умолчанию. `knkyemhs7jf6`
  (`listener` → `true`): `Killed`, `cause: "stray-error"`, `path: "isolated"`,
  `message: "listener is not a function"`, `killedBy` — тест «emits without a
  listener». `7mkvyn7b1260` (`value !== null` → `false`): `Killed`,
  `stray-error`, `message: "settled late"`. Сводка: `totalKilled: 4`,
  `totalSurvived: 2`, `score: 66.67`.
- То же с `--fast`: оба мутанта `Killed (stray-error)`, `path: "isolated"`,
  `isolatedBecause: "doubtful"`. Batch-попытка со stray-ошибкой стала
  сомнительной, а isolated-перезапуск убил мутанта. Сводка та же.
- `onUnhandledError() { return false }`, по умолчанию: оба мутанта
  `Killed (stray-error)`, сводка та же. С `--fast` скептик получил `Killed` в
  2 из 2 прогонов на фикстуре только с `emitLater`.
- Ручная проверка обоих мутантов в обоих конфигах даёт exit 0. Остальные четыре
  мутанта с ней совпадают: `listener` → `false` и `value !== null` → `true`
  выживают, `true` → `false` в `emitLater` и `value` → `undefined` в `settle`
  убиты (`assertion`).

## Подозреваемые места в коде

Где рождается вердикт:

- `adapters/vitest/runner.ts:1249-1267` (`listenForStrays`; `process.on` на
  `:1261-1262`, вызов из конструктора раннера на `:483`) и `:665-686`
  (`onStray`). Воркер ловит ошибки сам и записывает их без учёта настроек
  проекта. Записывается только текст (`getErrorMessage`, `:666`). В batch без
  активной попытки ошибка уходит как поздняя (`kind: 'late'`, `:672-682`), вне
  попыток — в `loadStrays` (`:684`).
- `core/run/classify-try.ts:34-38`: stray-ошибка в isolated-попытке, которая
  достигла мутанта, даёт `killed`/`stray-error`, в batch — `doubtful`. В этом
  репро мутант убивается в цикле по тестам
  `core/run/read-isolated-unit.ts:46-63` (в отчёте `killedBy` — тест). Ошибка
  после теста убила бы его на уровне юнита (`:93-105`). Исключения из dry run —
  `:48` (`strayTests`) и `:96` (`strayFiles`); их заполняет
  `core/run/read-dry-run.ts` (`:71-74` и `:48-50`).
- В `--fast` цепочка такая: batch-попытка со stray-ошибкой → `doubtful`
  (`classify-try.ts:34-38`) → `core/run/apply-batch-result.ts:158-159` (поздние
  ошибки — `:278-287`) → isolated-перезапуск с `isolatedBecause: 'doubtful'` →
  `Killed (stray-error)`. Batch решает только убийства и таймауты, остальные
  мутанты уходят в isolated как `batch-survivor` или `doubtful`
  (`core/run/run-batch-phases.ts:37-39`, `:91-97`). Поэтому итоговый вердикт и
  в `--fast` выносит isolated-путь.

Где вердикт не рождается (это важно для дизайна исправления):

- `adapters/vitest/run-specifications.ts:43` берёт `result.unhandledErrors`
  главного процесса, а `run-plan.ts:107-113` и `:142` передают его дальше как
  `error`. Но `run-isolated.ts:35-59` его не читает вовсе, а
  `run-batch.ts:77-82` использует только как текст сообщения о `crash` (`:79`).
- Кроме того, воркер Vitest не пересылает ошибку в главный процесс, если у
  события есть ещё слушатель: `node_modules/vitest/dist/chunks/init.PvxYpuCm.js:98-108`,
  проверка `processListeners(event).length > 1` на `:102` (в 5.1.0 — та же
  строка `init.CO4AB7HZ.js:102`). Слушатель Mootant в воркере есть всегда.
  Значит, в прогонах Mootant ошибки кода пользователя, по-видимому, вообще не
  доходят до `onUnhandledError` и `unhandledErrors` главного процесса. Это вывод
  из чтения кода, запуском он не проверен. Вызывать фильтр на `unhandledErrors`
  в `run-specifications.ts:43`, как предлагала прежняя версия промпта, поэтому
  не получится.

Что учесть при исправлении (варианты ниже выведены из чтения кода, запуском не
проверены):

- `dangerouslyIgnoreUnhandledErrors` — корневая настройка: в Vitest 5.0.5 она
  входит в `NonProjectOptions`
  (`node_modules/vitest/dist/chunks/plugin.d.C8mmycim.d.ts:4492`), и сам Vitest
  читает её у своего экземпляра (`this.config.dangerouslyIgnoreUnhandledErrors`,
  `cli-api.De07GUeT.js:13199`). `configureProject`
  (`adapters/vitest/configure-project.ts:22-56`) работает с конфигурацией
  отдельного проекта, поэтому надёжнее читать корневую, например
  `handle.vitest.config`. Передать флаг воркерам можно вместе с остальными
  опциями `vitest.provide('mootant', …)` (`run-specifications.ts:35-39`, тип
  `VitestWorkerOptions` — `adapters/vitest/types/vitest-worker.d.ts:193-221`).
  Через эту функцию идут и dry run (`adapters/vitest/run-dry.ts:85`), и
  batch/isolated (`run-plan.ts:109`).
- `onUnhandledError` — функция корневой конфигурации. Vitest отдаёт её в
  `StateManager` (`cli-api.De07GUeT.js:12312`) и вызывает в `catchError`
  (`:10868`) на сериализованной ошибке с полем `type` (`'Uncaught Exception'`
  или `'Unhandled Rejection'`: `init.PvxYpuCm.js:110-111`,
  `cli-api.De07GUeT.js:10852`) и полями `VITEST_TEST_NAME`/`VITEST_TEST_PATH`
  (`init.PvxYpuCm.js:104-107`). Через `vitest.provide` функцию не передать.
  Возможный вариант: воркер сохраняет не только текст, а достаточно полей ошибки
  (имя, сообщение, стек, `type`), а главный процесс отбрасывает stray-ошибки, для
  которых фильтр вернул `false`, там, где собирает факты:
  `adapters/vitest/build-isolated-facts.ts:28-30` и `:54` (isolated),
  `adapters/vitest/run-batch.ts:41-45` (batch-попытки и поздние ошибки),
  `adapters/vitest/run-dry.ts:153-159` и `:168-172` (dry run). Ошибки уже
  привязаны к попытке в воркере, так что сопоставлять их с асинхронным RPC
  Vitest не нужно.
- JSDoc `types/run/try-cause.d.ts:5-6` (`stray-error` — «an unhandled error»
  без оговорок) и `core/run/classify-try.ts:5-14` обновите под новую семантику.
  В `docs/content/guide/compatibility.mdx` (раздел Vitest, `:40-59`) опишите,
  как Mootant учитывает эти настройки.
- Флаг `--dangerouslyIgnoreUnhandledErrors` в команде `vitest run` из
  npm-скрипта адаптер не увидит и после исправления: скрипты он читает только
  для выбора раннера (`adapters/vitest/score-vitest.ts:22-28`, чтение на
  `:23`). Опишите это как ограничение.
- Ключ кэша уже включает файлы конфигурации Vitest
  (`adapters/vitest/get-cache-inputs.ts:47`) и версию со сборкой mootant
  (`core/cache/get-environment-key.ts:59-65`). Решите, нужна ли новая
  настройка в `describeProjectSettings` (`get-cache-inputs.ts:76-114`).
- Тестовый эталон `test/helpers/run-reference-mutants.ts` в режиме
  `separate: true` запускает `PLAIN_RUN_SCRIPT` (`:57-73`), который считает
  провалом `vitest.state.getUnhandledErrors().length > 0` (`:68-70`). При
  `dangerouslyIgnoreUnhandledErrors` ошибка в этом списке остаётся (настройка
  меняет только код выхода), и эталон тоже говорит «убит», то есть этот баг не
  ловит. При `onUnhandledError → false` список уже отфильтрован, и эталон даёт
  `failed: false`, как Vitest (проверено верификатором). В общем режиме эталон
  пишет свою конфигурацию (`DEFAULT_CONFIG`, `:78-79`, запись на `:155-158`), и
  настройки проекта в нём не участвуют. Если сверяете новый тест с эталоном,
  научите `PLAIN_RUN_SCRIPT` учитывать `dangerouslyIgnoreUnhandledErrors` или
  сравнивайте с кодом выхода `vitest run`, как `runPlain` в шаге 1.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.

  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.

- Тест из шага 1 нельзя копировать в `test/repros/` как есть. Этот каталог не
