# BUG-850: порог coverage 100 % падает на машине с `NODE_OPTIONS`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.
> Перепроверено независимо: не проводилось — баг не входил в пакеты
> независимой перепроверки, решения координатора по нему нет, серьёзность
> оставлена исходной; скептик: не привлекался. При редактуре промпта цитаты и
> механизм сверены чтением кода (без запусков): уточнено, что делают
> существующие тесты, почему `vi.stubEnv('NODE_OPTIONS', undefined)` в этом
> файле не сработает и как проверять готовность.

## Контекст

`pnpm test:unit` (`package.json:75`) запускает `vitest --run --coverage` с
порогом 100 % по statements, branches, functions и lines
(`vitest.config.ts:9-14`). Через `pnpm test` (`package.json:67`) на него
опирается `release:check` (`package.json:57`, `pnpm test && pnpm run build`).
В адаптере node:test есть две ветки, которые зависят от переменной окружения
**машины, где идут тесты**:

- `adapters/node-test/start-node-test-session.ts:119` —
  `...(environment['NODE_OPTIONS'] ?? '').split(/\s+/u).filter(Boolean),`;
- `adapters/node-test/start-node-test-session.ts:164-168` — вызов
  `placePreload(preload, execArgv, environment['NODE_OPTIONS'] ?? '')`,
  `?? ''` стоит на `:167`.

`environment` собирается из `process.env` (`:111-116`). Правая сторона `?? ''`
выполняется, только когда переменной **нет**. Если у разработчика или в CI
задан `NODE_OPTIONS` с любым значением, даже пустой строкой (`'' ?? ''`
возвращает левый операнд), эта сторона не выполняется ни в одном тесте. Тогда
порог branches не выполняется, и `test:unit` завершается с ошибкой, хотя сами
тесты зелёные. В CI проекта `NODE_OPTIONS` не задаётся (в `.github/` его нет;
джоба с `pnpm test:unit` — `.github/workflows/test.yml:216`), поэтому там
зелено. Откуда `NODE_OPTIONS` берётся на практике: `--use-openssl-ca` за
прокси (так было в среде анализа, его ставил прокси сессии),
`--max-old-space-size` в CI, отладчик VS Code (auto-attach, «JavaScript Debug
Terminal»). Два последних источника названы по общему опыту, в анализе они не
проверялись.

## Воспроизведение

Отдельного теста-воспроизведения у этого бага нет, в ветке воспроизведений
анализа тоже: баг виден на собственных unit-тестах репозитория. Собранный
mootant не нужен, CLI не запускается. Если для смежной проверки он всё же
понадобится: `pnpm build` → `pnpm pack` → в каталоге фикстуры
`npm i -D /путь/к/mootant-0.1.0.tgz`. Vitest в npm-фикстуру ставь командой
`npm i -D vitest@5`, а не `vitest@5.0.5`: в npm 10.9.9 это падает с
`Cannot read properties of null (reading 'edgesOut')` (ошибка arborist на
peer-зависимости `@vitest/browser-playwright@5.1.0`).

Подготовка чистого клона. Нужен pnpm 12: в CI `version: latest-12`
(`.github/actions/install-tools/action.yml:14`), в анализе — 12.16.1. pnpm 10
не читает `configDependencies` из `pnpm-workspace.yaml`: в среде анализа
`pnpm --version` внутри репозитория зависал. Node — `^20.19.0 || >=22.12.0`
(`package.json:150-152`); в CI — 24, в анализе — 22.23.4.

```bash
pnpm --version        # 12.x; если нет — например, npm i -g pnpm@12
pnpm install --frozen-lockfile --ignore-scripts  # как в CI
pnpm exec astro sync  # как в CI (.github/actions/install-dependencies/action.yml:24)
printenv NODE_OPTIONS # если что-то напечатано — порог coverage здесь уже не выполняется
```

Если `NODE_OPTIONS` в сессии уже задан (в среде анализа прокси ставил
`--use-openssl-ca`), команды, которым нужна сеть (`pnpm install`), запускай
как есть, а `env -u NODE_OPTIONS` используй только для тестов.

Фокусный прогон одного файла:

```bash
NODE_OPTIONS=--use-openssl-ca pnpm exec vitest --run --coverage \
  --coverage.include=adapters/node-test/start-node-test-session.ts \
  test/adapters/node-test/start-node-test-session.test.ts
# в анализе: 12/12 тестов зелёные, но % Branch 94.11 (32/34),
# Uncovered Line #s 119,167, ошибка порога branches, exit code не 0

env -u NODE_OPTIONS pnpm exec vitest --run --coverage \
  --coverage.include=adapters/node-test/start-node-test-session.ts \
  test/adapters/node-test/start-node-test-session.test.ts
# в анализе: Branch 100 % (34/34), exit code 0
```

Контроль по чтению кода (в анализе не запускался): с `NODE_OPTIONS=` (пустая
строка) первая команда должна дать тот же результат, потому что ветку
покрывает только отсутствующая переменная.

Весь сьют (в тишине на 4 vCPU — около 4,5 мин, под нагрузкой в разы дольше):

```bash
TERM=xterm-256color NODE_OPTIONS=--use-openssl-ca \
  pnpm exec vitest --run --coverage --coverage.reportOnFailure
# в анализе: ERROR: Coverage for branches (99.98%) does not meet global threshold (100%)

env -u NODE_OPTIONS TERM=xterm-256color \
  pnpm exec vitest --run --coverage --coverage.reportOnFailure
# в анализе: Branches : 100% ( 10223/10223 )
```

Почему не просто `pnpm test:unit`: если упал хоть один тест, Vitest не строит
отчёт coverage и не проверяет порог (`coverage.reportOnFailure` по умолчанию
`false`: `grep -n reportOnFailure node_modules/vitest/dist/chunks/defaults.*.js`),
и ошибка порога маскируется. Посторонние падения в типичной среде есть: под
root падает `test/adapters/node-test/score-node-test.test.ts:98-105`
(`chmod 000` не мешает root читать файл), при `TERM=linux` — 4 теста в
`test/cli/run-list.test.ts` и `test/cli/run-mutation.test.ts`
(`cli/terminal/is-unicode-supported.ts:13` выбирает ASCII), под нагрузкой —
таймауты. Это отдельные находки (BUG-854, BUG-853), к этому багу они не
относятся. Покрытие они не роняют: в анализе прогон под root без
`NODE_OPTIONS` с десятью упавшими тестами дал 100 % по всем метрикам.

## Ожидаемое поведение

Результат `pnpm test:unit` не зависит от того, задан ли `NODE_OPTIONS` в
окружении и какое у него значение. Тесты
`test/adapters/node-test/start-node-test-session.test.ts` сами задают нужное
состояние переменной (её нет или у неё конкретное значение), и обе стороны
`?? ''` покрыты при любом окружении машины.

## Фактическое поведение

- С `NODE_OPTIONS=--use-openssl-ca` (наблюдалось в анализе): фокусный прогон
  даёт 12/12 зелёных тестов, но branches 94,11 % (32/34), строки 119 и 167 не
  покрыты, порог не выполнен. Весь сьют:
  `ERROR: Coverage for branches (99.98%) does not meet global threshold (100%)`.
  Без `NODE_OPTIONS` — 100 %.
- По чтению кода (запуском не проверено): если `NODE_OPTIONS` машины грузит
  модуль, `placePreload` кладёт preload в `NODE_OPTIONS`, а не в аргументы.
  При `--require`/`-r` так происходит всегда
  (`adapters/node-test/place-preload.ts:41-46`), при `--import`, `--loader`,
  `--experimental-loader` — если команда теста сама не делает `--require`
  (`:47-55`). Тогда тесты, которые не задают переменную сами и ждут preload в
  `handle.args`, должны падать уже по существу, а не только по порогу. Это как
  минимум `start-node-test-session.test.ts:208-222`, `:386-421`, `:437-439`, а
  при `--require` ещё и `:263-271`.

## Подозреваемые места в коде

- `test/adapters/node-test/start-node-test-session.test.ts` — ни один из 12
  тестов не **снимает** `NODE_OPTIONS`. Три задают непустое значение прямым
  присваиванием в `process.env`: `:130` (`--max-old-space-size=100`), `:226`
  (`--import tsx`), `:275` (`--require ts-node/register`). Остальные девять
  наследуют значение машины: `SAVED = { ...process.env }` снимается при
  загрузке модуля (`:37`), а `afterEach` восстанавливает
  `process.env = { ...SAVED }` (`:119-125`, присваивание на `:123`).
- `adapters/node-test/start-node-test-session.ts:119,167` — ветки `?? ''`,
  которые покрываются только при отсутствующей переменной. Код адаптера
  менять не нужно.
- Проверено чтением, к багу не относится:
  `adapters/node-test/get-node-cache-inputs.ts:69`
  (`nodeOptions: input.env['NODE_OPTIONS'] ?? null`). Его тест передаёт `env`
  явно и покрывает обе стороны:
  `test/adapters/node-test/get-node-cache-inputs.test.ts:13-14`
  (`NODE_OPTIONS: '--conditions=dev'`) и `:56-59` (`env: {}` →
  `nodeOptions: null`). Других чтений `NODE_OPTIONS` в коде нет:
  `grep -rn "NODE_OPTIONS" adapters core cli` кроме комментариев даёт только
  `start-node-test-session.ts:119,167,170` и `get-node-cache-inputs.ts:69`.
  Прочие чтения окружения (`cli/terminal/is-interactive-terminal.ts:15`,
  `cli/terminal/is-unicode-supported.ts:11`,
  `cli/terminal/get-text-style.ts:25`) их тесты стабят через `vi.stubEnv`.
  Влияют ли `TERM`, `CI`, `NO_COLOR`, `FORCE_COLOR` на порог coverage, в
  анализе не проверялось.

**Направление исправления** (уточнено при редактуре чтением кода Vitest
5.0.5 из lockfile; запуском не проверено):

- **Работает:** в `describe('startNodeTestSession')` добавить `beforeEach`,
  который делает `delete process.env['NODE_OPTIONS']`. `afterEach` уже
  восстанавливает окружение, а тесты, которым нужно значение, задают его сами,
  как сейчас. Так покрывается `?? ''`, и все тесты файла перестают зависеть от
  `NODE_OPTIONS` машины, в том числе от значений, которые грузят модули.
  Удаление по литеральному ключу в проекте уже встречается:
  `adapters/node-test/start-node-test-session.ts:117`,
  `test/helpers/run-node-test-reference.ts:140`.
- **Не работает в этом файле как есть:** `vi.stubEnv('NODE_OPTIONS', undefined)`.
  В Vitest 5.0.5 `vi.stubEnv(name, undefined)` делает `delete` на прокси
  `import.meta.env`. У прокси есть только ловушки `get` и `set`, а его цель —
  объект `process.env`, который был при старте воркера. Проверить:
  `grep -rn "stubEnv(name, value)" -A 7 node_modules/vitest/dist/chunks/` и
  `grep -rn "function createImportMetaEnvProxy" -A 19 node_modules/vitest/dist/chunks/`.
  `afterEach` этого файла подменяет `process.env` копией (`:123`). Поэтому со
  второго теста `delete` уходит в старый объект, `startNodeTestSession`
  (`:112`) по-прежнему видит значение машины, и ветка остаётся непокрытой.
  Если нужен стиль `vi.stubEnv`, переведи на него весь файл: убери `SAVED` и
  `process.env = { ...SAVED }`, прямые присваивания (`:128-130`, `:226`,
  `:275`) замени на `vi.stubEnv`, в `afterEach` вызови `vi.unstubAllEnvs()`.
  Перед этим вызовом в проекте везде стоит `/* Cspell:disable-next-line */`
  (12 мест, например `test/cli/terminal/is-unicode-supported.test.ts:20-32`);
  без него, вероятно, упадёт `test:spelling` (не проверено).
- **Не работает:** пустое значение (`NODE_OPTIONS=`,
  `vi.stubEnv('NODE_OPTIONS', '')`, `test.env: { NODE_OPTIONS: '' }`), потому
  что `'' ?? ''` возвращает левый операнд. `test.env` в `vitest.config.ts`
  переменную и не удалит: Vitest только присваивает значения (`setupEnv` в
  `node_modules/vitest/dist/chunks/setup-common.*.js`:
  `metaEnv[key] = env[key]`), а присвоенный `undefined` Node превращает в
  строку `'undefined'`.
- **Не делать:** `/* v8 ignore */` у этих веток (в `adapters`, `core`, `cli`
  нет ни одного такого комментария), снижение порогов, правку адаптера ради
  покрытия.

Набросок по образцу соседних тестов (не запускался; перед коммитом прогони
ESLint). Хук ставится перед существующим `afterEach` (`:119`), тест — в конец
`describe`:

```ts
beforeEach(() => {
  delete process.env['NODE_OPTIONS']
})

it('leaves NODE_OPTIONS unset when the environment has none', async () => {
  let context = await createProject({ type: 'module' }, ['a.test.js'])
  mockRuntime('v26.11.1', true)

  let session = await startNodeTestSession(context, {})

  await expect(session.cacheInputs!()).resolves.toMatchObject({
    settings: { nodeOptions: null },
  })

  let handle = await readHandle(context)

  expect(handle.args).toStrictEqual(['--import', PRELOAD, ...REPORTERS])
  expect(handle.env['NODE_OPTIONS']).toBeUndefined()
})
```

`beforeEach` нужно добавить в импорт из `vitest` (`:2`). Именованные импорты и
сами строки импорта в проекте отсортированы по длине (perfectionist), поэтому
эта строка станет первой. Порядок поправит
`pnpm exec eslint --fix test/adapters/node-test/start-node-test-session.test.ts`.

## Критерий готовности

- В `test/adapters/node-test/start-node-test-session.test.ts` состояние
  `NODE_OPTIONS` задано явно для каждого теста: по умолчанию переменной нет
  (`beforeEach` с `delete process.env['NODE_OPTIONS']` или весь файл на
  `vi.stubEnv`, см. выше), а тесты, которые проверяют значение, задают его
  сами. Есть тест на случай без переменной: `handle.env['NODE_OPTIONS']` равен
  `undefined`, `handle.args` равен `['--import', PRELOAD, ...REPORTERS]`,
  `session.cacheInputs!()` даёт `settings.nodeOptions: null`. `runDry` в файле
  замокан (`:21-23`), `handle` — то, с чем запустились бы процессы тестов.
- Проверка «до/после» — фокусный прогон из «Воспроизведения». До правки
  команда с `NODE_OPTIONS=--use-openssl-ca` завершается ошибкой порога
  branches. После правки та же команда, она же с
  `NODE_OPTIONS=--max-old-space-size=4096` и с `env -u NODE_OPTIONS` дают для
  `start-node-test-session.ts` 100 % по всем метрикам, все тесты файла
  зелёные, exit code 0. Отдельный «падающий» тест не нужен, потому что правка
  только в тестах.
- Весь сьют: обе команды полного прогона из «Воспроизведения» (с
  `NODE_OPTIONS=--use-openssl-ca` и с `env -u NODE_OPTIONS`) дают в
  «Coverage summary» 100 % по statements, branches, functions и lines, а строки
  `does not meet global threshold` нет. Если в твоей среде падают посторонние
  тесты (root, `TERM`, нагрузка), перечисли их и покажи, что на исходном
  коммите они падают так же.
- `pnpm test:js`, `pnpm test:types`, `pnpm test:spelling`, `pnpm test:usage`,
  `pnpm test:format` зелёные. `pnpm test` целиком зелёный, кроме посторонних
  падений из предыдущего пункта и ложных ошибок `test:astro` после
  `pnpm build` (см. «Ограничения»).
- Желательно (не проверено): с `NODE_OPTIONS`, который грузит модуль, фокусный
  прогон тоже зелёный. Например: `printf '' > /tmp/empty.cjs` и
  `NODE_OPTIONS="--require /tmp/empty.cjs"`. До правки, по чтению кода, часть
  тестов файла в таком окружении падает.
- Желательно: общий `test.setupFiles` в `vitest.config.ts`, который
  нормализует `NODE_OPTIONS`, `TERM`, `CI`, `NO_COLOR`, `FORCE_COLOR`, чтобы
  такие зависимости не возвращались с новым кодом. Удалять переменные в нём
  нужно через `delete process.env[…]`, а не через `test.env` (см. выше). Тесты,
  которые проверяют сами переменные, уже стабят их явно
  (`test/cli/terminal/*.test.ts`). Как это скажется на остальных тестах, не
  проверено.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Не меняй поведение адаптера ради покрытия: правка — в тестах. Не прячь
  ветки за `/* v8 ignore */` и не снижай пороги в `vitest.config.ts`.
- Тесты и наброски из анализа нельзя копировать как есть. Для этого бага
  теста в `test/repros/` нет и не нужно: правь существующий
  `test/adapters/node-test/start-node-test-session.test.ts` в стиле проекта
  (строгий ESLint: имена файлов, `describe`/`it`, порядок импортов). Фикстуры,
  если понадобятся, клади только в `test/fixtures/**`.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`.
  `tsconfig.json:2-4` включает `**/*.ts` и не исключает `dist/`, поэтому после
  сборки `astro check` подхватывает `dist/types/html/inline-script.d.ts` с
  `/// <reference types="vite/client" />`, и объявления `*.svg` из Vite
  конфликтуют с SVG-компонентами Astro (в анализе — 14 ошибок `ts(2322)` в
  `docs/components/*.astro`). Для этого бага сборка не нужна. Если собирал,
  удали `dist/` или проверяй `test:unit`, `test:js`, `test:types` и остальные
  `test:*` по отдельности.
- Сообщения коммитов — Conventional Commits (commitlint).
