# BUG-201: вердикт мутанта зависит от того, какие ещё файлы в прогоне (`--mutant`, `--since`, узкие пути)

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест падает 3 из 3 на
> проверке `--mutant`; CLI на Vitest 5.0.5 и 5.1.0 во всех повторах даёт
> `Killed` в полном прогоне и `NoCoverage` при `--mutant`, узком пути и
> `--since`); скептик: не опровергнуто, но серьёзность снижена с medium до low —
> триггер узкий (inline-фабрика `vi.mock` без параметров, которая грузит
> оригинал через помощник без подстроки `importActual`, либо уже
> задокументированный вычисляемый `import()`), а ошибка только пессимистичная:
> ложных `Killed` нет, полный прогон верен.

## Контекст

Под Vitest тест-файлы dry run выбирает статический анализ самого Vitest.
Функция `findSpecifications` записывает файлы запроса в
`vitest.config.related` и вызывает `vitest.getRelevantTestSpecifications()`
(`adapters/vitest/run-dry.ts:225-247`, присваивание на `:231`, вызов на `:233`).
В `related` попадают только переключаемые файлы прогона
(`core/run/run-dry-phase.ts:156`, запрос с `files: null` на `:197`). А
переключаемые файлы — это файлы *выбранных* мутантов. `selectMutants`
(`core/run-mutants.ts:633-664`, вызов на `:202-210`) при `--mutant` оставляет
только файлы с выбранными id (`:658-663`), дальше идут `selectRunFiles`, хостинг
всех ожидающих мутантов этих файлов, `createSwitchedFiles` и
`context.switched.push` (`:379-394`). При `--since` переключаются изменённые
файлы путей (`core/files/select-changed-mutants.ts:22-30`). Изменённый файл
остаётся, даже если на изменённых строках нет мутантов (`:58-64`). При узком
пути (`mootant run src/api.js`) других файлов в листинге просто нет. Во всех
трёх случаях `related` меньше, чем при полном прогоне тех же путей.

Где теряется тест. Анализ Vitest не выбирает тест, который мокает мутируемый
модуль фабрикой `vi.mock`, если по эвристике Vitest фабрика «не грузит
оригинал». Правило в `@vitest/mocker` (`dist/chunk-hoistMocks.js:549`):
`factoryLoadsOriginal: factory != null && (factory.params.length > 0 ||
code.slice(factory.start, factory.end).includes("importActual"))`. Здесь
`factory` — только inline-функция (`:543`). Фабрика, переданная иначе
(например, переменной), даёт `hasFactory: false`, и модуль не подменяется.
Если правило не сработало, `resolveStaticMocks` в vitest помечает модуль как
подменённый (`replaced`; `dist/chunks/index.1TqnEahn.js:843-874`, решение на
`:862`). Дальше
`AffectedModulesResolver` (`dist/chunks/cli-api.De07GUeT.js:9930-10074`) для
тест-файла с моками требует пути до одного из `related`, который не проходит
через подменённый модуль (`findAffectedInEnvironment`, `:10027-10031`;
`GraphWalk.reachesChange`, `:10188-10200`). Номера строк — для Vitest 5.0.5 из
lockfile проекта: после `pnpm install` это `node_modules/vitest/dist/chunks/` и
`node_modules/.pnpm/@vitest+mocker@5.0.5_*/node_modules/@vitest/mocker/dist/`.
`npm i -D vitest@5` ставит 5.1.0, там чанк называется `cli-api.COfZo8lK.js`
(класс на `:5585`), `resolveStaticMocks` лежит в `index.Di8au7q4.js`, правило
`@vitest/mocker` то же (`:549`). Ищи по именам.

В фикстуре ниже фабрика `async () => ({ ...(await loadActual('../src/api.js')) })`
не имеет параметров, и в её тексте нет `importActual`: `vi.importActual`
вызывает помощник `loadActual` из `test/actual.js`. Поэтому Vitest считает
`src/api.js` подменённым в `test/greet.check.js`, хотя во время теста фабрика
грузит настоящий модуль — тот, что переключил mootant. В полном прогоне в
`related` есть и `src/service.js`. Тест статически импортирует его не через
мок, поэтому попадает в dry run, и мутант получает `Killed`. При `--mutant <id из
src/api.js>`, при `--since` с правкой только в `src/api.js` и при
`mootant run src/api.js` в `related` один `src/api.js`. Тест не выбирается,
dry run пуст, мутант получает `NoCoverage`, и выживший мутант — тоже
`NoCoverage` вместо `Survived`. Сам Vitest ведёт себя так же: `vitest related
src/api.js` отвечает «No affected test files found», а `vitest related
src/service.js` тест находит.

Не срабатывает (опыты скептика, все три прогона — `Killed`): идиоматичная
фабрика `async importOriginal => …`, прямой `vi.importActual` в фабрике,
помощник с `importActual` в имени (`importActualModule`). Срабатывает также
вычисляемый `import()` без `vi.mock`. Это ограничение задокументировано
(`docs/content/guide/compatibility.mdx:56-57`: «Tests that load a mutated file
only through a computed `import()` may not be selected»). Не задокументированы
случай с фабрикой `vi.mock` и то, что вердикт зависит от состава прогона:
полный прогон верен «по случайности», тест попадает в него через другой
переключаемый файл.

JSDoc `core/run-mutants.ts:340-342` говорит: «The dry run hosts every pending
mutant of the files of the run, selected or not, so the plan of a mutant does
not depend on the selection». Он появился в коммите 2e203ef вместе с хостингом
всех мутантов выбранных файлов (тест `test/core/run-mutants.test.ts:389`) и
относится к хостингу внутри файла. Но общее утверждение о плане не выполняется:
от выбора зависит набор тест-файлов dry run. Адаптер node:test не затронут:
первый dry run запускает тест-файлы с ещё неизвестными модулями и отбирает их
по фактически загруженным модулям (`adapters/node-test/run-dry.ts:75-80`,
`:127-129`). Верификатор проверил это на варианте с вычисляемым `import()`.

Вред. Ошибка только пессимистичная: `NoCoverage` или `Survived` вместо
`Killed`, ложных `Killed` нет. По опыту скептика, кэш не портится: полный
прогон с кэшем после `--mutant` снова даёт `Killed`. Страдают два рабочих
сценария:

- Перепроверка. Отчёт печатает `recheck` (`mootant run src --mutant <id>`) для
  `NoCoverage`, `Survived` и `Error`, а для `Killed` и `Timeout` — только с
  `--all` (`cli/report/build-run-report.ts:19-23`, `:89`, `:101-104`). Для
  выжившего `18v42cm0ffz0` из фикстуры предложенная перепроверка даёт
  `NoCoverage`.
- CI. `--since` вместе с `--threshold` (пример в
  `docs/content/guide/cli.mdx:104-109`) ложно падает: score 0 и exit 1, а у
  полного прогона с тем же порогом exit 0.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создай
сам. Нужны Node.js `^22.12.0 || ^24.0.0 || >=26.0.0` (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:23-24`) и pnpm 12. В CI стоит `latest-12`
(`.github/actions/install-tools/action.yml`). pnpm 10 не читает
`configDependencies` из `pnpm-workspace.yaml`, и даже `pnpm --version` внутри
репозитория у него зависает. Шаги 2–4 выполняй в одной сессии shell: они
используют переменные `REPO`, `TGZ` и функцию `verdicts`.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Фикстура лежит в `test/fixtures/**`: этот каталог исключён из корневого Vitest,
ESLint, knip, cspell и tsc. Тест фикстуры назван `*.check.js`. Все файлы шага
временные и в коммит не входят (см. «Ограничения»).

```bash
# в корне клона azat-io/mootant
pnpm install
mkdir -p test/fixtures/repros/BUG-201/src test/fixtures/repros/BUG-201/test test/repros

cat > test/fixtures/repros/BUG-201/package.json <<'EOF'
{
  "name": "bug-201",
  "private": true,
  "type": "module"
}
EOF

cat > test/fixtures/repros/BUG-201/vitest.config.js <<'EOF'
export default {
  test: {
    include: ['test/**/*.check.js'],
  },
}
EOF

cat > test/fixtures/repros/BUG-201/src/api.js <<'EOF'
export async function fetchUser(id) {
  return { id, name: `user${id}` }
}
EOF

cat > test/fixtures/repros/BUG-201/src/service.js <<'EOF'
import { fetchUser } from './api.js'

export async function greet(id) {
  let user = await fetchUser(id)
  return `Hello, ${user.name}!`
}
EOF

cat > test/fixtures/repros/BUG-201/test/actual.js <<'EOF'
import { vi } from 'vitest'

export function loadActual(specifier) {
  return vi.importActual(specifier)
}
EOF

cat > test/fixtures/repros/BUG-201/test/greet.check.js <<'EOF'
import { expect, test, vi } from 'vitest'

import { loadActual } from './actual.js'
import { greet } from '../src/service.js'

vi.mock('../src/api.js', async () => ({
  ...(await loadActual('../src/api.js')),

test('greets the real user', async () => {
  expect(await greet(2)).toBe('Hello, user2!')
})
EOF

cat > test/repros/BUG-201.test.ts <<'EOF'
import { describe, expect, it } from 'vitest'
import { readFileSync } from 'node:fs'
import path from 'node:path'

import type { RunResult } from '../../types/run/run-result'

import { runReferenceMutants } from '../helpers/run-reference-mutants'
import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

/**
 * Fixture project: `test/greet.check.js` imports `src/service.js` and mocks
 * `src/api.js` with a factory that loads the real module through a helper, so
 * Vitest's static analysis takes `src/api.js` for replaced in that test file;
 * at run time the test does run the real `fetchUser` and kills the mutant of
 * its template literal.
 */
let root = path.join(import.meta.dirname, '../fixtures/repros/BUG-201')

/**
 * Runs the fixture with the given paths and mutants.
 *
 * @param paths - Files and directories to mutate, relative to the fixture.
 * @param mutantIds - Ids of `--mutant`, or undefined for every mutant.
 * @returns Result of the run.
 */
function run(paths: string[], mutantIds?: string[]): Promise<RunResult> {
  return runMutants({
    builtIns: createBuiltIns('vitest', vitestAdapter()),
    concurrency: 2,
    cache: false,
    cwd: root,
    mutantIds,
    paths,
  })
}

describe('BUG-201: the verdict of a mutant depends on the other files of the run', () => {
  it('gives the template literal of fetchUser the same verdict alone as in the whole run', { timeout: 300_000 }, async () => {
    let full = await run(['src'])
    let source = readFileSync(path.join(root, 'src/api.js'), 'utf8')
    let target = full.results.find(
      ({ mutant }) =>
        mutant.file === 'src/api.js' &&
        mutant.mutator === 'string-literal' &&
        source.slice(mutant.start, mutant.end).startsWith('`user'),
    )!
    expect(target.status).toBe('Killed')

    let reference = await runReferenceMutants(root, [target.mutant], {
      sources: ['src/api.js'],
      separate: true,
    })
    expect(reference.original).toBe(true)
    expect(reference.killed.get(target.mutant.id)).toBe(true)

    let alone = await run(['src'], [target.mutant.id])
    let file = await run(['src/api.js'])
    // Actual: `NoCoverage` in both, since only `src/api.js` is related then
    // and the static analysis skips `test/greet.check.js`.
    expect(alone.results.map(result => result.status)).toStrictEqual([
      'Killed',
    ])
    expect(
      file.results.find(({ mutant }) => mutant.id === target.mutant.id)
        ?.status,
    ).toBe('Killed')
  })
})
EOF

pnpm exec vitest --run test/repros/BUG-201.test.ts
```

Тест делает три прогона `runMutants` с адаптером Vitest: полный (`paths:
['src']`, строки 41–49), только мутант `` `user${id}` `` → `''` (`mutantIds`,
строки 58 и 62–64) и узкий путь (`paths: ['src/api.js']`, строки 59 и 65–68).
Эталоном служит `runReferenceMutants` с `separate: true` (строки 51–56):
мутация вписывается в копию проекта, и каждая копия гоняет все свои тесты в
своём экземпляре Vitest. Помощники `test/helpers/run-reference-mutants.ts` и
`test/helpers/create-built-ins.ts` есть в 170ec52.

### Шаг 2. CLI на упакованном mootant

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому для CLI нужна
сборка. В фикстуру ставь `vitest@5` (сейчас это 5.1.0), а не `vitest@5.0.5`:
в npm 10.9.9 установка 5.0.5 падает с `Cannot read properties of null (reading
'edgesOut')`. Это баг arborist, не mootant. На 5.1.0 баг воспроизводится так
же, как на 5.0.5. Функция `verdicts` собрана по типам
`types/report/slim-run-report.d.ts` и не запускалась.

```bash
# в корне клона, после шага 1
REPO="$PWD"
pnpm build
pnpm pack                        # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"    # *.tgz нет в .gitignore, не оставляй его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"

# id, место и статус каждого мутанта, диагностики и число тестов dry run
verdicts() {
  node -e '
    let report = JSON.parse(require("node:fs").readFileSync(0, "utf8"))
    for (let m of report.mutants) console.log(m.id, m.file + ":" + m.line, m.status)
    for (let d of report.diagnostics) console.log("diagnostic", d.code, d.file ?? "-", d.message)
    console.log("tests in dry run:", report.summary.totalTests)
  '
}

FIX="$(mktemp -d)"
cp -R test/fixtures/repros/BUG-201/. "$FIX/"
cd "$FIX"
npm i -D vitest@5 "$TGZ"
npx vitest --run                          # без мутантов: 1 passed
npx vitest related src/api.js --run       # No affected test files found
npx vitest related src/service.js --run   # 1 passed
npx mootant list src                      # id мутантов

npx mootant run src --no-cache --json --all | verdicts
npx mootant run src --mutant jnhjhh9wmsza --no-cache --json --all | verdicts
npx mootant run src --mutant jnhjhh9wmsza --mutant cv04c482t8kd --no-cache --json --all | verdicts
npx mootant run src/api.js --no-cache --json --all | verdicts
# recheck, который отчёт полного прогона предлагает для выжившего (в отчёте без npx)
npx mootant run src --mutant 18v42cm0ffz0 --no-cache --json --all | verdicts

# эталон вручную: мутация `user${id}` -> '' вписана в файл
cp src/api.js "$PACK/api.js.orig"
cat > src/api.js <<'EOF'
export async function fetchUser(id) {
  return { id, name: '' }
}
EOF
npx vitest --run                          # падает: expected 'Hello, !' to be 'Hello, user2!'
cp "$PACK/api.js.orig" src/api.js
```

Нужные мутанты фикстуры: `jnhjhh9wmsza` (`src/api.js:2`, `` `user${id}` `` → `''`),
`18v42cm0ffz0` (`src/api.js:2`, `{ id, name: … }` → `{ name: … }`; `greet`
не читает `id`, поэтому мутант на деле выживает) и `cv04c482t8kd` (мутант
`src/service.js:4`). Id не зависят от машины: это SHA-256 от пути, области,
мутатора, исходного и нового текста и номера вхождения, без смещений
(`core/identity/create-mutant-id.ts:51-73`). Если id не совпали, возьми их из
`npx mootant list src`.

### Шаг 4. CI-сценарий `--since`

Копия фикстуры шага 1 становится git-репозиторием. Затем меняется только
строка 2 `src/api.js`, и только комментарием: поведение и id мутантов остаются
прежними. В анализе строку 2 правили иначе (точная правка не записана). Эта
правка комментарием запуском не проверялась. Команда `sed` — для GNU sed.

```bash
SINCE="$(mktemp -d)"
cp -R "$REPO/test/fixtures/repros/BUG-201/." "$SINCE/"
cd "$SINCE"
npm i -D vitest@5 "$TGZ"
printf 'node_modules\n' > .gitignore
git init -q
git add -A
git -c user.name=t -c user.email=t@example.com commit -qm init
sed -i '2s|$| // edited|' src/api.js

npx mootant run src --since HEAD --no-cache --json --all | verdicts
npx mootant run src --since HEAD --no-cache --threshold 50 > /dev/null; echo "exit $?"
npx mootant run src --no-cache --threshold 50 > /dev/null; echo "exit $?"
```

То же можно повторить на копии каталога `$MOCKS` из шага 3.

## Ожидаемое поведение

- `--mutant` и `--since` дают тот же вердикт, что полный прогон тех же путей, и
  он совпадает с эталоном (мутация вписана вручную, обычный Vitest). На
  фикстуре шагов 1, 2 и 4 `jnhjhh9wmsza` получает `Killed`, а `18v42cm0ffz0` —
  `Survived`, и с `--mutant`, и с `--since HEAD`. Предупреждения `never-served`
  для `src/api.js` нет. На фикстуре шага 3 оба мутанта строки 2 получают
  `Killed`. `--since HEAD --threshold 50` завершается с кодом 0, как полный

- Узкий путь (`mootant run src/api.js`). В идеале тоже `Killed`. Но статический

## Фактическое поведение

Шаг 2. Результат одинаков на Vitest 5.1.0 (npm, 3 повтора) и 5.0.5 (pnpm, 2

## Подозреваемые места в коде

Где теряется тест:

- Vitest: `AffectedModulesResolver` и эвристика `factoryLoadsOriginal` (см.
  «Контекст»). Это поведение Vitest, mootant его не меняет.
- `adapters/vitest/run-dry.ts:225-247` — `findSpecifications`. Тест-файлы dry
  run выбираются только статическим анализом Vitest по `request.related`.
  Проверки по факту загрузки, как у node:test, нет.
- `core/run/run-dry-phase.ts:156` — `related` равен переключаемым файлам.
  `core/run-mutants.ts:379-394` — переключаются только файлы выбранных мутантов
  (`selectMutants`, `:633-664`; для `--since` —
  `core/files/select-changed-mutants.ts:22-30`).
- `core/run/run-dry-phase.ts:360-367` — `never-served` с общей причиной
  (`:365`). Vitest-адаптер своей причины не передаёт: `unserved` заполняет
  только node:test (`adapters/node-test/run-dry.ts:151`).

Какое исправление работает, а какое нет:

1. **`related` = все файлы, которые переключил бы полный прогон тех же путей.**
   Это чинит `--mutant` и `--since`: тест находится через `src/service.js`.
   Косвенно это подтверждает опыт `--mutant jnhjhh9wmsza --mutant cv04c482t8kd`
   (второй мутант из `src/service.js`): на обеих фикстурах он даёт `Killed`.
   Файлы путей прогона — `selectRunFiles(context.listed, testFiles, …)`, так их
   уже строит подготовка кэша (`core/run-mutants.ts:445-446`). Но
   `createSwitchedFiles` пропускает файлы без ожидающих мутантов и с
   `source === null` (`core/instrument/create-switched-files.ts:69-73`). Отфильтруй
   так же, иначе изменится и dry run полного прогона. Контракт адаптера
   расширение допускает: `related` — подсказка, адаптер может запустить больше
   (`types/adapter/dry-run-request.d.ts:26-32`). Узкий путь так не чинится:
   при `paths: ['src/api.js']` в листинге только `src/api.js`. Цена: dry run у
   `--mutant` и `--since` становится таким же, как у полного прогона тех же
   путей. Dry run самого полного прогона не меняется. Насколько это дороже на
   реальных проектах, не замерено.
2. **Одной правкой строки `core/run/run-dry-phase.ts:156` не обойтись** (по
   чтению кода, запуском не проверено). Внутри модуля `related` значит
   «переключаемые файлы». Если упавшие тесты не дошли ни до одного сайта
   мутанта, `findBrokenFiles` считает сломанными все `related` (`:505-517`,
   `:516`). `recoverFromFailures` берёт для них `input.displays.get(file)!`
   (`:288`), а `displays` знает только файлы выбранных мутантов
   (`core/run-mutants.ts:405`). Повторные dry run передают
   `related` дальше (`:209-213`, `:304-308`, `:398-407`). Нужен отдельный вход
   в `DryPhaseInput` (`:19-52`) — файлы для отбора тестов — во всех запросах
   `runDry`. `switched` и `findBrokenFiles` оставь как есть.
3. **Только `diagnostic` не работает как исправление.** Вердикт не меняется,
   временный тест не пройдёт, а на фикстуре шага 3 `never-served` не
   срабатывает вовсе. Как дополнение годится: Vitest-адаптер может передавать
   причину в `unserved`, как node:test.
4. **Сильное исправление, которое чинит и узкий путь,** — отбирать тест-файлы
   по фактически загруженным модулям, как node:test. Для Vitest это значит
   запускать в первом dry run больше тест-файлов, и нужен замер. В Vitest 5 есть
   `experimental.recordDependencies`: `RecordedModulesResolver`
   (`cli-api.De07GUeT.js:10253-10295`, выбор резолвера на `:10396`) отбирает
   тесты по модулям, загруженным в прошлом записанном прогоне, а спецификацию
   без записи считает затронутой. Запись хранится в
   `<cacheDir>/dependencies.json` при включённом `cache` (`:6125`). Подходит ли
   это mootant (свой экземпляр Vitest, откуда запись в первом прогоне) — не
   проверено.
5. **Идея дешевле п. 1, не проверена.** Vitest выбирает тест, если путь от него
   до какого-то `related` не идёт через подменённый модуль (`reachesChange`).
   Тест фикстуры доходит до `src/service.js`, импортёра `src/api.js`, без мока.
   Значит, могло бы хватить статических импортёров переключаемых файлов в
   `related`. Если брать их по всему проекту, это чинит и узкий путь. Как
   получить импортёров до dry run и сколько это стоит, не проработано.

Не здесь:

- `core/run/read-test-imports.ts` тест-файлы dry run не выбирает. Он читает
  импорты тест-файлов, уже попавших в dry run (`core/run-mutants.ts:465-467`),
  для ранжирования.

Документация и комментарии:

- `docs/content/guide/compatibility.mdx:56-57` (раздел «## Vitest» с `:40`) —
  описан только вычисляемый `import()`.
- `core/run-mutants.ts:340-342` — JSDoc о независимости плана от выбора.

## Критерий готовности

- **Обязательно: `--mutant` и `--since` не меняют вердикт относительно полного
  прогона тех же путей.**
  - Появляется постоянный тест в стиле проекта, который падает до исправления
    и проходит после. Это тест в `test/adapters/vitest/index.test.ts` по
    образцу `runAllPaths` и `expectAgreement` (`:135-207`) на новой фикстуре
    `test/fixtures/equivalence/<имя>/`. Устрой её как соседние: `src/*.ts`,
    `test/*.test.ts`, свой `vitest.config.ts` с
    `include: ['test/**/*.test.ts']`. Паттерн тот же, что в шаге 1:
    inline-фабрика `vi.mock` без параметров грузит оригинал через помощник без
    `importActual` в имени, а тест статически импортирует второй мутируемый
    файл. Тест проверяет, что вердикт мутанта при `mutantIds: [id]` и
    `paths: ['src']` совпадает с вердиктом полного прогона и с эталоном
    `runReferenceMutants(…, { separate: true })` (`killed`; так эталон уже
    вызывается на `:891-912`).
  - `--since` покрыт тестом. Например, в `test/core/run-mutants.test.ts`:
    `readChangedLines` там уже замокан (тест «runs only the mutants on lines
    changed since a revision», `:560`), а фейковый адаптер записывает запросы
    dry run в `fake.calls.dry` (`test/helpers/create-fake-adapter.ts:112-114`,
    `:297-298`). При `since` и при `mutantIds` файлы для отбора тестов (при
    исправлении через `related` — `fake.calls.dry[0]!.related`) те же, что в
    полном прогоне тех же путей. Если выбран другой механизм, нужен
    равноценный тест на него.
  - Шаги 2–4 повторены после исправления: новые `pnpm build` и `pnpm pack`,
    свежие временные каталоги, чтобы npm не сверял новый tarball со старым
    lockfile. Результат: `--mutant jnhjhh9wmsza` даёт `Killed` без
    `never-served`, `--mutant 18v42cm0ffz0` — `Survived`. `--since HEAD` даёт
    `jnhjhh9wmsza` `Killed` и `18v42cm0ffz0` `Survived`, с `--threshold 50` —
    exit 0. На фикстуре шага 3 `--mutant jnhjhh9w` даёт `Killed`.
- **Узкий путь (`paths: ['src/api.js']`).**
  - Обязательно: ограничение описано в `docs/content/guide/compatibility.mdx`
    рядом с `:56-57`. Тест, который грузит мутируемый файл через inline-фабрику
    `vi.mock` без параметров, в тексте которой нет `importActual` (оригинал
    грузит помощник), или через вычисляемый `import()`, может не попасть в dry
    run, если в прогоне нет другого файла, который он импортирует статически.
    Тогда мутант получает `NoCoverage`. Перепроверять стоит с теми же путями,
    что и полный прогон.
  - По желанию: сильное исправление (п. 4 или 5 выше) отдельным коммитом, с
    замером и своим тестом, где узкий путь даёт `Killed`. С ним временный тест
    шага 1 проходит без изменений. Без него удали из временного теста проверку
    узкого пути (строки 65–68 и прогон `file` на строке 59). Оставшийся тест
    должен пройти.
- **Цена.** Dry run полного прогона не меняется: число тестов dry run
  (`summary.totalTests` в `--json`) у полного прогона одинаково до и после
  исправления. Для `--mutant` и `--since` замерь до и после число тестов и
  длительность dry run (`summary.duration.dryRun` в `--json --verbose`) на
  реальном каталоге. Например, в самом репозитории после `pnpm build`:
  `node bin/mootant.js run core/identity --mutant <id> --no-cache --json
  --verbose`. Цифры приведи в описании PR.
- JSDoc `core/run-mutants.ts:340-342` соответствует новому поведению.
- Временные `test/repros/` и `test/fixtures/repros/` удалены.
- Проверки проекта зелёные при запуске по отдельности: `pnpm test:unit` (с
  порогом покрытия 100%), `pnpm test:js`, `pnpm test:types`, `pnpm test:usage`,
  `pnpm test:spelling`, `pnpm test:format` и остальные `test:*`.
  `pnpm test:astro` запускай без `dist/` (см. «Ограничения»). Падения, которые
  зависят от окружения (см. «Ограничения»), сверь с прогоном на нетронутом
  коде.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Исправление — на стороне mootant. Эвристику `factoryLoadsOriginal` и отбор
  Vitest не трогай: это код `node_modules`.
- Dry run полного прогона не должен стать медленнее: для него набор тест-файлов
  не меняется. Удорожание dry run у `--mutant` и `--since` — цена
  согласованности, её нужно замерить (см. «Критерий готовности»). Для
  ориентира, по замеру анализа (4 vCPU): на самом mootant `run core/text` dry
  run выбрал 8 393 теста из 10 491 и шёл 4 мин 37 с. Статический отбор на
  большом проекте экономит минуты.
- Тест из шага 1 нельзя копировать в `test/repros/` как есть. Этот каталог не
  исключён ни из корневого Vitest, ни из ESLint, knip, cspell или tsc.
  Исключён только `test/fixtures/**` (`eslint.config.ts:15`,
  `knip.config.ts:5`, `cspell.config.ts:44`, `vitest.config.ts:18`,
  `tsconfig.json:2`). Постоянный тест перепиши в стиле проекта под строгий
  ESLint: имена файлов, `describe`/`it`, порядок импортов, JSDoc. Фикстуры клади

  tarball и временные каталоги в коммит не входят. Перед `pnpm test:*` удали
  `test/repros/`, иначе его подхватят Vitest и ESLint.
