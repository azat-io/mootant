# BUG-412: значения `provide()` и `define`, меняющиеся от прогона к прогону, отключают кэш

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.

## Контекст

Для ключа окружения кэша адаптер Vitest описывает настройки каждого проекта
(`describeProjectSettings`, `adapters/vitest/get-cache-inputs.ts:76-114`). В
поле `values` попадает весь `project.getProvidedContext()`, кроме ключа
`mootant` (`adapters/vitest/get-cache-inputs.ts:82-92`). Частый приём
интеграционных тестов — `globalSetup`, который поднимает сервер на случайном
порту, контейнер testcontainers или временную БД и передаёт тестам адрес через
`provide()`. Адрес новый на каждом прогоне, значит, ключ окружения новый на
каждом прогоне, и **ни один вердикт никогда не переиспользуется** — для всех
тестовых файлов проекта, даже тех, что этот адрес не читают. Причина нигде не
сообщается. То же с `define`, в который приложение кладёт время сборки
(`define: { __BUILD_TIME__: JSON.stringify(new Date().toISOString()) }`):
значения `define` входят в то же поле `values`, и кэш не срабатывает ни разу
(сценарий `volatile_define` в `analysis/tools/cache/s-inputs.sh` ветки
`analysis/2026-11`).

## Ожидаемое поведение

Второй прогон неизменённого проекта берёт все вердикты из кэша: тест
`math.test.ts` не читает `apiUrl`, и порт сервера не влияет на его вердикты.
Если значение `provide` всё-таки меняет ключ, отчёт об этом говорит.

## Фактическое поведение

`expected [] to have a length of 3 but got +0` — каждый прогон выполняет всех
мутантов заново, диагностики нет.

## Подозреваемые места в коде

- `adapters/vitest/get-cache-inputs.ts:82-92` — `getProvidedContext()`
  целиком в ключе окружения. Вариант исправления: учитывать значения
  `provide` так же, как переменные окружения, — по тестовому файлу и только
  те ключи, которые он прочитал через `inject()` (обёртка `inject` в воркере
  записывает имена, как `trackEnvironment` записывает переменные,
  `adapters/shared/track-environment.ts`), а в ключ окружения класть только
  имена ключей. Тогда тесты, которые адрес не читают, переиспользуют вердикты,
  а те, что читают, — пересчитываются, как сейчас.
- Для `define` аналог — учитывать в ключе тестового файла только те ключи
  `define`, чьи идентификаторы встречаются в текстах его зависимостей (Vite
  подставляет значение только туда, где идентификатор есть); остальное — только
  имена в ключе окружения.
- `adapters/vitest/runner.ts` (`startTracking`/`stopTracking`) — место, где
  воркер собирает входы теста; сюда же добавляется запись прочитанных ключей
  `inject`.
- `types/adapter/dry-file.d.ts`, `types/adapter/run-inputs.d.ts` — если ключи
  `inject` станут входами теста, их нужно описать.

## Критерий готовности

- Появляются тесты: интеграционный в `test/adapters/vitest/index.test.ts` по
  образцу теста выше (тест без `inject` переиспользует вердикты при новом
  порту), второй — тест с `inject('apiUrl')` при новом значении пересчитывается;
  то же для `define` со временем сборки (тест без `__BUILD_TIME__` в
  зависимостях переиспользует вердикты); unit-тест для `getCacheInputs` в
  `test/adapters/vitest/get-cache-inputs.test.ts`.
  Первый падает до исправления, все проходят после.
- `pnpm test` полностью зелёный (включая 100% coverage, `test:js`,
  `test:types`, `test:usage`, `test:spelling`).
- Поднят `CACHE_VERSION` (`core/cache/cache-version.ts:6`), если меняется
  рецепт ключа.
