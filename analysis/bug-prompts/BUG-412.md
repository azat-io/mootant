# BUG-412: значения `provide()` и `define`, меняющиеся от прогона к прогону, отключают кэш

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (тест исходного промпта падает 3 из 3
> в чистом клоне, вариант из ветки анализа — 3 из 3; на упакованном mootant с
> Vitest 5.1.0 при `provide` адреса на случайном порту или `define` с
> `new Date()` второй прогон берёт из кэша 0 вердиктов, в том числе с
> `--incremental`, а контроли с константами — все); скептик: не опроверг,
> medium — промах консервативный и устаревших вердиктов не даёт, но
> рекламируемый кэш молча не работает у целого класса проектов (включая
> SvelteKit с настройками по умолчанию), масштаб шире заявленного (в workspace
> меняющийся `provide` одного проекта сбрасывает кэш всех проектов), а
> включение значений в ключ задумано (JSDoc), но не описано в документации и не
> сопровождается диагностикой.

## Контекст

Кэш вердиктов обещает переиспользовать вердикт, «while the mutated file and the
files and environment variables its tests read stay the same»
(`docs/content/guide/configuration.mdx:352-355`; то же —
`docs/content/guide/getting-started.mdx:120-121` и `readme.md:63`). Но для
Vitest в ключ входят ещё и настройки каждого проекта (`describeProjectSettings`,
`adapters/vitest/get-cache-inputs.ts:76-114`). Поле `values` (`:82-92`) содержит
значения `define` в трёх видах: `project.vite.config.define` (`:84`),
`config.defines` (`:85`) и `_scriptDefines` (`:86`). Кроме того, туда попадает
весь `project.getProvidedContext()`, кроме собственного ключа mootant
`'mootant'` (`:87-89`).

Из настроек всех проектов строится один ключ окружения на весь прогон
(`core/cache/prepare-run-cache.ts:153-170`, `settings` на `:165`;
`core/cache/get-environment-key.ts:70-87`, `input.settings` на `:81`). Этот ключ
входит в ключ каждого тест-файла (`core/cache/get-test-file-keys.ts:57-66`,
`environment` на `:60`) и в инкрементальные ключи (`outsideKeys`,
`prepare-run-cache.ts:195-202`). Поэтому достаточно, чтобы одно значение
`provide` или `define` одного проекта менялось от прогона к прогону. Тогда не
переиспользуется ни один вердикт ни одного тест-файла во всех проектах, даже у
файлов, которые это значение не читают. `--incremental` не помогает.

Откуда берутся такие значения:

- `globalSetup` поднимает сервер на случайном порту, контейнер testcontainers
  или временную БД и передаёт тестам адрес через `project.provide()`;
- `define` хранит время сборки:
  `define: { __BUILD_TIME__: JSON.stringify(new Date().toISOString()) }`;
- SvelteKit с настройками по умолчанию (нашёл скептик). В `@sveltejs/kit`
  2.70.3 `kit.version.name` по умолчанию равен `Date.now().toString()`
  (`src/core/config/options.js:335`), и это значение уходит в `define` как
  `__SVELTEKIT_APP_VERSION__` (`src/exports/vite/index.js:418`). В проекте с
  `sveltekit()` в конфиге Vitest второй прогон взял из кэша 0 вердиктов (3 раза
  из 3), а с `kit.version.name: '1.0.0'` — 4 из 4.

Включать значения в ключ решили сознательно. JSDoc
`get-cache-inputs.ts:18-22` прямо упоминает «dates that global setup files
`provide`». JSDoc `:62-70` объясняет, почему значения там: конфигурация и
global setup могут брать их из файлов и переменных окружения главного процесса.
Это поведение закрепляют unit-тест и интеграционный тест (см. «Подозреваемые
места в коде»). Пользователю же об этом не сказано нигде: про `provide`,
`define` и `globalSetup` документация молчит.

Вердикты при этом верны: промах консервативный, устаревших вердиктов не бывает.
Беда в другом: заявленная функция молча не работает. Строка «Reused cached
verdicts for N of M mutants.» печатается только при `cached > 0`
(`core/run-mutants.ts:703-711`). При полном промахе нет ничего: ни в stderr, ни
в `diagnostics` JSON-отчёта, ни с `--verbose`.

Тест сохраняется под другим именем, чтобы не затереть файл шага 1. Из помощника
BUG-412 нужны `createCacheProject` (вместе с `writeProjectFiles`),

import {
  writeFile,
  realpath,
  mkdtemp,
  symlink,
  mkdir,
  rm,
} from 'node:fs/promises'
import { setTimeout } from 'node:timers/promises'
import { tmpdir } from 'node:os'
import path from 'node:path'

import type { RunResult } from '../../types/run/run-result'

import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

/**
 * Projects created by the running test file, removed by `removeCacheProjects`.
 */
let projects: string[] = []

/**
 * Template of the cache reproductions (BUG-402 and later): `isAdult` has the
 * survivors `age > 18` and `age >= 17` while no test asks about 18 or 17, and
 * `age == 18` is killed by `isAdult(30)`.
 */

  '  return age >= 18',
  '}',
  '',

 * Configuration of Vitest of the reproductions.
 */

  "import { defineConfig } from 'vitest/config'",
  '',
  "export default defineConfig({ test: { include: ['test/**/*.test.ts'] } })",
  '',
].join('\n')

/**
 * Creates a project in a temporary directory with a `node_modules` of its own,
 * where a link to the repository's Vitest stands for the installed one, so
 * the cache file of every reproduction is private.
 *
 * @param files - Texts by path relative to the root.
 * @returns Real path of the project.
 */
export async function createCacheProject(
  files: Record<string, string>,
): Promise<string> {
  let root = await realpath(
    await mkdtemp(path.join(tmpdir(), 'mootant-repro-')),
  )
  projects.push(root)
  await mkdir(path.join(root, 'node_modules'), { recursive: true })
  await symlink(
    await realpath(
      path.resolve(import.meta.dirname, '../../node_modules/vitest'),
    ),
    path.join(root, 'node_modules/vitest'),
  )
  await writeProjectFiles(root, { 'package.json': '{ "type": "module" }', ...files })
  return root
}

/**
 * Writes files of a project, creating their directories.
 *
 * @param root - Root of the project.
 * @param files - Texts by path relative to the root.
 */
export async function writeProjectFiles(
  root: string,
  files: Record<string, string>,
): Promise<void> {
  for (let [file, text] of Object.entries(files)) {
    let absolute = path.join(root, file)
    await mkdir(path.dirname(absolute), { recursive: true })
    await writeFile(absolute, text)
  }
  // Files modified in the millisecond a run starts count as changed during it.
  await setTimeout(5)
}

/**
 * Runs the mutants of a project with Vitest.
 *
 * @param root - Root of the project.
 * @param options - Paths and whether to use the cache.
 * @param options.cache - Whether to use the cache; on when omitted.
 * @param options.paths - Paths to mutate; `src` when omitted.
 * @returns Result of the run.
 */
export function runProject(
  root: string,
  options: { paths?: string[]; cache?: boolean } = {},
): Promise<RunResult> {
  return runMutants({
    builtIns: createBuiltIns('vitest', vitestAdapter()),
    paths: ['src'],
    concurrency: 1,
    cwd: root,
    ...options,
  })
}

/**
 * Lists the verdict of every mutant of a run by its replacement.
 *
 * @param result - Result of a run.
 * @returns Status by `<file>: <replacement>`.
 */
export function listVerdicts(result: RunResult): Record<string, string> {
  return Object.fromEntries(
    result.results.map(entry => [
      `${entry.mutant.file}: ${entry.mutant.replacement}`,
      entry.status,
    ]),
  )
}

/**
 * Removes the projects of the running test file.
 *
 * @returns Promise of the removal.
 */
export async function removeCacheProjects(): Promise<void> {
  await Promise.all(
    projects.splice(0).map(root => rm(root, { recursive: true, force: true })),
  )
}

/**
 * Counts the mutants of a run whose verdict came from the cache.
 *
 * @param result - Result of a run.
 * @returns Number of cached verdicts.
 */
export function countCached(result: RunResult): number {
  return result.results.filter(entry => entry.cached).length
}

### Шаг 2. CLI на упакованном mootant

Сквозная проверка, как у пользователя: npm, Vitest 5.1.0, три фикстуры по
сценариям верификаторов.

- `provide` — два тест-файла: `api.test.ts` читает адрес через
  `inject('apiUrl')`, `math.test.ts` не читает;
- `define` — один тест-файл, время сборки он не читает;
- `workspace` — два inline-проекта с общим root: у проекта `a` меняющийся
  `provide`, у проекта `b` нет `globalSetup`.

`bin/mootant.js` импортирует `../dist/cli/index.js` (`bin/mootant.js:3`), поэтому
для CLI нужна сборка. Ставьте `vitest@5` (сейчас это 5.1.0), а не
`vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает с `Cannot read properties of
null (reading 'edgesOut')`. Это баг arborist, а не mootant.

Команды рассчитаны на одну сессию shell: они используют переменные `TGZ`,
`FIX`, `OUT` и функции. Скрипт собран по сценариям верификаторов и в таком виде
целиком не запускался. Цифры в «Фактическом поведении» взяты из их отчётов на
таких же фикстурах.

## Ожидаемое поведение

- Второй прогон неизменённого проекта переиспользует вердикты каждого
  тест-файла, чьи входы не изменились. Тест-файл, который не читает меняющийся
  ключ `provide` (через `inject` или фикстуру с `injected: true`) и не читает
  меняющееся значение `define`, берёт из кэша все вердикты. В шаге 1 это 3 из 3
  в обоих тестах. В шаге 2: `src/math.ts` в фикстуре `provide`, все вердикты
  фикстуры `define`, все вердикты фикстуры `workspace`.
- Тест-файл, который прочитал изменившееся значение, прогоняется заново, как
  сейчас: это его вход (`api.test.ts` в фикстуре `provide`). Если значение
  прочитал только прогон мутанта, а не dry run, вердикт тоже не
  переиспользуется. Так уже работают переменные окружения (`RunInputs`).
- `provide` и `define` одного проекта workspace не влияют на ключи тест-файлов
  других проектов.
- С постоянными значениями всё берётся из кэша, как сейчас.
- Документация говорит, что значения `provide` и `define`, которые читают тесты,
  входят во входы вердикта. Диагностика полного промаха желательна, но
  необязательна (см. «Критерий готовности»).

### Как чинить `provide`

Идея исходного промпта верна: учитывать значения `provide` так же, как
переменные окружения. В ключ тест-файла идут только те ключи, которые он
прочитал, а в общем ключе окружения остаются только имена. Уточнения
верификатора и места в коде:

1. Воркер записывает прочитанные ключи. В Vitest 5.0.5 (версия из lockfile)
   `inject(key)` — это `getWorkerState().providedContext[key]`
   (`node_modules/vitest/dist/chunks/index.aTZaPVhf.js:8111-8112`).
   `runner.injectValue(key)` вызывает тот же `inject` (`:8505-8509`). Через
   него же читают фикстуры `test.extend` с `{ injected: true }`
   (`dist/chunks/run.BPv-BBRv.js:1537`). Раннер Vitest берёт то же состояние
   через `getWorkerState()` (`index.aTZaPVhf.js:8440`), а `providedContext` в
   состояние кладёт `dist/chunks/init.PvxYpuCm.js:178`.

   Обернуть ESM-экспорт `inject` непрактично. Перехватывать нужно через Proxy на
   `workerState.providedContext` в раннере mootant. Образец уже есть:
   `startTracking` (`adapters/vitest/runner.ts:1015-1039`) передаёт
   `workerState` как `holder` в `trackInputs` (`:1017-1020`), а
   `trackEnvironment` оборачивает `holder.metaEnv`
   (`adapters/shared/track-environment.ts:147-150`). Чтение ключа (`get`,
   `has`) записывает его имя, перечисление (`ownKeys`) — `*`, как у переменных
   окружения. Собственный ключ `'mootant'` не записывайте. Mootant читает его
   сам в конструкторе раннера (`this.injectValue('mootant')`, `runner.ts:476`),
   и из ключа он уже исключён (`get-cache-inputs.ts:88`). Обёртку удобно
   положить отдельным файлом в `adapters/vitest/worker/`.

   Не проверялось: перечисляет ли сам Vitest `providedContext` в воркере во
   время юнита (тогда каждый тест-файл получит `*`) и пересоздаётся ли
   `workerState.providedContext` между тест-файлами (тогда Proxy нужно ставить в
   каждом `startTracking`).
2. Прочитанные ключи нужно передать в главный процесс тем же путём, что имена
   переменных: поле в записи `end` (`adapters/vitest/types/vitest-worker.d.ts`,
   образец — `environment` на `:32-36`; запись делает `runner.ts:923-941`),
   затем `DryFile` (`adapters/vitest/run-dry.ts:179`, публичный тип
   `types/adapter/dry-file.d.ts:15-20`). Нужен и `RunInputs` прогонов мутантов
   (`adapters/vitest/read-unit-inputs.ts:23-41`,
   `types/adapter/run-inputs.d.ts:15-19`): прогон мутанта может прочитать ключ,
   которого не читал dry run.
3. Главный процесс. В `getCacheInputs` (`adapters/vitest/get-cache-inputs.ts:43-60`)
   хешируйте значение каждого ключа `getProvidedContext()` отдельно по проекту.
   Используйте `inspect(…, INSPECT_OPTIONS)` (`:23-28`): значения бывают `Map`,
   `BigInt`, `Date`. Хеши отдавайте новым полем `CacheInputs` рядом с
   `environment` (`types/adapter/cache-inputs.d.ts:6-13`). В `settings.values`
   оставьте только отсортированные имена ключей.
4. Ядро:
   - `getTestFileKeys` (`core/cache/get-test-file-keys.ts:52-66`): в ключ
     тест-файла добавьте пары «ключ — хеш значения» для прочитанных им ключей,
     по образцу `read` для переменных (`:54-56`);
   - `createRunCache` (`core/cache/create-run-cache.ts:22-38,160-194,321-331`):
     ключи, которые прогон мутанта прочитал сверх dry run, учитывайте так же,
     как сейчас переменные;
   - `prepareRunCache`: прочитанные dry run'ом ключи передавайте так же, как
     `reads` (`core/cache/prepare-run-cache.ts:203-205`).

   Возможный короткий путь — записывать ключи как псевдопеременные (с
   префиксом) в существующие `environment`/`reads`. Тогда псевдопеременные не
   должны попасть в хеш `*`: его строит
   `adapters/shared/index-environment-hashes.ts:38-43`. Этот путь не
   проверялся.

### Как чинить `define`

Исходный промпт предлагал учитывать ключи `define`, чьи идентификаторы
встречаются в текстах зависимостей, потому что «Vite подставляет значение
только туда, где идентификатор есть». Для Vitest 5 это неверно, проверено
верификатором и чтением `node_modules/vitest` 5.0.5. Режим браузера, где
`define` остаётся статическим (`dist/chunks/index.1TqnEahn.js:3774-3785`),
mootant не поддерживает (`docs/content/guide/compatibility.mdx:49`). Вне его
механизм такой:

- `deleteDefineConfig` (`index.1TqnEahn.js:2004-2047`) убирает `define` из
  конфига Vite. JSON-значения ключей без точки уходят в `config.defines`.
  Не-JSON значения и ключи с точкой уходят в `config._scriptDefines`. Ключи
  `import.meta.env.*` и `process.env.*` с JSON-значениями записываются в
  `process.env` главного процесса (`:2027-2034`).
- В воркере `setupDefines` делает `globalThis[key] = value`
  (`dist/chunks/setup-common.HGAqWOnX.js:12-14`). Из `_scriptDefines` строится
  скрипт (`createDefinesScript`, `index.1TqnEahn.js:3930-3959`). Он присваивает
  вложенные свойства `globalThis`, а `import.meta.*` кладёт в
  `__vitest_worker__.metaDefines`. Выполняется скрипт в воркере
  (`dist/chunks/base.CzXt2BO_.js:206-213`).
- Статической подстановки нет. Проба верификатора: `String(() => __BUILD_TIME__)`
  остаётся `() => __BUILD_TIME__`, а `globalThis['__BUILD' + '_TIME__']`
  возвращает значение.

Значит, поиск идентификатора в текстах — только эвристика. Она пропустит
вычисляемый доступ (`globalThis[name]`), перебор `globalThis` и чтения из кода
под `node_modules`: такие файлы в зависимости тест-файла не входят
(`adapters/vitest/get-module-file.ts:17-19`). Так, рантайм SvelteKit,
читающий `__SVELTEKIT_APP_VERSION__`, эвристика не увидит (вывод по чтению
кода). Эвристика может дать устаревший вердикт, поэтому выбирать её можно только
как явный компромисс, описанный в документации.

Надёжнее записывать чтения через аксессоры (геттеры) на `globalThis` для ключей
`config.defines` и верхних сегментов ключей `_scriptDefines`, по аналогии с
`trackEnvironment`. Главный процесс хеширует значения по ключам и проектам, а в
`settings.values` остаются только имена. Не проверялось, когда ставить
аксессоры относительно `setupDefines` и скрипта defines, то есть в каком порядке
они идут относительно `startTracking`. Ключи `import.meta.env.*` и
`process.env.*` становятся переменными окружения и, вероятно, уже учитываются
`trackEnvironment` как переменные (по чтению кода, не проверено). Что остаётся в
`project.vite.config.define` после `deleteDefineConfig`, тоже не проверялось.

### Что проверено и не годится

- Заменить значения именами (`Object.keys(...)`) в `get-cache-inputs.ts:84-89`.
  Верификатор сделал так для проверки причинности. Тест исходного промпта

  дала «2 passed» на варианте из ветки и тесте промпта. Но это не исправление:

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  Контракт адаптера публичен: `DryFile` экспортируется из `core/index.ts:30`.
  `CacheInputs` доступен через `AdapterSession.cacheInputs`
  (`types/adapter/adapter-session.d.ts:40`). `RunInputs` доступен через
  `IsolatedResult.inputs` и `BatchResult.inputs`
  (`types/adapter/isolated-result.d.ts:17`,
  `types/adapter/batch-result.d.ts:22`). Новые поля делайте необязательными:
  тогда node:test и сторонние адаптеры работают как раньше.
- Сообщения коммитов — Conventional Commits (commitlint).
- Значения `provide` и `define`, которые читает тест, должны по-прежнему
  инвалидировать его вердикты: это вход теста. Нельзя просто выкинуть значения
  из ключа, и нельзя исключать из учёта другие ключи, кроме `'mootant'`.
- Тесты-воспроизведения из анализа (шаг 1 и вариант из ветки) нельзя копировать
  в `test/repros/` как есть и оставлять в коммите. На тесте шага 1 верификатор
  насчитал 9 ошибок ESLint: `unicorn/filename-case`,
  `perfectionist/sort-imports`, `vitest/require-top-level-describe`,
  `no-await-in-loop` и другие. Каталог `test/repros/` не исключён ни из ESLint,
  ни из knip, cspell или tsc. Исключён только `test/fixtures/**`
  (`eslint.config.ts:15`, `knip.config.ts:5`, `cspell.config.ts:44`,
  `vitest.config.ts:18`, `tsconfig.json:2`). Постоянные тесты перепиши в стиле
  проекта под строгий ESLint: имена файлов, `describe`/`it`, порядок импортов,
  JSDoc. Фикстуры клади в `test/fixtures/**`. Перед финальными проверками удали
  `test/repros/`. Tarball и временные каталоги (`$PACK`, `$FIX`, `$OUT`) в
  коммит не входят.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: 14 ошибок
  `ts(2322)` в `docs/components/*.astro`. Причина в `tsconfig.json`: он включает
  `**/*.ts` (`:4`) и не исключает `dist/` (`:2`). После сборки в программу
  попадает `dist/types/html/inline-script.d.ts` (из

  Объявления `*.svg` из Vite конфликтуют с SVG-компонентами Astro. В CI джоба
  Astro пакет не собирает, поэтому там она зелёная. После шага 2 проверяй
  `test:unit`, `test:js`, `test:types` и остальные скрипты по отдельности, а
  `test:astro` запускай после `rm -rf dist`.
