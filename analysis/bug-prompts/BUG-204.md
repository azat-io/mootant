# BUG-204: мутант, который лишь замедляет проходящий тест, получает Timeout, причём недетерминированно

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.

## Контекст

Бюджет времени попытки — `scale × (ceil(factor × длительность dry run) +
constant)`, по умолчанию `3 × длительность + 250 мс`
(`core/run/get-try-limits.ts:16-28`, `core/config/resolve-run-settings.ts:29-32`);
у isolated-юнита это сумма по всем тестам файла плюс загрузка
(`core/run/plan-isolated.ts:16-44`), в Vitest — общий дедлайн для каждой
попытки юнита (`adapters/vitest/runner.ts:552`, `:853`), в node:test — сторож
процесса (`adapters/node-test/get-unit-deadline.ts`). Превышение после
достижения мутанта — `Timeout(time-limit)`/`Timeout(hang)`, подтверждаемый
одним повтором с удвоенными границами (`core/run/get-unit-evidence.ts:15-30`).
Для быстрых тестов бюджет — доли секунды, что на порядок меньше собственного
таймаута раннера (Vitest — 5 с, node:test — без таймаута). Мутант в коде
задержек/повторов/бэкоффа, который делает тест медленнее (но тест проходит),
записывается как обнаруженный (`Timeout` входит в score), а на границе бюджета
вердикт зависит от шума замера dry run и прыгает между `Timeout` и `Survived`
от прогона к прогону — один и тот же мутант в кэше может оказаться любым.

## Воспроизведение

Падающий тест — `test/repros/BUG-204.test.ts` в ветке `experiment/bug-repros`
(фикстура `test/fixtures/repros/BUG-204/`).

```bash
pnpm vitest run test/repros/BUG-204.test.ts
```

Фикстура:

```js
// test/fixtures/repros/BUG-204/src/retry.js
export async function retry(task, pause = 10) {
  try {
    return await task()
  } catch {
    let delay = Math.min(pause, 12000)
    await new Promise(resolve => {
      setTimeout(resolve, delay)
    })
    return task()
  }
}

// test/fixtures/repros/BUG-204/test/retry.check.js
import { expect, test } from 'vitest'
import { retry } from '../src/retry.js'

test('retries once', async () => {
  let calls = 0
  let value = await retry(async () => {
    calls++
    if (calls === 1) {
      throw new Error('flaky')
    }
    return 'ok'
  })
  expect(value).toBe('ok')
})

// test/fixtures/repros/BUG-204/vitest.config.js
export default {
  test: { include: ['test/**/*.check.js'], testTimeout: 30_000 },
}
```

Тест запускает `runMutants` (адаптер Vitest) и эталон `runReferenceMutants`
(`separate: true`) для мутанта `Math.min` → `Math.max` (задержка 12 с при
`testTimeout: 30_000` проекта). С задержкой 4 с и стандартным таймаутом 5 с
ошибка проявлялась не всегда: если dry run измерен под нагрузкой, бюджет
вырастает, и мутант выходит `Survived` — та же недетерминированность.
Недетерминированный вариант — фикстуры `/home/user/projects/oracle/vt/slow` и
`nt/slow` (мутант `9trb33kh`, задержки 1 с + 1 с), пять прогонов
`analysis/tools/oracle/determinism.sh … --preset strict`.

## Ожидаемое поведение

`Survived`: обычный Vitest с физически применённым мутантом проходит (тест
длится ~12 с, меньше собственного таймаута проекта 30 с). Повторные прогоны дают
один и тот же вердикт.

## Фактическое поведение

```
- [ "Survived", null ]
+ [ "Timeout", "time-limit" ]
```

`vt/slow`: `Timeout(time-limit)` в 4 прогонах из 5, `Survived` в одном;
`nt/slow`: `Survived` в первом прогоне, `Timeout(hang)` в 4 следующих; эталон
во всех случаях — survived (2,3–3,3 с на весь прогон набора).

## Подозреваемые места в коде

- `core/run/get-try-limits.ts:16-28` и `core/config/resolve-run-settings.ts:29-32`
  — маленькая константа (250 мс) при множителе 3.
- `core/run/get-unit-evidence.ts:15-30` — подтверждение удваивает тот же
  бюджет, а не проверяет, укладывается ли тест в собственный таймаут раннера.
- `adapters/vitest/runner.ts:853` — дедлайн попытки isolated-юнита считается от
  начала юнита и общего бюджета.

## Критерий готовности

- `test/repros/BUG-204.test.ts` проходит; добавлен тест для `getUnitEvidence`
  / `readIsolatedUnit`, который фиксирует новое правило подтверждения.
- Вариант исправления (с обоснованием в PR): подтверждать `time-limit` с
  бюджетом не меньше собственного таймаута теста раннера (Vitest:
  `testTimeout` теста; node:test: `--test-timeout`, если задан) или с заметно
  большей константой; либо явно отделить «медленный, но проходящий» исход от
  `Timeout` (например, `Survived` с предупреждением).
- Мутанты с бесконечным асинхронным циклом и неразрешающимся промисом в
  `test/fixtures/runner` по-прежнему `Timeout`; время полного прогона на
  `test/fixtures/runner` не растёт больше чем на одну подтверждающую попытку
  на такой мутант.
- `pnpm test` полностью зелёный (включая 100% coverage, `test:js`,
  `test:types`, `test:usage`, `test:spelling`).
