# BUG-652: подсказки перепроверки печатают `mootant …` без `npx` и не запускаются

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (изначально заявлена medium). Статус:
> подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (npm 10.9.9, Vitest 5.1.0, tarball
> из 170ec52, `mootant` не в `PATH`: строка `re-check one: mootant run src
> --mutant 69kd` и поле `recheck` из JSON в `bash -c` дают `mootant: command
> not found`, exit 127, а с `npx` та же команда отрабатывает с exit 0; то же
> при `pnpm exec`); скептик: не опроверг, но снизил до low — вердикты, score,
> код выхода и id в подсказке верны, не хватает только префикса запускателя,
> сбой громкий и обходится дописыванием `npx`, а документация в этом месте сама
> пишет `npx mootant …`. Координатор принял low.

## Контекст

Документация ставит Mootant локально и запускает через `npx`: `npm install -D
mootant`, затем `npx mootant run src` (`readme.md:77-78`,
`docs/content/guide/getting-started.mdx:68`, `:75-77`), а перепроверку мутанта
— `npx mootant run src --mutant q31p` (`getting-started.mdx:112-116`). Но
команды, которые Mootant сам печатает для копирования, начинаются с голого
`mootant`. Их собирает `formatCommand`, и первый элемент там зашит
(`cli/report/format-command.ts:77`: `let parts = ['mootant', command,
...options.paths.map(quote)]`). Где это видно:

- строка `re-check one:` в конце текстового отчёта
  (`cli/report/format-run-text-report.ts:173`);
- поле `recheck` у каждого мутанта в JSON, которое читают агенты
  (`cli/report/build-run-report.ts:101-104`; в слим-отчёт `--json` его копирует
  `cli/report/slim-run-report.ts:102`);
- блок «Run it again» на панели мутанта в HTML-отчёте
  (`cli/html/client/render-mutant-panel.ts:195-197`) и `recheck` в JSON, который
  HTML-отчёт отдаёт кнопкой скачивания
  (`cli/html/client/unpack-run-report.ts:68-71`,
  `cli/html/client/start-report.ts:443`); оба строятся из `meta.recheck`;
- команда повторного прогона на обзоре HTML-отчёта
  (`cli/html/client/render-overview.ts:150-154`). Это не `recheck`, а
  `meta.command` (`mootant run src --html`) — то же поле, что заголовок
  страницы (`cli/html/client/render-frame.ts:61`).

Все HTML-команды выводятся через `renderCommand` с кнопкой «Copy command»
(`cli/html/client/render-command.ts:12-25`). При локальной установке
`node_modules/.bin` не в `PATH`, и скопированная команда даёт `command not
found` (exit 127). Проект же обещает обратное: JSDoc `formatCommand` —
«Arguments a shell would split are quoted, so the line can be copied and run»
(`cli/report/format-command.ts:62-67`), тип отчёта — «Command line that runs
only this mutant again» (`types/report/run-report.d.ts:72-76`), документация —
«the command to re-check it» (`docs/content/guide/cli.mdx:121`) и «the command
that runs the first survivor again» (`getting-started.mdx:94-95`). Пример
сессии агента в документации (`docs/components/skill-session.ansi`) вызывает
голое `mootant` (`:3`, `:14`) и показывает такой же `recheck` (`:7`). Это
иллюстрация: самого skill на 170ec52 нет (BUG-651). Запускатель в `cli/` и
`core/` не определяется нигде: `npm_config_user_agent` не читается, а `npx`
встречается только в `adapters/node-test/resolve-command.ts`, где разбираются
скрипты тестов.

## Воспроизведение

Теста-воспроизведения для этого бага в анализе нет (в ветке
`experiment/bug-repros` тоже). Воспроизведение ручное, все команды и файлы
фикстуры приведены ниже целиком. Набросок автоматического теста — в «Критерии
готовности».

### Шаг 1. Собрать mootant из клона

В npm сейчас только заглушка `mootant@0.0.0` без `bin` (BUG-653), поэтому
`npm install -D mootant` не годится. `bin/mootant.js` импортирует
`../dist/cli/index.js`, так что перед упаковкой нужна сборка.

```bash
cd /абсолютный/путь/к/клону/mootant
# Нужен pnpm 12, как в CI (.github/actions/install-tools/action.yml:
# pnpm/action-setup, version: latest-12), например `npm i -g pnpm@12`.
# pnpm 10 не читает configDependencies из pnpm-workspace.yaml:1-2 и, по данным
# базовой линии анализа, зависает уже на `pnpm --version` внутри репозитория.
pnpm --version
pnpm install --frozen-lockfile --ignore-scripts   # так ставит CI
pnpm exec astro sync                              # так CI готовит типы перед проверками
pnpm build
pnpm pack                                         # → mootant-0.1.0.tgz в корне клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"   # *.tgz нет в .gitignore, не оставляй его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"
```

Нужен Node.js, на котором работает Vitest 5: `^22.12.0 || ^24.0.0 || >=26.0.0`
(`docs/content/guide/compatibility.mdx:22-24`). Верификаторы работали на Node
22.23.4 и npm 10.9.9.

### Шаг 2. Фикстура на npm

```bash
# Предусловие: mootant не должен лежать в PATH (глобальная установка скрывает
# баг). Команда не должна ничего напечатать:
command -v mootant

FIX="$(mktemp -d)/bug-652" && mkdir "$FIX" && cd "$FIX"
npm init -y >/dev/null && npm pkg set type=module scripts.test="vitest run"
# Не vitest@5.0.5: в npm 10.9.9 он падает с ошибкой arborist
# "Cannot read properties of null (reading 'edgesOut')".
# vitest@5 у верификаторов поставил 5.1.0.
npm i -D vitest@5 "$TGZ"
mkdir -p src test
printf 'export function getDiscount(total: number): number {\n  return total >= 100 ? 10 : 0\n}\n' > src/price.ts
cat > test/price.test.ts <<'TS'
import { expect, it } from 'vitest'
import { getDiscount } from '../src/price'
it('gives large orders 10% off', () => {
  expect(getDiscount(150)).toBe(10)
})
TS
```

Тест не проверяет ни границу 100, ни ветку с `0`, поэтому часть мутантов
выживает (у верификаторов JSON-отчёт перечислил три мутанта), и текстовый
отчёт заканчивается подсказкой перепроверки.

### Шаг 3. Скопировать напечатанные команды

```bash
# Текстовый отчёт: последняя строка — подсказка перепроверки
LINE="$(npx mootant run src | tail -1)"; echo "$LINE"
CMD="${LINE#re-check one: }"
bash -c "$CMD"; echo "exit=$?"     # команда как напечатана
npx $CMD; echo "exit=$?"           # та же команда с npx

# JSON: поле recheck у каждого мутанта отчёта
npx mootant run src --json | grep -o '"recheck":"[^"]*"'

# HTML: meta.recheck («Run it again») и meta.command (обзор и заголовок)
npx mootant run src --html >/dev/null
grep -oE '"recheck":"[^"]*"|"command":"mootant[^"]*"' .mootant/report.html | sort -u
```

Через pnpm (`pnpm exec mootant run src`, pnpm 12.16.1, mootant поставлен в
проект) верификатор получил то же самое. Как он готовил pnpm-фикстуру, не
записано, поэтому её команд здесь нет.

## Ожидаемое поведение

Каждая напечатанная команда — строка `re-check one:`, поле `recheck` в JSON,
«Run it again» и команда на обзоре HTML-отчёта — запускается копированием в
той оболочке, где пользователь запустил Mootant. Префикс выбирается по первому
подходящему пункту:

1. По первому токену `npm_config_user_agent` (`имя/версия`):

   | Как запущен Mootant | Первый токен | Префикс |
   | --- | --- | --- |
   | `npx mootant`, `npm exec mootant`, скрипт через `npm test` / `npm run` | `npm/…` | `npx mootant` |
   | `pnpm exec mootant`, скрипт через `pnpm test` / `pnpm run` | `pnpm/…` | `pnpm exec mootant` |
   | Yarn (`yarn mootant`) | `yarn/…` | `yarn mootant` |
   | `bunx mootant`, `bun run` | `bun/…` | `bunx mootant` |

2. Переменной нет (прямой `./node_modules/.bin/mootant` или
   `node node_modules/.bin/mootant`, глобальная установка) или менеджер
   неизвестен. Тогда префикс берётся по lockfile корня проекта, в порядке
   `findLockfile` (`core/cache/find-lockfile.ts:7-14`; поиск идёт вверх от
   корня, как в workspace, `:23-38`): `pnpm-lock.yaml` → `pnpm exec mootant`;
   `package-lock.json` или `npm-shrinkwrap.json` → `npx mootant`; `yarn.lock` →
   `yarn mootant`; `bun.lock` или `bun.lockb` → `bunx mootant`.
3. Нет ни переменной, ни lockfile — голое `mootant`.

Заголовок отчёта (`● mootant run src …`) не меняется: это команда «как
набрано» (`cli/report/format-header.ts:27`: «Command as typed»). Про заголовок
HTML (`cli/html/client/render-frame.ts:61`) см. «Направление исправления»,
п. 4.

## Фактическое поведение

На 170ec52, у обоих верификаторов одинаково. Id мутанта у тебя может
отличаться, бери его из своего вывода.

```text
$ command -v mootant
$ LINE="$(npx mootant run src | tail -1)"; echo "$LINE"
re-check one: mootant run src --mutant 69kd
$ bash -c "$CMD"; echo "exit=$?"
…: mootant: command not found
exit=127
$ npx $CMD; echo "exit=$?"
…                                        (отчёт: survived 1)
exit=0
$ npx mootant run src --json | grep -o '"recheck":"[^"]*"'
"recheck":"mootant run src --mutant 69kd92dczrne"
…                                        (всего три мутанта, у всех голое mootant)
$ grep -oE … .mootant/report.html | sort -u
"command":"mootant run src --html"
"recheck":"mootant run src"
```

Префикс сообщения bash зависит от версии и способа вызова. У верификатора при
подстановке `$(…)` в скрипте было `/bin/bash: line 1: mootant: command not
found`. Через `pnpm exec mootant run src` (pnpm 12.16.1) — та же строка
`re-check one:` без префикса, `bash -c` даёт exit 127.

Голое `mootant` закреплено в существующих тестах. На 170ec52 у верификатора
проходят 75 из 75 тестов в `test/cli/report/format-command.test.ts`,
`test/cli/run-mutation.test.ts`, `test/cli/report/format-run-text-report.test.ts`,
`test/cli/report/build-run-report.test.ts`,
`test/cli/html/client/render-mutant-panel.test.ts` и
`test/cli/html/client/render-overview.test.ts`.

### Направление исправления

1. Чистая функция выбора префикса (одна функция — один файл, например в
   `cli/report/`). Вход — значение `npm_config_user_agent` и путь lockfile (или
   null), выход — префикс. Разбирай только первый токен `имя/версия`: остальная
   часть строки у менеджеров разная (pnpm 12.16.1 пишет `node/?`). Значения,
   которые верификаторы видели в процессе mootant:
   - `npx` и `npm exec` (npm 10.9.9): `npm/10.9.9 node/v22.23.4 linux x64
     workspaces/false`;
   - `pnpm exec`: pnpm 12.16.1 — `pnpm/12.16.1 npm/? node/? linux x64`;
     pnpm 10.28.0 — `pnpm/10.28.0 npm/? node/v22.23.4 linux x64`;
   - Yarn 1.22.22: `yarn/1.22.22 npm/? node/v22.23.4 linux x64`;
   - `bunx` и `bun run` (Bun 1.4.4): `bun/1.4.4 npm/? node/v26.3.0 linux x64`;
   - `node node_modules/.bin/mootant` и `./node_modules/.bin/mootant`:
     переменной нет.

   Переменную читай как `process.env['npm_config_user_agent']`, по образцу
   `cli/terminal/is-unicode-supported.ts:11-13`.
2. Без user agent или с неизвестным менеджером — lockfile корня
   (`findLockfile(result.root)`), иначе голое `mootant` (см. «Ожидаемое
   поведение»). Известный user agent важнее lockfile: `npx mootant` находит
   локальный бинарник и в проекте на pnpm.
3. Префикс добавляй только к `recheck` и к команде на обзоре HTML (п. 4) — в
   `cli/run-mutation.ts` или параметром `formatCommand`. Заголовок (`command`)
   остаётся «как набрано». Если префикс добавляется в `cli/run-mutation.ts`,
   форматтеры (`format-run-text-report`, `build-run-report`, HTML-клиент)
   получают `recheck` готовой строкой, и их тесты могут остаться как есть.
   Если префикс уходит в `formatCommand` или форматтеры, голое `mootant`
   придётся поменять в тестах и хелперах: `test/cli/run-mutation.test.ts:149-153`,
   `:203-208`, `:235`, `:253`, `:273`, `:289`, `:342`;
   `test/helpers/create-run-report.ts:15`; `test/helpers/create-html-report.ts:33-35`;
   `test/cli/report/format-command.test.ts`,
   `test/cli/report/format-run-text-report.test.ts`,
   `test/cli/report/format-run-report.test.ts:13-14`;
   `test/cli/html/build-html-report.test.ts:12-14`, `:140-141`;
   `test/cli/html/client/render-frame.test.ts:22`,
   `render-mutant-panel.test.ts:61`, `render-overview.test.ts:59`,
   `unpack-run-report.test.ts:76-87`, `start-report.test.ts:624`.
4. Обзор HTML (`render-overview.ts:154`) берёт `meta.command` — то же поле, что
   заголовок страницы (`render-frame.ts:61`). Поэтому «заголовок не менять» и
   «исправить команду на обзоре» совместимы только при отдельном поле в
   `HtmlReportMeta` (`types/report/html-report.d.ts:281-322`), например
   префикса запускателя. Его заполняют `cli/html/build-html-report.ts:187-201`
   и `cli/run-mutation.ts:76-81`. Альтернатива — осознанно добавить префикс в
   `meta.command`: его JSDoc (`html-report.d.ts:303-306`) и так обещает
   «Command line of the run, which runs it again». Тогда заголовок HTML покажет
   `npx mootant run src --html`, а текстовый заголовок останется без префикса.
   Выбери вариант и закрепи его тестом.
5. Известные ограничения — опиши их в JSDoc функции:
   - `pnpm dlx` по user agent не отличить от `pnpm exec`. Верификатор получил
     при `pnpm --package=<tgz> dlx mootant` тот же
     `pnpm/12.16.1 npm/? node/? linux x64`, а напечатанная `pnpm exec mootant`
     без локальной установки падает с `Command "mootant" not found`. Про
     `yarn dlx` верификатор пишет то же, но проверен только pnpm.
   - Глобальная установка внутри проекта с lockfile получит префикс по
     lockfile. Он сработает, только если mootant стоит в проекте и локально
     (по чтению кода, не проверено). Сегодня у глобальной установки голое
     `mootant` работает, так что для неё это регресс. Уточнить можно
     проверкой, лежит ли запущенный `bin/mootant.js` внутри `node_modules`
     проекта — не проверено.

## Критерий готовности

- Чистая функция выбора префикса покрыта unit-тестом
  `test/cli/report/<имя>.test.ts`. Тесты проекта лежат в `test/` по пути
  исходника (например, `test/cli/report/format-command.test.ts`), а не рядом с
  ним. Входы и ожидаемые префиксы:

  | `npm_config_user_agent` | lockfile | Префикс |
  | --- | --- | --- |
  | `npm/10.9.9 node/v22.23.4 linux x64 workspaces/false` | любой | `npx mootant` |
  | `pnpm/12.16.1 npm/? node/? linux x64` | любой | `pnpm exec mootant` |
  | `pnpm/10.28.0 npm/? node/v22.23.4 linux x64` | любой | `pnpm exec mootant` |
  | `yarn/1.22.22 npm/? node/v22.23.4 linux x64` | любой | `yarn mootant` |
  | `bun/1.4.4 npm/? node/v26.3.0 linux x64` | любой | `bunx mootant` |
  | нет или неизвестный менеджер (например, `foo/1.0.0`) | `pnpm-lock.yaml` | `pnpm exec mootant` |
  | нет | `package-lock.json` или `npm-shrinkwrap.json` | `npx mootant` |
  | нет | `yarn.lock` | `yarn mootant` |
  | нет | `bun.lock` или `bun.lockb` | `bunx mootant` |
  | нет | нет | `mootant` |

  исправления и проходит после. При npm user agent последняя строка текста —

  HTML-отчёта есть `"recheck":"npx mootant run src"`, а первая строка текста
  (заголовок) не содержит `npx`. Набросок ниже. По чтению кода до исправления
  он падает на первой проверке (`formatCommand` всегда начинает с `mootant`),
  но он не запускался:

