# BUG-653: документированная установка `npm install -D mootant` ставит заглушку 0.0.0

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: critical (блокер релиза; решение
> координатора — по шкале анализа «инструмент неработоспособен для всех»,
> см. ниже мнение скептика). Статус: подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (в npm только `0.0.0-stage` и
> `0.0.0`, `latest` = 0.0.0; после `npm install -D mootant` команда
> `npx mootant run src` падает с `could not determine executable to run`,
> exit 1; установка из GitHub даёт `ERR_MODULE_NOT_FOUND …/dist/cli/index.js`;
> tarball, собранный из 170ec52, в чистом проекте работает); скептик: не
> опроверг, но предлагал high — вердикты не искажаются (сбой громкий, ложного
> score нет), а исправляется это шагом релиза (выпустить версию и снять
> заглушку), а не правкой кода. Координатор оставил critical: документированная
> установка не работает ни у одного нового пользователя.

## Контекст

Команду `npm install -D mootant` дают три места: `readme.md:77` (затем
`npx mootant run src`, строка 78), `docs/content/guide/getting-started.mdx:68`
(затем `npx mootant run src`, строка 76) и главная страница сайта —
`docs/components/Hero.astro:54` (`command="npm install -D mootant"`; страница
собирается через `docs/layouts/Home.astro:25`). Сайт деплоится при каждом push
в `main` (`.github/workflows/docs.yml:3-6`). В npm (на 2026-11-04) опубликованы
только `0.0.0-stage` и `0.0.0` от 2026-10-10, `latest` = 0.0.0. Это заглушка
для настройки OIDC trusted publishing («OIDC trusted publishing setup package
for mootant»; у `0.0.0-stage` описание «Temporary package placeholder for
staged publishing»): в tarball только `package.json` без `bin` и `scripts` и
README «DO NOT USE THIS PACKAGE». Версии 0.1.0 из `package.json:3` в npm нет,
тегов и релизов на GitHub нет. Ни плашка `readme.md:68` («Early development.
Expect breaking changes.»), ни плашка сайта
`docs/components/DevelopmentBanner.astro:13` (выводится на всех страницах
через `docs/components/Body.astro:19`) не говорят, что пакета нет. Бейдж
`readme.md:21` показывает npm v0.0.0, но это слабый намёк.

Установка из GitHub (`npm install -D github:azat-io/mootant`) тоже не
работает: `dist/` в git нет (`.gitignore:13`), пакет приходит без него, и
`bin/mootant.js:3` (`import { run } from '../dist/cli/index.js'`) падает с
`ERR_MODULE_NOT_FOUND` (почему npm не собирает пакет — в «Что сделать», п. 4).
`npx mootant …` без локальной установки (так команды показаны в
`docs/content/guide/cli.mdx:21,73,108,117,134` и на страницах
`docs/content/mutators/*.md`) скачивает `mootant@latest`, то есть ту же
заглушку, и падает с той же ошибкой. Любой новый пользователь и любой агент
останавливаются на первом шаге.

Релизный workflow `.github/workflows/release.yml` (тег `v*` — строки 3-6,
`id-token: write` — 10, `npm publish --no-git-checks` — 53) выглядит готовым,
но OIDC-публикацию из сессии проверить нельзя. По данным скептика, у workflow
ещё не было ни одного запуска.

## Воспроизведение

Теста-воспроизведения нет: дефект в реестре npm и в документации, а не в
коде. Нужны сеть (registry.npmjs.org, github.com) и Node.js 22.12+ (Vitest 5
требует `^22.12.0 || ^24.0.0 || >=26.0.0`,
`docs/content/guide/compatibility.mdx:22-24`), для шага 4 — ещё pnpm 12.
Шаги 1–3 идут вне клона, во временных каталогах. Результаты в комментариях
получены верификатором на npm 10.9.9 и Node 22.23.4. Если
`npm view mootant dist-tags.latest` печатает уже не `0.0.0`, выпуск
состоялся: проверяйте критерий «после выпуска».

### Шаг 1. Что опубликовано в npm

```bash
npm view mootant             # mootant@0.0.0, "OIDC trusted publishing setup package for mootant", latest: 0.0.0
npm view mootant versions    # две версии: 0.0.0-stage и 0.0.0
npm view mootant@0.1.0       # E404: No match found for version 0.1.0
```

### Шаг 2. Документированный путь ставит заглушку

```bash
D="$(mktemp -d)" && cd "$D" && npm init -y >/dev/null
npm install -D mootant                # в package.json появляется "mootant": "^0.0.0"
ls node_modules/mootant               # только README.md («DO NOT USE THIS PACKAGE») и package.json без bin
npx mootant run src; echo "exit=$?"   # npm error could not determine executable to run; exit=1
```

Каталога `src` нет, но это не важно: npx падает раньше. Та же ошибка у
`npx mootant --version` и `npx mootant list src`. Без локальной установки —
то же самое:

```bash
E="$(mktemp -d)" && cd "$E"
npx --yes mootant --version; echo "exit=$?"   # npm error could not determine executable to run; exit=1
```

### Шаг 3. Установка из GitHub тоже не работает (около 2 минут)

Ставится текущий HEAD ветки `main` (на момент анализа — 170ec52).

```bash
G="$(mktemp -d)" && cd "$G" && npm init -y >/dev/null
npm install -D github:azat-io/mootant   # ~2 мин: npm ставит в клоне все devDependencies
ls node_modules/mootant                 # каталога dist/ нет
npx mootant --version; echo "exit=$?"
# Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/node_modules/mootant/dist/cli/index.js'
#   imported from …/mootant/bin/mootant.js
# exit=1
```

### Шаг 4. Рабочий пакет из исходников (эталон и проверка исправления)

`bin/mootant.js` импортирует `../dist/cli/index.js`, а скриптов `prepack` и
`prepare` нет, поэтому перед `pnpm pack` обязательна сборка: без `pnpm build`
tarball получится без `dist/`. Нужен pnpm 12 (`contributing.md:98`; в CI —
`latest-12`, `.github/actions/install-tools/action.yml:14`; поля
`packageManager` в `package.json` нет, corepack версию не выберет). pnpm 10 с
этим репозиторием не работает из-за `configDependencies` в
`pnpm-workspace.yaml:1-2`: в анализе у pnpm 10.28 `pnpm --version` внутри
репозитория зависал, а установка падала с «doesn't have an integrity
checksum». Поставьте pnpm 12 любым способом (например, `npm i -g pnpm@12`;
этот способ не проверялся) и проверьте версию вне клона.

```bash
# в корне клона azat-io/mootant
pnpm install
pnpm build
pnpm pack                          # mootant-0.1.0.tgz в корне клона (у верификатора 648 374 байт)
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"      # *.tgz нет в .gitignore, не оставляйте его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"

DEMO="$(mktemp -d)"
cp -R docs/demo/. "$DEMO/"         # демо-проект сайта из репозитория: 8 файлов в src/, тесты на Vitest
cd "$DEMO"
npm i -D "$TGZ"
npx mootant list src; echo "exit=$?"   # у верификатора (без vitest): 99 мутантов в 8 файлах, exit=0
npm i -D vitest@5                      # не vitest@5.0.5: в npm 10.9.9 он падает с 'edgesOut' (баг arborist)
npx mootant --version                  # у верификатора: mootant/0.1.0 linux-x64 node-v22.23.4
npx mootant run src; echo "exit=$?"
```

`run` на копии `docs/demo` верификаторы не запускали. На своей фикстуре из 6
мутантов с `vitest@5` (5.1.0) верификатор получил `killed 4, survived 2`,
score 66.67%, exit 0. Путь `git clone` → `pnpm install` → `pnpm build` →
`pnpm pack` → установка tarball в чистый проект он прошёл целиком на pnpm
12.16.1: `--version`, `list` и `run` завершились с кодом 0.

## Ожидаемое поведение

Либо `npm install -D mootant` ставит работающую версию (0.1.x), и
`npx mootant run src` запускается. Либо, пока выпуска нет, документация
(readme, getting-started, главная страница сайта и плашка) прямо говорит, что
пакет ещё не опубликован и что `npm install -D mootant` ставит заглушку, и
даёт рабочий путь установки. После выпуска те, кто уже поставил заглушку,
узнают, что им нужен `npm i -D mootant@latest`.

## Что сделать

1. Главное исправление — выпуск; его делает мейнтейнер. Скрипт `release`
   (`package.json:56`): `release:check` (`pnpm test && pnpm run build`, строка
   57) → `release:version` → `release:prepare` → `release:git` (коммит
   `build: publish v…`, тег `v$npm_package_version` и
   `git push --atomic origin HEAD v…`, строки 58-62); тег запускает
   `.github/workflows/release.yml`. В сессии — только проверка готовности
   пакета: шаг 4 «Воспроизведения». `pnpm release:check` запускать не
   обязательно (см. «Ограничения»: после сборки `test:astro` даёт ложные
   ошибки, а у `test:unit` есть зависимости от окружения).

   Номер первой версии — решение мейнтейнера, в критериях он не фиксируется.
   Проверено чтением changelogen 0.6.2 (версия из `pnpm-lock.yaml`), не
   запускалось: `release:version` (`changelogen --output changelog.md --release
   --no-commit --no-tag`, строка 66) всегда поднимает версию из
   `package.json`, причём у 0.x коммит `feat` даёт patch, а breaking — minor
   (`bumpVersion` в `node_modules/changelogen/dist/shared/changelogen.*.mjs`).
   Значит, `pnpm release` из 0.1.0 выпустит 0.1.1 (или 0.2.0, если в истории
   есть breaking-коммит; в последних 50 коммитах до 170ec52 их нет, вся
   история не проверялась), но не 0.1.0. А `changelogen --release -r 0.1.0`
   при `"version": "0.1.0"` завершится с «Unable to bump version based on
   changes.» (`node_modules/changelogen/dist/chunks/default.mjs:63-71`).

2. Пока выпуска нет — честная документация в четырёх местах: `readme.md`
   (раздел «Getting started», 66-86), `docs/content/guide/getting-started.mdx`
   («Installation» и «First run», 63-77), главная страница
   (`docs/components/Hero.astro:54`) и плашка сайта
   (`docs/components/DevelopmentBanner.astro:13`). Написать, что пакет ещё не
   опубликован в npm, что `npm install -D mootant` и `npx mootant` без
   локальной установки получают заглушку 0.0.0, и дать путь из исходников:

   ```bash
   git clone https://github.com/azat-io/mootant.git
   cd mootant
   pnpm install      # нужен pnpm 12
   pnpm build
   pnpm pack         # mootant-0.1.0.tgz
   cd /path/to/your-project
   npm install -D vitest@5 /path/to/mootant/mootant-0.1.0.tgz   # vitest@5 — для проектов на Vitest
   npx mootant run src
   ```

   Не предлагать `npm install -D github:azat-io/mootant`: это не работает
   (шаг 3). Шаг установки в проект оставлять обязательным и после выпуска: по
   эксперименту анализа `npx --package=<tgz> mootant run src` без локальной
   установки в проекте на Vitest падает с `Error: mootant and the project load
   different copies of Vitest (none, …/node_modules/vitest); install mootant
   as a devDependency of the project.` Как переделать `Hero.astro` (заменить
   команду, добавить оговорку или вести на getting-started) — на усмотрение;
   главное, чтобы главная не вела на заглушку. После выпуска строки «не
   опубликован» убрать.

3. Предупредить тех, кто уже поставил заглушку. У них в `package.json` стоит
   `"mootant": "^0.0.0"`, а это `>=0.0.0 <0.0.1-0` (semver 7.7.4 из npm
   10.9.9, `classes/range.js:322-355`): 0.1.x в диапазон не входит, и после
   выпуска `npm install` и `npm update` оставят 0.0.0. В readme или заметках
   к выпуску (`changelog.md`, GitHub Release) нужна строка
   `npm i -D mootant@latest`.

4. Не чинить установку из GitHub добавлением `prepare` в рамках этой задачи:
   выпуск это не заменит. Прежний довод «`prepare` поставит каждому
   пользователю git-зависимости все devDependencies» неверен: npm ставит их
   уже сейчас. В `package.json:50` есть `scripts.build`, поэтому pacote 19.0.2
   (npm 10.9.9) при подготовке git-зависимости выполняет в клоне
   `npm install --force` с `--include=dev` (`lib/git.js:152-191`,
   `lib/fetcher.js:99-120`) — отсюда ~2 минуты на шаге 3. При упаковке же он
   запускает только `prepare` (`lib/dir.js:30-36`), которого нет, поэтому
   `dist/` не появляется. `prepare` добавил бы к подготовке сборку
   (`vite build`); пройдёт ли она в дереве, поставленном npm без
   `pnpm-lock.yaml`, не проверено. Поддерживать ли установку из GitHub —
   отдельное решение мейнтейнера.

5. Смоук-тест упакованного пакета в CI, чтобы следующий выпуск не сломал
   установку: новый джоб под `jobs:` в `.github/workflows/test.yml` по
   образцу соседних (например, `js`, строки 85-111: harden-runner с
   `egress-policy: block`, actions по SHA, `install-tools`,
   `install-dependencies`, `build-package`). `registry.npmjs.org` в allowlist
   уже есть. Набросок (в CI не запускался):

   ```yaml
   package:
     name: Package
     runs-on: ubuntu-latest

     steps:
       - name: Harden Runner
         uses: step-security/harden-runner@46b06cea07f9e64621fdf066ba77ac6915163d43 # v2.22.3
         with:
           egress-policy: block
           allowed-endpoints: >
             api.github.com:443 github.com:443 registry.npmjs.org:443
             release-assets.githubusercontent.com:443

       - name: Checkout
         uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1

       - name: Install Tools
         uses: ./.github/actions/install-tools

       - name: Install Dependencies
         uses: ./.github/actions/install-dependencies

       - name: Build Package
         uses: ./.github/actions/build-package

       - name: Test Packed Package
         run: |
           pnpm pack
           tgz="$PWD/$(ls mootant-*.tgz)"
           project="$(mktemp -d)"
           cp -R docs/demo/. "$project/"
           cd "$project"
           npm install -D "$tgz"
           npx mootant list src
   ```

   Копия `docs/demo` во временном каталоге — чтобы не менять файлы
   репозитория; vitest для `list` не нужен. При желании тот же шаг можно
   добавить в `release.yml` перед `npm publish` (сейчас на теге тесты не
   запускаются), но укрепление релиза — отдельная задача.

6. Вне рамок задачи. `npx skills add azat-io/mootant`
   (`docs/content/guide/getting-started.mdx:142`,
   `docs/components/Skill.astro:39`; в git нет `SKILL.md`) — отдельный баг (в
   анализе BUG-651). Замечания к `release.yml` — тоже отдельно: например,
   `--no-git-checks` (строка 53) — флаг pnpm, а не npm (по эксперименту
   анализа npm 11.19.1 пишет `Unknown cli config "--git-checks"`).

## Критерий готовности

- Автотеста, который падает до исправления, у этого бага нет: дефект в
  реестре npm и в документации. Его роль играет смоук-джоб из п. 5. Перед
  коммитом прогоните его команды локально: на собранном tarball
  `npx mootant list src` на копии `docs/demo` завершается с кодом 0, а после
  `rm -rf node_modules/mootant/dist` во временном проекте падает с
  `ERR_MODULE_NOT_FOUND` и ненулевым кодом (следует из `bin/mootant.js:3`, не
  запускалось). Значит, смоук ловит пакет без `dist/`.
- До выпуска (выполнимо в сессии): в `readme.md`, `getting-started.mdx`,
  `Hero.astro` и `DevelopmentBanner.astro` нет рекомендации
  `npm install -D mootant` без оговорки, что пакет не опубликован
  (`grep -rn "install -D mootant" readme.md docs/` — каждое совпадение стоит
  рядом с оговоркой или убрано). Путь из исходников, скопированный из
  документации буквально (проект — копия `docs/demo` во временном каталоге),
  даёт `npx mootant --version` → `mootant/0.1.0 …`, `npx mootant list src` с
  кодом 0, а `npx mootant run src` печатает отчёт, а не ошибку установки.
- После выпуска (проверяет мейнтейнер вне сессии): `npm view mootant
  dist-tags.latest` — не `0.0.0`; в чистом каталоге
  `npm init -y && npm i -D vitest@5 mootant && npx mootant --version`
  печатает `mootant/<выпущенная версия> …`; строки «не опубликован» убраны;
  строка `npm i -D mootant@latest` для владельцев `^0.0.0` есть в readme или
  в заметках к выпуску.
- Вместо «`pnpm test` полностью зелёный» (правки только в Markdown, MDX,
  Astro и YAML): `pnpm test:format` (Prettier проверяет md, mdx, astro и yml,
  `package.json:70`) и `pnpm test:spelling` (каталог `.github` cspell не
  проверяет, `cspell.config.ts:40`). Если менялись `.astro` — ещё
  `pnpm test:js` (ESLint проверяет и Astro), `pnpm test:css` и
  `pnpm test:astro` на дереве без `dist/` (`rm -rf dist`). Если менялся
  workflow — `pnpm test:usage` (knip 6.44.0 разбирает `run:`-шаги в
  `.github/workflows`). `test:unit` и `test:types` такие правки не
  затрагивают; если запускаете — по отдельности, с оговорками из
  «Ограничений».

## Ограничения

- Соблюдай стиль проекта: строгий ESLint (`@azat-io/eslint-config`,
  проверяет и `.astro`), stylelint для `{cli,docs}/**/*.{astro,css}`
  (`package.json:69`), cspell, Prettier для Markdown, MDX, Astro и YAML
  (`package.json:70`).
- Не публикуй пакет, не создавай теги и не запускай `pnpm release`,
  `pnpm release:version` и `pnpm release:git` без явного разрешения
  мейнтейнера: они меняют `package.json`, создают `changelog.md`, коммитят,
  ставят тег и пушат (`package.json:56-66`).
- Не меняй `version`, `exports`, `bin` и `files` в `package.json`: задача —
  выпуск и документация, а не формат пакета.
- В анализе теста-воспроизведения для этого бага нет. Если кроме CI-джоба
  добавляете автоматическую проверку, не кладите её в `test/repros/`: этот
  каталог не исключён ни из ESLint, ни из knip, cspell или tsc. Исключён
  только `test/fixtures/**` (`eslint.config.ts:15`, `knip.config.ts:5`,
  `cspell.config.ts:44`, `vitest.config.ts:18`, `tsconfig.json:2`). Тесты
  пишите в стиле проекта под строгий ESLint (имена файлов, `describe`/`it`,
  порядок импортов, JSDoc), фикстуры кладите в `test/fixtures/**`. Tarball и
  временные каталоги в коммит не входят.
- `pnpm test` после `pnpm build` (а сборка нужна для `pnpm pack`) даёт ложные
  ошибки `test:astro`: 14 ошибок `ts(2322)` в `docs/components/*.astro`.
  Причина: `tsconfig.json:2-4` включает `**/*.ts` и не исключает `dist/`.
  После сборки в программу попадает `dist/types/html/inline-script.d.ts` (из
  `types/html/inline-script.d.ts:1`) с `/// <reference types="vite/client" />`,
  и объявления `*.svg` из Vite конфликтуют с SVG-компонентами Astro. В CI
  джоба Astro пакет не собирает (`.github/workflows/test.yml:10-33`), поэтому
  там она зелёная. Это не регресс ваших правок: проверяйте `test:unit`,
  `test:js` и `test:types` по отдельности, а `test:astro` — после
  `rm -rf dist`. По той же причине повторный `pnpm release:check` краснеет на
  `test:astro`.

  Полный набор идёт около 9 минут последовательно на свободной 4-ядерной
