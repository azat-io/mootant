# BUG-200: лимит срабатываний сайтов превращает «горячий, но конечный» мутант в Timeout

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (в анализе была medium). Статус:
> подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест падает ровно как
> описано: оба мутанта получают `["Timeout", "hit-limit"]`, а обычный Vitest с
> вписанными мутантами проходит; с нуля на упакованном mootant то же для
> Vitest 5.1.0, для `--fast` и для node:test, score 100 вместо 84,62);
> скептик: не опроверг, но снизил до low — это задокументированный компромисс
> эвристики (`docs/content/guide/configuration.mdx:436-441`), Stryker 10.1.1
> делает так же, а `run.hitLimit` даёт обходной путь; дефектом остаются
> завышенный score и сообщение «likely stuck in a loop» у мутанта, чей тест
> проходит за миллисекунды.

## Контекст

Mootant ставит мутанту `Timeout` (в score такой мутант считается
обнаруженным), как только код вычислил больше сайтов мутантов, чем разрешает
hit limit. Лимит одной попытки (теста) или загрузки тестового файла равен
`max(floor, factor × hits dry run)`, по умолчанию `max(100000, 100 × hits)`
(`core/config/resolve-run-settings.ts:25-28`, `core/run/get-try-limits.ts:16-28`).
На isolated-пути (режим по умолчанию) лимит юнита — это лимит загрузки файла
плюс сумма лимитов всех его тестов (`core/run/plan-isolated.ts:24-40`), то есть
не меньше (1 + число тестов файла) × 100000. В репро с одним тестом это
200000, то же число стоит в сообщении. Лимит на отдельный тест действует
только в `--fast` (batch: `core/run/plan-batch.ts:92-96`,
`adapters/vitest/runner.ts:847`); у адаптера node:test batch-режима нет
(`adapters/node-test/index.ts:24`).

Превышение окончательно. На isolated-пути его проверяют первым, раньше всех
остальных фактов (`core/run/read-isolated-unit.ts:31-38`), а на подтверждение
повтором уходят только `time-limit` и `hang` (`core/run/get-unit-evidence.ts:22-28`).
В batch `hit-limit` тоже окончателен (`core/run/apply-batch-result.ts:164-171`).
В рантайме `hit()` бросает `MootantHitLimitError` прямо в пользовательский код
(`core/runtime/install-mutant-runtime.ts:40-44`), и каждый следующий `hit()`
бросает тоже (`types/adapter/mutant-runtime.d.ts:16-17`). Код, документация и
сообщение объясняют правило бесконечным циклом: «only a loop through sites
gets there» (`core/run/classify-try.ts:6-7`), «A mutant that goes over it, such
as a loop made endless, counts as a timeout without waiting for the time
limit» (`docs/content/guide/configuration.mdx:436-441`), «the code is likely
stuck in a loop» (`core/runtime/create-hit-limit-error.ts:21`), «the hit
counter stopped a loop» (`types/run/try-cause.d.ts:13`).

На деле лимит ловит и конечного мутанта, который на быстром тесте поднимает
число вычислений сайтов выше лимита юнита: отключённую мемоизацию или кэш,
удалённый `break` или ранний `return` в поиске, линейный обход вместо
бинарного. Тест с таким мутантом проходит за миллисекунды, то есть мутант
выжил, а Mootant записывает его как обнаруженный. В итоге score завышен,
непроверенный кэш спрятан от пользователя, а сообщение говорит о бесконечном
цикле. Затронуты оба адаптера (Vitest и node:test). По возвращаемым значениям
такие мутанты эквивалентны оригиналу, убить их может только spy- или
перф-тест.

Почему серьёзность low. Поведение задокументировано как эвристика.
Stryker 10.1.1 делает то же самое: лимит — `100 × hits` самого мутанта без
пола (`@stryker-mutator/core/dist/src/mutants/mutant-test-planner.js:16`,
`:126`), результат — окончательный `Timeout` «Hit limit reached»
(`@stryker-mutator/api/dist/src/test-runner/run-result-helpers.js:4-11`). По
замеру скептика Stryker на этой фикстуре тоже даёт обоим мутантам `Timeout`
(score 100%), а при `fib(18)` даёт `Timeout` там, где Mootant благодаря полу
100000 даёт `Survived`. Репро с одним тестом в файле — худший случай: тот же
`fib(25)` плюс 19 тривиальных тестов в файле даёт обоим мутантам `Survived`, с
4 тестами — `Timeout` (замеры скептика). Обходной путь — `run.hitLimit` в
конфигурации, CLI-флага для него нет. Довод против полного снятия находки:
документация обещает лишь досрочную остановку («without waiting for the time
limit»), а таймер этим мутантам `Timeout` не дал бы. С поднятым лимитом
временной лимит не сработал ни при одном проверенном n от 22 до 33.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создай
сам. Нужны Node.js 22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:23-24`) и pnpm 12. В CI стоит
`latest-12` (`.github/actions/install-tools/action.yml:14`), а pnpm 10 не
читает `configDependencies` из `pnpm-workspace.yaml:1-2`, и даже `pnpm
--version` внутри репозитория у него зависает. Счётчик сайтов
детерминирован, поэтому результат не зависит от нагрузки машины.

### Шаг 1. Падающий тест на исходниках (сборка не нужна)

Тест импортирует адаптер из исходников. Без собранного `runner.js` рядом с
модулем адаптер берёт воркер-раннер из `runner.ts`
(`adapters/vitest/get-runner-path.ts:12-15`). Тест фикстуры назван
`*.check.js`, а `test/fixtures/**` исключён из корневого Vitest
(`vitest.config.ts:18`), поэтому корневой прогон фикстуру не подхватит.
Хелперы `test/helpers/create-built-ins.ts` и
`test/helpers/run-reference-mutants.ts` есть в 170ec52. Все файлы шага
временные и в коммит не входят (см. «Ограничения»).

```bash
# в корне клона azat-io/mootant
pnpm install
mkdir -p test/fixtures/repros/BUG-200/src test/fixtures/repros/BUG-200/test test/repros

cat > test/fixtures/repros/BUG-200/package.json <<'EOF'
{
  "name": "bug-200",
  "private": true,
  "type": "module"
}
EOF

cat > test/fixtures/repros/BUG-200/vitest.config.js <<'EOF'
export default {
  test: {
    include: ['test/**/*.check.js'],
  },
}
EOF

cat > test/fixtures/repros/BUG-200/src/memo.js <<'EOF'
let memo = new Map()

export function fib(n) {
  if (n < 2) {
    return n
  }
  if (memo.has(n)) {
    return memo.get(n)
  }
  let value = fib(n - 1) + fib(n - 2)
  memo.set(n, value)
  return value
}
EOF

cat > test/fixtures/repros/BUG-200/test/memo.check.js <<'EOF'
import { expect, test } from 'vitest'

import { fib } from '../src/memo.js'

test('fib', () => {
  expect(fib(25)).toBe(75025)
})
EOF

cat > test/repros/BUG-200.test.ts <<'EOF'
import { describe, expect, it } from 'vitest'
import { readFileSync } from 'node:fs'
import path from 'node:path'

import { runReferenceMutants } from '../helpers/run-reference-mutants'
import { createBuiltIns } from '../helpers/create-built-ins'
import { vitestAdapter } from '../../adapters/vitest/index'
import { runMutants } from '../../core/run-mutants'

/**
 * Fixture project: a memoized `fib` and one test of `fib(25)`. Without the
 * memo, `fib(25)` makes 242785 calls, a few milliseconds of work, but 1.4 to 2
 * million mutant site evaluations, over the hit limit of its isolated unit:
 * `max(100000, 100 × hits of the dry run)` for loading the test file plus the
 * same for its one test, 200000 here.
 */
let root = path.join(import.meta.dirname, '../fixtures/repros/BUG-200')

describe('BUG-200: a mutant that only makes code hotter ends as a hit-limit Timeout', () => {
  it('lets the tests decide the mutants that turn the memo off', { timeout: 180_000 }, async () => {
    let result = await runMutants({
      builtIns: createBuiltIns('vitest', vitestAdapter()),
      concurrency: 2,
      paths: ['src'],
      cache: false,
      cwd: root,
    })
    let source = readFileSync(path.join(root, 'src/memo.js'), 'utf8')
    let memoOff = result.results.filter(({ mutant }) => {
      let original = source.slice(mutant.start, mutant.end)
      return (
        (original === 'memo.has(n)' && mutant.replacement === 'false') ||
        original === 'memo.set(n, value)'
      )
    })
    expect(memoOff).toHaveLength(2)

    let reference = await runReferenceMutants(
      root,
      memoOff.map(({ mutant }) => mutant),
      { sources: ['src/memo.js'], separate: true },
    )
    // A plain Vitest run of each applied mutant passes: the tests do not
    // detect either mutant.
    expect(reference.original).toBe(true)
    expect([...reference.killed.values()]).toStrictEqual([false, false])

    // Actual: both end as `Timeout` with cause `hit-limit`, counted as
    // detected in the score.
    expect(memoOff.map(({ status, cause }) => [status, cause])).toStrictEqual([
      ['Survived', null],
      ['Survived', null],
    ])
  })
})
EOF

pnpm exec vitest run test/repros/BUG-200.test.ts
```

Что делает тест. `runMutants` с одним адаптером Vitest
(`createBuiltIns('vitest', vitestAdapter())`, `concurrency: 2`,
`paths: ['src']`, `cache: false`) решает мутантов фикстуры. Тест выбирает двух
мутантов, отключающих мемоизацию: `memo.has(n)` → `false` (мутатор
`condition`, строка 7 `memo.js`) и `memo.set(n, value)` → `;`
(`statement-removal`, строка 11), и проверяет, что их ровно два. Затем
`runReferenceMutants(root, …, { sources: ['src/memo.js'], separate: true })`
вписывает каждого мутанта в свою копию фикстуры и прогоняет копию обычным
Vitest в отдельном экземпляре (`test/helpers/run-reference-mutants.ts:120-154`).
Нетронутая копия проходит (`original: true`), обе копии с мутантами тоже
(`killed` — `[false, false]`). Последний `expect` ждёт `['Survived', null]` для
обоих мутантов. Комментарий в начале теста исправлен по замерам
верификаторов: в анализе там стояло «about 1.2 million» и лимит одной
попытки. У верификатора тест шёл от 7,5 до 15,7 с.

### Шаг 2. CLI на упакованном mootant: Vitest, `--fast`, обходной путь, node:test

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому для CLI нужна
сборка. Ставь `vitest@5` (сейчас это 5.1.0; в lockfile репозитория 5.0.5,
баг воспроизводится на обеих версиях), а не `vitest@5.0.5`: в npm 10.9.9
установка 5.0.5 падает с `Cannot read properties of null (reading
'edgesOut')`. Это баг arborist, не mootant. `mootant run` без путей падает с
«mootant run needs paths, such as "mootant run src".» (`core/run-mutants.ts:184`),
поэтому путь `src` указан явно. Команды рассчитаны на одну сессию shell: они
используют переменные `PACK`, `TGZ`, `FIX`, `NT` и функцию `show`.

```bash

      console.log(m.id, m.status, m.cause, m.path, m.isolatedBecause,
        JSON.stringify(m.original), "->", JSON.stringify(m.replacement))
      if (m.status === "Timeout") console.log("   ", m.message)
    }
    let { totalKilled, totalTimeout, totalSurvived, score, runs } = report.summary
    console.log({ totalKilled, totalTimeout, totalSurvived, score, runs })

EOF
cat > test/memo.test.js <<'EOF'

import { fib } from '../src/memo.js'

test('fib', () => {
  expect(fib(25)).toBe(75025)

EOF
npm i -D vitest@5 "$TGZ"
npx vitest run; echo "exit=$?"   # без мутантов: 1 passed, exit=0
npx mootant run src --json --all --verbose --no-cache > default.json
npx mootant run src --json --all --verbose --no-cache --fast > fast.json
show default.json
show fast.json

# ручная проверка двух мутантов (GNU sed): вписать, прогнать vitest, вернуть файл

npx vitest run; echo "exit=$?"   # 1 passed, exit=0
cp "$PACK/memo.js" src/memo.js

npx vitest run; echo "exit=$?"   # 1 passed, exit=0
cp "$PACK/memo.js" src/memo.js

# обходной путь: поднятый hit limit

npx mootant run src --json --all --verbose --no-cache > raised.json
```

## Ожидаемое поведение

Вердикт совпадает с тем, что дал бы обычный прогон тестов с таймером. С
вписанной мутацией `npx vitest run` и `node --test` проходят, тест идёт 4–7 мс,
а `fib(25)` без мемоизации — это 242 785 вызовов (замеры верификатора).
Значит, `memo.has(n)` → `false` и `memo.set(n, value)` → `;` — `Survived` с
`cause: null`, и по умолчанию, и с `--fast`, и на node:test. Сводка шага 2
для Vitest: `totalKilled: 11`, `totalSurvived: 2`, `score: 84.62`, как сейчас с
поднятым `run.hitLimit`. Мутант, который делает цикл действительно
бесконечным, по-прежнему `Timeout`.

Решение по итогам перепроверки — «стоит описать в документации». Поэтому
даже если вердикты решено не менять, документация и сообщение об ошибке
должны честно говорить: hit limit может дать `Timeout` и конечному, но
«горячему» мутанту, а лимит isolated-юнита считается на весь тестовый файл.
Они же должны подсказывать, как этого избежать (`run.hitLimit`).

## Фактическое поведение

Шаг 1 падает на последнем `expect`. Предыдущие проходят: мутантов два,
`reference.original` — `true`, `killed` — `[false, false]`. Сокращённый diff
Vitest:

```
- [ "Survived", null ], [ "Survived", null ]
+ [ "Timeout", "hit-limit" ], [ "Timeout", "hit-limit" ]
```

Шаг 2 (оба верификатора, Vitest 5.1.0):

- По умолчанию оба мутанта — `Timeout` с `cause: "hit-limit"` и
  `path: "isolated"`. Сообщение: «mootant stopped the test after 200000
  evaluations of mutant sites, at mutant twzenj03mape; the code is likely
  stuck in a loop.» Здесь `twzenj03mape` — сайт `n < 2`, на котором счётчик
  перешёл лимит, а не проверяемый мутант. Подтверждающего прогона нет:
  `runs` — `{ dry: 1, isolated: 1 }`. Сводка: 13 мутантов, `totalKilled: 11`,
  `totalTimeout: 2`, `totalSurvived: 0`, `score: 100`. В отчёте `--verbose` у
  `jngxgvvzznh2` `duration` 37 мс.
- С `--fast` `memo.has(n)` → `false` получает `Timeout hit-limit` на
  batch-пути, и в сообщении стоит лимит попытки 100000. `memo.set(n, value)` →
  `;` получает `Timeout hit-limit` на isolated-пути
  (`isolatedBecause: "first-reach"`).
- Ручная проверка: с каждым вписанным мутантом `npx vitest run` даёт 1 passed
  и exit 0.
- С `.mootantrc.json` (`floor` 1e9, `factor` 1e6) оба мутанта `Survived`,
  `score: 84.62` (скептик, 2 прогона). Граница по замеру верификатора: с
  `floor` 400000 и 700000 (лимит юнита 800000 и 1400000) мутанты ещё
  получают `hit-limit`, с `floor` 1000000 (лимит 2000000) — уже `Survived`.
  Значит, юнит с мутантом вычисляет от 1,4 до 2 млн сайтов.
- node:test: оба мутанта `Timeout hit-limit` на isolated-пути (лимит юнита
  тоже 200000), `score: 100`, 3 прогона из 3. `node --test` с вписанным
  мутантом даёт pass 1, fail 0.

Для `fib(n)` с одним тестом в файле при лимитах по умолчанию n = 18 и 20 дают
`Survived`, n = 22, 25, 30 и 33 — `Timeout hit-limit` (скептик; n = 21 не
проверялось).

## Подозреваемые места в коде

- `core/run/read-isolated-unit.ts:31-38` — превышение лимита юнита сразу даёт
  окончательный `Timeout`. Проверка идёт раньше остальных и не смотрит, сколько
  длился юнит и прошли ли тесты до броска `MootantHitLimitError`.
- `core/run/get-unit-evidence.ts:22-28` — на подтверждение уходят только
  `time-limit` и `hang`, а `hit-limit` остаётся окончательным (это закрепляет
  `test/core/run/get-unit-evidence.test.ts:39`).
- `core/run/plan-isolated.ts:23` и `core/run/get-try-limits.ts:22-26` —
  подтверждающий юнит получает `scale = 2`, но удваивается только таймаут:
  `hitLimit` от `scale` не зависит.
- `core/run/classify-try.ts:26-28` — то же правило для отдельной попытки, на
  isolated- и на batch-пути. JSDoc `:6-7` объясняет его бесконечным циклом.
- `core/run/apply-batch-result.ts:164-171` (и JSDoc `:125-126`) — в `--fast`
  `hit-limit` окончателен, а `time-limit` ждёт подтверждения.
- `core/runtime/install-mutant-runtime.ts:40-44` — бросок внутри кода
  пользователя превращает «долго» в «упал». После такого провала
  isolated-юнит не запускает остальные тесты файла
  (`adapters/vitest/runner.ts:889-891`, для node:test —
  `adapters/node-test/preload/create-try-tracker.ts:207-209`).
- `core/config/resolve-run-settings.ts:25-28` — `factor` 100 и `floor` 100000.
  Подъём умолчаний только сдвигает границу (см. ниже).
- Тексты: `core/runtime/create-hit-limit-error.ts:21`,
  `docs/content/guide/configuration.mdx:436-441` (там же «in each test», хотя

### Направление исправления: что сработает, а что нет

Всё ниже выведено чтением кода 170ec52, запуском не проверялось, кроме
отмеченных замеров.

- Поднять умолчания `factor` и `floor` на порядки — не исправление, а сдвиг
  границы. Число вычислений растёт с n экспоненциально: `fib(30)` делает в 11
  раз больше вызовов, чем `fib(25)`, а `fib(25)` уже требует лимита юнита
  больше 1,4 млн (замер: с лимитом 2 млн оба мутанта `Survived`). Чем выше
  лимит, тем дольше настоящий бесконечный синхронный цикл крутится до
  остановки.
- Считать только сайты, вычисленные после достижения мутанта (вариант (б)
  первой версии промпта), этому репро не поможет. Сайт `memo.has(n)`
  достигается на первом же вызове `fib(25)`, а `memo.set(n, value)` — после
  первого спуска до `fib(2)`. Почти все вычисления идут уже после достижения.
- Если только добавить `'hit-limit'` в условие `getUnitEvidence`
  (`core/run/get-unit-evidence.ts:22-28`), подтверждения не получится. Повтор
  с `request.confirming` получит тот же `hitLimit`
  (`core/run/get-try-limits.ts:26` не зависит от `scale`), снова его превысит,
  и вердикт станет окончательным. Подтверждающему юниту нужен другой лимит. Но
  `IsolatedRequest` несёт только `confirming: boolean`, без причины
  (`types/run/run-state.d.ts:83-103`), так что `planIsolated` не отличит
  подтверждение `hit-limit` от подтверждения `time-limit`.
- «Без лимита» через `Infinity` в плане Vitest не пройдёт. План пишется
  через `JSON.stringify` (`adapters/vitest/write-plan-files.ts:36`), и
  `Infinity` станет `null`. Раннер запишет его в `runtime.hitLimit`
  (`adapters/vitest/runner.ts:551`), а проверка `runtime.hits >
  runtime.hitLimit` (`core/runtime/install-mutant-runtime.ts:42`) с `null`
  истинна уже на первом сайте, то есть бросать будет каждый сайт. node:test
  передаёт юнит тоже через JSON (`adapters/node-test/run-test-file.ts:48`), но
  превращает `null` в `Infinity`
  (`adapters/node-test/preload/create-try-tracker.ts:150`). `TryLimits`
  (`hitLimit: number`) и `IsolatedUnit` — публичные типы
  (`core/index.ts:10`, `:26`), поэтому `number | null` в них — изменение API
  адаптеров.
- Совсем без лимита настоящий бесконечный синхронный цикл таймер в воркере
  не остановит. Его остановит главный процесс, и только после всего
  удвоенного бюджета юнита: у Vitest — сторож по пульсу
  (`adapters/vitest/watch-heartbeats.ts:21-31`), у node:test — дедлайн
  процесса юнита (`adapters/node-test/get-unit-deadline.ts:20-25`,
  `adapters/node-test/build-isolated-facts.ts:59-61`). Юнит получит
  `incomplete: 'hang'`, то есть `Timeout` с причиной `hang`
  (`core/run/read-isolated-unit.ts:39-41`), и предупреждение
  `worker-hang` (`core/run/apply-isolated-result.ts:68-70`, `:124-134`). Это
  меняет ожидания существующих тестов: `test/adapters/vitest/index.test.ts:997`
  отбирает такие мутанты по `cause === 'hit-limit'`, `:1003` требует пустых
  `isolated.diagnostics`, а `test/adapters/node-test/index.test.ts:439` ждёт
  `Timeout | hit-limit`. Компромисс — оставить в подтверждающем прогоне
  конечный, но намного больший лимит, чтобы настоящий цикл по-прежнему ловил
  счётчик. Каким он должен быть, чтобы конечный «горячий» код успевал
  уложиться в таймер, не измерено.
- Batch (`--fast`): лимит считается на тест (`core/run/plan-batch.ts:92-96`,
  `adapters/vitest/runner.ts:847`), а `hit-limit` окончателен
  (`core/run/apply-batch-result.ts:165`). В репро `memo.has(n)` → `false`
  получил `Timeout` именно на batch-пути. Один из вариантов — не решать такую
  попытку в batch, а отправить мутанта на isolated-путь, как сомнительную
  попытку (`routeIsolated`, `core/run/apply-batch-result.ts:158-161`), где
  сработает подтверждение.
- Кэш: таймауты в кэш не пишутся (`core/cache/create-run-cache.ts:143-144`,
  `:313-320`), так что старых ложных `Timeout` в кэше нет.

## Критерий готовности

Серьёзность low, решение по итогам перепроверки — как минимум описать
поведение в документации. Поэтому документация и сообщение обязательны, а
смена вердиктов рекомендуется: скептик называет её улучшением («подтверждать
hit-limit прогоном без лимита»). В PR явно напиши, делаешь ли вторую часть.

Обязательно:

- Раздел `hitLimit` в `docs/content/guide/configuration.mdx:436-441` описывает
  поведение после PR. Там сказано, что на isolated-пути лимит считается на
  юнит (загрузка файла плюс все его тесты), а на тест — только в `--fast`.
  Если вердикты не меняются, там прямо сказано, что `Timeout` с причиной
  `hit-limit` может получить и конечный мутант, который лишь делает код
  «горячее» (отключённая мемоизация или кэш), и как это обойти
  (`run.hitLimit`). Если меняются — описано подтверждение.
- Сообщение `core/runtime/create-hit-limit-error.ts:21` не утверждает
  безусловно «likely stuck in a loop». Оно называет и второй вариант (намного
  больше вычислений, чем без мутанта) и настройку `run.hitLimit`. Имя ошибки
  `MootantHitLimitError` прежнее, тест
  `test/core/runtime/create-hit-limit-error.test.ts:10-12` обновлён.
- JSDoc согласованы с поведением: `core/run/classify-try.ts:6-7`,
  `types/run/try-cause.d.ts:13`, `types/config/run-config.d.ts:14-18`,
  `types/run/run-state.d.ts:116`.
- Если вердикты не меняются, временный тест из шага 1 остаётся красным. Это
  ожидаемо: он проверяет вторую часть.
