# BUG-300: опустошённая строка внутри элемента прячет удаление элемента (solitary)

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (заявлено medium, снижено после
> перепроверки). Статус: подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест падает 2 из 2; на
> фикстуре с нуля с упакованным mootant и Vitest 5.1.0 `mootant run` даёт
> 5 мутантов, killed 5, score 100 %, а физически удалённые `'else'` и `'for'`
> проходят тесты); скептик: не опроверг, но снизил до low — пропуск
> задокументирован и задуман (документация приводит ровно этот пример,
> `['card', 'paypal']`), `coarseMutants`/`--preset strict` его возвращает
> (75 % на примере), а в выборке `core/` ни один такой пропуск не спрятал
> выжившего мутанта. Итог координатора — low: это уточнение эвристики
> `solitary`, а не дефект реализации; для этого класса неверны текст причины
> пропуска и обещание категории `subsumed`.

## Контекст

Правило `solitary` (`applySolitaryRule`,
`core/generate/apply-solitary-rule.ts:60`; вызывается в
`core/generate/generate-file-mutants.ts:258-259`, только если выключен
`coarseMutants`) выбрасывает «грубого» мутанта — например, удаление элемента
массива (`core/mutators/array-element.ts:55-59`, `solitary: [element!]`) или
свойства объекта (`core/mutators/object-property.ts:22`,
`solitary: [property]`), — если внутри его диапазона `solitary` есть
засчитываемый «тонкий» мутант. Поиск — `findCountedCandidate` (`:97-115`),
решение — `countsFor` (`:124-136`). Тонкий мутант не засчитывается, только
если его мутатор объявил `meta.countsForSolitary: false` (`:125-127`; из
встроенных так делает только `optional-chaining`,
`core/mutators/optional-chaining.ts:104`), если это вариант того же мутатора
на том же диапазоне (`:128-134`), если он сам выброшен (`:108`) или если он
игнорируется, а грубый будет запущен (`:135`). Причина пропуска в отчёте:
«a finer … mutant lies inside the code it removes, and killing that mutant
needs a test that observes this code»
(`core/generate/generate-file-mutants.ts:359`).

Для строкового элемента тонкий мутант — `string-literal` `'else'` → `''`
(`Literal`, `core/mutators/string-literal.ts:92-103`: непустая строка
опустошается, пустая заполняется `FILLER = 'mootant'`, `:28`, `:97`). Его
убивает любой тест, который подаёт на вход пустую строку: `''` становится
членом множества, хотя тест ничего не говорит о том, есть ли в нём `'else'`.
Один тест «пустое слово — не ключевое» убивает все три `''`-мутанта элементов
`new Set(['if', 'else', 'for'])`, и все три удаления элементов пропадают из
отчёта. `mootant run` показывает 100 %, хотя принадлежность `'else'` и `'for'`
не проверяет ни один тест. Шаблон частый (множества ключевых слов,
расширений, команд, допустимых значений), но дыра прячется только при
определённой форме тестов: есть проба `''` (или падение кода), но нет
проверки каждого элемента. Без теста с `''` счёт 60 %, и выживают как раз
`'else'` → `''` и `'for'` → `''`, то есть пробел виден на тех же элементах
(прогон скептика). Документация string-literal советует подавать на вход саму
строку (`docs/content/mutators/string-literal.md:45`), а тест
`isKeyword('else')` убивает и строковый мутант, и удаление.

Поведение задокументировано и задумано. Это главный довод скептика, с которым
согласился координатор:

- `docs/content/mutators/array-element.md:42-44`: «In `recommended`, Mootant
  doesn't remove an element that has a mutant inside: `['card', 'paypal']` gets
  no removal, because string-literal changes both strings». На `:48-49` и
  `:144-148` сказано, что такие удаления возвращает `coarseMutants` (включён в
  `strict`). В таблице пропусков на `:136` пример `solitary` — ровно
  `['card', 'paypal']` → `['paypal']`. Для свойств то же:
  `docs/content/mutators/object-property.md:37-44` и `:124`.
- `docs/content/mutators.md:46-52` («A category is Mootant's decision, not a
  proof… That is likely, not certain»), `docs/content/guide/configuration.mdx:150`
  (таблица пресетов: Coarse mutants — Dropped / Kept) и `:273-278`, JSDoc
  `coarseMutants` в `types/config/preset-settings.d.ts:22-29`. У правила
  `heuristic: true` (`core/skips/skip-rules.ts:302-305`), и
  `mootant list --skipped --json` помечает такие пропуски
  `"heuristic": true`.
- Тесты закрепляют пропуск строкового свойства как `solitary`
  (`test/core/mutators/object-property.test.ts:107`, `:113`). Приёмочная
  фикстура `list` закрепляет пропуск строкового элемента:
  `test/fixtures/list/source/typed.ts:108`, `[5, 'five'] -> [5]` из-за
  string-literal (`test/fixtures/list/expected-skipped.json:4933-4952`; в
  `test/fixtures/list/expectations.json:4705-4717` этот мутант есть только в
  `strict`, `"presets": ["strict"]` на `:4716`).

Дефектом остаются формулировки, которые для этого класса логически неверны:
текст причины (`generate-file-mutants.ts:359`), определение `subsumed` — «Is
caught by any test that catches another mutant»
(`docs/content/mutators.md:42`) — и «since a test that kills the finer one
already has to observe this code»
(`docs/content/guide/configuration.mdx:276-277`). Тест `isKeyword('')`
убивает тонкий мутант, не наблюдая `'else'`. Собственный принцип проекта —
не засчитывать мутант, которого убивают, не наблюдая окружающий код
(`types/mutator/mutator-meta.d.ts:6-11`, `countsForSolitary`), — сюда
подходит, но задаётся на весь мутатор. По словам скептика, `run`, в том числе
`--json` для агентов, показывает 100 % и пропущенных грубых мутантов не
упоминает, так что один тест с `''` — правдоподобный способ «подогнать» счёт.

Масштаб (подсчёт верификаторов: `mootant list core --skipped --json` на копии
`core/` из 170ec52, `recommended`, без конфига): всего 5 476 пропусков
`solitary`, из них с владельцем `string-literal` — 2 028 удалений элементов
массивов и 980 удалений свойств. Это охват шаблона, а не потерянные мутанты.
Элемент целиком — строковый литерал в 1 486 случаях из 2 028 (690 из них
внутри `new Set([...])`), значение свойства — строка (`key: 'str'`) в 747 из
980. По оценке скептика, узкое исправление (а) ниже добавило бы около 1 486
мутантов к 16 279 (+9,1 %).

Эмпирика эксперимента «unskip» из анализа (пропущенные мутанты прогонялись
как обычные). Данные лежат в ветке анализа (`analysis/bugs/skips.md`, раздел
«Эмпирическая выборка по правилам»; `analysis/data/skips/core-run/joined.jsonl`,
`analysis/data/skips/perf-run/`). В чистом клоне их нет, повторить их там
нельзя:

- Выборка `core/` (25 файлов с «своими» тестовыми файлами, а не весь `core`):
  90 пропусков `solitary`, 0 скрытых. Из 46 удалений элементов и свойств со
  строковым владельцем 40 убиты, 6 видны через выжившего владельца, 0 скрыто.
  Среди них 13 удалений элементов множеств ровно этого шаблона
  (`core/syntax/is-vue-macro-call.ts:6-14`,
  `core/syntax/is-non-thenable.ts:10-23`), и все 13 убиты.
- eslint-plugin-perfectionist (`486c3c8`, правила `sort-heritage-clauses` и
  `sort-export-attributes`): 13 из 81 пропуска `solitary` выжили при убитом
  владельце, и у всех 13 владелец убит падением кода, а не проверкой («Schema
  for rule … is invalid», «Unreachable case», «Incorrect locale information
  provided», «Cannot read properties of undefined»). Полезных среди них 3:
  удаление вызова `validateGroupsConfig(...)`
  (`rules/sort-heritage-clauses/sort-heritage-clause.ts:98`) и удаление
  `type: 'array'`/`type: 'object'` из JSON-схемы правила
  (`rules/sort-heritage-clauses.ts:50, 53`). Остальные 10 — удаление значений
  по умолчанию, равных отсутствию значения. Удалений элементов массива среди
  13 нет, поэтому узкое исправление (а) не покрыло бы ни одного из них.

Общий механизм шире строк: тонкий мутант делает значение недопустимым (`''`
в поле-перечислении, локали или JSON-схеме, пропавший обязательный аргумент),
код падает, и любой тест «убивает» его, ничего не сказав о том, наблюдается
ли удаляемый код. Статическое правило не знает, как умрёт тонкий мутант, —
см. вариант (г) в «Подозреваемых местах».

## Воспроизведение

Нужны Node.js `^20.19.0 || >=22.12.0` (поле `engines` в `package.json`) и
pnpm 12 (`contributing.md:98`): pnpm 10 не читает `configDependencies` из
`pnpm-workspace.yaml` и зависает.

### Шаг 1. Unit-тест (сборка не нужна)

В анализе тест лежал в `test/repros/BUG-300.test.ts` ветки
`experiment/bug-repros`, которой в чистом клоне нет. Создай этот файл
временно, только чтобы увидеть падение. В таком виде его не коммить (см.
«Ограничения»). Хелперы есть в 170ec52. `listMutantTexts`
(`test/helpers/list-mutant-texts.ts`) прогоняет весь конвейер со всеми
встроенными мутаторами (через `runMutator`, `test/helpers/run-mutator.ts`) и
возвращает выданные мутанты одного мутатора как `original -> replacement`.
`listSkipped` (`test/helpers/list-skipped.ts`) работает как
`mootant list --skipped` и возвращает пропуски мутатора как
`original -> replacement (category rule)`.

```ts
import { describe, expect, it } from 'vitest'

import { listMutantTexts } from '../helpers/list-mutant-texts'
import { listSkipped } from '../helpers/list-skipped'

/**
 * Lookup set probed by a test with an empty word: `isKeyword('')` kills every
 * `'…'` → `''` mutant of the set, without telling whether `'else'` or `'for'`
 * are in it.
 */
let keywords = [
  "const KEYWORDS = new Set(['if', 'else', 'for'])",
  'export function isKeyword(word) {',
  '  return KEYWORDS.has(word)',
  '}',
]

describe('BUG-300: an emptied string element hides the removal of the element', () => {
  it('keeps the removal of each element of a lookup set', () => {
    expect(
      listMutantTexts('array-element', keywords, { file: 'example.js' }),
    ).toStrictEqual([
      "['if', 'else', 'for'] -> ['else', 'for']",
      "['if', 'else', 'for'] -> ['if', 'for']",
      "['if', 'else', 'for'] -> ['if', 'else']",
    ])
  })

  it('does not drop the removals as solitary', () => {
    expect(
      listSkipped('array-element', keywords.join('\n'), { file: 'example.js' }),
    ).toStrictEqual([])
  })
})
```

```bash
pnpm install
mkdir -p test/repros             # сохрани сюда файл выше как BUG-300.test.ts
pnpm exec vitest --run test/repros/BUG-300.test.ts   # 2 failed, см. «Фактическое поведение»
```

### Шаг 2. Сквозная проверка на упакованном mootant

`bin/mootant.js` импортирует `../dist/cli/index.js`, а в `files` пакета только
`bin` и `dist`, поэтому для CLI нужны сборка и упаковка. В npm-фикстуре ставь
`vitest@5` (сейчас это 5.1.0), а не `vitest@5.0.5`: в npm 10.9.9 установка
5.0.5 без `--legacy-peer-deps` падает в arborist с
`Cannot read properties of null (reading 'edgesOut')`. Это баг npm, а не
mootant. Исходная команда анализа (`--legacy-peer-deps`, `vitest@5.0.5`,
`vite@8.3.5`) у верификатора этого бага тоже поставилась, но без
`--legacy-peer-deps` `vite` (обязательный peer Vitest 5) npm ставит сам. На
результат версия Vitest не влияет: оба верификатора получили на 5.1.0 то же,
что анализ на 5.0.5. Конфиг mootant не нужен, Vitest определяется
автоматически.

Модуль и тест взяты дословно из фикстуры анализа (`analysis/data/skips/fx1`,
файлы `src/keywords.js` и `test/keywords.test.js`). Её `package.json`
ссылается на несуществующий tarball, поэтому здесь свой.

```bash
# в корне клона, после шага 1
pnpm build
pnpm pack                        # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"    # *.tgz нет в .gitignore, не оставляй его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"

FIX="$(mktemp -d)"
cd "$FIX"
mkdir src test
cat > package.json <<'EOF'
{
  "name": "bug-300",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "vitest --run"
  }
}
EOF
cat > src/keywords.js <<'EOF'
const KEYWORDS = new Set(['if', 'else', 'for'])

export function isKeyword(word) {
  return KEYWORDS.has(word)
}
EOF
cat > test/keywords.test.js <<'EOF'
import { expect, it } from 'vitest'

import { isKeyword } from '../src/keywords.js'

it('accepts a keyword', () => {
  expect(isKeyword('if')).toBe(true)
})

it('rejects an empty word', () => {
  expect(isKeyword('')).toBe(false)
})

  expect(isKeyword('foo')).toBe(false)
})
EOF
npm i -D vitest@5 "$TGZ"
npx vitest --run                                  # все 3 теста проходят
npx mootant list src --skipped                    # 5 мутантов; в skipped: три удаления array-element, subsumed solitary
npx mootant list src --skipped --json             # "rule": "solitary", "heuristic": true, "by": string-literal 1:27 / 1:33 / 1:41
npx mootant run src --no-cache                    # killed 5, survived 0, score 100%
npx mootant run src --no-cache --preset strict    # 8 мутантов: killed 6, survived 2, score 75%
```

Те же удаления, вписанные руками (GNU sed; на macOS — `sed -i ''`):

```bash
cp src/keywords.js "$PACK/"
sed -i "s/'else', //" src/keywords.js   # ['if', 'for']
npx vitest --run                        # все тесты проходят: удаление 'else' выжило бы
cp "$PACK/keywords.js" src/
sed -i "s/, 'for'//" src/keywords.js    # ['if', 'else']
npx vitest --run                        # все тесты проходят: удаление 'for' выжило бы
cp "$PACK/keywords.js" src/
```

Команды `sed` в таком виде не запускались: верификаторы делали ту же замену
своими средствами. Удаление `'if'` (`['else', 'for']`) убивает тест «accepts
a keyword». Числа в комментариях взяты из прогонов верификаторов; «3 теста» —
по числу `it` в фикстуре. Удаления `'else'` и `'for'` убил бы тест
`expect(isKeyword('else')).toBe(true)` (и так для каждого элемента). Это
следует из кода, отдельно не запускалось.

## Ожидаемое поведение

Мутант `string-literal`, который опустошает строку (`'else'` → `''`), не
засчитывается для `solitary` удаления элемента, если сам элемент — этот
строковый литерал целиком (диапазон тонкого мутанта совпадает с диапазоном
`solitary`). Его убивает тест с пустой строкой, который удаляемый элемент не
наблюдает. В примере `keywords` в `recommended` выдаются все три удаления:
`['else', 'for']`, `['if', 'for']` и `['if', 'else']` (именно их ждёт тест
шага 1), а `list --skipped` удалений `array-element` не показывает. Исходная
версия промпта называла только удаления `'else'` и `'for'`. Это неточно:
`'if'` тоже строка, его удаление выдаётся и убивается тестом «accepts a
keyword». `mootant run src` на фикстуре шага 2 должен показать 8 мутантов:
killed 6, survived 2 (удаления `'else'` и `'for'`), score 75 %, как сейчас
`--preset strict`. Это расчёт по прогону `strict`, после исправления не
запускалось. В `strict` ничего не меняется: там `applySolitaryRule` не
вызывается (`generate-file-mutants.ts:258-259`).

Остаются пропущенными как `solitary`:

- Удаление пустого элемента `''`. Его тонкий мутант — заполнение
  `''` → `'mootant'`, а такой мутант на деле убивает только тест, который
  проверяет наличие `''` в коллекции, и этот же тест убивает удаление. Довод
  про пустую строку на заполнение не переносится (замечание верификатора;
  исходная версия промпта ошибочно включала и этот случай).
- Удаление нестрокового элемента с тонким мутантом внутри: `[a + 1, b]` →
  `[b]`, элементы `x = [1, 2]`, `[inner, 4]` в `[user, [inner, 4], other]`.
- Элемент, где строка — только часть выражения (`'a' + b`,
  `cond ? 'a' : 'b'`): диапазон строкового мутанта не совпадает с элементом.
  Шаблонная строка-элемент (`` `abc` `` → `` `` ``, `` `/x/${id}` `` → `''`,
  ветка `TemplateLiteral`, `core/mutators/string-literal.ts:67-91`)
  опустошается целиком. Как её трактовать, реши сам и зафиксируй тестом.
- Удаления свойств объектов (`{ type: 'cardinal' }` → `{}`). Довод про
  принадлежность к коллекции к ним не относится. Это поведение закрепляют
  15 ожиданий `(subsumed solitary)` в
  `test/core/mutators/object-property.test.ts` (строки 88-170) и
  документация свойств. Менять его — отдельное решение с отдельным
  обоснованием. Условие (а) свойства и так не затронет: у `object-property`
  диапазон `solitary` — всё свойство `key: 'str'`, и с диапазоном строки он
  не совпадает.

## Фактическое поведение

Шаг 1 (суть сообщений Vitest, не дословный лог; 2 прогона из 2; соседние
тесты `apply-solitary-rule`, `array-element`, `object-property` и
`string-literal` на 170ec52 зелёные):

```
× keeps the removal of each element of a lookup set
  expected [] to strictly equal [ …(3) ]
× does not drop the removals as solitary
  expected [ …(3) ] to strictly equal []
```

В `recommended` у `array-element` нет ни одного мутанта, а `listSkipped`
возвращает три удаления. Первое верификатор видел дословно, остальные два
записаны по тому же формату:

```
['if', 'else', 'for'] -> ['else', 'for'] (subsumed solitary)
['if', 'else', 'for'] -> ['if', 'for'] (subsumed solitary)
['if', 'else', 'for'] -> ['if', 'else'] (subsumed solitary)
```

Шаг 2 (оба верификатора; скептик — три прогона подряд с одинаковым
результатом):

- `mootant list src`: 5 мутантов — три `string-literal` (`'if'`, `'else'`,
  `'for'` → `''`) и два `return-value`.
- `mootant list src --skipped` и `--skipped --json`: три записи
  `array-element` с `"rule": "solitary"`, `"category": "subsumed"`,
  `"heuristic": true` и причиной «a finer string-literal mutant lies inside
  the code it removes, and killing that mutant needs a test that observes
  this code». Владелец в `"by"` — `string-literal`, строка 1, колонки 27, 33
  и 41 (`'if'`, `'else'`, `'for'`). Поля записи собирает
  `cli/report/build-list-report.ts:141-173`. Без `--verbose` из них убраны
  `start` и `end` (`cli/report/slim-list-report.ts:28-34`). Исходная версия
  промпта приводила здесь пересказ, а не реальный вывод.
- `mootant run src --no-cache`: killed 5, survived 0, score 100 %. Исходная
  версия промпта ошибочно писала «killed 8»: 8 мутантов бывает только в
  `strict`. По `run --json --all --verbose` мутанты `'else'` → `''` и
  `'for'` → `''` убил тест «rejects an empty word»
  (`expected true to be false`), а `'if'` → `''` — тест «accepts a keyword».
- `mootant run src --no-cache --preset strict` (`coarseMutants: true`):
  8 мутантов, killed 6, survived 2 (`['if', 'for']` и `['if', 'else']`),
  score 75 %.
- Вручную: с `['if', 'for']` и с `['if', 'else']` тесты проходят, с
  `['else', 'for']` падают.
- Без теста `isKeyword('')` (прогон скептика): score 60 %, выжили
  `'else'` → `''` и `'for'` → `''`.

## Подозреваемые места в коде

- `core/generate/apply-solitary-rule.ts:124-136` (`countsFor`) решает,
  засчитывается ли тонкий мутант. Понятия «тонкий мутант, которого убивают,
  не наблюдая удаляемый код» в нём нет. `countsFor` получает только
  `coarse`, а у удаления элемента `coarse.start`/`coarse.end` — это весь
  массив (`node` в `core/mutators/array-element.ts:58`), а не элемент.
  Сравнение с ними для условия (а) не сработает.
- `core/generate/apply-solitary-rule.ts:97-115` (`findCountedCandidate`).
  Здесь доступен `range` (диапазон элемента из `solitary`), поэтому проверку
  «тонкий мутант покрывает элемент целиком»
  (`inner.start === range.start && inner.end === range.end`) естественно
  делать здесь или передать `range` в `countsFor`.
- `core/mutators/string-literal.ts:92-103` (`Literal`) и `:67-91`
  (`TemplateLiteral`). Опустошение и заполнение различаются только значением
  замены (`:97`). В кандидате от этого остаётся лишь `text`: `''`, `""` или
  ``` `` ``` при опустошении и `'mootant'` при заполнении.
- `types/mutator/mutator-meta.d.ts:6-11`: `countsForSolitary` задаётся на
  весь мутатор, поэтому «`countsForSolitary: false` только для элементов
  коллекций» без нового механизма не выразить. `false` для всего
  `string-literal` снимет защиту со всех грубых мутантов вокруг строк
  (удаления инструкций и т. п.), а не только с элементов.
- `types/mutant/mutant-candidate.d.ts:10-62` (`MutantCandidate`, внутренний
  тип). Типа узла в нём нет, только диапазоны `solitary`, `start`/`end`,
  `text`, `registered` и `ignoreRule`. Кандидат собирается из `Replacement` в
  `core/generate/collect-candidates.ts:350-366` (`solitary` — на `:358`).
- `types/mutator/replacement.d.ts:9-44` (`Replacement`, публичный тип:
  экспорт в `core/index.ts:25`). Признака «эта замена не засчитывается для
  `solitary`» на уровне одной замены в нём нет. Поля замены проверяет
  `core/generate/validate-replacement.ts:49-84` (сейчас только `node` и
  `focus`).
- `core/generate/generate-file-mutants.ts:356-363`: выброшенные кандидаты
  становятся пропусками с причиной (`:359`). Диапазоны `solitary` задаются в
  `core/mutators/array-element.ts:55-59` и
  `core/mutators/object-property.ts:17-25`.

Возможные исправления (выбери одно и обоснуй):

(а) Узкое — его и ждёт тест шага 1. Опустошающий мутант `string-literal`,
чей диапазон совпадает с диапазоном `solitary` (элемент целиком — строковый
литерал), не засчитывается для удаления этого элемента. Заполнение
`''` → `'mootant'` засчитывается по-прежнему. Два способа выразить:

1. Проверка в общем конвейере: `inner.registered.id === 'string-literal'`,
   пустой строковый литерал в `inner.text` и совпадение диапазонов с
   `range`. Хардкод id мутатора в общем конвейере уже есть:
   `core/generate/collect-candidates.ts:340`
   (`registered.id !== 'optional-chaining'`). Публичный API не меняется.
   Минус: `apply-solitary-rule.ts` начинает знать о конкретном мутаторе, а
   мутатор плагина с тем же свойством этим воспользоваться не сможет.
2. Новое необязательное поле в публичном `Replacement` — признак «замена не
   засчитывается для `solitary` грубого мутанта, чей диапазон она покрывает
   целиком». Его ставит только опустошающая ветка `string-literal`, а
   `collect-candidates.ts` переносит его в `MutantCandidate`. Это совместимое
   добавление в публичный API: опиши компромисс (см. «Ограничения»).

Цена (а): около 1 486 новых мутантов на `core/` (+9,1 %, оценка скептика)
при нулевой ожидаемой пользе в выборке `core/`. Случаи perfectionist (а) не
покрывает.

(б) Шире: не засчитывать мутанты, чья замена — «пустое значение того же
типа» (`''`, `[]` и т. п.), для удаления содержащего их элемента. Какие
встроенные мутаторы, кроме `string-literal`, дают такие замены внутри
элементов, не проверялось. `number-literal` `0` не даёт: он прибавляет 1
(`docs/content/mutators/number-literal.md:30-38`).

(в) Отдельная подкатегория через `coarseMutants: 'partial'` — не делай без
явного согласия мейнтейнера. Такого значения нет: настройка булева
(`types/config/preset-settings.d.ts:29`, проверка в
`core/plugins/get-settings-problem.ts:14`), и третье значение меняет формат
конфига. Обход для пользователя уже есть: `settings: { coarseMutants: true }`
(`docs/content/guide/configuration.mdx:204-222`) или `--preset strict`.

(г) «Ленивый» `solitary` во время прогона: если все тонкие мутанты внутри
убиты исключением из кода продукта, а не проверкой теста, прогнать и
грубого. Это покрыло бы и случаи perfectionist, но нужно знать, как именно
убит мутант. Умеют ли это адаптеры, не проверялось. Это крупное изменение
конвейера, вне рамок узкого исправления.

(д) Только тексты — если ты или мейнтейнер решите не расширять набор
мутантов. Поведение не меняется. Из причины пропуска
(`generate-file-mutants.ts:359`) убирается утверждение «needs a test that
observes this code», из `docs/content/guide/configuration.mdx:276-277` —
«already has to observe this code». Случай с пустой строкой назван в
`docs/content/mutators/array-element.md:42-49` как известное ограничение с
обходом `coarseMutants`/`strict`. Текст причины закреплён в
`test/core/generate/generate-file-mutants.test.ts:4367` и в 60 записях
`solitary` файла `test/fixtures/list/expected-skipped.json`.
