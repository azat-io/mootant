# BUG-509: `--json` — в stdout попадает чужой вывод, отчёт не парсится как JSON

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на
> коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (скрипт из шага 1 — 3 из 3 с тем же
> выводом; на упакованном mootant с Vitest 5.1.0 stdout `--json` не парсится
> при коде выхода 0 из-за `console.log` и `process.stdout.write` в
> `vitest.config`, хуков Vite-плагина, `globalSetup` (setup и teardown),
> `mootant.config.js` в `run` и `list`, `dotenv.config()` и
> vite-plugin-svelte); скептик: не опровергнуто, medium на нижней границе.
> Вердикт и код выхода верны, отчёт целиком лежит последней строкой, сбой
> громкий, но для скриптов и агентов это прямой отказ документированного
> интерфейса в реалистичных конфигурациях, а обхода внутри mootant нет.

## Контекст

`--json` — интерфейс «for scripts and agents» (`docs/content/guide/cli.mdx:99`).
JSDoc `runMutation` обещает, что stdout содержит только отчёт, «pure JSON with
`--json`» (`cli/run-mutation.ts:22-25`), документация — что прогресс идёт в
stderr (`docs/content/guide/cli.mdx:125`). Отчёт — одна строка
(`JSON.stringify` без отступов, `cli/report/format-run-report.ts:16`). Её
печатает `console.info` в самом конце (`cli/run-mutation.ts:63-72`), у `list`
так же (`cli/run-list.ts:31-37`, `cli/report/format-report.ts:20`). До этого
stdout открыт для любого кода в главном процессе mootant. Опции записать отчёт
в файл нет (справка CLI, `cli/parse-arguments.ts:11-59`).

Перехвачен только вывод, который проходит через тестовый раннер. То, что
печатают тесты в воркерах Vitest (`console.*` и `process.stdout.write`),
забирает репортёр `createOutputReporter`
(`adapters/vitest/start-vitest-session.ts:97-100`), логгер Vitest пишет в
свои потоки (`:111-116`). Через логгер Vitest идут и
`config.logger.warn`, и `this.warn` Vite-плагинов (проверено скептиком на
Vitest 5.1.0). Всё это попадает в `onOutput`, оттуда событием `output` — в
прогресс CLI (`core/run-mutants.ts:289-295`). Прогресс с `--verbose` печатает
этот вывод в stderr, а без него копит для упавшего прогона
(`cli/create-run-progress.ts:371-382`). У node:test вывод тестовых процессов
идёт по пайпам (`adapters/node-test/run-test-process.ts:116-128`).

Прямые `console.*` и `process.stdout.write` в главном процессе не перехватывает
ничто. Такой код выполняется внутри `runMutants`. Конфиг mootant и его плагины
грузит `prepareRun` (`core/run-mutants.ts:173`; у `list` —
`core/list-mutants.ts:68-69`), конфиг Vitest и плагины Vite — старт адаптера
(`core/run-mutants.ts:275-300`). Хуки `transform` работают весь прогон, а
teardown `globalSetup` выполняется при закрытии сессии в `finally`
(`:320-322`), то есть тоже до печати отчёта. Реальные источники (все проверены
верификаторами, см. «Фактическое поведение»):

- программный `dotenv.config()` в конфиге Vitest. dotenv 17.2.3 печатает
  `[dotenv@17.2.3] injecting env (1) from .env -- tip: …`, 17.4.2 —
  `◇ injected env (1) from .env // tip: …` (в 17.4.2 это `console.log` в
  `node_modules/dotenv/lib/main.js:130-131`, вызов в `:294-310`). А
  `import 'dotenv/config'` во всех проверенных 17.x (17.0.0–17.4.2) по
  умолчанию молчит: `node_modules/dotenv/lib/cli-options.js:12-14` ставит
  `quiet = 'true'`;
- `@sveltejs/vite-plugin-svelte` 7.3.1. Его `log.info` — это `console.log`
  (`node_modules/@sveltejs/vite-plugin-svelte/src/utils/log.js:28`). Через
  него идут «no Svelte config found … using default configuration»
  (`src/utils/load-svelte-config.js:73` того же пакета) и все предупреждения
  компилятора в serve-режиме, в котором работает Vitest
  (`src/utils/log.js:212-219`). Поэтому stdout ломается и при наличии
  `svelte.config.js`, если есть хоть одно предупреждение;
- `globalSetup` с логами (и setup, и teardown), шумные Vite-плагины,
  `console.log` в `mootant.config.js` (и в `run --json`, и в `list --json`).

`JSON.parse(stdout)` или `jq` у агента падает. Снаружи баг можно обойти: отчёт
всегда последняя строка stdout (`tail -n 1`), источник можно заглушить
(например, `DOTENV_CONFIG_QUIET`, `node_modules/dotenv/lib/main.js:292`).
Внутри mootant обхода нет.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, все файлы ниже
создайте сами. Нужны Node.js 22.12 или новее (Vitest 5 требует
`^22.12.0 || ^24.0.0 || >=26.0.0`, `docs/content/guide/compatibility.mdx:23-24`)
и pnpm 12 (`contributing.md:98`; в CI стоит `latest-12`,
`.github/actions/install-tools/action.yml:11-15`). `bin/mootant.js`
импортирует `../dist/cli/index.js` (`bin/mootant.js:3`), поэтому CLI работает
только после `pnpm build`. Во всех командах `run` стоит `--no-cache`, иначе
mootant оставит кэш в `node_modules/.cache/mootant/run-v3.json` фикстуры
(`core/cache/get-cache-path.ts:13-20`, `core/cache/cache-version.ts:6`). Шаги
2 и 3 рассчитаны на одну сессию shell: они используют переменные `CLONE`, `TGZ`
и `FIX`.

### Шаг 1. Фикстура в дереве клона (так баг найден)

Фикстура лежит в `test/repros/BUG-509/` и берёт Vitest из `node_modules` клона
(в lockfile — 5.0.5). Тест назван `*.check.js`, чтобы корневой Vitest
репозитория его не подхватывал. Каталог временный и в коммит не входит (см.
«Ограничения»). Строка в `vitest.config.js` повторяет баннер dotenv 17.2.3 без
хвоста `-- tip: …`. Баг от этого не зависит: с настоящим `dotenv.config()` он
тоже воспроизводится (шаг 2).

```bash
export default {
  test: { include: ['test/**/*.check.js'] },
}
EOF

cat > test/repros/BUG-509/src/add.js <<'EOF'

  return a + b
}
EOF

cat > test/repros/BUG-509/test/add.check.js <<'EOF'

  expect(add(2, 3)).toBe(5)

cat > test/repros/BUG-509/run.sh <<'EOF'

# BUG-509: with --json, stdout must hold only the report, but whatever code in
# mootant's own process prints there (a Vitest config, a Vite plugin) comes
# first, so JSON.parse of stdout fails. Builds dist when it is missing.
# Exit 1 = reproduced.

bash test/repros/BUG-509/run.sh; echo "run.sh exit: $?"   # 1 = воспроизведено
```

Вердикт `run.sh` неспецифичен. `REPRODUCED` и код 1 выходят на любом stdout,
который не является JSON, в том числе на пустом, когда упала сборка или сам
mootant (верификатор проверил это заглушкой). Воспроизведение засчитывается,
только если в выводе `mootant exit code: 0`, а перед `{"summary"` стоит строка
из конфига (см. «Фактическое поведение»). Строгая проверка вручную (в таком
виде в анализе не запускалась):

```bash
cd test/repros/BUG-509
node ../../../bin/mootant.js run src --json --no-cache </dev/null >out.json 2>err.txt
code=$?; echo "exit=$code lines=$(wc -l <out.json)"   # до исправления: exit=0 lines=2
tail -n 1 out.json | node -e 'JSON.parse(require("fs").readFileSync(0, "utf8")); console.log("last line is JSON")'
node -e 'JSON.parse(require("fs").readFileSync("out.json", "utf8")); console.log("stdout is JSON")'   # до исправления: SyntaxError
rm -f out.json err.txt
cd ../../..
```

## Ожидаемое поведение

С `--json` stdout содержит ровно один JSON-документ — одну строку отчёта, и у
`run`, и у `list`. Всё, что код в процессе mootant пишет в stdout во время
команды (конфиг mootant и его плагины, конфиг Vitest, плагины Vite,
`globalSetup` вместе с teardown), уходит в stderr. Это происходит либо сразу,
либо так же, как с выводом тестов и логгера Vitest: с `--verbose` и в блоке
«Output of the tests» упавшего прогона. Код выхода и содержимое отчёта не
меняются. Без `--json` поведение не меняется.

## Подозреваемые места в коде

- `cli/run-mutation.ts:43-50` — вызов `runMutants`. Всё, что пишется в stdout
  за время вызова, остаётся в stdout. Отчёт печатается после (`:63-72`), путь
  ошибки — `:83-94`.
- `cli/run-list.ts:19-26` — то же для `listMutants`. Отчёт — `:31-37`, ошибка
  — `:41-45`.
- `core/run-mutants.ts:173`, `:275-300`, `:320-322` и
  `core/list-mutants.ts:68-69` — где внутри этих вызовов выполняется код
  пользователя (см. «Контекст»).
- `adapters/vitest/start-vitest-session.ts:91-117` — перехвачены только
  репортёр (`:97-100`) и логгер Vitest (`:111-116`).
- `cli/create-run-progress.ts:371-382` и `:388-403` — как прогресс обращается
  с событием `output`.

### Как чинить (направление по чтению кода, запуском не проверено)

1. Перехватывать в CLI на время всего вызова `runMutants` / `listMutants` и
   только при `--json`. Перехват только вокруг `createVitest` в адаптере не
   годится: он не поймает конфиг mootant, хуки `transform` во время прогона,
   teardown `globalSetup` и адаптер node:test.
2. Подменять `process.stdout.write`, а не `console.log`. Подмена `console.log`
   не ловит прямой `process.stdout.write` (вариант `P_CONFIG_WRITE`, хук
   `transform` у воспроизводящего агента). Кроме того, часть библиотек
   сохраняет ссылку на `console.log` при импорте (vite-plugin-svelte 7.3.1:
   `log: console.log`, `src/utils/log.js:28` в пакете). Глобальный
   `console` в Node пишет через `process.stdout.write`, так что подмена
   `write` ловит и `console.log/info/debug` (так устроен `console` в Node; с
   исправлением не проверялось).
3. Вернуть исходный `process.stdout.write` в `finally` сразу после
   `runMutants` / `listMutants`, до `console.info` с отчётом: отчёт сам идёт
   через `process.stdout.write`. Если вернуть после `console.info`, отчёт уйдёт
   в stderr, а stdout останется пустым. На пути ошибки поток тоже надо вернуть.
4. Куда направлять перехваченное:
   - у `run` — в прогресс событием `{ kind: 'output', file: null, text }`
     (`progress.handle`). Тогда оно ведёт себя как вывод логгера Vitest. С
     `--verbose` его печатает `spinner.print`, который сначала стирает строку
     спиннера (`cli/terminal/create-spinner.ts:177-185`). Без `--verbose` оно
     копится и показывается в блоке «Output of the tests» упавшего прогона под
     заголовком `other output` (`cli/run-mutation.ts:85-91`,
     `cli/create-run-progress.ts:388-403`). Можно и просто писать в
     `process.stderr.write`, но в интерактивном терминале текст попадёт в
     середину кадра спиннера: `render` пишет кадр без перевода строки
     (`cli/terminal/create-spinner.ts:134-140`);
   - у `list` нет ни спиннера, ни прогресса — пишите в `process.stderr.write`.

   Выбранный вариант закрепите в тестах (см. «Критерий готовности»).
5. Замена должна принимать `write(chunk, encoding?, callback?)`, вызывать
   колбэк, если он передан, и возвращать `true`. Текст передаётся как есть, без
   лишних переводов строки. По стилю проекта это отдельный файл с одной
   функцией, JSDoc и своим тестом, например `cli/terminal/redirect-stdout.ts`
   (имя — только предложение).
6. Ограничение: запись прямо в дескриптор 1 (`fs.writeSync(1, …)`) подмена
   `process.stdout.write` не ловит (замечание верификатора). Опишите это в
   JSDoc. Полностью надёжный канал — запись отчёта в файл, но это новая опция
   CLI, её можно предложить отдельно.
7. Тесты. Существующие тесты мокают ядро (`test/cli/run-mutation.test.ts:22`,
   `test/cli/run-list.test.ts:12`) и глушат `console.info` через
   `mockImplementation` (`test/cli/run-mutation.test.ts:64`,
   `test/cli/run-list.test.ts:128`). Отчёт они проверяют по `consoleInfoSpy`.
   Новому тесту нужны шпионы на `process.stdout.write` и `process.stderr.write`
   (образец — `vi.spyOn(process.stderr, 'write').mockImplementation(() => true)`
   в `test/cli/terminal/create-spinner.test.ts:90`). Замоканный `runMutants`
   должен писать шум до того, как вернёт результат (образец мока с событиями —
   `test/cli/run-mutation.test.ts:177-192`). Шум имитируйте вызовом
   `process.stdout.write(…)`, а не `console.log`. В воркерах Vitest
   `globalThis.console` заменён собственным `Console` Vitest с его потоками,
   если не задан `disableConsoleIntercept` (Vitest 5.0.5:
   `node_modules/vitest/dist/chunks/base.CzXt2BO_.js:52` и `:60-63`,
   `node_modules/vitest/dist/chunks/console.DtI4yxfN.js:83-147`). Корневой
   `vitest.config.ts` его не задаёт. Поэтому `console.log` в юнит-тесте до
   `process.stdout.write` не дойдёт, и такой тест не отличит исправленный код
   от неисправленного (по чтению кода Vitest, запуском не проверено). Путь
   через `console.log` проверяют сквозные шаги 1–3.

## Критерий готовности

- Появляются юнит-тесты. Первые два падают до исправления и проходят после:
  - в `test/cli/run-mutation.test.ts`: при `json: true` замоканный
    `runMutants` пишет строку через `process.stdout.write`. В шпион
    `process.stdout.write` она не попадает и приходит туда, куда её направляет
    исправление (`progress.handle` с `{ kind: 'output', file: null, text }`
    или шпион `process.stderr.write`). `console.info` вызывается ровно один
    раз, с JSON-документом. После `runMutation` в `process.stdout.write` та же
    функция, что до вызова, в том числе когда `runMutants` отклоняется;
  - в `test/cli/run-list.test.ts` — то же для `listMutants`, строка приходит в
    шпион `process.stderr.write`;
  - страховка, которая проходит и до исправления: при `json: false` запись
    ядра через `process.stdout.write` по-прежнему доходит до stdout (без
    `--json` поведение не меняется).
- Существующие тесты обоих файлов проходят без правок.
- Если перехват сделан подменой `process.stdout.write`, в JSDoc функции
  перехвата записано ограничение: запись прямо в дескриптор 1 не

- Сквозная проверка на CLI, собранном заново после исправления (`pnpm build`:

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.

  копировать как есть в постоянные тесты. Этот каталог не исключён ни из
  ESLint, ни из knip, cspell или tsc. Исключён только `test/fixtures/**`
