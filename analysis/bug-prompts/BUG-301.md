# BUG-301: тонкий мутант инициализатора локальной переменной прячет `return x` → `0` (solitary), хотя переменную читают ещё где-то

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (в анализе была medium). Статус:
> подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (репро-тест во всех трёх прогонах
> падает на обеих проверках: `count -> 0` не выдан, а пропущен как
> `subsumed solitary`; на сквозной фикстуре с упакованным mootant и Vitest
> 5.1.0 `mootant run` даёт killed 3, score 100 %, а физически вписанный
> `return 0` тест проходит; так же пропускаются варианты с
> `onItem(item, ++count)`, с чтением в колбэке `forEach` и с двумя
> `return count`); скептик: не опроверг, но снизил до low — пропуск
> задокументирован как догадка (`docs/content/mutators/return-value.md:84-94`,
> в `--json` `"heuristic": true`), `--preset strict` и
> `settings.coarseMutants: true` возвращают мутанта (score 100 % → 80 %), охват
> узкий (на `core/` самого Mootant ≈ 62–81 таких пропусков из 16 195, среди 33
> возвращённых в прогон мутантов `return-value`/`solitary` скрытых выживших
> нет); остаётся уточнить эвристику: её посылка ложна, когда переменную читают
> ещё где-то, и этот случай не описан в документации.

## Контекст

`return-value` заменяет небулево возвращаемое значение пустым (`0`, `''`,
`[]`, `undefined`). Правило `solitary` выбрасывает такого «грубого» мутанта,
если внутри одного из его диапазонов есть засчитанный «тонкий» мутант:
`applySolitaryRule` (`core/generate/apply-solitary-rule.ts:60-87`, сброс — на
`:77`) ищет его через `findCountedCandidate` (`:97-115`). Причина пропуска:
«a finer … mutant lies inside the code it removes, and killing that mutant
needs a test that observes this code»
(`core/generate/generate-file-mutants.ts:359`). Правило помечено
`heuristic: true` (`core/skips/skip-rules.ts:302-305`), а настройка
`coarseMutants` выключает его целиком
(`core/generate/generate-file-mutants.ts:258-259`).

Для возвращаемой локальной переменной диапазоны — само выражение плюс
`getLocalRanges` (`core/mutators/return-value.ts:170-171`). Переменную находит
`getLocalBinding` (`:378-391`): `const`, `let` или `var` (`:47`), объявленная
в runtime-дереве той же функции; для цепочки членов (`return r.hits`) берётся
её корень (`getMemberRoot`, `:380`). `getLocalRanges` (`:349-365`) добавляет
инициализатор и записи переменной, которые лежат в runtime-дереве той же
функции (`isRuntimeNode` и тот же `getEnclosingFunction`). Записи во вложенных
функциях не попадают, но для пропуска хватает одного инициализатора. Других
чтений переменной никто не проверяет.

Посылка правила ломается, когда переменную читает не только этот `return`:
тонкий мутант инициализатора (`let count = 0` → `1`) или записи
(`count++` → `count--`) убивается через другое чтение (аргумент колбэка,
другой `return`, условие), а возвращаемое значение тест может не проверять
вовсе. Для простого присваивания проект такое исключение уже сделал: удаление
`=`-присваивания не `solitary`, потому что «a mutant of the assigned value only
shows that the value is observed» (`core/mutators/statement-removal.ts:458-462`).
В выводе `mootant run` (и в тексте, и в `--json --all`) пропусков нет
(проверил скептик), их показывает `mootant list --skipped`. HTML-отчёт
`run --html` строится с `skipped: true` (`cli/html/build-html-report.ts:84`),
для этого бага он не проверялся.

Пропуск задокументирован как догадка. `docs/content/mutators/return-value.md:84-88`
прямо называет случай `sum` после `let sum = 0`, а `:90-94` предупреждает, что
догадка может ошибаться (пример с пустым списком), и отсылает к
`coarseMutants`. То же в `docs/content/mutators.md:51-52` («likely, not
certain») и `docs/content/guide/configuration.mdx:273-278` («That is not a
proof, so `strict` keeps it»). Не описан только механизм этого случая:
значение наблюдается через другой канал. Обход есть: `--preset strict` или
`settings.coarseMutants: true` возвращают мутанта (см. «Фактическое
поведение»). Масштаб по данным скептика: на `core/` самого Mootant из 996
пропусков `return-value`/`solitary` через инициализатор или записи сработали
96, другие чтения есть у ≈ 62–81 из них (≤ 0,6 % из 16 195 пропусков).
Утверждение анализа, что это класс «чаще» примера с пустым списком, данными не
подкреплено.

Корень общий с BUG-304 (отдельный промпт): та же `getLocalRanges` через
`getAssignedValues` (`core/mutators/return-value.ts:508-517`) даёт источники
правила `R6` для булевых значений. Там серьёзность medium (`heuristic: false`,
`strict` его не отключает), а политика для составных записей другая, см.
«Ожидаемое поведение» и «Ограничения».

### Шаг 1. Unit-тест (сборка не нужна)

В анализе тест лежал в `test/repros/BUG-301.test.ts` ветки
`experiment/bug-repros`, которой в чистом клоне нет. Создай этот файл
временно, только чтобы увидеть падение. В таком виде его не коммить (см.
«Ограничения»). Хелперы `test/helpers/list-mutant-texts.ts` и
`test/helpers/list-skipped.ts` есть в 170ec52 и уже импортированы в
`test/core/mutators/return-value.test.ts`. `listMutantTexts` прогоняет весь
конвейер со всеми встроенными мутаторами, как `mootant list`, и возвращает
выданные мутанты одного мутатора как `original -> replacement`. `listSkipped`
делает то же, как `mootant list --skipped`, и возвращает пропуски мутатора как
`original -> replacement (category rule)`.

```ts
import { describe, expect, it } from 'vitest'

import { listMutantTexts } from '../helpers/list-mutant-texts'
import { listSkipped } from '../helpers/list-skipped'

/**
 * A local that the function passes to a callback before it returns it: the
 * mutants of its initializer and update are killed through the callback, so
 * they say nothing about whether a test reads the returned value.
 */
let processAll = [
  'export function processAll(items, onItem) {',
  '  let count = 0',
  '  for (let item of items) {',
  '    count++',
  '    onItem(item, count)',
  '  }',
  '  return count',
  '}',
]

describe('BUG-301: a finer mutant of a returned local hides the returned default', () => {
  it('keeps the default of a returned local that is also read elsewhere', () => {
    expect(
      listMutantTexts('return-value', processAll, { file: 'example.js' }),
    ).toStrictEqual(['count -> 0'])
  })

  it('does not drop the default as solitary', () => {
    expect(
      listSkipped('return-value', processAll.join('\n'), {
        file: 'example.js',
      }),
    ).toStrictEqual([])
  })
})
```

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому для CLI нужна
сборка. В npm-фикстуре ставь `vitest@5` (верификаторам поставился 5.1.0), а не

## Ожидаемое поведение

Инициализатор и записи локальной переменной входят в диапазоны `solitary`
возвращаемого значения, только если переменную не читает ничто, кроме этого
`return`. В примере `processAll` выдаётся мутант `count -> 0`, и
`mootant run src/process.js --no-cache` показывает его как Survived. Если
переменную читает только `return`, пропуск остаётся. Обязательный контроль —
`sum` после `let sum = 0` и `sum += x`
(`test/core/mutators/return-value.test.ts:91-94`, `:803-858`).

Что считать «другим чтением» (уточнения верификаторов; пункты с пометкой «не
проверялось» выведены чтением кода):

1. Готовый счётчик ссылок не подходит. `Binding.references` — это «reads and
   write targets» без объявляющего идентификатора
   (`types/syntax/binding.d.ts:23-27`). Верификатор снял их через
   `analyzeScopes`: в `processAll` — `count@92` (`count++`), `count@117`
   (аргумент `onItem`) и `count@137` (`return`); у варианта
   `onItem(item, ++count)` — `++count` и `return`; у контроля `sum` —
   `sum += x` и `return`. Структура у `++count` и у `sum` одинаковая, поэтому
   проверка только по `references` либо сломает `sum` (если цели записей
   считать чтениями), либо пропустит `++count` (если их исключать). Условие
   `binding.references.length !== 1` из `missing-await`
   (`core/mutators/missing-await.ts:162`) работает там лишь потому, что у той
   переменной записей нет.
2. Ссылка самого возвращаемого значения — не «другое» чтение. Для
   `return count` это `count`, для цепочки членов `return r.hits` — её корень
   (`getMemberRoot(value)`, `core/syntax/get-member-root.ts:15-26`). Тест
   «counts the initializer of a returned member chain» (`:860-880`) должен
   пройти без правок.
3. Цель записи (операнд `++`/`--`, левая часть `=`, `+=`, `||=` и т. п.) — не
   чтение, если результат записи не используется: выражение-оператор, `init`
   или `update` цикла `for`, операнд `void`, не последний элемент
   последовательности. Готовая проверка — `syntax.isResultUnused(write)`
   (`types/syntax/syntax-helpers.d.ts:217-220`,
   `core/syntax/is-result-unused.ts:23-42`). Так `count++;` и `sum += x;` — не
   чтения, а `onItem(item, ++count)` — чтение. Верификатор сформулировал
   условие так: «чтение — ссылка, которая не цель записи, или запись, чей
   результат используется»; соответствие `isResultUnused` найдено чтением кода
   и не проверялось.
4. Любая другая ссылка в runtime-дереве — чтение, в том числе во вложенной
   функции (колбэк `forEach`, замыкание), во втором `return`, в аргументе
   вызова, в записи в другое хранилище (`this.total = count`). Скептик
   называет это «утечкой». `references` собираются обходом всей программы
   (`core/hints/analyze-scopes.ts:257-281`), так что чтения во вложенных
   функциях там есть. Фильтр `getEnclosingFunction`, которым `getLocalRanges`
   отбирает записи, для поиска чтений не годится.
5. Ссылки вне runtime-дерева (аргументы логирующих вызовов, ambient-код) —
   не чтения, как и записи там, которые `getLocalRanges` уже отбрасывает через
   `isRuntimeNode`. Иначе упадёт тест `:788-791` (`console.log(++done)`,
   ожидание `[]`). Проверяй `syntax.isRuntimeNode(reference)` до
   `getContextSlot` и `isResultUnused`: эти помощники привязаны к
   runtime-дереву (`types/syntax/syntax-helpers.d.ts:267-272`), а
   `isResultUnused` для узла вне него бросает ошибку
   (`core/syntax/is-result-unused.ts:21`).
6. Реши сам и зафиксируй тестом:
   - Приёмник мутирующего метода с неиспользуемым результатом
     (`paths.push(x)`, `map.set(k, v)`). По п. 4 это чтение, и `paths -> []`
     вернётся лишним мутантом: это шум, а не ложный вердикт. Скептик
     предлагает такие вызовы чтением не считать. В `core/` это ≈ 19–30 из 96
     случаев, где переменную только наполняют и эвристика верна; цена
     буквального правила, по его оценке, — не больше 81 лишнего мутанта на
     `core/`, ≈ 0,5 %. Образец разбора `x.push(…)` с неиспользуемым
     результатом — `readArrayCall` в `core/syntax/is-joined-array.ts:57-86`.
   - Ссылка в правой части записи той же переменной (`sum = sum + x;`). По
     п. 4 это чтение, хотя значение уходит только обратно в переменную (не
     проверялось; в `return-value.test.ts` такой формы нет).
   - Запись как тело стрелки-колбэка `forEach` (`items.forEach(() => count++)`).
     `isResultUnused` такой результат отброшенным не считает: множество
     `discarded` — только обработчики событий шаблонов
     (`core/syntax/create-syntax-helpers.ts:67-71`). Для этого случая есть
     `syntax.isForEachResult` (`types/syntax/syntax-helpers.d.ts:199-203`).

Где ставить проверку (по чтению кода): в месте вызова для `solitary`
(`core/mutators/return-value.ts:170-171`: при других чтениях диапазон один —
`target`) или в `getLocalRanges` с параметром политики. Проверка прямо в
`getLocalRanges` без параметра поменяет и `R6`: её вызывает `getAssignedValues`
(`:512`). Само правило `applySolitaryRule` менять не нужно. Оно общее для
`return-value`, `statement-removal`, `array-element` и `object-property`, а
лишние диапазоны приходят из `return-value`.

## Фактическое поведение

Шаг 1 (суть сообщений Vitest, не дословный лог; одинаково во всех трёх
прогонах):

```
× keeps the default of a returned local that is also read elsewhere
  expected [] to strictly equal [ 'count -> 0' ]
× does not drop the default as solitary
  expected [ 'count -> 0 (subsumed solitary)' ] to strictly equal []
```

Шаг 2, `npx mootant list src/process.js --skipped`: в секции `skipped:` есть
`count -> 0`. Раскладка ниже приблизительная: колонки выравниваются, а стрелка
(`->` или `→`) зависит от терминала (`cli/report/format-text-report.ts:84-104`,
`cli/terminal/get-symbols.ts:49`, `:56`). Верификатор дословно видел строку
`7:10 return-value count -> 0 subsumed solitary` и начало причины, полный
текст причины собран по шаблону `core/generate/generate-file-mutants.ts:359`.

```
skipped:

src/process.js
  7:10  return-value  count -> 0  subsumed  solitary
        a finer number-literal mutant lies inside the code it removes, and killing that mutant needs a test that observes this code
```

По данным анализа в той же секции ещё два пропуска на `4:5`, к багу они не
относятся: `count++ -> ++count` (`equivalent`, `unused-result`) и
`count++ -> ;` (`subsumed`, `solitary`, тонкий мутант — update-operator). В
`--json` у `count -> 0` поля `"rule": "solitary"`, `"category": "subsumed"`,
`"heuristic": true` и `"by"` с `mutator: "number-literal"`, `line: 2`,
`column: 15`, то есть `0` в `let count = 0` (поля —
`cli/report/build-list-report.ts:149-172`).

`mootant run src/process.js --no-cache`: mutants 3, killed 3, survived 0,
score 100 % (три прогона, результат одинаковый). С физически вписанным
`return 0` `vitest --run` даёт 1 passed. С `--preset strict` или
`settings.coarseMutants: true`: mutants 5, killed 4, survived 1
(`7:10 return-value`), score 80 % (три прогона).

Что ещё видели верификаторы (сквозными прогонами):

- Кто держит пропуск: без number-literal — update-operator (`count++` →
  `count--`), без него — statement-removal (`count++` → `;`), без всех трёх
  `count -> 0` выдаётся. Каким способом выключали мутаторы, в отчёте не
  записано.
- На 170ec52 так же пропускаются (`subsumed solitary`) варианты с
  `onItem(item, ++count)`, с чтением в колбэке `forEach` и с двумя
  `return count`. Контроль `let sum = 0; … sum += x; return sum` пропущен, как
  и должен. Точный текст вариантов не сохранился.
- Скептик: то же в TS-модуле с `let user = {…}; store.save(user); return user`
  и `onLabel(label); return label` — в `recommended` score 100 %, в
  `--preset strict` 75 % (выжили 2 мутанта `return-value`). Точный текст файла
  не сохранился.

## Подозреваемые места в коде

- `core/mutators/return-value.ts:170-171` —
  `solitary = [target, ...getLocalRanges(value, context)]` для небулевых
  значений: инициализатор и записи добавляются без проверки других чтений.
  Отсюда удобнее всего включать условие только для `solitary`, см. «Где
  ставить проверку».
- `core/mutators/return-value.ts:349-365` (`getLocalRanges`) — инициализатор и
  записи в runtime-дереве той же функции. Её вызывает и `getAssignedValues`
  (`:508-517`, правило `R6`, BUG-304).
- `core/mutators/return-value.ts:378-391` (`getLocalBinding`) — здесь есть
  `Binding` с `references` и `writes`; корень цепочки членов — через
  `getMemberRoot` (`:380`).
- `types/syntax/binding.d.ts:23-27` (`references`: чтения и цели записей по
  всему файлу, без объявляющего идентификатора) и `:41-47` (`writes`: записи
  целиком).

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, один экспорт на файл (локальные
  функции рядом допустимы: в `core/mutators/return-value.ts` один экспорт и
  13 локальных функций), JSDoc на каждую функцию, `let` вместо `const` там,
  где так принято в проекте, строгий ESLint (`@azat-io/eslint-config`),
  cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  Новых полей в `types/` для исправления не нужно: `Binding.references`,
  `Binding.writes`, `syntax.isRuntimeNode`, `syntax.getContextSlot` и
  `syntax.isResultUnused` уже есть.
- Не меняй поведение `R6` (BUG-304) в рамках этого исправления без отдельного
  обоснования. Доказательному `R6` нужна консервативная политика для составных
  записей (`ok ||= …` — чтение), а здесь составная запись с неиспользуемым
  результатом чтением не считается. Общий помощник «есть ли у переменной
  другие чтения» уместен (скептик советует чинить оба бага одним предикатом),
  но с параметром этой политики.
- Тест-воспроизведение из анализа нельзя копировать как есть в `test/repros/`:
  перепиши его в стиле проекта. Строгий ESLint (`eslint.config.ts`:
  `@azat-io/eslint-config` с правилами perfectionist и vitest) проверяет имена
  файлов, `describe`/`it`, порядок импортов и ключей. Проверки BUG-301 добавь в
  `test/core/mutators/return-value.test.ts`, временный
  `test/repros/BUG-301.test.ts` удали. Фикстуры, если понадобятся, клади только
  в `test/fixtures/**`: их игнорируют ESLint (`eslint.config.ts:15`), `tsc`
  (`tsconfig.json:2`) и Vitest (`vitest.config.ts:18`).
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro` (14 ошибок
  `ts(2322)` в `docs/components/*.astro`): `tsconfig.json:2-4` включает
  `**/*.ts` и не исключает `dist/`, а `dist/types/html/inline-script.d.ts`
  подтягивает типы `vite/client` (так установила базовая линия анализа). После
  сборки удаляй `dist/` или проверяй `test:unit`, `test:js`, `test:types` (и
  остальные `test:*`) по отдельности.
- Тесты, зависящие от окружения (к багу не относятся): по два теста в
  `test/cli/run-list.test.ts` (`:160`, `:180`) и
  `test/cli/run-mutation.test.ts` (`:127`, `:194`) ждут Unicode и падают при
