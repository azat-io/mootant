# BUG-504: node:test — SIGHUP/SIGQUIT оставляют тестовый процесс зависшего мутанта навсегда

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium (итог координатора после перепроверки;
> в анализе баг объединён с BUG-601 и BUG-503 как «осиротевшие тестовые
> процессы после сигнала процессу CLI»). Статус: подтверждён. Найдено на
> коммите 170ec52.
>
> Перепроверено независимо (в рамках BUG-601; отдельно BUG-504 не
> перепроверялся): воспроизведено — node:test + SIGHUP процессу mootant 3 из 3
> (exit 129, процесс юнита с ppid 1 жив через 10 и 40 с), закрытие терминала
> (pty) — сирота 3 из 3, SIGTERM, SIGINT и Ctrl+C — чисто, SIGQUIT независимо
> не проверялся; скептик: BUG-601 в целом оценил как low, но именно node:test +
> SIGHUP назвал специфичным для mootant (простой `node --test` при SIGHUP группе
> процессов не оставляет, сироту даёт `detached: true`) и ближайшим к medium,
> исправлять первым — добавить `SIGHUP` в
> `adapters/node-test/track-process-group.ts:7`. Координатор оставил medium.

## Контекст

Адаптер node:test запускает каждый прогон тест-файла — в dry run и для каждого
юнита «мутант × тест-файл» (`adapters/node-test/run-dry.ts:84`,
`adapters/node-test/run-isolated.ts:58` →
`adapters/node-test/run-test-file.ts:42`) — отдельным процессом с
`detached: true` (`adapters/node-test/run-test-process.ts:117-123`). На POSIX
это новая сессия и группа (у процесса юнита sid = pgid = pid), поэтому сигналы
терминала до него не доходят, и останавливать его должен сам mootant. Зависший
юнит останавливает сторож (`run-test-process.ts:133-139`), но сторож работает
внутри процесса mootant. Пока тестовый процесс жив, `trackProcessGroup`
(`adapters/node-test/track-process-group.ts:7,18-23,40-46`; вызывается из
`run-test-process.ts:130-131`) убивает его группу при `exit` процесса mootant и
на SIGINT/SIGTERM — и только на них, хотя JSDoc (`track-process-group.ts:9-16`)
прямо называет причину: эти процессы «не получают сигналов терминала». SIGHUP
(закрыли терминал, оборвалась SSH-сессия) и SIGQUIT (Ctrl+\) завершают mootant
действием по умолчанию: событие `exit` не наступает, сторож умирает вместе с
mootant, и тестовый процесс зависшего мутанта крутится навсегда (ppid 1,
состояние R, занимает ядро CPU до ручного `kill`). SIGKILL и OOM-killer дают
тот же исход, но их не обработать; SIGHUP и SIGQUIT — можно.

На вердикты баг не влияет (прерванный прогон отчёта не выдаёт); ущерб —
бесконечный процесс. В анализе он объединён с BUG-601: сигнал только процессу
CLI оставляет тестовые процессы (у Vitest — воркеры, это BUG-503) и рабочий
каталог `$TMPDIR/mootant-*` (BUG-600). Этот промпт — самостоятельное
минимальное исправление node:test-части. Каталог `mootant-*`, который остаётся
после любого прерывания, сюда не входит.

## Воспроизведение

В ветке анализа `experiment/bug-repros` это была фикстура `test/repros/BUG-504/`
со скриптом `run.sh <SIGNAL>`. В чистом клоне её нет, поэтому ниже она
целиком. Нужны Linux (скрипт использует procps-вариант `ps`: `--ppid`,
`etimes`; на macOS не проверялся), Node.js `^20.19.0 || >=22.12.0` (в анализе —
22.23.4) и pnpm 12 (в анализе — 12.16.1; pnpm 10 не читает `configDependencies`
из `pnpm-workspace.yaml`, и pnpm в репозитории зависает). Все команды выполняй
в одной сессии shell.

**Шаг 1.** Собери mootant в корне клона (`bin/mootant.js` импортирует
`dist/cli/index.js`):

```bash
pnpm install
pnpm build
export MOOTANT_REPO=$PWD
```

**Шаг 2.** Создай фикстуру вне репозитория: внутри дерева её подхватили бы
ESLint, Prettier, cspell и knip. Раннер — `node:test`, Vitest не нужен
(peer-зависимость `vitest` у mootant необязательная). Встроенный адаптер mootant
грузит из своего `dist` относительным импортом
(`cli/built-in-adapters.ts:32-35`), поэтому ставить mootant в фикстуру для
этого варианта не нужно.

```bash
FIX=$(mktemp -d)/bug-504
mkdir -p "$FIX/src" "$FIX/test"
cat > "$FIX/package.json" <<'EOF'
{
  "name": "bug-504-fixture",
  "private": true,
  "type": "module",
  "scripts": { "test": "node --test test/step.check.js" }
}
EOF
cat > "$FIX/mootant.config.js" <<'EOF'
export default {
  // the hung mutant keeps its test process busy for about 30 s
  run: { runner: 'node-test', timeout: { constant: 30000 } },
}
EOF
cat > "$FIX/src/step.js" <<'EOF'
export function getStep(size) {
  return size - 9
}
EOF
cat > "$FIX/test/step.check.js" <<'EOF'
import { it } from 'node:test'
import assert from 'node:assert/strict'

import { getStep } from '../src/step.js'

it('counts to ten', () => {
  let step = getStep(10)
  let n = 0
  // the mutant 9 -> 10 makes the step 0: an endless synchronous loop
  for (let i = 0; i < 10; i += step) {
    n++
  }
  assert.equal(n, 10)
})
EOF
```

Почему фикстура такая. Мутатор числовых литералов прибавляет к числу единицу
(JSDoc `core/mutators/number-literal.ts:33-43`; в пресете по умолчанию все 20
встроенных мутаторов, `docs/content/guide/configuration.mdx:147`): мутант
`9 → 10` обнуляет шаг цикла, и тест уходит в бесконечный синхронный цикл.
Мутированный код (`getStep`) вычисляется один раз, поэтому `hitLimit` зависания
не замечает, и юнит останавливает только сторож по таймауту.
`timeout.constant: 30000` растягивает это окно, чтобы успеть послать сигнал.
Команду и тест-файл адаптер берёт из `scripts.test`
(`adapters/node-test/find-test-command.ts:7-10`). С таймаутом по умолчанию
(`{ factor: 3, constant: 250 }`) окно — около 1 с плюс ~1,5 с на подтверждение
таймаута (замер скептика на похожей фикстуре): сценарий редкий, но реальный.

**Шаг 3.** Скрипт проверки — `run.sh` из ветки анализа. Изменён только способ
найти mootant: `MOOTANT_BIN` или `bin/mootant.js` клона из `MOOTANT_REPO` (в
исходнике путь вычислялся от положения скрипта внутри репозитория). В
изменённом виде скрипт не запускался: при подготовке промпта запуск программ
был запрещён.

```bash
cat > "$FIX/run.sh" <<'EOF'
#!/bin/bash
# BUG-504: node:test runs every test file detached, in a session of its own,
# and mootant stops these processes only on SIGINT and SIGTERM. SIGHUP (the
# terminal or the SSH session closes) or SIGQUIT (Ctrl+\) ends mootant and
# leaves the test process of a hung mutant running for good.
# Linux with procps ps. Mootant: $MOOTANT_BIN, else bin/mootant.js of the clone
# in $MOOTANT_REPO (built when dist is missing).
# Exit 1 = reproduced, 0 = no test process left, 2 = setup problem.
set -u
HERE=$(cd "$(dirname "$0")" && pwd)
SIGNAL=${1:-HUP}
BIN=${MOOTANT_BIN:-}
if [ -z "$BIN" ]; then
  REPO=${MOOTANT_REPO:-}
  [ -n "$REPO" ] || { echo "set MOOTANT_REPO or MOOTANT_BIN"; exit 2; }
  [ -f "$REPO/dist/cli/index.js" ] || (cd "$REPO" && pnpm run build >/dev/null)
  BIN=$REPO/bin/mootant.js
fi
cd "$HERE"
export TMPDIR=$(mktemp -d)
node "$BIN" run src --no-cache </dev/null >/dev/null 2>&1 &
MOOTANT=$!
CHILD=""
for _ in $(seq 1 120); do
  CHILD=$(ps -o pid=,etimes= --ppid "$MOOTANT" | awk '$2 >= 3 {print $1; exit}')
  [ -n "$CHILD" ] && break
  sleep 0.5
done
[ -z "$CHILD" ] && { echo "no hung test process found"; kill "$MOOTANT"; exit 2; }
kill -s "$SIGNAL" "$MOOTANT"
wait "$MOOTANT"; echo "mootant exit code: $?"
sleep 2
if kill -0 "$CHILD" 2>/dev/null; then
  echo "REPRODUCED: test process $CHILD outlived mootant: $(ps -o pid=,ppid=,sid=,stat=,pcpu= -p "$CHILD")"
  kill -KILL -- "-$CHILD" 2>/dev/null || kill -KILL "$CHILD"
  rm -rf "$TMPDIR"
  exit 1
fi
echo "ok: no test process left"
rm -rf "$TMPDIR"
EOF
chmod +x "$FIX/run.sh"
```

**Шаг 4.** Запуск. Каждый прогон ждёт зависший юнит (до 60 с) и ещё 2 с после
сигнала.

```bash
"$FIX/run.sh" HUP    # выход 1 = воспроизведено
"$FIX/run.sh" QUIT   # выход 1 = воспроизведено
"$FIX/run.sh" TERM   # контроль: SIGTERM уже обрабатывается, выход 0
```

Вариант «как у пользователя» — mootant из тарбола. После правки кода тарбол
нужно пересобрать и переустановить.

```bash
(cd "$MOOTANT_REPO" && pnpm build && pnpm pack)   # mootant-0.1.0.tgz в корне клона
(cd "$FIX" && npm i -D "$MOOTANT_REPO/mootant-0.1.0.tgz")
MOOTANT_BIN="$FIX/node_modules/mootant/bin/mootant.js" "$FIX/run.sh" HUP
```

Этой фикстуре Vitest не нужен. Если он понадобится в другой npm-фикстуре,
ставь `npm i -D vitest@5`, а не `vitest@5.0.5`: в npm 10.9.9 установка 5.0.5
падает с ошибкой arborist `Cannot read properties of null (reading 'edgesOut')`.

## Ожидаемое поведение

На SIGHUP и SIGQUIT, присланные процессу mootant (по pid, группе или при
закрытии терминала), mootant останавливает группы своих тестовых процессов так
же, как на SIGINT/SIGTERM (`stopLiveProcessGroups`), и затем умирает от того же
сигнала: shell видит код 129/131, `child_process` — `code === null` и
`signal === 'SIGHUP'`/`'SIGQUIT'`. Так node:test-адаптер уже ведёт себя на
SIGTERM: по замеру верификатора mootant умирает от сигнала 15. Переподнятый
SIGQUIT, как и сейчас, может оставить core dump — это обычная семантика Ctrl+\.
На Windows ничего не ломается (см. «Подозреваемые места в коде»).

## Фактическое поведение

Вывод `run.sh` в анализе (запуски `HUP`, `QUIT`, `TERM`; в строке
`REPRODUCED` — pid, ppid, sid, stat, %CPU: процесс — лидер своей сессии,
ppid 1):

```
mootant exit code: 129
REPRODUCED: test process 16242 outlived mootant: 16242     1 16242 Rsl  30.2
mootant exit code: 131
REPRODUCED: test process 17013 outlived mootant: 17013     1 17013 Rsl  29.9
mootant exit code: 143
ok: no test process left
```

Независимая перепроверка (верификаторы BUG-601; своя фикстура с зависанием в
немутируемом модуле, `timeout.constant: 20000`). node:test + SIGHUP — 3 из 3:
exit 129, процесс юнита (pgid = sid = pid, `Rsl`) с ppid 1 жив через 10 и
40 с. Закрытие pty — сирота 3 из 3. SIGTERM, SIGINT и Ctrl+C — процессов не
остаётся. SIGQUIT только процессу mootant в матрице анализа давал 131 и сироту;
Ctrl+\ в настоящем терминале не проверялся. Во всех прерванных прогонах в
TMPDIR оставался каталог `mootant-*` — это отдельный дефект (BUG-600).

## Подозреваемые места в коде

- `adapters/node-test/track-process-group.ts:7` —
  `SIGNALS = ['SIGINT', 'SIGTERM']`. По этому списку идут и подписка
  (`:18-23`), и снятие (`:51-56`). `onSignal` (`:40-46`) уже убивает группы
  (`stopLiveProcessGroups`, `adapters/node-test/stop-live-process-groups.ts:8-13`
  → `SIGKILL` группе, `adapters/node-test/stop-process-group.ts:9-19`) и
  переподнимает сигнал, если других слушателей нет (`:43-45`). Других
  слушателей SIGHUP/SIGQUIT в процессе mootant нет. В `adapters`, `core`, `cli`
  и `bin` их никто не ставит: спиннер
  (`cli/terminal/create-spinner.ts:51-54,147-161`) слушает только SIGINT/SIGTERM
  и только в интерактивном терминале. Рантайм-зависимости (`lilconfig`,
  `oxc-parser`, `@eslint-community/regexpp`) их тоже не ставят.
  Поэтому после добавления сигналов в список mootant умрёт от того же сигнала.
  Если появится CLI-владелец отмены (общее исправление BUG-601), `onSignal`
  уступит сигнал ему. Так уже задумано и закреплено тестом «leaves a signal to
  other listeners» (`test/adapters/node-test/track-process-group.test.ts:69-79`).
- JSDoc `track-process-group.ts:9-16` и `run-test-process.ts:76-77` перечисляют
  «exit, SIGINT или SIGTERM» — обнови вместе со списком.
- `adapters/node-test/run-test-process.ts:117-123` — `detached: true`. Из-за
  него сигналы терминала не доходят до тестов. Убирать его не нужно: на нём
  держится остановка всей группы вместе с серверами и воркерами, которые
  запустили тесты (JSDoc `adapters/node-test/stop-process-group.ts:1-8`).
- Windows (не проверено). Переподнять SIGHUP через
  `process.kill(process.pid, 'SIGHUP')` на win32, по-видимому, нельзя. Пакет
  signal-exit 4.1.0 есть в `pnpm-lock.yaml`; после `pnpm install` он лежит в
  `node_modules/.pnpm/signal-exit@4.1.0/node_modules/signal-exit/dist/mjs/`.
  В `index.js:98-101,139` он пишет, что так бросается `ENOSYS`, и на win32
  переподнимает вместо SIGHUP сигнал SIGINT. SIGQUIT он на win32 вовсе не
  слушает (`signals.js:28-35`). `onSignal` (`:43-45`) такой оговорки не делает.
  Поэтому не вызывай `process.kill(process.pid, …)` с SIGHUP или SIGQUIT на
  win32: либо подписывайся на них только вне win32, либо не переподнимай их там.
  Ветки `process.platform !== 'win32'` в проекте уже есть
  (`adapters/vitest/stop-hung-worker.ts:19-24`), как и тест с подменой платформы
  (`test/adapters/vitest/stop-hung-worker.test.ts:87-96`). `SIGNALS` —
  константа модуля (`:7`). Если вычислять список по платформе при загрузке
  модуля, ветку win32 не покрыть подменой `process.platform` в тесте, поэтому
  проверяй платформу при вызове. CI гоняет тесты только на `ubuntu-latest`
  (`.github/workflows/test.yml`), а порог покрытия — 100%
  (`vitest.config.ts:9-15`), поэтому ветку win32 нужно покрыть моком.

## Критерий готовности

- В `test/adapters/node-test/track-process-group.test.ts` есть проверка для
  `SIGHUP` и `SIGQUIT` по образцу теста SIGINT (`:51-67`). Шаги: снять чужие
  слушатели сигнала, замокать `process.kill` (иначе тест реально пошлёт сигнал
  воркеру Vitest), вызвать `process.emit(signal, signal)`, вернуть слушатели.
  Ожидается: вызовы `kill` — `[[-41, 'SIGKILL'], [process.pid, signal]]`,
  слушатели после этого сняты (помощник `countListeners`, `:11-15`, расширь на
  новые сигналы). До исправления тест падает (слушателя нет, `kill` не
  вызывается), после — проходит.
- Ветка win32, какую бы ты ни выбрал, покрыта тестом с
  `vi.spyOn(process, 'platform', 'get').mockReturnValue('win32')`. На win32 нет
  вызова `process.kill(process.pid, 'SIGHUP')` или `'SIGQUIT'`.
- Ручная проверка после `pnpm build`. `"$FIX/run.sh" HUP` и
  `"$FIX/run.sh" QUIT` печатают `ok: no test process left` и завершаются с
  кодом 0, а строка `mootant exit code` показывает 129 и 131.
  `"$FIX/run.sh" TERM` по-прежнему даёт 143 и код 0.
- Зелёные `pnpm test:unit` (с порогом покрытия 100%), `pnpm test:js`,
  `pnpm test:types`, `pnpm test:usage`, `pnpm test:spelling` и остальные
  `test:*`. `pnpm test:astro` проверяй на дереве без `dist/` (см.
  «Ограничения»). Требование «`pnpm test` полностью зелёный» сразу после
  `pnpm build` невыполнимо: сборка даёт ложные ошибки `test:astro`.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Скрипт и фикстура из «Воспроизведения» — инструмент ручной проверки.
  Тест-воспроизведение из анализа (`test/repros/BUG-504/` в ветке
  `experiment/bug-repros`) нельзя копировать в `test/repros/` как есть. Его
  нужно переписать в стиле проекта: Vitest, `describe`/`it`, строгий ESLint
  (имена файлов, порядок импортов, JSDoc у функций). Фикстуры, если
  понадобятся, клади в `test/fixtures/**`. Их исключают ESLint
  (`eslint.config.ts:15`), knip (`knip.config.ts:5`), cspell
  (`cspell.config.ts:44`) и `tsconfig.json:2`, но Prettier (`test:format`)
  проверяет и их.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`
  (14 × `ts(2322)` в `docs/components/*.astro`). `tsconfig.json:2-4` не
  исключает `dist/`, и `dist/types/html/inline-script.d.ts` подтягивает
  `vite/client` (базовая линия анализа, 00-baseline). Проверяй `pnpm test:unit`,
  `pnpm test:js`, `pnpm test:types` и остальные `test:*` по отдельности, а
  `test:astro` запускай без `dist/`.
- `test:unit` может падать и из-за окружения, а не из-за правки (там же). При
  `TERM=linux` падают 4 теста CLI, которые ждут Unicode. Под root падает
  `test/adapters/node-test/score-node-test.test.ts:102`. При заданном
  `NODE_OPTIONS` покрытие ниже 100%. Сравни с прогоном до изменений или
  запускай с `TERM=xterm-256color` и `env -u NODE_OPTIONS`.
