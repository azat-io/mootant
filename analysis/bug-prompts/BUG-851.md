# BUG-851: тест-сьют падает под нагрузкой CPU (таймауты и лимиты по стене)

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено — данных нет (BUG-851 не попал в
> перепроверку двумя агентами, решения координатора по нему нет, поэтому
> серьёзность оставлена заявленной); скептик: не проводился. При редактуре
> цитаты кода сверены с 170ec52 только чтением, без запусков, а команда
> искусственной нагрузки из «Воспроизведения» в анализе не запускалась:
> падения взяты из двух прогонов под естественной нагрузкой машины.

## Контекст

`pnpm test:unit` (`vitest --run --coverage`, `package.json:75`) — это джоба
`unit` в CI (`.github/workflows/test.yml`) и среда догфудинга Mootant. В
тишине на 4 vCPU он идёт ≈ 250–260 с (тихие прогоны анализа: ≈ 251 с и
260,2 с). Под нагрузкой CPU тесты падают по времени при верной логике:

- **load-1**: load average 29–34, 3 воркера Vitest (по умолчанию), 1 382 с.
  22 падения, из них 20 по времени в 10 файлах. Два остальных — другие баги:
  BUG-852 (точное сравнение float в `test/adapters/vitest/runner.test.ts:693`)
  и BUG-854 (`test/adapters/node-test/score-node-test.test.ts:98` под root).
- **e-load**: load average 18–42, `--maxWorkers=2`, без `NODE_OPTIONS`,
  1 170 с. 10 падений: 9 по времени (7 из них те же, что в load-1) и
  root-тест.
- Всего за два прогона по времени упали 22 разных теста. Набор от прогона к
  прогону меняется: это нестабильность, а не детерминированная поломка.

Механизмы (полный список падений — в «Фактическом поведении»):

1. **Дефолтный `testTimeout` 5 000 мс у CPU-тяжёлых тестов**: в
   `vitest.config.ts:7-20` его нет. Время в скобках — под нагрузкой:
   - `test/cli/report/format-header.test.ts:21-29` — тело из 300 000 строк
     (44,8 с);
   - `test/cli/terminal/get-max-display-width.test.ts:17-21` — 200 000
     текстов (13,9 с);
   - `test/core/cache/prune-cache-entries.test.ts:48-61` — 200 002 записи, на
     две больше предела `MAX_ENTRIES = 200_000`
     (`core/cache/prune-cache-entries.ts:11`) (6,5 с);
   - `test/cli/index.test.ts:211-241` — разбор каждого мутанта эталонных
     списков `test/fixtures/list` (10,0 с);
   - `test/cli/html/client/start-report.test.ts:476-491` — happy-dom, отчёт
     на 1 000 тестов (6,8 с);
   - `test/core/run-mutants.test.ts:822-840` — загрузка компиляторов
     Svelte/Vue (5,3 с);
   - `test/core/generate/generate-file-mutants.test.ts:4685-4711` —
     property-тест на 200 сгенерированных формул
     (`createFormulaCases(12_345, 200, …)`), случай «keeps no weak mutant and

## Воспроизведение

Отдельного теста-воспроизведения у бага нет: в ветке `experiment/bug-repros`
файлов BUG-851 нет. Воспроизведение — прогон штатного сьюта под нагрузкой
CPU. Внешних фикстур тоже нет. Mootant для догфудинга берётся из самого клона
(`pnpm build` → `node bin/mootant.js`), так что `pnpm pack` и установка
tarball не нужны. Если всё же проверять на внешнем npm-проекте: `pnpm pack`,
затем `npm i -D ./mootant-<версия>.tgz vitest@5`. Не `vitest@5.0.5`: в npm
10.9.9 arborist падает с `Cannot read properties of null (reading
'edgesOut')`.

**Шаг 0. Подготовка** (всё — из корня клона):

```bash
pnpm --version   # нужен pnpm 12 (CI ставит pnpm/action-setup с version: latest-12)
pnpm install --frozen-lockfile
pnpm build       # для воспроизведения нужен только в шаге 4: bin/mootant.js импортирует ../dist/cli/index.js
```

По базовой линии анализа pnpm 10 не читает `configDependencies` из
`pnpm-workspace.yaml`, и pnpm внутри репозитория зависает. Сам сьют `dist/`
не использует.

**Шаг 1. Тихий прогон** (машина свободна; ≈ 4–5 мин, в Claude Code — с
таймаутом команды 600000):

```bash
time env -u NODE_OPTIONS TERM=xterm-256color \
  pnpm exec vitest --run --coverage --coverage.reportOnFailure \
  --reporter=default --reporter=json --outputFile.json=/tmp/quiet.json
```

Ожидаемо зелёный. Под root падает только
`test/adapters/node-test/score-node-test.test.ts:98` (BUG-854), при
`TERM=linux` — 4 теста CLI (BUG-853), с `NODE_OPTIONS` — порог branches
(BUG-850). Поэтому `TERM` и `NODE_OPTIONS` заданы явно.

**Шаг 2. Скрипт нагрузки.** Он запускает команду под нагрузкой ≈ ×7 по числу
ядер и гасит нагрузку при выходе. Запускай его одним процессом: `trap` и
`jobs` видят только циклы своего шелла.

```bash
cat > /tmp/under-load.sh <<'EOF'
#!/usr/bin/env bash
# Использование: bash /tmp/under-load.sh <команда> [аргументы…]
set -u
n=$(( $(nproc) * 7 ))   # на 4 vCPU — 28 циклов, load average ≈ 30
for i in $(seq "$n"); do
  timeout 3600 sh -c 'while :; do :; done' &   # страховка: цикл сам умрёт через час
done
trap 'kill $(jobs -p) 2>/dev/null' EXIT
"$@"
code=$?
uptime
exit "$code"
EOF
```

**Шаг 3. Полный прогон под нагрузкой.** Идёт ≈ 20–25 мин, а
foreground-команда в Claude Code ограничена 10 мин, поэтому запускай в фоне
(`run_in_background`):

```bash
env -u NODE_OPTIONS TERM=xterm-256color bash /tmp/under-load.sh \
  pnpm exec vitest --run --coverage --coverage.reportOnFailure \
  --reporter=default --reporter=json --outputFile.json=/tmp/load.json \
  > /tmp/load.log 2>&1
```

Ожидаемо — от 9 до 20 падений из таблицы в «Фактическом поведении»: «Test
timed out in 5000ms» (и 30000/60000/120000ms в
`test/adapters/vitest/index.test.ts`), «expected [ 'hung' ] to strictly equal
[ Array(1) ]», «expected false to be true» на
`test/adapters/node-test/index.test.ts:350`. Набор плавает. Отдельно может
упасть `test/adapters/vitest/runner.test.ts:693` (`2049.9999999999995`
вместо `2050`), но это BUG-852. **Не проверено**, что именно эти циклы дают
такую картину: в анализе нагрузку давали параллельные процессы анализа.
Ориентир — load average 18–42 на 4 vCPU по `uptime` в конце лога.

Узкие варианты под той же нагрузкой (каждый — минуты; в анализе такими
командами не запускались, **не проверено**):

```bash
# лимит runProgram: свежий воркер после двух зависаний (:4799-4804)
env -u NODE_OPTIONS TERM=xterm-256color bash /tmp/under-load.sh \
  pnpm exec vitest --run test/core/generate/generate-file-mutants.test.ts -t observes
# эталон node:test: прогон исходной копии
env -u NODE_OPTIONS TERM=xterm-256color bash /tmp/under-load.sh \
  pnpm exec vitest --run test/adapters/node-test/index.test.ts -t 'agrees with mutants applied by hand'
# тесты spread на дефолтных 5 с
env -u NODE_OPTIONS TERM=xterm-256color bash /tmp/under-load.sh \
  pnpm exec vitest --run test/cli/report/format-header.test.ts test/cli/terminal/get-max-display-width.test.ts
```

Падение эталона node:test и `test/cli/index.test.ts:211` анализ
воспроизводил ещё в подмножестве из 14 файлов под load 27, но список этих
файлов не сохранился.

**Шаг 4. Догфудинг** под той же нагрузкой (после `pnpm build`, из корня
клона):

```bash
env -u NODE_OPTIONS TERM=xterm-256color bash /tmp/under-load.sh \
  node bin/mootant.js run cli/terminal --concurrency 2
```

В анализе первая из двух попыток (load ≈ 32) упала в dry run с «Tests fail
without mutants; fix them first (2 tests)»: `test/cli/index.test.ts` и
`test/cli/report/format-header.test.ts`, оба «Test timed out in 5000ms».
Анализ запускал с `--config` на файл `defineConfig({})` (то же, что значения
по умолчанию) и с `--json --all --verbose`. В чистом клоне конфига Mootant в
корне нет.

## Ожидаемое поведение

Под нагрузкой тесты идут дольше, но не падают. Лимиты, которые отличают
«завис» от «медленно», задаются с запасом или масштабируются и не включают
накладные расходы вроде старта воркера. Проверки по-прежнему ловят то, ради
чего написаны: бесконечный цикл даёт `hung` или `'Timeout'`, spread большого
массива роняет тест, предел кэша — ровно 200 000 записей.

## Подозреваемые места в коде

- `vitest.config.ts:7-20` — в `test` нет `testTimeout`, действует дефолт
  Vitest 5 000 мс. Порог coverage считается только по `adapters/**`,
  `cli/**`, `core/**` (`:15`), так что новые ветки в `test/helpers` его не
  затронут.
- `test/helpers/run-program.ts:8` — `TIME_LIMIT = 1000`; `:77-85` — таймер
  стартует до того, как новый воркер готов.
- `test/adapters/node-test/index.test.ts:140` — `timeout: 4000` на каждый
  прогон эталона, в том числе на прогон исходной копии со всеми тест-файлами
  (`test/helpers/run-node-test-reference.ts:78-85`, таймер `:148-151`).
- `test/adapters/vitest/index.test.ts:529-1919` — явные таймауты 30–180 с;
  `:961` — проверка по стене `< 40_000`.
- Тесты spread: размер входа (200–300 тыс.) берётся с большим запасом над
  лимитом spread в V8. По замеру анализа на его машине (Node 22.23.4,
  `Math.max(...array)`) лимит ≈ 130 000 аргументов. Он зависит от размера
  стека; в этой версии промпта не перепроверялся. Это:
  - `format-header.test.ts:21-29`: `formatHeader` вызывает
    `getMaxDisplayWidth(body.split('\n'))`, `cli/report/format-header.ts:46`;
  - `get-max-display-width.test.ts:17-21`;
  - не падавший `test/cli/report/get-short-id-length.test.ts:23-29`
    (300 000 id).
- Тесты, где размер задаёт не spread. Уменьшать их нельзя без потери смысла,
  поэтому для них подходит только явный таймаут:
  - `prune-cache-entries.test.ts:48-61` — предел `MAX_ENTRIES`;
  - `test/cli/create-run-progress.test.ts:431-439` — 100 000 символов, это
    `OUTPUT_LIMIT` (`cli/create-run-progress.ts:90`);
  - цепочки по 20 000 операндов против рекурсии:
    `test/core/syntax/get-logical-chain.test.ts:26-35`,
    `test/core/tree/walk-tree.test.ts:84-96` и
    `create-syntactic-type-provider.test.ts:88-95`.

  Все они идут на дефолтных 5 с. Из них в двух прогонах падали только
  `prune-cache-entries` и `create-syntactic-type-provider`.

## Критерий готовности

Детерминированного теста «падает до исправления, проходит после» здесь нет:
дефект проявляется только под нагрузкой. Его заменяют прогоны под нагрузкой
и проверка регрессии spread ниже.

- `runProgram` (`test/helpers/run-program.ts`) не даёт ложного `hung` под
  нагрузкой. Варианты: старт воркера не входит в лимит (например, таймер
  запускается по сообщению «готов» от воркера после загрузки модуля) **и/или**
  `TIME_LIMIT` поднят до 5–10 с либо умножается на коэффициент из окружения.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ослабляй проверки. Таймаут в оракулах должен по-прежнему отличать
  бесконечный цикл от завершения (`generate-file-mutants.test.ts:4799-4800` →
  `hung`, `pause`/`queue` в эталоне node:test → `'Timeout'`). Тесты spread
  должны по-прежнему падать на spread большого массива, а
  `prune-cache-entries` — проверять предел 200 000.
- Правки — только в `test/**` и `vitest.config.ts`. Продуктовый код
  (`adapters/`, `cli/`, `core/`) и публичный API (`exports` в `package.json`,
  типы в `types/`, формат конфига) не трогай. Например, не делай
  `MAX_ENTRIES` настраиваемым ради теста. Если без этого нельзя — опиши
  компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Тест-воспроизведение из анализа нельзя копировать как есть в
  `test/repros/`. У этого бага его нет, но если для проверки механизма
  понадобится вспомогательный тест, пиши его сразу в стиле проекта, иначе
  строгий ESLint его не пропустит:
  - имя вроде `BUG-851.test.ts` нарушает `unicorn/filename-case`: разрешены
    только kebab-case и PascalCase;
  - perfectionist сортирует строки импорта и имена внутри `{ … }` по длине
    строки по убыванию;
  - `vitest/consistent-test-it` требует `it`,
    `vitest/require-top-level-describe` — `describe` верхнего уровня
    (в проекте его называют по функции, например `describe('runProgram', …)`),
    `vitest/prefer-lowercase-title` — названия со строчной буквы.

  Тест клади рядом с соседними в `test/**`, а статические фикстуры — в
  `test/fixtures/**`. Их исключают Vitest (`vitest.config.ts:18`), ESLint
  (`eslint.config.ts:15`), `tsc` (`tsconfig.json:2`) и knip
  (`knip.config.ts:5`).
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: по базовой
  линии анализа это 14 ошибок `ts(2322)` в `docs/components/*.astro`.
  Причина — `tsconfig.json:2-4` не исключает `dist/`, и в программу попадает
  `dist/types/html/inline-script.d.ts` с
  `/// <reference types="vite/client" />`. В CI джоба Astro пакет не
  собирает, поэтому она зелёная. После сборки проверяй `test:unit`,
  `test:js`, `test:types` и остальные `test:*` по отдельности, а
  `test:astro` запускай только после `rm -rf dist`.
- По базовой линии анализа есть падения, которые не относятся к BUG-851 и
  есть и без исправления:
  - 4 теста CLI в `test/cli/run-list.test.ts` и
    `test/cli/run-mutation.test.ts` ждут Unicode-символов, а при
    `TERM=linux` вывод идёт в ASCII (`cli/terminal/is-unicode-supported.ts:13`,
    BUG-853);
  - «skips test files it cannot read»
    (`test/adapters/node-test/score-node-test.test.ts:98-105`) падает под
    root: `chmod 000` root'у не мешает (BUG-854);
  - при заданном `NODE_OPTIONS` (например, `--use-openssl-ca` у прокси) не
    покрывается правая ветка `?? ''` в
    `adapters/node-test/start-node-test-session.ts:119` и `:167`, и
    покрытие branches падает ниже 100 % (BUG-850);
  - под нагрузкой чаще падает точное сравнение float в
    `test/adapters/vitest/runner.test.ts:693` (BUG-852).
- Нагрузка из шага 2 занимает все ядра. Не запускай её на общей машине, где
