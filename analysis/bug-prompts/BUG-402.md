# BUG-402: кэш не видит файлы, от которых зависят виртуальные модули Vite

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (тест шага 1 падает 3 из 3, его
> вариант из ветки анализа — 2 из 2, интеграционный сценарий у скептика — 4 из
> 4; на реальном графе Vite 8.3.5 у виртуального узла
> `file = '\0virtual:limits'`, а не `null`, поэтому исправление по условию
> `file === null` не работает); скептик: не опроверг, medium — устаревший
> вердикт в обе стороны без предупреждения, но триггер узкий: нужен файл,
> подключённый к виртуальному модулю через `this.addWatchFile()`, и правка
> только этого файла при сохранившемся кэше, а популярные плагины
> (`@vitejs/plugin-vue`, `vite-plugin-svelte`, `astro`), по его данным,
> вызывают `addWatchFile` для реальных модулей.

## Контекст

Кэш вердиктов (`core/cache/*`) переиспользует вердикт мутанта, пока не
изменились мутируемый файл и всё, от чего зависит тестовый файл: ключ
тест-файла — дайджест хешей всех файлов из его списка зависимостей
(`core/cache/get-test-file-keys.ts:41-66`). Для Vitest этот список строит
`collectDependencies` (`adapters/vitest/collect-dependencies.ts:76-155`), и для
dry run (`adapters/vitest/run-dry.ts:200`), и для входов юнитов
(`adapters/vitest/read-unit-inputs.ts:32`). В список входят модули, которые
вычислил воркер (он сообщает ключи `evaluatedModules`,
`adapters/vitest/worker/list-dependencies.ts:37`), и всё, что они достигают в
графе модулей Vite, «which takes in files plugins watch»
(`adapters/vitest/collect-dependencies.ts:58-64`, контракт
`types/adapter/dry-file.d.ts:6-9`).

Сами виртуальные модули (`\0virtual:…`, `virtual:…`) в список не входят, и это
задумано (`:62-63`). Но вместе с ними выбрасывается всё, что они импортируют.
`add()` возвращает `false` для любого id, который после среза `?query`/`#hash`
не является абсолютным путём вне `node_modules`
(`adapters/vitest/collect-dependencies.ts:93-100`,
`adapters/vitest/get-module-file.ts:17-20`). Такой узел не обходится ни как
корень из отчёта воркера (`:131-134`), ни как импорт другого модуля
(`:121-124`). Файл теряется в обоих местах: в сценарии ниже `'\0virtual:limits'`
есть и в отчёте воркера, и среди импортов тест-файла.

Как watch-файл попадает в граф (Vite 8.3.5 из lockfile; после `pnpm install`
это `node_modules/vite/dist/node/chunks/node.js`):
`LoadPluginContext.addWatchFile` кладёт файл в `_addedImports` (`:8888-8892`),
они переносятся из `load` в `transform` (`:8543`, `:8563`), а
`vite:import-analysis` добавляет их в `importedUrls` виртуального модуля
(`:26773-26781`) и вызывает `moduleGraph.updateModuleInfo` (`:26785`). У
виртуального узла поле `file` **не** `null`: Vite ставит
`mod.file = cleanUrl(resolvedId)` (`:36905`; `cleanUrl` на `:529-531` только
срезает `?query`/`#hash`), то есть `file === '\0virtual:limits'`. Верификатор
подтвердил это на живом графе: у тест-файла есть импорт
`{ file: '\0virtual:limits', id: '\0virtual:limits' }`, у виртуального узла —
импорт `{ file: '<root>/limits.json' }`. JSDoc `GraphNode.file` («or null for a
virtual one», `adapters/vitest/collect-dependencies.ts:23-26`), фабрика узлов
существующего теста (`test/adapters/vitest/collect-dependencies.test.ts:70-78`)
и unit-тест шага 1 этому не соответствуют: у них виртуальный узел без `file`.

После правки такого файла кэш возвращает **старые вердикты в обе стороны**:
ложный `Survived` и ложный `Killed`. Предупреждения нет (`diagnostics: []`),
`--incremental` не нужен. Обойти это пользователь не может: чтения файлов
отслеживает `trackInputs`, а он ставится только в воркере
(`adapters/vitest/runner.ts:1017`), тогда как `readFileSync` плагина выполняется
в процессе Vite. Затронуты плагины, которые встраивают содержимое файла
(данные, конфиги, сгенерированные списки) в виртуальный модуль и объявляют
файл через `addWatchFile`. Реальный пример — `vite-plugin-i18next-loader@4.1.0`:
его `load` для `'\0virtual:i18next-loader'` встраивает локали и вызывает
`this.addWatchFile` для каждого файла (`src/index.ts:203-213` пакета).

Не затронуты (проверено контролями):

- плагины, генерирующие `import` реальных файлов: эти файлы воркер вычисляет и
  сообщает сам;
- `addWatchFile` из `load()` или `transform()` **реального** модуля: его узел
  обходится, и файл попадает в список.

Исправление не покроет:

- плагины, которые читают файлы, не вызывая `addWatchFile`: у скептика такой
  сценарий даёт устаревший вердикт и до, и после пробной правки;
- виртуальные id, оканчивающиеся на `.json` или `.map` (например,
  `'\0virtual:data.json'`): `vite:import-analysis` пропускает такой модуль
  целиком (`skipRE` и `canSkipImportAnalysis`, `chunks/node.js:26448-26449`,
  ранний выход на `:26544-26547`), и его watch-файлы в граф не попадают. Это
  вывод по чтению исходников Vite, экспериментально не проверялось.

Оба ограничения стоит описать в документации рядом с оговоркой про дочерние
процессы (`docs/content/guide/configuration.mdx:357-359`).

### Шаг 1. Падающие тесты (unit и интеграционный, сборка не нужна)

Первый тест вызывает `collectDependencies` на фейковом графе: тест-файл
импортирует `'\0virtual:limits'`, а тот — `/p/limits.json`. Второй создаёт во
временном каталоге проект с плагином, который строит `virtual:limits` из
`limits.json` и вызывает `this.addWatchFile()`. В `node_modules` проекта он
кладёт ссылку на Vitest репозитория и трижды запускает `runMutants`: с кэшем
при `age: 30`, с кэшем после правки на `age: 18` и без кэша. Файл временный, в
коммит не входит (см. «Ограничения»).


(`file: id.startsWith('/') ? id : null`), а в Vite 8 у него

`file === null` этот unit-тест проходит, а интеграционный — нет (проверено
верификатором). Постоянный unit-тест должен моделировать узел так же, как Vite
(см. «Критерий готовности»).

## Ожидаемое поведение

После правки `limits.json` вердикты прогона с кэшем совпадают с прогоном без
кэша: `age > 18` — `Killed`, `age == 18` — `Survived`. Мутанты, которые
покрывает `test/math.test.ts`, из кэша не берутся. Файл, который плагин объявил
через `addWatchFile` для виртуального модуля, входит в `DryFile.dependencies`
тест-файла, импортирующего этот модуль (контракт
`types/adapter/dry-file.d.ts:6-9`). Сами виртуальные id в список по-прежнему не
входят. В unit-тесте шага 1 `collectDependencies` возвращает `/p/limits.json`.

## Подозреваемые места в коде

- `adapters/vitest/collect-dependencies.ts:121-124`. Фильтр
  `add(imported.file ?? imported.id ?? '')` одновременно решает «добавить файл в
  список» и «обходить ли узел», и виртуальный узел отбрасывается вместе со
  всем, что он импортирует. Обходить (не добавляя в список) нужно и узлы, у
  которых `file ?? id` после среза `?query`/`#hash` не пуст, **не является
  абсолютным путём**, не содержит `/node_modules/` и не начинается с `node:`.
  От циклов защищает `seen`. Условие `file === null` **не годится**: в Vite 8 у
  виртуального узла `file` равен его id. Проверено: правка только этого места по
  условию `file === null`, без правки корней, даёт зелёный unit-тест шага 1 и
  красный интеграционный (`1 failed | 1 passed`).
- `adapters/vitest/collect-dependencies.ts:131-134`. Для корней из отчёта
  воркера `if (!add(id)) continue` пропускает `'\0virtual:limits'`, хотя воркер
  его сообщает (`adapters/vitest/worker/list-dependencies.ts:37`). Такой id надо
  искать в графе (цикл `:135-144`; узел находится в окружении `ssr`) и обходить,
  не добавляя. В шаге 1 виртуальный модуль приходит и как корень, и как импорт
  тест-файла, поэтому тесты шага 1 не различают, какое из двух мест исправлено.
  Хватает ли одного из них для интеграционного сценария, не проверено. Чини оба.
- `adapters/vitest/get-module-file.ts:17-20`. Правило «абсолютный путь вне
  `node_modules`» верно для того, что попадает в список, но как условие обхода
  не годится. `getModuleFile` используется ещё в
  `adapters/vitest/get-cache-inputs.ts:153`, поэтому его смысл не меняй, а для
  обхода заведи отдельный предикат.
- `adapters/vitest/collect-dependencies.ts:23-26` и `:54-64`. По JSDoc у
  виртуального узла `GraphNode.file` равен null, а для Vite 8 это неверно.
  Описание функции должно говорить, что виртуальные модули обходятся, но в
  список не входят.
- `adapters/vitest/collect-dependencies.ts:116-120`. После исправления обход
  дойдёт и до узлов watch-файлов. Такой узел, вероятно, ни разу не
  трансформировался: воркер его не импортирует, ведь виртуальный модуль
  встраивает содержимое. Тогда `visit()` вызовет для него `transformRequest`.
  Для JSON это преобразование в модуль, а если Vite не умеет преобразовать
  файл, ошибка будет поймана (`:117-119`). Это лишняя работа. Что у таких узлов
  действительно `transformResult === null`, не проверено.
- `test/adapters/vitest/collect-dependencies.test.ts`. `createNode` (`:70-78`)
  даёт виртуальным узлам `file: null`, в отличие от Vite. Виртуальные узлы теста
  (`:128-137`, `:158-159`) не имеют импортов, поэтому исключение их импортов
  тест не закрепляет. После исправления его ожидания меняться не должны.
- Смежное место, не проверялось и в критерий не входит:
  `adapters/vitest/get-cache-inputs.ts:150-158` берёт для global setup только
  id, вычисленные главным процессом, без обхода графа. Виртуальный модуль,
  импортированный из global setup, вероятно, теряет свои watch-файлы так же.

Пробная правка скептика, с которой всё проходит. Она не в стиле проекта и дана
только как ориентир:

```ts
// внутри collectDependencies, рядом с add()
function isVirtual(candidate: string): boolean {
  let clean = candidate.replace(/[#?].*$/u, '')
  return (
    clean !== '' &&
    !path.isAbsolute(clean) &&
    !clean.includes('/node_modules/') &&
    !clean.startsWith('node:')
  )
}

// в visit(), вместо фильтра на :121-124
let next = [...node.importedModules].filter(imported => {
  if (seen.has(imported)) {
    return false
  }
  let candidate = imported.file ?? imported.id ?? ''
  return add(candidate) || isVirtual(candidate)
})

// для корней, вместо условия на :132
if (!add(id) && !isVirtual(id)) {
  continue
}
```

С ней `limits.json` попадает в зависимости, оба теста шага 1 проходят, а список
зависимостей `test/math.test.ts` вырастает ровно на `limits.json`. Контроль с
реальным модулем проходит и до правки, и после. Сценарий без `addWatchFile`
падает и до, и после. Похожая правка воспроизводящего верификатора («обходить
неабсолютные id, не добавляя их» для корней и промежуточных узлов) дала 7
зелёных тестов из 7: два теста шага 1, три диагностических и два существующих
в `test/adapters/vitest/collect-dependencies.test.ts`.

## Критерий готовности

- Unit-тесты в `test/adapters/vitest/collect-dependencies.test.ts` в стиле
  проекта, на хелперах файла (`createEnvironment` `:35-60`, `createNode`
  `:70-78`, `createProject` `:86-94`). Виртуальный узел моделируется как в
  Vite 8: `file` равен id без `?query`/`#hash` (например, `'\0virtual:limits'`),
  а не `null`. Для этого поправь `createNode` или заведи вторую фабрику и обнови
  JSDoc. Сценарии:
  1. виртуальный модуль в середине графа: тест-файл → `'\0virtual:limits'` →
     `limits.json`, а в `reported` только тест-файл;
  2. виртуальный модуль только как корень: `'\0virtual:limits'` есть в
     `reported`, а тест-файл его не импортирует;
  3. сценарий 1 с id без `\0` (`'virtual:limits'`);
  4. цепочка «виртуальный → виртуальный → файл» и импорт файла из
     `node_modules` виртуальным модулем: файл из цепочки в результате есть, а
     файла из `node_modules` нет;
  5. цикл через виртуальный модуль (`a.ts` → виртуальный → `a.ts`) завершается.

  Во всех сценариях реальные импорты, включая файлы из `addWatchFile`, в
  результате есть, а самих виртуальных id нет. По чтению кода сценарии 1–3
  падают на 170ec52, а сценарий 1 падает и при неверной правке `file === null`.
- Линейность обхода (каждый узел графа посещается не больше одного раза)
  проверяется тестом, а не замером времени: список `transformed` (как на
  `:180-183`) показывает, что `transformRequest` вызывается только для узлов с
  `transformResult === null` и не больше одного раза на узел. Реши, нужен ли
  `transformRequest` узлу watch-файла, достижимому только через виртуальный
  модуль, и закрепи выбранное поведение тестом.
- Существующие тесты `test/adapters/vitest/collect-dependencies.test.ts`
  проходят без изменения ожиданий (с пробной правкой так и было).
- Интеграционный тест в `test/adapters/vitest/index.test.ts`, в блоке
  `describe('vitest adapter with the cache', …)` (`:1440`). Образец —
  `'runs mutants again after a change of a file loaded outside Vite'`
  (`:1600-1636`) с его хелперами `copyFixture` (`:346`), `run` (`:373`) и
  `splitCached` (`:426`). Нужна новая фикстура в `test/fixtures/`, например
  `cache-virtual/`: `package.json` `{ "type": "module" }`, `vitest.config.ts` с
  плагином из шага 2, `limits.json`, `src/math.ts`, `test/math.test.ts`.
  Переменную для неё заведи по образцу `inputsFixture` (`:258-261`). Тест
  проверяет три вещи. Повторный прогон без изменений берёт всё из кэша. После
  правки `limits.json` мутанты `src/math.ts` запускаются заново: `splitCached`
  даёт `ran: ['src/math.ts']` и `cached: []`, а вердикты совпадают с прогоном
  `cache: false`. Следующий прогон снова берёт всё из кэша. На 170ec52 тест
  должен падать, как второй тест шага 1; в такой форме он не прогонялся.
- Тесты шага 1 после исправления проходят, затем каталог `test/repros/` удалён.
- Если выполнялся шаг 2, после исправления его надо повторить (новые
  `pnpm build` и `pnpm pack`, свежий `FIX`). r2 должен совпасть с r3, все четыре
  вердикта — `cached=false`, как сейчас у контроля с реальным модулем.
- JSDoc в `adapters/vitest/collect-dependencies.ts:23-26` и `:54-64` описывает
  новое поведение. В `docs/content/guide/configuration.mdx` рядом с `:357-359`
  описаны оба оставшихся ограничения: плагины без `addWatchFile` и виртуальные
  id на `.json`/`.map`.
- Проверки проекта зелёные при запуске по отдельности: `pnpm test:unit` (порог
  покрытия 100% для `adapters/**`, `cli/**`, `core/**`, `vitest.config.ts:9-15`;
  значит, все ветви нового предиката покрыты unit-тестами), `pnpm test:js`,
  `pnpm test:types`, `pnpm test:usage`, `pnpm test:spelling`,
  `pnpm test:format` и остальные `test:*`. `pnpm test:astro` запускай без
  `dist/`. Падения, которые зависят от окружения, сверь с прогоном на

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip. Новый модуль (например,
  предикат обхода) получает свой тест по пути файла (`contributing.md:191-192`).
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Поднимать `CACHE_VERSION` (`core/cache/cache-version.ts:6`) для этой правки
  не нужно. Формат файла и рецепт ключа не меняются, меняется только состав
  списка зависимостей. Ключ — дайджест хешей файлов из списка
  (`core/cache/get-test-file-keys.ts:41-66`), а dry run идёт при каждом запуске:
  у полностью кэшированного прогона `runs: { dry: 1 }`
  (`test/adapters/vitest/index.test.ts:1471`). Поэтому у затронутых тест-файлов
  ключ сменится сам, а у остальных останется прежним. Поднимай версию, только
  если всё же меняешь формат или рецепт (`core/cache/cache-version.ts:1-5`).
- Тест из шага 1 нельзя копировать в `test/repros/` как есть. ESLint проекта
  находит в нём 11 ошибок (`unicorn/filename-case`, `no-await-in-loop`,
  `perfectionist/sort-modules`, `perfectionist/sort-maps`,
  `vitest/require-top-level-describe`, `vitest/prefer-lowercase-title`,
  `func-style`, `typescript/explicit-function-return-type`,
  `slop/no-chained-type-assertions`, `no-template-curly-in-string`). Каталог
  `test/repros/` не исключён ни из ESLint, ни из knip, cspell или tsc.
  Исключён только `test/fixtures/**` (`eslint.config.ts:15`, `knip.config.ts:5`,
  `cspell.config.ts:44`, `vitest.config.ts:18`, `tsconfig.json:2`). Постоянные
  тесты перепиши в стиле проекта под строгий ESLint (имена файлов,
  `describe`/`it`, порядок импортов, JSDoc). Фикстуры клади в
  `test/fixtures/**`. Каталог `test/repros/`, tarball и временные каталоги в
  коммит не входят.
- `test/fixtures/**` не исключён из `test:format`. Prettier проверяет
  `**/*.{astro,js,ts,json,md,mdx,yml}` (`package.json:70`), `.prettierignore`
  нет, а `prettier.config.ts:9-12` отдельно настраивает только
  `test/fixtures/list/source/**`. Новую фикстуру отформатируй:
  `pnpm exec prettier --write test/fixtures/<имя>`.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: 14 ошибок
  `ts(2322)` в `docs/components/*.astro`. Причина в том, что `tsconfig.json`
  включает `**/*.ts` (`:4`) и не исключает `dist/` (`:2`). После сборки в
  программу попадает `dist/types/html/inline-script.d.ts` (из
  `types/html/inline-script.d.ts:1`, `/// <reference types="vite/client" />`),
  и объявления `*.svg` из Vite конфликтуют с SVG-компонентами Astro. В CI джоба
  Astro пакет не собирает, поэтому там она зелёная. После шага 2 проверяй
  `test:unit`, `test:js`, `test:types` и остальные скрипты по отдельности, а
  `test:astro` запускай после `rm -rf dist`.
- Известные зависимости `test:unit` от окружения, не связанные с этим багом:
  - 4 теста в `test/cli/run-list.test.ts` и `test/cli/run-mutation.test.ts`
    ждут Unicode-символы и падают при `TERM=linux`
    (`cli/terminal/is-unicode-supported.ts:13`); запускай с
    `TERM=xterm-256color`;
  - тест «skips test files it cannot read»
    (`test/adapters/node-test/score-node-test.test.ts:98`) падает под root;
  - при заданном `NODE_OPTIONS` покрытие ветвей не достигает 100% в
    `adapters/node-test/start-node-test-session.ts:119,167`; запускай с
    `env -u NODE_OPTIONS`.
- Границы задачи. Отслеживать чтения файлов плагинами в процессе Vite не нужно,
  это отдельная задача. Здесь достаточно обходить виртуальные модули и описать
  в документации то, что исправление не покрывает.
