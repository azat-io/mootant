# BUG-106: регулярное выражение, начинающееся с `<!--`, ломает switched-модуль в Vite 8

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (юнит-тест падает 2 из 2 в трёх
> прогонах; сквозной прогон на Vite 8.3.5 с Vitest 5.1.0, а через `run.sh`
> анализа и с 5.0.5, даёт 9 из 9 мутантов `Error`, две `instrumentation-break`,
> `passed: false`; тот же проект на Vite 7.3.1 — 6 Killed, 3 Survived);
> скептик: не опроверг, medium — ложных Killed/Survived нет, прогон падает
> громко, триггер узкий (4 файла из 1466 в корпусе анализа) и обходится, но это
> тулчейн по умолчанию (Vitest 5 + Vite 8) и реальный код (vuejs/core, Svelte):
> теряются все мутанты файла, через BUG-100 обычно и всего прогона, а настоящая
> ошибка разбора не видна даже с `--verbose`.

## Контекст

Mootant хостит мутанты в switched-тексте файла: выражение становится
`(check ? (replacement) : (original))`, и обе ветки всегда берутся в скобки
(`core/instrument/render-mutant-range.ts:91-95`, шаблоны
`${getCheck(mutant.id)} ? (${mutant.replacement}) : ` и
`${guard}(${branches.join('')}(${original}))`).

Модуль, который загружает тест, Vite 8 разбирает в двух местах, и оба раза
это oxc без явного `sourceType`. Строки ниже — Vite 8.3.5 из lockfile, после
`pnpm install` это `node_modules/vite/dist/node/chunks/node.js`:

- `.ts` — уже на трансформе, в плагине `vite:oxc`: `transformWithOxc`
  (`:7593-7618`) передаёт `lang`, но не `sourceType`;
- `.js` — в `ssrTransformScript`: `parseAstAsync(code)` без опций (`:16494`).
  У rolldown 1.2.16 `defaultParserOptions = { lang: "js", preserveParens: false }`
  (`node_modules/.pnpm/rolldown@1.2.16/node_modules/rolldown/dist/parse-ast-index.mjs:27-29`),
  `sourceType` не задан.

Без явного `sourceType` oxc ведёт себя как `unambiguous` (проверено:
`parseAst('const a = (/<!--x/g)\nexport {}')` из rolldown — ошибка, с
`{ sourceType: 'module' }` — разбирается). В oxc есть ошибка лексера: в модуле
(файле с `import`/`export`) скобка, за которой сразу идёт литерал регулярного
выражения, начинающийся с `<!--`, даёт ошибку разбора «HTML comments are not
allowed in modules». Проверено на 0.156.0 и 0.157.0 (последняя на 2026-11-04).
0.156.0 — это и `oxc-parser` из зависимостей Mootant (`package.json:81`), и oxc
в Vite 8.3.5: по `pnpm-lock.yaml` `vite@8.3.5` → `rolldown 1.2.16` →
`@oxc-project/types 0.156.0`.

```text
const a = (/<!--x/g)\nexport {}           -> ERR   (unambiguous)
const a = (c ? (/<!--x/g) : 1)\nexport {} -> ERR
const a = /<!--x/g\nexport {}             -> ok
f(/<!--x/g)\nexport {}                    -> ok
const a = (0, /<!--x/g)\nexport {}        -> ok
const a = (c ? /<!--x/g : 1)\nexport {}   -> ok
const a = (/<!--x/g)\nexport {}  (module) -> ok
```

Таблицу верификаторы подтвердили на `oxc-parser` 0.156.0 и 0.157.0 и на
`parseAst` rolldown 1.2.16. Их уточнения (всё — в модуле):

- пробел, перевод строки или комментарий между `(` и литералом не помогают:
  `( /<!--x/g)` и `(\n/<!--x/g)` тоже дают ошибку, так что «вставить пробел» —
  не исправление;
- ломается и выражение, которое начинается с такого литерала:
  `(/<!--x/g.source)`;
- скобка ломает разбор в любой ветке: ошибку дают и `(c ? 1 : (/<!--x/g))`,
  и `c ? /<!--x/g : (/<!--y/g)`; без скобок в обеих ветках
  `(c ? /<!--x/g : c2 ? /<!--y/g : /<!--z/g)` разбирается;
- скобки `if (…)` и `while (…)` не затронуты (`if (/<!--x/.test(s))`
  разбирается); литерал `/<!-…` (одно тире) ошибку не вызывает;
- без `import`/`export` та же конструкция разбирается (как скрипт).

Исходный код такой конструкции обычно не содержит
(`html.replace(/<!--…-->/g, '')` — аргумент вызова, разбирается нормально).
Но switched-текст создаёт её для каждого мутанта, чей диапазон или replacement
начинается с такого литерала. Это `regex-flag` и `regex-pattern` по
регулярному выражению для HTML-комментариев (сам `/<!--[\s\S]*?-->/g` стоит
примером в `docs/content/mutators/regex-pattern.md:190`). Это и replacement
`regex-pattern`, который удаляет первую альтернативу:
`/^(?:-?>)+|<!--|-->|--!>|<!-$/g` → `/<!--|-->|--!>|<!-$/g`. Так выглядит
`commentStripRE` из `packages/shared/src/escapeHtml.ts` vuejs/core (в
`@vue/shared` 3.5.44 — `dist/shared.esm-bundler.js:417`). Такие литералы есть
и в Svelte 5.57.3 (`src/compiler/phases/1-parse/index.js:15`,
`src/compiler/preprocess/index.js:254,256`). В корпусе анализа скептик
насчитал 4 затронутых файла из 1466.

Модуль не трансформируется, тест-файлы падают при загрузке в instrumented dry
run, и все мутанты файла получают `Error` с диагностикой
`instrumentation-break`: «Tests fail with the switched src/strip.js and pass
without it; its mutants are not run.» (`core/run/run-dry-phase.ts:289`). Текст
ошибки Vite в отчёт не попадает (по данным скептика — и с `--verbose`), так что
пользователь не может найти причину. Увидеть её можно, только подставив
switched-текст вручную (шаг 3).

Каскад в BUG-100 здесь типичен, а не редок. Тест-файл, который не загрузился,
ничего не покрывает. Поэтому `findBrokenFiles`
(`core/run/run-dry-phase.ts:505-517`) не находит файлов по покрытию и
объявляет сломанными все switched-файлы прогона (`related`). Оба верификатора
добавляли в проект здоровый файл со своим проходящим тестом. Он тоже получал
`instrumentation-break`, и `Error` получали все 10 мутантов.

Физически применённый мутант (replacement, подставленный дословно, без скобок)
разбирается нормально. Но хелпер тестов `applyMutant`
(`test/helpers/apply-mutant.ts:61`, `${before}${guard}(${replacement})${after}`;
JSDoc на `:40-45` обещает «the way the mutant switch will host it») тоже
берёт replacement в скобки. В модуле на таком мутанте падает и он (проверено:
дифференциальный тест с `export {}` падает на `runProgram(applyMutant(…))` с
`PARSE_ERROR` из `transformWithOxc`).

Обходы для пользователя (проверены скептиком): комментарий
`// mootant-ignore-next-line regex-pattern, regex-flag` над строкой с
литералом (прогон проходит, score 100) или Vite 7.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет, файлы ниже создай
сам. Нужны Node.js 22.12 или новее (Vitest 5 требует
`^22.12.0 || ^24.0.0 || >=26.0.0`, `docs/content/guide/compatibility.mdx:22-24`)
и pnpm 12: в CI стоит `latest-12` (`.github/actions/install-tools/action.yml:14`),
а `pnpm-workspace.yaml:1-2` использует `configDependencies`. `pnpm install`
ставит из lockfile `oxc-parser` 0.156.0, Vitest 5.0.5 и Vite 8.3.5.

### Шаг 1. Падающий юнит-тест (сборка не нужна)

Тест строит switched-текст двух модулей и разбирает его тем же `parseFile`,
что Mootant (через `getSyntaxFingerprint`; для `.ts` — `unambiguous`,
`core/parser/get-parser-options.ts:14`). Файл временный, в коммит не входит
(см. «Ограничения»). Код — дословно из ветки анализа:

```bash
# в корне клона azat-io/mootant (баг найден на коммите 170ec52)
pnpm install
mkdir -p test/repros
cat > test/repros/BUG-106.test.ts <<'EOF'
import { describe, expect, it } from 'vitest'

import { getSyntaxFingerprint } from '../helpers/get-syntax-fingerprint'
import { instrumentFile } from '../../core/instrument/instrument-file'
import { generateMutants } from '../helpers/generate-mutants'

describe('BUG-106: a regular expression that starts with <!-- breaks the switched module', () => {
  it.each([
    [
      'strip.ts',
      [
        'export function strip(html: string): string {',
        "  return html.replace(/<!--[\\s\\S]*?-->/g, '')",
        '}',
      ],
    ],
    [
      'escape.ts',
      [
        '// as in packages/shared/src/escapeHtml.ts of vuejs/core',
        'const commentStripRE = /^(?:-?>)+|<!--|-->|--!>|<!-$/g',
        'export function escapeHtmlComment(src: string): string {',
        "  return src.replace(commentStripRE, '')",
        '}',
      ],
    ],
  ])(
    'hosts the mutants of %s in a module that parses as Vite 8 parses it',
    (file, lines) => {
      // oxc, which Vite 8 and rolldown parse modules with, reads `(/<!--`
      // as an HTML comment in a module of ambiguous source type; the mutant
      // switch writes every replacement and original in parentheses.
      let source = lines.join('\n')
      let mutants = generateMutants(source, { preset: 'recommended', file })
      let switched = instrumentFile({ mutants, source, file })

      expect(getSyntaxFingerprint(file, source)).not.toBeNull()
      expect(mutants.some(mutant => mutant.mutator === 'regex-pattern')).toBe(
        true,
      )
      expect(getSyntaxFingerprint(file, switched)).not.toBeNull()
    },
  )
})
EOF
pnpm exec vitest --run test/repros/BUG-106.test.ts
```

Внимание: тест — прокси. Он разбирает текст собственным `oxc-parser` Mootant,
а не парсером Vite пользователя. Если поднять `oxc-parser` до версии с
исправленным лексером, тест позеленеет без исправления, а у пользователей
Vite 8.3.5 (rolldown 1.2.16, oxc 0.156) ошибка останется. Поэтому в «Критерии
готовности» есть проверка формы switched-текста, не зависящая от парсера.

## Ожидаемое поведение

Switched-текст любого файла, который разбирается в исходном виде, разбирается
и тем парсером, которым Vite 8 читает модули: oxc без явного `sourceType`, то
есть как `unambiguous` (`vite:oxc` для `.ts`, `parseAstAsync` для `.js`). В
частности, его принимает `parseFile` Mootant (`core/parser/parse-file.ts:77`) в
том же режиме. Мутанты регулярных выражений для HTML-комментариев получают
вердикты. В проекте шага 2 ожидается то же, что сейчас на Vite 7.3.1: 6 Killed,
3 Survived, без диагностик.

## Фактическое поведение

Шаг 1: `2 failed` в каждом из трёх прогонов,
`AssertionError: expected null not to be null` на
`test/repros/BUG-106.test.ts:41:56`. Это третий `expect`; первые два проходят
(исходник разбирается, мутант `regex-pattern` есть). В switched-тексте
`strip.ts` три вхождения `(/<!--`, в `escape.ts` — одно, от мутанта
`regex-pattern` с replacement `/<!--|-->|--!>|<!-$/g`.

Шаг 2 на Vite 8.3.5 (Vitest 5.1.0; так же на 5.0.5 через `run.sh` анализа):
обычный `vitest --run` проходит, а mootant пишет в stderr «Some tests failed;
running them again without mutants to check.» и выходит с кодом 1:

```text
exit=1
{"summary":{"totalErrorMutants":9,"duration":{"total":…},"totalNoCoverage":0,"totalSurvived":0,"totalWarnings":0,"totalIgnored":0,"totalTimeout":0,"totalMutants":9,"totalKilled":0,"totalErrors":2,"totalTests":0,"totalFiles":2,"passed":false},"diagnostics":["instrumentation-break src/strip.js","instrumentation-break src/strip.ts"]}
```

Контроль на `vite@7.3.1`: `"coveredScore":66.67,"score":66.67`,
`"totalKilled":6`, `"totalSurvived":3`, `"totalErrorMutants":0`,
`"passed":true`, `diagnostics: []`, exit 0 — проблема только у Vite 8
(rolldown/oxc).

Каскад BUG-100: с `src/math.js` все 10 мутантов `Error`, у `src/math.js` тоже
`instrumentation-break`.

Шаг 3 (Vite 8.3.5), текст ошибки зависит от расширения:

- `src/strip.js`: «RolldownError: Parse failure: Parse failed with 3 errors:
  HTML comments are not allowed in modules» — из `ssrTransformScript`
  (префикс `Parse failure:` ставит он же, `chunks/node.js:16497`); в файле три
  вхождения `(/<!--`;
- `src/strip.ts`: «Error: Transform failed with 2 errors: [PARSE_ERROR] HTML
  comments are not allowed in modules», `Plugin: vite:oxc` — раньше, на
  oxc-трансформе; в файле два вхождения `(/<!--`.

## Подозреваемые места в коде

- `core/instrument/render-mutant-range.ts:91-95` — основное место: обе ветки
  (replacement и original) всегда в скобках. Проверенное направление — не
  брать ветку в скобки, если её текст начинается с `/`. Такой вариант
  верификаторы проверили: разбирается; TS-стрелки с типом возврата в ветке
  `?:` без скобок oxc тоже разбирает правильно (скептик). Условие должно быть
  по тексту, а не по типу узла: `(/<!--x/g.source)` тоже ломается. Применять
  его нужно к обеим веткам: `c ? /<!--x/g : (/<!--y/g)` всё ещё ломается.
  Пробел или перевод строки после `(` не помогают. Грамматически скобки в
  ветке `?:` нужны `SequenceExpression` (запятая верхнего уровня); бывают ли у
  мутаторов Mootant такие тексты, начинающиеся с `/`, — не проверено. Более
  широкий вариант (без скобок для всех литералов, идентификаторов, вызовов)
  для бага не нужен и меняет точные строки существующих тестов
  (`test/core/instrument/render-mutant-range.test.ts`,
  `test/core/instrument/instrument-file.test.ts:316-367`,
  `test/core/instrument/create-switched-files.test.ts`).
- `test/helpers/apply-mutant.ts:52-62` — оракул тестов должен хостить мутант
  так же, как `renderMutantRange`, и меняться синхронно с ним. Иначе
  разойдутся `runMutator` (`test/helpers/run-mutator.ts:88-92`, «does not
  parse when hosted»), дифференциальный тест
  (`test/core/instrument/instrument-file.test.ts:417`) и другие пользователи
  хелпера (`test/core/generate/generate-file-mutants.test.ts`,
  `test/cli/index.test.ts:223`, `test/helpers/run-reference-mutants.ts:142`,
  `test/helpers/run-node-test-reference.ts:101`). Правило удобно вынести в
  одну функцию в `core/instrument/` и вызывать из обоих мест.
- `core/instrument/create-switched-files.ts:74-104` — нет проверки, что
  switched-текст JS/TS разбирается: проверяется только компиляция Svelte и Vue
  (`:77-93`). Проверка `parseFile` до dry run дала бы `instrument-error` по
  файлу вместо `instrumentation-break` и каскада BUG-100. Это страховка, а не
  исправление: `oxc-parser` Mootant может не совпадать по версии с oxc в Vite
  пользователя.
- `core/parser/parse-file.ts:77` (опции — `core/parser/get-parser-options.ts:11-14`,
  `unambiguous` для `.js`/`.jsx`/`.ts`/`.tsx`) — тот же `parseSync`. Исходный
  файл с `(/<!--…/)` в модуле Mootant считает непарсящимся (`mootant list` —
  `parse-error`, 0 мутантов), хотя Node выполняет его как ESM (проверено обоими
  верификаторами). Под Vite 8 такой файл, судя по матрице `parseAst`, не
  загрузится и без Mootant (сквозным прогоном не проверялось). Значит, это
  касается `node:test` и Vite 7 — отдельная, менее важная проблема.
- Апстрим: сообщить об ошибке в oxc (лексер в режиме `unambiguous` после `(`;
  с `sourceType: 'module'` ошибки нет).

## Критерий готовности

- Постоянный регрессионный тест в стиле проекта: оба модуля шага 1 (`strip.ts`
  и `escape.ts`) — в `test/core/instrument/instrument-file.test.ts`, рядом с
  тестом `:379-402`. Тот уже проверяет `getSyntaxFingerprint(file, switched)`
  для фикстур `test/fixtures/list`, но ни в одной из них нет литерала с
  `<!--`, поэтому баг не пойман. На 170ec52 новый тест падает с
  `expected null not to be null`, после исправления проходит.
- Проверка, не зависящая от версии парсера (тест выше — прокси, см. шаг 1):
  точные строки рендера в `test/core/instrument/render-mutant-range.test.ts`.
  Нужен диапазон, у которого original и replacement начинаются с `/`
  (например, `/<!--x/g` и `/<!--y/g`), и диапазон с original вида
  `/<!--x/.test(s)`: ни одна их ветка не в скобках. Если выбран узкий вариант
  исправления, ожидания существующих тестов для других текстов не меняются.
- `applyMutant` хостит по тому же правилу. Проверка: `runMutator` из
  `test/helpers/run-mutator.ts` на модульном исходнике с таким литералом (как
  в шаге 1) не бросает «Mutant of … does not parse when hosted» (`:88-92`). По
  чтению кода на 170ec52 он должен бросать; запуском это не проверялось.
- Дифференциальный тест «switched ≡ мутант, применённый по одному»
  (`test/core/instrument/instrument-file.test.ts:404-435`) регрессию не
  ловит, и требовать от него «падает до исправления» нельзя. Программы
  `PROGRAMS` исполняются как скрипт (`runProgram` → `transformWithOxc` →
  `runInThisContext`, `test/helpers/run-program.ts:58`,
  `test/helpers/program-worker.ts:164`). Без `import`/`export` текст на
  170ec52 разбирается: программа с `/<!--[\s\S]*?-->/g` прошла 2 из 2. А
  `export {}` `runInThisContext` выполнить не может. Такую программу в
  `PROGRAMS` добавить стоит — она проверит семантику веток без скобок, — но
  только как дополнительную проверку.
- Шаг 2, повторённый после исправления (новые `pnpm build` и `pnpm pack`,
  свежий каталог `FIX`): нет `instrumentation-break`, `totalErrorMutants: 0`,
  все 9 мутантов `Killed` или `Survived`. Итог совпадает с контрольным
  прогоном того же проекта на `vite@7.3.1` (сейчас там 6 Killed, 3 Survived,
  `passed: true`, exit 0).
- Тест шага 1 после исправления проходит, затем каталог `test/repros/` удалён.
- `INSTRUMENTER_VERSION` (`core/instrument/instrumenter-version.ts:6`) входит
  в ключ кэша через `core/cache/get-environment-key.ts:77`. По JSDoc (`:1-5`)
  его поднимают, когда switched-код может вести себя иначе. Здесь меняется
  только запись ветки, а прогон с ошибками (`instrumentation-break`) в кэш не
  пишется (`core/cache/save-run-cache.ts:64-69`, флаг `failed` из
  `core/run-mutants.ts:516-520`), так что устаревших `Error` в кэше нет. По
  чтению кода подъём не обязателен. Если всё же поднимаешь, обнови
  `test/core/instrument/instrumenter-version.test.ts:7`
  (`expect(INSTRUMENTER_VERSION).toBe(1)`), иначе он упадёт.
- Проверки проекта зелёные при запуске по отдельности: `pnpm test:unit` (порог
  покрытия 100% для `adapters/**`, `cli/**`, `core/**`, `vitest.config.ts:9-15`),
