# BUG-856: тесты `core/git` не защищают разбор диффа для `--since`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (заявлено medium, снижено после
> перепроверки). Статус: подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено — не завершено (верификатор
> остановлен координатором ради окна замеров производительности); скептик: не
> опроверг — вручную внёс каждую из 14 мутаций в копию 170ec52 и запускал
> обычный Vitest (на старых тестах проходят все 14, 38/38; с тестами из шага 3
> исходный код проходит 41/41, а каждая мутация роняет 1–2 новых теста), но
> снизил серьёзность до low. Итог координатора — low: в 170ec52 нет ни одного
> неверного вердикта или потерянного мутанта, это слабость тестов самого
> Mootant, а не дефект поведения для пользователей.

## Контекст

`--since <ref>` оставляет только мутантов на изменённых строках. Это
документированный путь «проверить только изменения PR»
(`docs/content/guide/cli.mdx:98,104-109`). Строки читаются из
`git diff --unified=0` (`core/git/parse-unified-diff.ts`), список бинарных для
git файлов — из `git diff --numstat -z` (`core/git/parse-binary-paths.ts`,
`core/git/read-changed-lines.ts:76-77`). Регрессия в этом разборе молча
теряла бы мутантов (или приписывала бы строки не тому файлу) и завышала бы
score. Код сейчас верен, но тесты его не держат. Покрытие `core/git` — 100 %
(118/118 statements, 52/52 branches), а `mootant run core/git` оставляет 37
выживших. Тесты из шага 3 убивают 14 из них. По оценке скептика видимых
пользователю пробелов среди этих 14 — 13: `run-git.ts:57` проверяет только
контракт функции. Остальные 23 выживших — эквивалентные, шумовые и слабые
проверки текста ошибки (список — в «Критерии готовности»).

Главное: тест `test/core/git/parse-unified-diff.test.ts:81-94` («never reads
changed lines as headers») не может упасть по своей причине. Он должен
проверять, что строки ханка пропускаются по счётчику
(`core/git/parse-unified-diff.ts:29-33,44-47`), но его «коварные» строки
(`'---- a/x'`, `'-@@ -1 +1 @@'`, `'++++ b/other.ts'`, `'+@@ -7 +7 @@'`)
разборщик не принял бы за заголовки и без пропуска. У `HUNK_PATTERN` есть
якорь `^` (`:8`), поэтому `-@@`/`+@@` с ним не совпадают. Заголовок файла
распознаётся по `line.startsWith('+++ ')` с пробелом (`:35`), а у
`'++++ b/other.ts'` четвёртый символ `+`. Строки `--- …` разборщик не читает
вовсе. Двусмысленна только добавленная строка с текстом `++ …`: в диффе она
выглядит как `+++ …`.

Насколько это узко (доводы скептика; вывод о дыре в тестах они не отменяют):

- Мутанты логики пропуска значимы, только если в изменённом файле добавлена
  строка, которая с первой колонки начинается с `++ ` (Prettier печатает
  `++i`, так что это редкость). Тогда ханки того же файла после неё
  приписываются ложному пути. На настоящем git 2.43 (шаг 5) исходный код
  даёт `{"a.ts":[3,9]}`, а без пропуска — `{"a.ts":[3],"<root>":[9]}`:
  строка 9 молча теряется. С мутантом `-\d+` → `-[^]+` в `HUNK_PATTERN`
  теряется ханк, идущий после ханка вида `-2,0` (обычная форма диффа):
  `{"a.ts":[3]}`.
- Мутантам групп `removed` и `added` нужен контекст функции после `@@`, в
  котором есть ` +N @@` или ` @@`.
- Без `maxBuffer` сбой был бы громким (`git could not run: stdout maxBuffer
  length exceeded`), а не тихим. `--numstat` без `base` затрагивает только
  бинарный для git исходник, изменённый коммитом на ветке.
- `unquote-git-path.ts:39` практически недостижим: `runGit` всегда передаёт
  `core.quotePath=false` (`core/git/run-git.ts:46`), и октальный escape перед
  цифрой git печатает только для управляющих символов в имени файла
  (`x\0012.ts`).
- `core/git` не входит в публичный API: в `core/index.ts` нет git-экспортов.

новом `main` сверь номера строк, а `mutate.mjs` из шага 2 сам откажется

## Ожидаемое поведение

Тесты `test/core/git/` падают, если:

- строка ханка, похожая на заголовок `+++ ` (добавленная строка с текстом
  `++ …`), не пропущена по счётчику. Чтобы тест ловил все 7 мутантов логики
  пропуска, двусмысленная строка должна стоять **последней** в ханке (иначе
  выживает `> 0` → `> 1`), после строки `\ No newline at end of file` (иначе
  выживают оба мутанта её обработки на `:30`), и хотя бы в одном таком ханке
  должно быть опущено число удалённых строк, как в `@@ -3 +3,2 @@` (иначе
  выживает `removed = '1'` → `''` на `:44`);
- после ханка `-N,0` теряется следующий ханк того же файла, или контекст
  функции после `@@` ломает разбор чисел заголовка. Для мутантов групп
  `removed`/`added` контекст должен содержать ` +N @@` или ` @@`, как
  `@@ -30,0 +34,1 @@ let s = 'a +1 @@'`; без такого контекста они выживают;
- бинарный для git файл (с NUL-байтом), изменённый **коммитом** на ветке,
  выпал из `--since`. Файл, изменённый только в рабочем дереве, удаление
  `base` из `--numstat` (`core/git/read-changed-lines.ts:77`) не ловит: без
  `base` git сравнивает рабочее дерево с индексом;
- вывод git больше 1 МиБ (дефолтный `maxBuffer` у `execFile`) ломает
  `runGit`. Нужен настоящий вывод: мок `execFile`, как в
  `test/core/git/run-git.test.ts:78-101`, удаление `maxBuffer` не ловит;
- `runGit` неуспешной команды теряет `stdout`. Это контракт функции
  (`core/git/run-git.ts:36`: «a failing command resolves too»). Все
  вызывающие при коде ≠ 0 читают только `stderr` (`find-git-root.ts:16-23`,
  `get-merge-base.ts:19-23,33-35,40-42,47-51`, `read-changed-lines.ts:110-114`),
  так что для продукта этот мутант эквивалентен: закрыть его дешёвым
  `toStrictEqual` или явно принять — на твой выбор;
- октальный escape в кавычках пути, за которым идёт цифра, читается неверно.
