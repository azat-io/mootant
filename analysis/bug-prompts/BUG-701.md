# BUG-701: любая сменившаяся переменная окружения сбрасывает кэш тест-файлов, которые перечисляют `process.env`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён (фикстура и
> perfectionist в стенде analysis/bench); независимая перепроверка не
> проводилась. Найдено на коммите 170ec52.

## Контекст

Кэш вердиктов обещает переиспользовать вердикт, «while the mutated file and the
files and environment variables its tests read stay the same»
(`docs/content/guide/configuration.mdx:350-355`). Переменные отслеживаются в
процессе тестов. `trackEnvironment` один раз на процесс ставит прокси на место
`process.env` (`adapters/shared/track-environment.ts:117-156`, подмена — `:139`)
и оборачивает функции `node:child_process`, которые запускают процессы
(`:9-17`, `:140-144`). Чтение переменной по имени записывает её имя (`:225-229`,
`:241-252`). Перечисление (ловушка `ownKeys`: `{ ...process.env }`,
`Object.keys`, `for…in`, `JSON.stringify`) записывает `*` (`:231-240`), потому
что «the code may depend on all of them» (JSDoc `:94-116`). `*` записывается и
при запуске процесса, который наследует окружение: без `env` в опциях или с
`env: process.env` (`:184-197`, проверка — `:191-195`). А если промисифицированные
`exec`/`execFile` созданы до установки трекинга, `*` получает сразу каждый
получатель (`:124-131`, `:152-154`). Имена вместе с `*` собирает `trackInputs`
(`adapters/shared/track-inputs.ts:45-47`, `:54`), и адаптер отдаёт их ядру как
`DryFile.environment` (`types/adapter/dry-file.d.ts:15-20`) и
`RunInputs.environment` (`types/adapter/run-inputs.d.ts:15-19`).

Значения ядро берёт из `CacheInputs.environment`
(`types/adapter/cache-inputs.d.ts:6-13`): хэш каждой переменной по имени, а под
ключом `*` — один хэш всех переменных, кроме короткого списка `VOLATILE`
(`adapters/shared/index-environment-hashes.ts:9-17`: `ITERM_SESSION_ID`,
`TERM_SESSION_ID`, `WINDOWID`, `OLDPWD`, `SHLVL`, `PWD`, `_`) и тех, что адаптер
передал в `ignored` (`:40-42`). Оба встроенных адаптера строят его этой
функцией:

- Vitest — из хэшей окружения, которые первый воркер проекта пишет в dry run
  (`adapters/vitest/runner.ts:1022-1038`; `adapters/vitest/get-cache-inputs.ts:51-55`,
  `ignored` — `VITEST_WORKER_ID` и `VITEST_POOL_ID`);
- node:test — из окружения тестовых процессов
  (`adapters/node-test/start-node-test-session.ts:111-117`,
  `adapters/node-test/hash-environment.ts:16-23`, `ignored` пуст).

Ядро кладёт в ключ тест-файла хэш каждого прочитанного имени, и `*` —
как обычное имя (`core/cache/get-test-file-keys.ts:52-56`, в дайджесте — `:64`).
Так же строятся инкрементальные ключи (`outsideKeys`,
`core/cache/prepare-run-cache.ts:195-202`), поэтому `--incremental` не
помогает. Если `*` впервые прочитал прогон мутанта, хэш сохраняется во входах
записи (`core/cache/create-run-cache.ts:321-331`) и сверяется при чтении
(`:184-194`).

Итог: тест-файл, который хоть раз перечислил окружение (сам или через
библиотеку в том же процессе) или запустил процесс с унаследованным окружением,
теряет все свои вердикты при смене любой переменной вне `VOLATILE`, даже той,
которую никто не читает. В CI на каждом прогоне новые `GITHUB_RUN_ID`,
`GITHUB_RUN_NUMBER`, `GITHUB_SHA` и т. п. Поэтому для таких тест-файлов кэш
между прогонами CI не срабатывает никогда, даже если
`node_modules/.cache/mootant` восстановлен из кэша CI и включён
`--incremental`. По оценке анализа, это тесты, которые запускают процессы
(`child_process`, `execa`, `tinyexec`), и тесты на ESLint RuleTester. У
eslint-plugin-perfectionist стенд бенчмарка получил полный промах (см.
«Фактическое поведение»); каким кодом его тесты перечисляют окружение, не
выяснялось. На стенде этот эффект давали `HYPERFINE_RANDOMIZED_ENVIRONMENT_OFFSET`
(hyperfine задаёт её каждому прогону) и разный `TMPDIR`; стенд обходит это:
снимает переменную и держит один `TMPDIR` на проект.

Ключ окружения прогона (`core/cache/get-environment-key.ts:70-88`) `*` не
содержит. Он стоит первым в ключе каждого тест-файла
(`core/cache/get-test-file-keys.ts:60`), но из переменных в него через
`settings` попадают только `NODE_ENV`, `LANG`, `LC_*` и `TZ`
(`adapters/shared/verdict-variable-pattern.ts:6`;
`adapters/vitest/get-cache-inputs.ts:99-101`,
`adapters/node-test/get-node-cache-inputs.ts:66-68`). Поэтому вердикты
тест-файлов, которые `*` не читали, смену переменных переживают, и промах
частичный.

Вердикты при этом верны: промах консервативный. Но он молчаливый. Строка
«Reused cached verdicts for N of M mutants.» печатается только при `N > 0`
(`core/run-mutants.ts:703-711`), причина промаха нигде не называется, а
документация о `*` ничего не говорит. Раздел про CI
(`docs/content/guide/getting-started.mdx:123-134`) о кэше молчит, хотя
`readme.md:63` обещает: «Mootant caches verdicts between runs».

Близкий дубль — BUG-413 из раздела анализа о кэше (low): тест, запускающий
дочерний процесс без явного `env`, зависит от `*`. В сценарии анализа
`spawn_star` (тест с `execFileSync(process.execPath, ['-e', …])`) второй прогон
в том же окружении взял из кэша 4 вердикта из 4, с другим `GITHUB_RUN_ID` — 0 из
4, при запуске через `npm run` (свои переменные `npm_*`) — 0 из 4. Исправление
BUG-701 закрывает его по крайней мере для переменных CI.

## Воспроизведение

Веток `analysis/2026-11` и `experiment/bug-repros` в публичном репозитории нет,
поэтому всё нужное приведено ниже. Проверялось на Linux, Node.js 22.23.4 и
npm 10.9.9. Нужны Node.js 22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:22-24`), npm с доступом к реестру и
pnpm 12. В CI стоит `latest-12` (`.github/actions/install-tools/action.yml:14`),
а `pnpm-workspace.yaml:1-2` использует `configDependencies`. pnpm 10 с этим
репозиторием не работает: в анализе `pnpm --version` внутри репозитория
зависал, а pnpm 10.x падает с ошибкой об отсутствии integrity у
`@pnpm/plugin-trusted-deps`.

### Шаг 1. Собрать пакет mootant

`dist/` в git нет (`.gitignore:13`), а скрипта `prepack` в `package.json` нет,
так что без явной сборки `pnpm pack` упакует пакет без `dist/`.

```bash
# в корне клона azat-io/mootant
pnpm install --frozen-lockfile
pnpm build
pnpm pack                              # пишет mootant-<версия>.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-*.tgz "$PACK/mootant.tgz"   # *.tgz нет в .gitignore, не оставляйте его в дереве
```

### Шаг 2. Скрипт

Сохраните скрипт вне клона как `"$PACK/bug-701.sh"` и запустите
`bash "$PACK/bug-701.sh" "$PACK/mootant.tgz"`. Скрипт создаёт фикстуру во
временном каталоге, ставит в неё `vitest@5` и tarball и четыре раза запускает
`mootant run src`. Между прогонами меняются только переменные окружения:

- `cold` — пустой кэш; `GITHUB_RUN_ID=1001`, `GITHUB_RUN_NUMBER=1`,
  `GITHUB_SHA=111…1`, `X=1`;
- `same` — то же окружение;
- `ci` — другие `GITHUB_RUN_ID`, `GITHUB_RUN_NUMBER` и `GITHUB_SHA`, как у
  следующего прогона CI; `X=1`;
- `other` — окружение `ci`, но `X=2`: переменная, которую CI не задаёт.

Ни один тест эти переменные по имени не читает. `test/add.test.js` перечисляет
окружение (`{ ...process.env }`), `test/plain.test.js` — нет. Для каждого
прогона скрипт печатает, сколько вердиктов взято из кэша (`summary.totalCached`
полного JSON-отчёта), id мутантов, прогнанных заново, и строку mootant о кэше
из stderr. После холодного прогона печатается список мутантов.

Итог — в последней строке вывода. Код выхода 1 значит, что баг есть: прогон
`ci` берёт из кэша меньше вердиктов, чем `same`. Код 0 — бага нет. Код 2 —
результат неубедителен: кэш не работает даже при том же окружении. Если скрипт
остановился раньше (`bug-701.sh: failed at line …`), это ошибка окружения, а не
результат проверки. Фикстуру скрипт удаляет на выходе.

Это `repro.sh` из каталога `analysis/bench/repro/bug-701/` ветки анализа.
Фикстура (`package.json`, `src/add.js`, `test/add.test.js`,
`test/plain.test.js`) перенесена побайтно. Правки:

- `vitest@5` вместо `vitest@5.0.5 vite@8.3.5 --legacy-peer-deps`. В npm 10.9.9
  установка 5.0.5 падает внутри arborist с `Cannot read properties of null
  (reading 'edgesOut')`; это баг npm, а не mootant. Сейчас `vitest@5`
  разрешается в 5.1.0;
- tarball передаётся аргументом (в исходнике — переменная `MOOTANT_TGZ` или
  жёсткий путь), фикстура создаётся во временном каталоге;
- добавлен сценарий `ci`: в исходнике был только переход `X=1` → `X=2` (здесь
  `other`);
- подсчёт по полному JSON-отчёту, итоговая строка и код выхода; исходник только
  показывал stderr mootant.

```bash
#!/usr/bin/env bash
# BUG-701: a variable no test reads by name, such as the run id CI sets, drops
# the cached verdicts of every test file that lists process.env (spreads it,
# starts a child process with it).
# Usage: bug-701.sh <mootant tarball>
# Exit code: 1 while a change of the variables CI changes from run to run drops
# cached verdicts, 0 once it does not, 2 when even the same environment reuses
# nothing.
set -euo pipefail
tgz=$(realpath "${1:?path to the tarball from pnpm pack}")
work=$(mktemp -d "${TMPDIR:-/tmp}/mootant-bug-701-XXXXXX")
trap 'rm -rf "$work"' EXIT
trap 'echo "bug-701.sh: failed at line $LINENO" >&2' ERR
mkdir "$work/project" "$work/out"
cd "$work/project"
git init -q

# The fixture: test/add.test.js lists the variables, test/plain.test.js does not.
cat >package.json <<'JSON'
{
  "name": "bug-701",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "vitest run"
  }
}
JSON
mkdir -p src test
cat >src/add.js <<'JS'
export function add(left, right) {
  if (left === 0) {
    return right
  }
  return left + right
}
JS
cat >test/add.test.js <<'JS'
import { expect, test } from 'vitest'

import { add } from '../src/add.js'

test('adds', () => {
  // Lists the variables, as code that spreads process.env or starts a child
  // process with it does.
  let variables = { ...process.env }
  expect(Object.keys(variables).length).toBeGreaterThan(0)
  expect(add(2, 3)).toBe(5)
})
JS
cat >test/plain.test.js <<'JS'
import { expect, test } from 'vitest'

import { add } from '../src/add.js'

test('adds zero', () => {
  expect(add(0, 3)).toBe(3)
})
JS

# vitest@5, not 5.0.5: npm 10.9.9 fails on 5.0.5 inside arborist ('edgesOut').
npm install -D --ignore-scripts --no-audit --no-fund vitest@5 >/dev/null
npm install -D --ignore-scripts --no-audit --no-fund "$tgz" >/dev/null
echo "node $(node --version), npm $(npm --version)," \
  "vitest $(node -p 'require("./node_modules/vitest/package.json").version')," \
  "mootant $(node -p 'require("./node_modules/mootant/package.json").version')"

cat >"$work/out/summary.cjs" <<'JS'
// Usage: summary.cjs <out directory> <label> [list]
let fs = require('node:fs')
let path = require('node:path')
let [directory, label, list] = process.argv.slice(2)
let report = JSON.parse(fs.readFileSync(path.join(directory, `${label}.json`), 'utf8'))
let stderr = fs.readFileSync(path.join(directory, `${label}.err`), 'utf8')
if (list) {
  let flat = text => text.replaceAll(/\s+/gu, ' ')
  for (let mutant of report.mutants) {
    console.log(
      `  ${mutant.id}  ${mutant.file}:${mutant.line}  ${flat(mutant.original)} -> ` +
        `${flat(mutant.replacement)}  ${mutant.status}` +
        (mutant.killedIn ? ` in ${mutant.killedIn}` : ''),
    )
  }
  process.exit(0)
}
let cached = report.summary.totalCached ?? 0
let again = report.mutants.filter(mutant => !mutant.cached).map(mutant => mutant.id)
let note = stderr
  .replaceAll(/\u001b\[[0-9;]*m/gu, '')
  .split('\n')
  .find(line => line.includes('Reused'))
console.log(
  `${label.padEnd(6)} ${cached} of ${report.summary.totalMutants} cached` +
    (again.length > 0 ? `, ran again: ${again.join(' ')}` : '') +
    ` (${note?.trim() ?? 'no note about the cache'})`,
)
fs.writeFileSync(path.join(directory, `${label}.cached`), String(cached))
JS

# One run in the environment of this script plus the given variables. Calls the
# bin directly: npx would add npm_* variables of its own.
run() { # run <label> [NAME=value...]
  local label=$1
  shift
  env "$@" node node_modules/mootant/bin/mootant.js run src --json --all --verbose \
    >"$work/out/$label.json" 2>"$work/out/$label.err"
  node "$work/out/summary.cjs" "$work/out" "$label"
}

# What CI changes from one run to the next; X stands for any other variable.
first=(GITHUB_RUN_ID=1001 GITHUB_RUN_NUMBER=1 GITHUB_SHA=1111111111111111111111111111111111111111 X=1)
next=(GITHUB_RUN_ID=1002 GITHUB_RUN_NUMBER=2 GITHUB_SHA=2222222222222222222222222222222222222222 X=1)
other=(GITHUB_RUN_ID=1002 GITHUB_RUN_NUMBER=2 GITHUB_SHA=2222222222222222222222222222222222222222 X=2)

rm -rf node_modules/.cache/mootant
run cold "${first[@]}"
node "$work/out/summary.cjs" "$work/out" cold list
run same "${first[@]}"  # the same environment
run ci "${next[@]}"     # only GITHUB_RUN_ID, GITHUB_RUN_NUMBER and GITHUB_SHA differ
run other "${other[@]}" # then only X differs

same=$(cat "$work/out/same.cached")
ci=$(cat "$work/out/ci.cached")
if [ "$same" = 0 ]; then
  echo "inconclusive: the cache is not reused even in the same environment"
  exit 2
fi
if [ "$ci" != "$same" ]; then
  echo "BUG-701 reproduced: a change of the CI run variables alone drops cached verdicts"
  exit 1
fi
echo "BUG-701 not reproduced"
```

## Ожидаемое поведение

- Смена только тех переменных, которые CI меняет от прогона к прогону и которые
  тест не читает по имени, кэш не сбрасывает. В скрипте шага 2 прогон `ci`
  берёт из кэша столько же вердиктов, сколько `same` (5 из 5), последняя
  строка — `BUG-701 not reproduced`, код выхода 0.
- Переменная, которую тест прочитал по имени, по-прежнему входит в ключ этого
  тест-файла (`core/cache/get-test-file-keys.ts:52-56`), в том числе переменная
  CI.
- Результат прогона `other` зависит от выбранного направления. В варианте A он
  как сейчас, 1 из 5: `X` мог использовать дочерний процесс или код, который
  перечислил окружение. В варианте B — 5 из 5, и это компромисс, описанный в
  документации.
- Без явного решения гарантии не ослабевают. Смена переменной, которую видит
  только дочерний процесс, по-прежнему прогоняет заново тесты, запускающие
  процессы (`test/adapters/vitest/index.test.ts:1820-1826`). Смена `VOLATILE`
  по-прежнему ничего не прогоняет заново (`:1813-1818`).
- Документация кэша (`docs/content/guide/configuration.mdx:350-359`) говорит,
  что тест, который перечисляет переменные окружения или запускает процессы с
  унаследованным окружением, зависит от всех переменных, и называет исключения.
- Желательно, но не обязательно: при промахе из-за `*` mootant называет причину
  (см. «Критерий готовности»).

### Как чинить

Ни один вариант ниже не реализован и не проверен.

**Вариант A (рекомендуется): переменные CI, новые на каждом прогоне, не входят
в `*`.** Рядом с `VOLATILE` (`adapters/shared/index-environment-hashes.ts:9-17`)
заведите список таких переменных и исключите их из `*` (`:40-42`). Хэши по имени
(`:39`) оставьте. Оба встроенных адаптера строят `*` этой функцией, так что одна
правка чинит и Vitest, и node:test. Кандидаты для GitHub Actions взяты из
документации GitHub Actions; на настоящем раннере их не проверяли:

- значения, новые на каждом прогоне: `GITHUB_RUN_ID`, `GITHUB_RUN_NUMBER`,
  `GITHUB_RUN_ATTEMPT`, `GITHUB_SHA`, `GITHUB_WORKFLOW_SHA`;
- пути к файлам команд шага: `GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_PATH`,
  `GITHUB_STATE`, `GITHUB_STEP_SUMMARY`. По известным дампам окружения в них
  есть id шага; проверьте;
- раннер: `RUNNER_NAME`; `RUNNER_TRACKING_ID` встречается в дампах окружения,
  но не в документации;
- значения, которые различаются между ветками и событиями: `GITHUB_REF`,
  `GITHUB_REF_NAME`, `GITHUB_HEAD_REF`, `GITHUB_BASE_REF`, `GITHUB_EVENT_NAME`,
  `GITHUB_ACTOR`, `GITHUB_TRIGGERING_ACTOR`. Они важны, если кэш общий для
  веток и PR; включать ли их, решите сами и обоснуйте;
- токен, если workflow кладёт его в окружение (`GITHUB_TOKEN`, `GH_TOKEN`): он
  тоже новый на каждом прогоне;
- другие CI — по их документации: GitLab (`CI_JOB_ID`, `CI_PIPELINE_ID`,
  `CI_COMMIT_SHA`, `CI_JOB_TOKEN`, …), CircleCI (`CIRCLE_BUILD_NUM`,
  `CIRCLE_SHA1`, `CIRCLE_WORKFLOW_ID`), Buildkite (`BUILDKITE_BUILD_ID`,
  `BUILDKITE_JOB_ID`, `BUILDKITE_COMMIT`).

Точные имена надёжнее шаблонов вроде `GITHUB_*`. Постоянные переменные
(`CI`, `GITHUB_ACTIONS`) от прогона к прогону не меняются, а дочерний процесс
может от них зависеть (по ним, например, переключают формат вывода). Итоговый
список и его источники опишите в JSDoc. Сторонние адаптеры считают `*` сами, по
описанию в `types/adapter/cache-inputs.d.ts:6-13`, поэтому новое правило
опишите и там.

**Вариант B (компромисс): в `*` — имена переменных без значений.** Значения
тогда входят в ключ только у переменных, прочитанных по имени; это то, что уже
делает `core/cache/get-test-file-keys.ts:52-56`. Цена — устаревшие вердикты
(в обе стороны) при смене значения, которое видит только дочерний процесс или
код, перечисливший окружение. Шаг `:1820-1826` в
`test/adapters/vitest/index.test.ts` закрепляет как раз этот случай: значение
`MOOTANT_CHILD` читает только дочерний процесс, так что в варианте B шаг
упадёт. Поэтому вариант B допустим только как явный компромисс: ожидание
меняется с обоснованием в PR, а в документации к совету из
`docs/content/guide/configuration.mdx:357-359` («After changes that only child
processes … see, delete that directory») добавляются значения переменных.
Можно сделать его необязательной настройкой, но это меняет формат конфига (см.
«Ограничения»). Убрать `*` совсем и учитывать только значения переменных,
прочитанных по имени, ещё слабее: тогда не видно даже появления и исчезновения
переменных. Не рекомендуется.

**Что не годится:**

- Добавить переменные CI в списки `ignored` трекинга
  (`adapters/vitest/worker/vitest-variables.ts:6`, используется в
  `adapters/vitest/runner.ts:1019`; `adapters/node-test/preload/preload.ts:23`).
  Трекинг никогда не сообщает о переменных из `ignored`
  (`adapters/shared/track-environment.ts:146`, `:226`). Тест, читающий
  `GITHUB_SHA` по имени, потерял бы эту зависимость и получал бы устаревшие
  вердикты.
- Выкинуть переменные CI и из хэшей по имени (`adapters/shared/index-environment-hashes.ts:39`).
  Прочитанное имя тогда получит хэш `null`
  (`core/cache/get-test-file-keys.ts:56`), и ключ перестанет меняться вместе со
  значением.
- Перестать записывать `*` при перечислении или запуске процесса. Сломается шаг
  `:1820-1826`, и это то же ослабление, что в варианте B, только без описания.

**Диагностика (желательно, необязательно).** Сейчас назвать причину промаха
нечем: файл кэша не хранит составляющих ключа и хэшей окружения
(`types/cache/run-cache-file.d.ts:7-24`, `types/cache/stored-cache.d.ts:7-17`,
`core/cache/write-run-cache.ts:45-51`). Есть два пути:

1. Хранить по проекту отсортированные имена переменных, вошедших в `*`, и сам
   хэш `*`. Когда тест-файл, читавший `*`, промахнулся, выводить `note` в
   stderr или предупреждение в `RunResult.diagnostics` (коды —
   `types/mutant/diagnostic.d.ts:10-33`). Например: какие переменные
   появились или исчезли, или «изменилось значение одной из переменных».
2. Хранить хэши значений по именам и называть изменившиеся переменные. Учтите,
   что каталог кэша в CI сохраняют в общее хранилище, а в окружении CI бывают
   токены. Сейчас файл хранит хэши только тех переменных, которые прогон
   мутанта прочитал сверх dry run (`types/cache/cached-inputs.d.ts:7-11`).

Какие тест-файлы читают `*`, сейчас не видно ни в одном отчёте. Это есть только
в `DryFile.environment` внутри `prepareRunCache`.
