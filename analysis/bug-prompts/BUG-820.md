# BUG-820: yarn PnP + `node:test` — прогон молча бесполезен (все мутанты NoCoverage, exit 0)

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён одним сквозным
> прогоном в эксперименте анализа M10 (yarn 4.10.3 через corepack, Node
> 22.23.4, упакованный mootant 170ec52). Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено — данных нет (BUG-820 не попал в
> перепроверку двумя агентами, итогового решения координатора по нему нет,
> поэтому серьёзность оставлена заявленной); скептик: не проводился. Эта
> версия промпта сверена с 170ec52, журналом M10 и файлами Yarn из его
> фикстуры только чтением, без запусков. Исправлено против исходной версии:
> предупреждений было два (`config-overridden` и `never-served`), dry run
> насчитал 0 тестов, а тест теряется в `adapters/node-test/run-dry.ts:127-128`.
> Почему хуки mootant не увидели модуль, не установлено, ниже две гипотезы.

## Контекст

Адаптер node:test переключает мутируемые модули в каждом тестовом процессе
через свой preload. `placePreload` ставит preload первым `--require` или
`--import` (`adapters/node-test/place-preload.ts:20-57`). Preload ставит
module hooks: синхронный `load`-хук через `module.registerHooks`, где он
есть (Node 22.15+ и 23.5+), иначе `module.register()`. Кроме того, он патчит
`Module.prototype._compile`
(`adapters/node-test/preload/install-module-hooks.ts:56-86`). `load`-хук пишет
запись `load` для каждого загруженного `file:`-модуля и подменяет текст
переключаемых файлов (`adapters/node-test/preload/create-load-hook.ts:36-61`,
запись — `:45`). Поставив хуки, preload пишет запись `start`
(`adapters/node-test/preload/preload.ts:71`).

Yarn 4 с `nodeLinker: pnp` (значение по умолчанию) запускает скрипты и
бинарники с `NODE_OPTIONS="--require <root>/.pnp.cjs --experimental-loader file:///<root>/.pnp.loader.mjs …"`.
Так делает хук `setupScriptEnvironment` PnP-плагина в бандле yarn 4.10.3
(прочитано в `yarn.js`). При другом `nodeLinker` yarn эти два флага из
`NODE_OPTIONS` убирает. Пакеты лежат в zip-архивах кэша Yarn. Node читает их
только после `.pnp.cjs`, который патчит `fs`, или через `.pnp.loader.mjs`.

Mootant считает `--experimental-loader` и `--loader` устаревшими
загрузчиками, «whose hooks run before mootant's module hooks»
(`adapters/node-test/start-node-test-session.ts:30-33`). На каждый такой
загрузчик он добавляет только предупреждение `config-overridden`
(`:123-132`): «The loader … runs before mootant's module hooks, so mootant
cannot switch the modules it changes.» Так задумано: JSDoc функции говорит «a
legacy `--loader` gets a warning» (`:50-51`). Прогон продолжается.

Итог M10: dry run насчитал 0 тестов, все 12 мутантов получили `NoCoverage`,
score 0%, код выхода 0. С той же парой `src`/`test` под npm (Node 20.19.0)
dry run видит 4 теста, вердикт — 6 killed, 5 survived, 1 no coverage.
Пользователь видит «тесты ничего не покрывают», хотя тесты есть. Что
`yarn test` в PnP-фикстуре зелёный, в анализе отдельно не проверялось. Yarn 4
PnP с Vitest в том же эксперименте работал: 6/5/1, exit 0.

### Где теряются тесты (по чтению кода)

- Первый dry run запускает все тест-файлы
  (`adapters/node-test/run-dry.ts:75-80`).
- Множество модулей, которые загрузил файл, адаптер строит только из записей
  mootant: `load` от его хука и `require.cache` на выходе процесса
  (`adapters/node-test/list-loaded-files.ts:10-24`).
- Если в этом множестве нет ни одного переключаемого файла, результаты файла
  отбрасываются целиком: и тесты, и падение загрузки
  (`run-dry.ts:117-129`, `continue` — `:127-128`). Так задумано, см. JSDoc
  `:32-37`: «so a test file that loads none of them cannot fail the run». В
  M10 так выпал `test/discount.test.js`, отсюда «dry run 0 tests».
- `core/run/run-dry-phase.ts` выдаёт для `src/discount.js` диагностику
  `never-served` (`:337-370`). Она всегда предупреждение (`:528-541`). По
  JSDoc `:128-130`, «Without related tests the dry run is empty, so every
  mutant ends without coverage».
- Код выхода 1 бывает только при диагностиках уровня error, вердиктах `Error`
  или score ниже `--threshold` (`cli/report/build-run-report.ts:151-156`,
  `cli/run-mutation.ts:73-75`). Два предупреждения дают exit 0.

### Почему в записях нет `src/discount.js` — не установлено

С журналом согласуются две гипотезы. Запуском не проверена ни одна.

- **(a) Порядок хуков.** `load`-хук PnP-загрузчика (функция `load$1` в
  `.pnp.loader.mjs` yarn 4.10.3, в фикстуре анализа строки 1518-1557) для
  любого `file:` URL с известным форматом сам читает файл и возвращает
  `{ format, source, shortCircuit: true }`, не вызывая `nextLoad`. Если хук
  mootant стоит в цепочке после него, как утверждает комментарий
  `start-node-test-session.ts:30-33`, то для ES-модулей он не вызывается. Тогда
  нет ни записи `load`, ни подмены. Как Node 22.23.4 упорядочивает синхронные
  хуки `registerHooks` относительно асинхронных хуков `--experimental-loader`,
  не проверено.
- **(b) Preload не загружается вовсе.** В `NODE_OPTIONS` от yarn уже есть
  `--require`, поэтому `placePreload` ставит preload самым первым:
  `--require="<preload>" --require <root>/.pnp.cjs --experimental-loader …`
  (`place-preload.ts:41-45`, затем `start-node-test-session.ts:164-171`).
  - Путь к preload mootant берёт от своего модуля, через
    `import.meta.dirname` (`adapters/node-test/get-preload-path.ts:13-20`).
  - В фикстуре M10 mootant не распакован. Его `packageLocation` в `.pnp.cjs`:
    `./.yarn/__virtual__/mootant-virtual-68abcf45ae/6/root/.yarn/berry/cache/mootant-file-fcfc6d1aeb-10c0.zip/node_modules/mootant/`.
    В `.yarn/unplugged/` лежит только `@oxc-parser/binding-linux-x64-gnu`.
  - До загрузки `.pnp.cjs` Node путь внутри zip прочитать не может. Если
    тестовый процесс падает на первом `--require`, он не оставляет ни одной
    записи, даже `start`. `run-dry.ts:127-128` молча отбрасывает и такое
    падение.
  - Косвенный признак, но не доказательство: dry run в M10 длился «0.0s».
    Это время по стене (`core/run-mutants.ts:410-424`). Та же пара файлов под
    npm на Node 20.19.0 — «4 tests in 0.2s».

## Воспроизведение

Ветки `experiment/bug-repros` и материалов анализа в публичном репозитории
нет. Готового падающего теста для BUG-820 не было и там: баг воспроизведён
только сквозным прогоном. Ниже фикстура M10 целиком, все файлы создайте сами.

Нужны:

- Node.js 22.12 или новее. В M10 был 22.23.4, другие версии с PnP не
  проверялись. Где нет `module.registerHooks`, mootant ставит хуки через
  `module.register()` (`install-module-hooks.ts:77-80`), и поведение может
  отличаться.
- pnpm 12, чтобы собрать mootant (`contributing.md:98`; в CI стоит
  `latest-12`, `.github/actions/install-tools/action.yml:11-15`). По наблюдению
  анализа, pnpm 10 не читает `configDependencies` из `pnpm-workspace.yaml`, и
  его команды в репозитории зависают.
- corepack: он поставит yarn 4.10.3 по полю `packageManager`. В Node 22 и 24
  corepack входит.
- Доступ к npm registry: yarn ставит зависимости mootant.

Пакет `mootant` из npm для проверки не годится. По данным анализа на
2026-11-04, там только заглушка 0.0.0 без `bin`. Нужен tarball из клона.

- `bin/mootant.js` импортирует `../dist/cli/index.js` (`bin/mootant.js:3`), а
  скрипта `prepack` в `package.json` нет. Поэтому перед `pnpm pack` нужен
  `pnpm build`.
- Vitest этой фикстуре не нужен. Адаптер node:test выбирается по тест-скрипту
  `node --test` (`adapters/node-test/score-node-test.ts:31-38`), а `vitest` у
  mootant — необязательная peer-зависимость (`package.json:146-148`).
- Если Vitest понадобится в другой npm-фикстуре, ставьте `npm i -D vitest@5`,
  а не `vitest@5.0.5`. В npm 10.9.9 установка 5.0.5 падает с
  `Cannot read properties of null (reading 'edgesOut')`, это баг arborist.
- `mootant run` без путей падает с «mootant run needs paths»
  (`core/run-mutants.ts:183-185`), поэтому команда — `mootant run src`.
- По коду на первом прогоне `--no-cache` вердиктов не меняет. Он только не
  даёт оставить кэш, который после исправления мог бы вернуть старые
  вердикты.

Команды рассчитаны на одну сессию shell: переменные `CLONE`, `PACK`, `FIX`,
`CTRL`.

```bash
# Шаг 1. Tarball mootant (в корне клона azat-io/mootant)
CLONE="$(pwd)"
pnpm install          # pnpm 12
pnpm build
pnpm pack
PACK="$(mktemp -d)"
mv mootant-*.tgz "$PACK/"     # *.tgz нет в .gitignore, не оставляйте его в дереве

# Шаг 2. Фикстура M10: yarn 4 PnP + node:test
FIX="$(mktemp -d)"
cd "$FIX"
mkdir -p src test
cp "$PACK"/mootant-*.tgz ./mootant.tgz

cat > package.json <<'EOF'
{
  "name": "nt-pnp",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "packageManager": "yarn@4.10.3",
  "scripts": {
    "test": "node --test"
  },
  "devDependencies": {
    "mootant": "file:./mootant.tgz"
  }
}
EOF

# В анализе была ещё строка npmRegistryServer со значением по умолчанию
cat > .yarnrc.yml <<'EOF'
nodeLinker: pnp
enableTelemetry: false
EOF

cat > src/discount.js <<'EOF'
export function discount(total, isMember) {
  if (total >= 100 || isMember) {
    return total * 0.9
  }
  return total
}

export function label(value) {
  return value > 0 ? 'positive' : 'non-positive'
}
EOF

cat > test/discount.test.js <<'EOF'
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { discount, label } from '../src/discount.js'

test('discounts large orders', () => {
  assert.equal(discount(200, false), 180)
})
test('keeps small orders', () => {
  assert.equal(discount(50, false), 50)
})
test('discounts members', () => {
  assert.equal(discount(50, true), 45)
})
test('labels', () => {
  assert.equal(label(5), 'positive')
})
EOF

corepack enable      # или вызывайте `corepack yarn …` вместо `yarn …`
yarn install         # если yarn откажется создавать yarn.lock (CI=true включает
                     # immutable-установки): YARN_ENABLE_IMMUTABLE_INSTALLS=false yarn install
yarn test            # контроль: 4 теста должны пройти (в анализе под PnP не запускалось)
grep -n 'packageLocation' .pnp.cjs | grep mootant    # mootant внутри zip или в .yarn/unplugged
yarn mootant run src --no-cache; echo "exit=$?"            # до исправления: no coverage 12, exit=0
yarn mootant run src --no-cache --verbose; echo "exit=$?"  # то же плюс вывод тестовых процессов
cd "$CLONE"

# Шаг 3. Контроль: те же файлы под npm, без PnP
CTRL="$(mktemp -d)"
cd "$CTRL"
mkdir -p src test
cp "$FIX"/src/discount.js src/
cp "$FIX"/test/discount.test.js test/
cat > package.json <<'EOF'
{
  "name": "nt-npm",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "node --test"
  }
}
EOF
npm i -D "$PACK"/mootant-*.tgz
npx mootant run src --no-cache; echo "exit=$?"   # в анализе (Node 20.19.0): dry run 4 tests, 6/5/1
cd "$CLONE"
```

`--verbose` у `run` показывает, что печатают тесты
(`cli/parse-arguments.ts:54-57`). Туда попадают stdout и stderr тестовых
процессов (`adapters/node-test/run-test-process.ts:116-129`), в том числе
процесса, который dry run потом отбросит. По этому выводу видно, какая
гипотеза верна. Чего ждать в каждом случае, см. «Направление исправления».

После исправления пересоберите tarball (шаг 1) и создайте фикстуры заново в
новых каталогах (шаги 2 и 3). Подхватит ли yarn в старой фикстуре новый
tarball с тем же именем, не проверялось.

## Ожидаемое поведение

Одно из двух:

1. Mootant переключает модули и под Yarn PnP. На фикстуре шага 2 вердикты те
   же, что на контрольной npm-фикстуре шага 3: в анализе 6 killed, 5
   survived, 1 no coverage.
2. Если переключение невозможно, прогон завершается ошибкой (exit 1) с
   понятным сообщением. Сообщение называет загрузчик PnP и предлагает
   `nodeLinker: node-modules` в `.yarnrc.yml` или Vitest. Отчёт с 0% и exit 0
   недопустим.

Что yarn 4 с `nodeLinker: node-modules` и node:test работает, в анализе не
проверялось. Проверялись npm с node:test, а также yarn 1, pnpm и yarn 4 PnP с
Vitest. По коду yarn 4.10.3 при таком `nodeLinker` флагов PnP в
`NODE_OPTIONS` не будет. Прежде чем писать этот совет в сообщение и
документацию, проверьте его на фикстуре.

В обоих случаях процесс, где preload mootant не отработал (нет записи
`start`), не должен молча выпадать из dry run как «не связанный с
мутируемыми файлами».

## Подозреваемые места в коде

- `adapters/node-test/run-dry.ts:117-129`, отбрасывание — `:127-128`
  (задумано, JSDoc `:32-37`). Здесь пропадают тесты и падение тестового
  процесса, если в его записях нет переключаемого файла. Процесс без записи
  `start`, то есть без отработавшего preload, отбрасывается так же, как честно
  «несвязанный» файл.
- `adapters/node-test/list-loaded-files.ts:10-24`. «Загруженные модули»
  строятся только из записей хуков mootant и `require.cache`. Если хук не
  вызывался или preload не загрузился, множество пусто.
- `adapters/node-test/start-node-test-session.ts:30-33`, `:118-132`.
  Устаревший загрузчик даёт только предупреждение. Признак «был устаревший
  загрузчик» в `NodeTestHandle` (`:176-204`) не попадает, и `runDry` на него
  опереться не может.
- `adapters/node-test/place-preload.ts:41-45`. Preload встаёт перед
  `--require <root>/.pnp.cjs` (гипотеза b).
- `adapters/node-test/preload/install-module-hooks.ts:71-86` и
  `adapters/node-test/preload/create-load-hook.ts:36-61`. Запись `load` и
  подмена происходят, только если Node вызвал хук mootant (гипотеза a).
- `core/run/run-dry-phase.ts:337-370`, `:528-541`. Исходная версия промпта
  просила выяснить, «почему never-served не поднял ошибку». Диагностика
  сработала, она есть в журнале. Но `never-served` по замыслу всегда
  предупреждение.
- `cli/report/build-run-report.ts:151-156`. Предупреждения на
  `summary.passed` не влияют, отсюда exit 0.

### Направление исправления

Всё ниже — по чтению кода, запуском не проверялось.

1. **Сначала установите механизм** на фикстуре шага 2 через `--verbose`.
   - Ошибка загрузки `…/preload.js` в выводе процесса (например,
     `Cannot find module`) означает гипотезу (b).
   - Если spec-репортёр показывает 4 пройденных теста, а переключения нет,
     preload отработал, и вероятнее (a).
   - Возможно, верны обе: после исправления (b) проявится (a).
2. **Что не годится.**
   - Делать ошибкой любой `--experimental-loader`/`--loader`. Это ломает
     задуманное поведение, его закрепляет тест
     `test/adapters/node-test/start-node-test-session.test.ts:236-272`: он ждёт
     предупреждение для `--loader ./loader.mjs`. Загрузчик, который отдаёт
     `file:`-модули дальше через `nextLoad`, может и не мешать переключению
     (не проверено).
   - Делать ошибкой `never-served` везде. Мутируемый файл, который не
     импортирует ни один тест, по замыслу получает `NoCoverage` с
     предупреждением, а не роняет прогон.
   - Править только текст предупреждения: exit 0 и 0% останутся.
3. **Что подходит по коду.**
   - Если процесс dry run не оставил записи `start`, preload mootant не
     отработал. Такой процесс не отбрасывать в `run-dry.ts:127-128`, а
     останавливать прогон ошибкой с тест-файлом, кодом выхода и выводом
     процесса. Это закрывает (b) и любой другой сбой preload и от
     загрузчиков не зависит. Существующий тест
     `test/adapters/node-test/run-dry.test.ts:107-158` моделирует
     «несвязанный» упавший `b.test.js` без записи `start` (код 1) и ждёт, что
     его отбросят. Добавьте в его записи `start` через помощник `createStart`
     (`:97-99`), и смысл теста сохранится.
   - Если был устаревший загрузчик, а инструментированный dry run не подал ни
     одного переключаемого файла (`served` пуст), завершать прогон ошибкой с
     именем загрузчика и советом (для Yarn PnP — `nodeLinker: node-modules`
     или Vitest). Это закрывает (a). Для этого признак загрузчика нужно
     передать из сессии в `runDry`, например полем `NodeTestHandle`.
   - Настоящая поддержка PnP (вариант 1 в «Ожидаемом поведении») обойдётся
     дороже. Для (b) можно ставить preload сразу после
     `--require <root>/.pnp.cjs`, чтобы zip уже читался. Не проверено,
     сохранится ли тогда гарантия «preload раньше модулей проекта»
     (`place-preload.ts:20-25`) и не помешает ли дальше (a).

## Критерий готовности

- До исправления на фикстуре шага 2 установлено, какая гипотеза верна, по
  выводу `--verbose`. Это записано в описании PR.
- На каждый механизм, который вы исправили, есть автотест: до исправления он
  падает, после проходит. Unit-тесты пишите в стиле соседних, с моком
  `runTestFile`:
  - «Preload не отработал». В `test/adapters/node-test/run-dry.test.ts`
    процесс тест-файла не оставил записи `start` и вышел с кодом 1. `runDry`
    его не теряет: отклоняется с `Error`, где названы тест-файл и причина
    (или делает другое по выбранному дизайну, но не молча).
  - «Устаревший загрузчик мешает хукам», если выбран вариант 2 «Ожидаемого
    поведения». В `NODE_OPTIONS` есть устаревший загрузчик, а у
    инструментированного dry run пустой `served`. Тогда прогон завершается
    ошибкой с именем загрузчика. Если выбран вариант 1 (поддержка PnP),
    вместо этого нужен тест, что с таким загрузчиком переключаемый файл
    попадает в `served`. Нужен интеграционный тест (см. ниже).
- Тест только в `test/adapters/node-test/start-node-test-session.test.ts`
  этого не проверит. Там `runDry` и `runIsolated` замоканы (`:21-27`), видны
  только диагностики и флаги сессии.
- Интеграционный вариант можно сделать в `test/adapters/node-test/index.test.ts`.
  - Образец — «stops on a test file that fails to load without mutants»
    (`:300-312`).
  - Фикстура — `test/fixtures/node-test/<имя>/`. Её загрузчик повторяет
    `load$1` из `.pnp.loader.mjs`: сам читает `file:` и возвращает
    `shortCircuit: true`.
  - Загрузчик передаётся так:
    `nodeTestAdapter({ node, env: { NODE_OPTIONS: '--experimental-loader ./loader.mjs' } })`
    (опция `env` — `adapters/node-test/types/node-test-adapter-options.d.ts:9`).
  - Воспроизводит ли такая фикстура баг на текущем коде, зависит от
    гипотезы (a) и не проверено. Если до исправления она не падает, падающим
    тестом её не считайте.
- Сквозная проверка: tarball пересобран, фикстуры созданы заново.
  `yarn mootant run src --no-cache` даёт одно из двух:
  - те же вердикты, что контрольная npm-фикстура;
  - код выхода не 0 и сообщение, которое называет загрузчик PnP и
    предлагает обход.

  «no coverage 12» с exit 0 быть не должно.
- Без регрессий: контрольная npm-фикстура даёт тот же результат, что до
  исправления. Существующие тесты загрузчиков (`--import tsx`, `--require`) в
  `test/adapters/node-test/` зелёные.
- `docs/content/guide/compatibility.mdx`, раздел `## node:test` (`:61-80`),
  упоминает Yarn PnP с node:test: что произойдёт и как это обойти. Обход
  сначала проверен на фикстуре (см. «Ожидаемое поведение»).
- По отдельности зелёные `pnpm test:unit` (порог coverage 100%, новые ветки
  покрыты), `pnpm test:js`, `pnpm test:types`, `pnpm test:usage`,
  `pnpm test:spelling` и `pnpm test:format`.
  - `test:unit` запускайте так:
    `env -u NODE_OPTIONS TERM=xterm-256color pnpm test:unit`.
  - Если окружение как в CI (нет `dist/`, не root, нет `NODE_OPTIONS`, `TERM`
    не `linux`), `pnpm test` зелёный целиком.
  - Падения, которые есть и на нетронутом 170ec52 (см. «Ограничения»),
    исправлению не мешают. Перечислите их в отчёте.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости. Если без этого нельзя, опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Не ломай поддержку загрузчиков, с которыми переключение работает
  (`--import tsx`, `--require` и т.п.). Не делай ошибкой устаревший
  загрузчик, пока не доказано, что он мешает переключению.
- Готового теста-воспроизведения из анализа для BUG-820 нет. Свой тест по
  шагам выше (как и тесты-воспроизведения анализа для других багов) нельзя
  класть в `test/repros/` как есть. Его нужно переписать в стиле проекта,
  иначе строгий ESLint его не пропустит:
  - имя вроде `BUG-820.test.ts` нарушает `unicorn/filename-case`: разрешены
    только kebab-case и PascalCase;
  - perfectionist сортирует строки импорта и имена внутри `{ … }` по длине
    строки, по убыванию;
  - `describe` называют по функции (`describe('startNodeTestSession', …)` в
    `test/adapters/node-test/start-node-test-session.test.ts:118`);
  - окружение восстанавливают через `process.env = { ...SAVED }` (там же,
    `:37`, `:123`).

  Сценарии добавляйте в существующие `test/adapters/node-test/*.test.ts`.
  Фикстуры (проект, загрузчик) кладите в `test/fixtures/**`. Их исключают
  Vitest (`vitest.config.ts:18`), ESLint (`eslint.config.ts`), `tsc`
  (`tsconfig.json:2`), knip (`knip.config.ts`) и cspell (`cspell.config.ts`).
  Если cspell не знает новых слов вне фикстур (например, `nodeLinker` в
  документации), добавьте их в `words` в `cspell.config.ts`.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`. По базовой
  линии анализа это 14 ошибок `ts(2322)` в `docs/components/*.astro`.
  - Причина: `tsconfig.json:2-4` не исключает `dist/`, и в программу попадает
    `dist/types/html/inline-script.d.ts` с
    `/// <reference types="vite/client" />`.
  - В CI джоба Astro пакет не собирает, поэтому она зелёная.
  - Сборка нужна для tarball. После неё проверяйте `test:unit`, `test:js`,
    `test:types` и остальные `test:*` по отдельности, а `test:astro`
    запускайте только после `rm -rf dist`.
- По базовой линии анализа есть тесты, которые зависят от окружения и падают
  и без исправления:
  - 4 теста CLI в `test/cli/run-list.test.ts` и
    `test/cli/run-mutation.test.ts` ждут символов Unicode, а при `TERM=linux`
    вывод идёт в ASCII (`cli/terminal/is-unicode-supported.ts:13`);
  - «skips test files it cannot read»
    (`test/adapters/node-test/score-node-test.test.ts:98-105`) падает под
    root, потому что `chmod 000` root не мешает;
  - при заданном `NODE_OPTIONS` (например, `--use-openssl-ca` у прокси) не
    покрывается правая ветка `?? ''` в
    `adapters/node-test/start-node-test-session.ts:119` и `:167`, и покрытие
    branches падает ниже 100%.

  Новые тесты, которые меняют `NODE_OPTIONS`, должны восстанавливать его после
  каждого теста.
