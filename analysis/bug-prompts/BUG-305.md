# BUG-305: `--since` выкидывает мутанта изменённой строки, «владелец» которого стоит на неизменённой строке

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: high. Статус: подтверждён.
> Найдено на коммите 170ec52.
> Перепроверено независимо: воспроизведено (тест падает 3/3, сквозной сценарий
> собран с нуля, независимый подсчёт масштаба совпал: 357 строк в core, 268 в
> perfectionist); скептик: не опроверг и предлагал medium, потому что для O19
> сохранение пропуска задокументировано (`docs/content/mutators.md:63-64`), но
> итог — high: это обоснование предполагает, что владелец запускается, а под
> `--since` он не запускается, и `run --since HEAD --threshold 80` даёт
> `score none` и код 0 там, где полный прогон даёт 0% и код 1.

## Контекст

Правила пропуска решают при генерации, что кандидат не нужен: его поведение
покрывает другой мутант («владелец» или «оправдывающий» мутант, в выводе — поле
`by` пропуска).

- `O19` (категория `owned`): удаление единственного оператора then-ветки `if`
  без `else` ≡ `if (false)`; копия другой ветки или булева константа в `return`
  ≡ константа, которую выдаёт владелец условия. Решается **статически**, «with
  every mutator enabled and without ignore comments»
  (`core/mutators/shared/get-owner-constant.ts:35-41` →
  `core/mutators/shared/create-static-run-context.ts:4-20`, где `runs()` всегда
  `true`).
- `R4`, `R5`, `R6` (`subsumed`): пропуск, пока «запускается» мутант, который
  сдвигает условие к той же константе. Проверку делает `runs()`
  (`core/mutators/shared/create-run-context.ts:47-59`), а он смотрит только на
  пресет и ignore-комментарии (`isActive`,
  `core/generate/generate-file-mutants.ts:420-429`).
- `solitary` (`subsumed`, эвристика): грубый кандидат выбрасывается, если в его
  диапазоне есть более тонкий; `countsFor` учитывает только ignore
  (`core/generate/apply-solitary-rule.ts:124-136`, условие на строке 135).

Где реализованы правила: `getForcedThenSkip` — O19 и R4 для then-ветки
(`core/mutators/statement-removal.ts:152-188`), `getBranchCopySkip` — O19 и R5
(`core/mutators/shared/get-branch-copy-skip.ts:35-92`), `getConstantSkip` — O19
и R6 (`core/mutators/return-value.ts:202-239`); категории —
`core/skips/skip-rules.ts:302-305`, `314-325`, `354-357`. Конвейер файла —
`generateFileMutants` (`core/generate/generate-file-mutants.ts:231-306`: сбор
кандидатов 248, id 257, solitary 258-259, дедупликация 260-263).

Где теряется тест. Генерация про `--since` не знает: `listFileMutants` не
получает изменённых строк (`core/files/list-file-mutants.ts:19-60`). Отбор идёт
**после** генерации (`core/list-mutants.ts:71-88`,
`core/run-mutants.ts:186-210`): `selectChangedMutants`
(`core/files/select-changed-mutants.ts:18-66`, фильтр на 61-62) оставляет
мутанты и пропуски, чьи строки задевают изменённую, и о владельцах не знает.
Владелец на неизменённой строке отбрасывается, а пропущенный кандидат
изменённой строки остаётся только в `skipped` (его видно в `list --skipped` и в
HTML-отчёте) и не запускается. `selectMutants` в `run`
(`core/run-mutants.ts:633-664`) владельцев тоже не подтягивает. Изменённая
строка остаётся без мутантов, хотя кандидат был, а по правилу «Without mutants
to score, any threshold passes» (`docs/content/guide/cli.mdx:68`) PR проходит
порог.

Это рекламируемый сценарий CI (`readme.md:63-64`,
`docs/content/guide/getting-started.mdx:123-130`,
`docs/content/guide/cli.mdx:98`, `104-112`). Для R4, R5, R6 и solitary
документация обещает возврат «when the other mutant doesn't run»
(`docs/content/mutators.md:63-64`,
`docs/content/mutators/statement-removal.md:222-223`,
`docs/content/mutators/return-value.md:182-183`,
`docs/content/mutators/string-literal.md:153-154`); под `--since` другой мутант
не запускается, а возврата нет. Для O19 документация говорит обратное:
«`owned` changes stay skipped» (`docs/content/mutators.md:64`; «The other
changes stay skipped» — `statement-removal.md:227`, `return-value.md:187`), с
обоснованием «another mutant already makes the test `false`»
(`statement-removal.md:86-88`), которое под `--since` неверно.

Границы (уточнение скептика): эффект есть, только если на изменённой строке нет
других кандидатов, например это единственный оператор then-ветки `if` без
`else`. Владелец всегда выше (строка `if` или инициализатор), чаще всего на одну
строку. Типичные затронутые строки: `return null`/`return x`, простые вызовы,
голый `return`, `throw`.

Масштаб — по `mootant list <пути> --skipped --json` на 170ec52: каталог `core/`
Mootant и каталоги `rules/`, `utils/` eslint-plugin-perfectionist на коммите
486c3c8. Оба верификатора пересчитали своими скриптами, цифры совпали. Скрипт
анализа в репозитории отсутствует, метод описан здесь:

- пропусков, у которых `by.line` лежит вне строк самого пропуска (от `line` до
  `line` + число переводов строк в исходном тексте): 726 в core (O19 413, R4
  191, solitary 96, R5 13, R6 13) и 420 в perfectionist (O19 313, R4 32,
  solitary 46, R5 29, R6 0). O3 (720 и 176 таких пропусков) не учтён: его
  владелец — многострочный `&&`/`||`, диапазон которого покрывает строку
  операнда, и `--since` этого владельца выбирает;
- строк, которые при изменении только их самих остаются под `--since` без
  единого мутанта, хотя на них есть такой пропуск: 357 в core и 268 в
  perfectionist (около 3,3% и 3,5% строк, где есть хотя бы один мутант: 10 472
  и 7 435); на O19 из них приходится 166 и 205. Оценка снизу: учтены только
  однострочные пропуски; строка считается пустой, если её не задевает диапазон
  (от первой до последней строки) ни одного выданного мутанта.

## Воспроизведение

### 1. Падающий unit-тест

Тест из ветки анализа `experiment/bug-repros` (`test/repros/BUG-305.test.ts`).
В чистом клоне этой ветки нет: создайте файл сами (каталога `test/repros/` в
170ec52 тоже нет). Хелпер `test/helpers/create-git-repository.ts` в 170ec52
есть.

```ts
import { afterEach, describe, expect, it } from 'vitest'

import type { GitRepository } from '../helpers/create-git-repository'

import { createGitRepository } from '../helpers/create-git-repository'
import { listMutants } from '../../core/list-mutants'

/**
 * Repository of the running test.
 */
let repository: GitRepository | null = null

/**
 * Function whose then-branch changes in the second commit: the removal of the
 * changed statement is skipped as O19 in favor of condition's `false` on the
 * unchanged `if` line, which `--since` then leaves out.
 *
 * @param call - Statement of the then-branch.
 * @returns Source of the file.
 */
function createSource(call: string): string {
  return [
    'export function open(user, door) {',
    '  if (user.isAdmin) {',
    `    ${call}`,
    '  }',
    '}',
    '',
  ].join('\n')
}

describe('BUG-305: --since drops a mutant whose owner lies on an unchanged line', () => {
  afterEach(async () => {
    await repository?.remove()
    repository = null
  })

  it('keeps a mutant of the changed line when the mutant it is left to is not selected', async () => {
    repository = await createGitRepository()
    let { write, root, git } = repository
    await write('src/access.js', createSource('door.unlock(user)'))
    git('add', '.')
    git('commit', '--quiet', '-m', 'base')
    await write('src/access.js', createSource('door.open(user)'))

    let result = await listMutants({
      paths: ['src'],
      since: 'HEAD',
      skipped: true,
      cwd: root,
    })
    let mutants = result.files.flatMap(file =>
      file.mutants.map(
        mutant => `${mutant.mutator}: ${mutant.replacement}`,
      ),
    )

    /*
     * Without `--since` the line holds the O19 removal and line 2 holds its
     * owner, condition's `false`. With `--since` only line 3 is selected, so
     * the owner is gone and the changed call has no mutant at all.
     */
    expect(mutants).toContain('statement-removal: ;')
  })
})
```

```bash
pnpm install          # pnpm 12, см. «Ограничения»
pnpm exec vitest --run test/repros/BUG-305.test.ts
# FAIL … AssertionError: expected [] to include 'statement-removal: ;'
```

Падает детерминированно (3 из 3; `listMutants` тестов не запускает, от

`since` мутанты — `condition: true`, `condition: false` (строка 2), пропуск —
`statement-removal: ;` (O19, `by` — `condition`); с `since: 'HEAD'` мутантов
нет, пропуск тот же, а `readChangedLines` видит изменённой строку 3.
Утверждение теста соответствует пути C из «Направления исправления» (вернуть
сам O19-кандидат); при пути B его нужно заменить (см. «Критерий готовности»).
Файл нужен только для проверки, в коммит в таком виде не включать (см.
«Ограничения»).

## Ожидаемое поведение

Пропуск с владельцем не должен оставлять изменённый код непроверенным, когда
отбор `--since` не берёт владельца.

- R4, R5, R6, solitary (`subsumed`): действует документированное правило.
  Мутант на неизменённой строке под `--since` не запускается, значит,
  пропущенный кандидат изменённой строки выдаётся так же, как при выключенном
  мутаторе. В сценариях п. 3 это `statement-removal` `;` на строке 3 и
  `return-value` `count -> 0` на строке 8.
- O19 (`owned`, статичен намеренно): либо в отбор добавляется сам владелец
  (`by`; в примере — `condition` → `false` на строке 2), либо возвращается
  кандидат (`statement-removal` `;` на строке 3) и переписывается документация
  об `owned`. Фраза прежней версии промпта «так уже устроен `context.runs` для
  ignore-комментариев» верна для R4/R5/R6, но не для O19: он ignore-комментарии
  сознательно не учитывает (`create-static-run-context.ts:4-8`).
- В примере п. 2 `run src --since HEAD --threshold 80` оценивает изменённую
  строку (выживший мутант, 0%) и завершается с кодом 1, как полный прогон.
- `list --since` и `run --since` решают одинаково: владелец или возвращённый
  кандидат появляется в обоих. Id мутантов от `--since` не зависят.

## Фактическое поведение

`list src --since HEAD --skipped` — `mutants 0`, единственный пропуск O19 на
строке 3. `run src --since HEAD --threshold 80` — `score none (no mutants to
score)`, код 0. Полный прогон — 2 выживших, 0%, `below threshold 80%`, код 1. В
сценариях R4 и solitary — тоже `mutants 0`. Вывод см. в п. 2 и п. 3.

### Направление исправления (уточнения верификаторов)

Постфильтр «вернуть пропуск в `selectChangedMutants`» почти неработоспособен:

- пропуски уровня сбора (O19, R4, R5, R6) не получают id: `assignMutantIds`
  вызывается только для `collection.candidates`
  (`core/generate/generate-file-mutants.ts:257`), а `collectCandidates` пишет
  `by.id: null` (`core/generate/collect-candidates.ts:220`); у `SkippedMutant`
  по контракту нет id, и он не запускается
  (`types/mutant/skipped-mutant.d.ts:6-8`);
- `SkipJustifier` — это `{ id, mutator, start }`
  (`types/mutant/skip-justifier.d.ts:4-21`): ни конца диапазона, ни замены, а у
  O19 `id` всегда `null`;
- регионы для кэша вердиктов считаются только для выданных мутантов
  (`generate-file-mutants.ts:286-299`);
- в `run` пропуски собираются только при `--html` (`core/run-mutants.ts:198`,
  `skipped: html !== null`);
- `listFileMutants` изменённых строк не получает.

Ловушка с id. `assignMutantIds` (`core/identity/assign-mutant-ids.ts:7-53`)
различает кандидатов с одинаковыми scope, мутатором, исходным текстом и заменой
счётчиком предшественников в каноническом порядке. Если кандидат, который
выдаётся только под `--since`, попадёт в общую нумерацию, у следующего за ним
такого же кандидата id под `--since` сдвинется, а возвращённый получит его id из
полного прогона (слот кэша вердиктов строится из id:
`core/cache/create-run-cache.ts:216-222`). Если же всегда включать пропущенные
O19-кандидаты в нумерацию, id соседей изменятся и без `--since`. Оба варианта
нарушают инвариант «id одинаков с `--since` и без»
(`core/run-mutants.ts:617-620`). Кандидатов, выдаваемых только под `--since`,
нужно нумеровать так, чтобы они не сдвигали счётчики кандидатов полного прогона
(например, после них; идея не проверялась). Solitary-кандидаты id уже имеют: id
назначаются до правила (`generate-file-mutants.ts:257-259`), поэтому их возврат
ничего не сдвигает.

Рабочие пути:

- **A. Изменённые строки — в генерацию** (для R4, R5, R6, solitary;
  предложение воспроизводящего верификатора). Передать изменённые строки через
  `listMutants`/`runMutants` → `listFileMutants` → `generateFileMutants` и
  считать мутанта вне изменённых строк незапускаемым: в `isActive` (его
  контракт — «will run», `types/mutator/mutator-context.d.ts:12-18`) и в
  `countsFor` (как кандидата с `ignoreRule`). Тогда `runs()` вернёт кандидата
  так же, как для выключенного мутатора; мутанты неизменённых строк сохраняют
  свои пропуски (ветка `isEnabled && !isActive(candidate)` в `runs()`).
  `selectChangedMutants` остаётся как есть. Нужна защита от ловушки с id.
- **B. Подтянуть владельца в отбор** (для O19; предложение скептика,
  согласовано с документацией). При `--since` добавлять в отбор
  мутанта-владельца (`by`) пропуска, стоящего на изменённой строке. Новых
  кандидатов нет, id не меняются. Нужно: при `--since` собирать пропуски всегда
  (по JSDoc `generate-file-mutants.ts:221-224` они «never change the mutants or
  their ids»), а печатать только с `--skipped`; сопоставлять `by` с выданным
  мутантом по `mutator` + `start` (замены в `by` нет, а у `condition` на одном
  узле два мутанта, `true` и `false`: подтягивать оба или аддитивно расширить
  `SkipJustifier`); делать это одинаково в `list` и `run`, включая
  `selectMutants` (`--mutant` вместе с `--since`); дополнить описание `--since`
  (`docs/content/guide/cli.mdx:98`). Путь B применим и к subsumed-правилам (без
  ловушки с id), но для них документация обещает возврат самого кандидата.
- **C. Вернуть сам O19-кандидат.** Тогда нужно переписать «`owned` changes stay
  skipped» (`docs/content/mutators.md:63-64`, `statement-removal.md:227`,
  `return-value.md:187`) и решить ловушку с id. На этот путь рассчитано
  утверждение теста из анализа (`statement-removal: ;`).

Выбор пути для O19 (B или C) и для subsumed-правил (A или B) опишите в PR.

## Критерий готовности

- Тест-воспроизведение переписан в стиле проекта и добавлен в
  `test/core/list-mutants.test.ts`: в describe «listMutants with --since in a
  git repository» (строки 387-510, уже работает с настоящим git через
  `createGitRepository`) или рядом. На 170ec52 он падает, после исправления
  проходит. Утверждение фиксирует выбранный путь для O19: при пути B среди
  мутантов есть `condition` с заменой `false` на строке 2, при пути C —
  `statement-removal` с заменой `;` на строке 3.
- Там же тесты по сценариям R4 и solitary из п. 3: с `--since` изменённая
  строка не остаётся без мутантов. При пути A среди мутантов есть
  `statement-removal` `;` на строке 3 и `return-value` `count -> 0` (замена
  `0`) на строке 8. Если для них выбран путь B — их `by`: `comparison-operator`
  на строке 2 и `number-literal` `0 -> 1` на строке 2, и документация говорит
  именно это.
- `list --since` и `run --since` решают одинаково: подтянутый владелец или
  возвращённый кандидат есть в обоих.
- Id: тест, что у мутантов, отобранных с `--since` и присутствующих в листинге
  без `--since` (тот же файл, мутатор, диапазон и замена), id совпадают, —
  минимум на трёх сценариях. При пути A или C — ещё сценарий с двумя
  одинаковыми операторами в одной функции, где возвращаемый кандидат стоит
  раньше (подобрать самостоятельно; в анализе не проверялся).
- Без `--since` ничего не меняется: `test/cli/index.test.ts` (точное сравнение
  с `test/fixtures/list/expected-*.json`, включая id и пропуски) и
  `test/core/generate/*` зелёные без перегенерации ожидаемых файлов.
- Сквозная проверка п. 2 после пересборки (`pnpm build && pnpm pack`, затем
  `npm i -D /tmp/mootant.tgz` в фикстуре; если подхватилась старая сборка,
  удалите `node_modules` и `package-lock.json` и поставьте заново вместе с

  печатает `score none`, даёт 0% и код 1.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  `MutatorContext.isActive` и `SkipJustifier` лежат в `types/`: менять их смысл
  или форму только аддитивно и с обновлением JSDoc.
- Id мутантов не должны зависеть от `--since`: слот кэша вердиктов строится из
  id (`core/cache/create-run-cache.ts:216-222`), а `--mutant` разрешается по
  всем мутантам листинга (`core/run-mutants.ts:617-620`).
- Тест-воспроизведение из анализа нельзя копировать как есть в `test/repros/`:
  перепиши его в стиле проекта. Строгий ESLint (`eslint.config.ts`:
  `@azat-io/eslint-config` с правилами perfectionist и vitest) проверяет имена
  файлов, `describe`/`it` и порядок импортов. Фикстуры клади только в
  `test/fixtures/**`: их игнорируют ESLint (`eslint.config.ts`), `tsc`
  (`tsconfig.json:2`) и Vitest (`vitest.config.ts`).
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro` (14 ошибок
  `ts(2322)` в `docs/components/*.astro`): `tsconfig.json:2-4` включает
  `**/*.ts` и не исключает `dist/`, а `dist/types/html/inline-script.d.ts`
  подтягивает типы `vite/client`. После сборки удаляй `dist/` или проверяй
  `test:unit`, `test:js`, `test:types` (и остальные `test:*`) по отдельности.
- Тесты, зависящие от окружения (к багу не относятся): по два теста в
  `test/cli/run-list.test.ts` и `test/cli/run-mutation.test.ts` ждут Unicode и
  падают при `TERM=linux` (запускай с `TERM=xterm-256color`); «skips test files
  it cannot read» в `test/adapters/node-test/score-node-test.test.ts` падает под
  root; при заданном `NODE_OPTIONS` покрытие веток меньше 100%
  (`adapters/node-test/start-node-test-session.ts:119`, `167`), поэтому
  запускай `env -u NODE_OPTIONS pnpm test:unit`.
- Для установки зависимостей нужен pnpm 12: pnpm 10 не читает
  `configDependencies` из `pnpm-workspace.yaml` и зависает. В npm-фикстурах
  ставь `vitest@5`, не `vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает в
  arborist (`Cannot read properties of null (reading 'edgesOut')`).
