# BUG-307: `x || 0` для числа считается эквивалентным `x`, хотя он защищает от `NaN`

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён.
> Найдено на коммите 170ec52.
> Перепроверено независимо: воспроизведено (unit-тест падает 2/2 в трёх
> прогонах; на сквозной фикстуре с упакованным mootant `mootant run` даёт
> 100 %, а с физически удалёнными `|| 0` тесты остаются зелёными, хотя
> `ratio(0, 0)` и `toCount('abc')` возвращают `NaN` вместо `0`); скептик: не
> опроверг, medium на нижней границе — оговорка «`NaN` aside»
> задокументирована и правило помечено `heuristic`, но это дефект дизайна:
> категория `equivalent` по определению не меняет поведение, пропуск не
> возвращают ни `strict`, ни опции, а то же различие по `NaN` у `nullish-swap`
> отнесено к `noise`; охват шире заявленного (ветка `&&`, `||=` и `&&=` в
> `assignment-operator`).

## Контекст

`logical-operator` не выдаёт удаление правого операнда `||`, если правый
операнд — «единственное ложное значение типа» левого. Флаг считается один раз,
в `keepsFalsyDefault` (`core/mutators/shared/get-logical-drops.ts:81-84`):
левая часть — строка, число, BigInt или булево (`hasDefinedFalsyValue`), не
может быть nullish (`!mayBeNullish`), а правая — каноничное ложное значение
этого типа (`isCanonicalFalsy`). Читают флаг две ветки:
для `||` — `getRightKeptSkip` (`:158-160`; правый операнд даже не становится
кандидатом на удаление), для `&&` — `getDropLeftSkip` (`:119-121`; удаление
левого операнда, `x && 0` → `0`). Обе возвращают `falsyDefaultNote`
(`:89-93`): правило `canonical-falsy-default` с безусловной причиной «the
right operand is the only falsy value of the left operand's type, so the
result is the same». Категория правила — `equivalent`, `heuristic: true`
(`core/skips/skip-rules.ts:10-13`). Значения берутся из таблицы
`core/mutators/shared/get-canonical-falsy.ts:7-12` (JSDoc: «`NaN` aside» на
стр. 5, «`0` for a number (`NaN` ignored)» на стр. 16), сравнение с литералом
— `core/mutators/shared/is-canonical-falsy.ts:19-22`.

Для строк, булевых и BigInt это верно, для чисел — нет: `NaN || 0` даёт `0`,
а без `|| 0` остаётся `NaN`. С `&&` то же: `NaN && 0` — `NaN`, а мутант — `0`.
Различает и `-0` (`-0 || 0` даёт `+0`; `toBe` в Vitest сравнивает через
`Object.is`). Именно ради `NaN` пишут `done / total || 0` (деление 0/0) и
`Number(text) || 0` (нечисловой ввод), то есть мутант отличается от оригинала
ровно на входе, ради которого существует код. Тип `number` выводится
синтаксически и в `.js`: `/` с операндами неизвестного типа
(`core/hints/infer-operator-type.ts:125-126`), унарный `+` (`:218-219`),
вызовы `parseFloat`, `parseInt`, `Number`, `Math.*`
(`core/hints/well-known-calls.ts:57`, `:77`, `:95`, `:96`).

Документация называет правило `equivalent` с оговоркой «Default is the type's
only falsy value, `NaN` aside» (`docs/content/mutators/logical-operator.md:205`,
`docs/content/mutators/assignment-operator.md:180`), а категория `equivalent`
по `docs/content/mutators.md:38` — «Can't alter what the code does, apart from
details such as `undefined` for `null`». `NaN` → `0` — не «деталь»: у числа
`x || 0` отличается от `x` только на `NaN` и `-0`, то есть правило скрывает
единственное, что этот код делает. В текстовом выводе `mootant list --skipped`
причина безусловна, флаг `heuristic` есть только в `--json`
(`docs/content/mutators.md:46-50`) и в HTML-отчёте
(`cli/html/client/render-skip-panel.ts:83`). То же различие по `NaN` у
перестановки `??` ↔ `||` отнесено к `noise` (правило `nullish-swap`,
`core/skips/skip-rules.ts:282-285`; `logical-operator.md:162-165`: «only `NaN`
and `-0` tell the swap apart») и возвращается опцией `nullishSwap: 'always'` и
пресетом `strict` (`core/mutators/shared/distinguishes-nullish-swap.ts:47-51`,
условие для числа — `:50`). `canonical-falsy-default` не возвращает ничто
(`logical-operator.md:227`: «The other changes stay skipped»; скептик
проверил с `--preset strict --json`).

Для `Number(text) || 0` других мутантов этой защиты нет. Перестановка на `??`
не рассматривается: `swapApplies` требует, чтобы левая часть могла быть
nullish (`get-logical-drops.ts:212-217`). Удаление левого операнда (`-> 0`)
убивается любым ненулевым входом, а `number-literal` `0 -> 1` — нулевым
(`toCount('')`), без всякого `NaN`. Тест без случая `NaN` даёт 100 %, хотя
защита не проверена. Парадокс: когда тип не выведен, защиту проверяют.
`Number.parseInt` и `Number.parseFloat` в таблице нет (поиск —
`core/hints/infer-call-type.ts:97-99` и `:144`), поэтому у
`Number.parseInt(text, 10) || 0` левая часть `unknown`, и Mootant выдаёт
перестановку `Number.parseInt(text, 10) ?? 0`, которая различает как раз
`NaN`; у скептика она выжила без NaN-теста.

Охват шире двух примеров (данные верификаторов): тем же правилом пропускаются
`parseInt(t, 10) || 0`, `+text || 0`, `Math.sqrt(v) || 0`, `a % b || 0`,
`sum / values.length || 0` и `count || 0` при `count: number` (TS). Двойник
правила — `getGuardSkip` в `core/mutators/assignment-operator.ts:283-313`
(правило на `:302-311`, вызов на `:157`). Он пропускает удаление `||=`
(`:186`): у верификатора `value ||= 0` → `value` при `value = done / total`
пропущен. По чтению кода через него же пропускается замена `&&=` на `=`
(`:172`: `value &&= 0` → `value = 0`), хотя `NaN &&= 0` оставляет `NaN`.

## Ожидаемое поведение

1. Для числовой левой части удаление `|| 0` (и для `&&` удаление левого
   операнда, `x && 0` → `0`) не пропускается как `equivalent`, если левая
   часть может быть `NaN`. Обязательно — для выражений, которые дают `NaN` по
   синтаксису: деление и `%`, `Number()`, `parseInt`/`parseFloat`, `Math.*`,
   унарный `+`, арифметика с операндом неизвестного типа. В шагах 1–2 оба
   удаления выдаются.
2. Пропуск `canonical-falsy-default` (`equivalent`) остаётся для строк,
   булевых, BigInt и для чисел, которые доказанно не `NaN`: для них
   `context.syntax.getValueBound(left)` возвращает границу с
   `nullable: false`. Это `.length`, результат `indexOf`/`findIndex`/`search`,
   счётчики (`core/syntax/get-value-bound.ts:70-92`). Граница значит «каждое
   значение — число не меньше `lower`» (`types/syntax/value-bound.d.ts:3-7`),
   поэтому `NaN` она исключает. `-0` формально не исключает: `.length` и
   позиции его не дают, для счётчиков это не проверено.
3. Число без доказанной границы и без «NaN-синтаксиса» (TS-параметр
   `count: number`, `let x: number`) верификаторы не рассудили. Выбери явно:
   - **(а) Удаление выдаётся** — рекомендуемый вариант. Условие одно («пропуск
     у числа — только при доказанной границе»), оно одинаково работает для
     `||`, `&&`, `||=` и `&&=` и не требует разбирать, откуда пришло значение:
     у `let value = done / total; value ||= 0` границы нет, и удаление
     выдаётся. Вариант прямо следует из контракта `equivalent` и из исходного
     замысла («пропуск — для чисел, которые не могут быть `NaN`»). Цена:
     мутанты на защитных `count || 0` при `count: number` в TS (скептик
     считает их частым шумом) и эквивалентные удаления там, где граница не
     выводится, хотя `NaN` невозможен. Это константы из одних литералов
     (`get-value-bound.ts:94-97`) и разности вроде `items.length - 1 || 0`:
     `getValueBound` складывает только `+` (`:404`). Ожидание
     `test/core/mutators/logical-operator.test.ts:295-301` меняется.
   - **(б) Список «NaN-выражений»**: у `count: number` пропуск остаётся, тест
     `:295-301` не меняется. Но такой пропуск по-прежнему объявлен
     `equivalent`, хотя NaN-параметр его различает. Если выбираешь (б),
     рассмотри для этих случаев отдельное правило категории `noise`, которое
     возвращает `strict`, как у `nullish-swap`. Цель `||=` — почти всегда имя,
     поэтому для `assignment-operator` вариант (б) должен смотреть в
     инициализатор и записи имени, иначе случай
     `let value = done / total; value ||= 0` останется с багом.
4. Условие одно для обеих веток `logical-operator` и для `getGuardSkip` в
   `assignment-operator`: правило с одним именем не должно значить разное в
   двух мутаторах. Сами `getCanonicalFalsy` и `isCanonicalFalsy` не меняй (см.
   «Подозреваемые места в коде»).
5. Причина пропуска у числа говорит, почему `NaN` исключён. Например, её можно
   дополнить текстом `ValueBound.because` («a length is never negative»).
6. Строки `canonical-falsy-default` в документации обоих мутаторов описывают
   условие для чисел.

Что уже проверено правкой изолированной копии 170ec52 (верификатор):

- `&& getTypeView(leftType).type !== 'number'` в условии на строке 158 (только
  `||`): тест-воспроизведение проходит 2/2, четыре файла (repro,
  `logical-operator`, `get-logical-drops`, `assignment-operator`) — 219/219.
  Но этого мало. По чтению кода так начнёт выдаваться и истинно эквивалентное
  `list.length || 0 -> list.length`, а его не закрепляет ни один тест. Ветка
  `&&`, `||=` и `&&=` при этом остаются с багом.
- То же условие внутри `keepsFalsyDefault` (`:81-84`): воспроизведение
  проходит, но падает `logical-operator.test.ts:399` на кейсе `count && 0`
  (`:295-301`), потому что ветка `&&` читает тот же флаг. Для варианта (а)
  это ожидаемое следствие: ожидание теста нужно обновить, а не обходить
  `keepsFalsyDefault`.

## Фактическое поведение

Шаг 1 (суть сообщений Vitest, не дословный лог; одинаково в трёх прогонах):

```
× keeps the drop of the default of done / total || 0
  AssertionError: expected [ 'done / total || 0 -> 0' ] to include 'done / total || 0 -> done / total'
× keeps the drop of the default of Number(text) || 0
  AssertionError: expected [ 'Number(text) || 0 -> 0' ] to include 'Number(text) || 0 -> Number(text)'
```

На сниппете с `return done / total || 0` весь конвейер выдаёт только
`done / total || 0 -> 0`, `/ -> *` и `0 -> 1`.

Шаг 2, `npx mootant list src/nan.js --skipped`, пропущенные кандидаты.
Раскладка приблизительная: заголовки, отступы и стрелка зависят от терминала.
Текст причины дословно взят из `core/mutators/shared/get-logical-drops.ts:91`.

```
2:10 logical-operator  done / total || 0 -> done / total  equivalent  canonical-falsy-default
     the right operand is the only falsy value of the left operand's type, so the result is the same
6:10 logical-operator  Number(text) || 0 -> Number(text)  equivalent  canonical-falsy-default
     the right operand is the only falsy value of the left operand's type, so the result is the same
```

В `--json` у обоих `"rule": "canonical-falsy-default"`,
`"category": "equivalent"`, `"heuristic": true` (поля —
`cli/report/build-list-report.ts:161-168`). Прогон
`mootant run src/nan.js --no-cache` (два раза): killed 5, survived 0, score
100 % (в JSON `coveredScore` 100, `score` 100). С физически удалёнными `|| 0`
`vitest --run` даёт 2 passed, а `ratio(0, 0)` и `toCount('abc')` возвращают
`NaN` вместо `0`. На копии `fx1` из анализа (с непокрытым `toPage`) —
covered 100 %, общий score 55,56 %, те же два пропуска.

Другие формы (сквозные прогоны верификаторов): как
`equivalent canonical-falsy-default` пропускаются ещё `parseInt(t, 10) || 0`,
`+text || 0`, `Math.sqrt(v) || 0`, `a % b || 0`, `sum / values.length || 0`,
`count || 0` при `count: number` (TS), а в `assignment-operator` —
`value ||= 0 -> value` при `value = done / total`. С `--preset strict` пропуск
остаётся. Ожидаемо (и верно) пропускаются `note || ''`, `list.length || 0`,
`v || 0n`. Физическая замена у скептика: тесты 6 из 6 зелёные, а
`ratio(0, 0)`, `toCount('abc')`, `plusParse('x')` и `avg([])` возвращают
`NaN` вместо `0`.

## Подозреваемые места в коде

- `core/mutators/shared/get-logical-drops.ts:81-84` — `keepsFalsyDefault` не
  различает числа, которые могут быть `NaN`. Это место для условия: флаг
  читают обе ветки, `&&` (`:119-121`) и `||` (`:158-160`); `context.syntax`
  здесь уже используется (`:76`). Причина пропуска — `:89-93`.
- `core/mutators/assignment-operator.ts:283-313` — `getGuardSkip` с тем же
  допущением (правило — `:302-311`). Вызов — `:157` в `getLogicalVariants`
  (`:137-209`); варианты `&&=` → `=` (`:172`) и удаление `||=` (`:186`).
  Сигнатура `(target: InferredType, right: Node)` не даёт ни узла цели, ни
  контекста: для `getValueBound` их нужно передать из `getLogicalVariants`.
- `core/syntax/get-value-bound.ts:70-140` — `getValueBound`: `.length`
  (`:271-272`), позиции (`:62-68`, `:79-80`), счётчики (`:222-224`), сумма —
  только `+` (`:404`), значения из одних литералов — без границы (`:94-97`).
  В мутаторе — `context.syntax.getValueBound(node)`
  (`core/syntax/create-syntax-helpers.ts:150`,
  `types/syntax/syntax-helpers.d.ts:109-117`). Пример потребителя —
  `core/mutators/shared/get-comparison-plan.ts:688-690`
  (`bound && !bound.nullable`).
- `core/mutators/shared/get-canonical-falsy.ts:4-24` и
  `core/mutators/shared/is-canonical-falsy.ts:9-22` — «`0` for a number (`NaN`
  ignored)». Таблицу и функции не меняй: их читают ещё
  `distinguishes-nullish-swap.ts:47-51` (`nullish-swap`) и
  `core/mutators/shared/get-or-default-skip.ts:41-52` (`O16`). Условие про
  `NaN` ставь в местах использования.
- `core/mutators/shared/distinguishes-nullish-swap.ts:27-32` (JSDoc) и
  `:47-51` — та же оговорка про `NaN` для `nullish-swap`. Там это `noise`
  (`core/skips/skip-rules.ts:282-285`), и его возвращает
  `nullishSwap: 'always'`. `core/mutators/shared/get-nullish-swap-skip.ts`
  только делегирует ему решение (`:32-38`), логики про число в нём нет.

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip. Новый предикат
  (например, «число не может быть `NaN`») — отдельный файл в
  `core/mutators/shared/` со своим тестом.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  `keepsFalsyDefault` и `getGuardSkip` внутренние. Новое правило в
  `core/skips/skip-rules.ts` (вариант (б) с `noise`) расширяет `SkipRuleId`
  (`types/mutant/skip-rule-id.d.ts`) и таблицы правил в документации —
  упомяни это в PR.
- Тест-воспроизведение из анализа нельзя копировать как есть в `test/repros/`:
  перепиши его в стиле проекта. Строгий ESLint (`eslint.config.ts`:
  `@azat-io/eslint-config` с правилами perfectionist и vitest) проверяет имена
  файлов, `describe`/`it`, порядок импортов и ключей. Проверки BUG-307 добавь
  в существующие файлы (`test/core/mutators/logical-operator.test.ts`,
  `test/core/mutators/assignment-operator.test.ts`, при необходимости
  `test/core/mutators/shared/get-logical-drops.test.ts`), временный

  только в `test/fixtures/**`: их игнорируют ESLint (`eslint.config.ts:15`),
  `tsc` (`tsconfig.json:2`) и Vitest (`vitest.config.ts:18`).
