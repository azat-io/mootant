# BUG-506: `mootant run` не завершается, если что-то в его процессе держит event loop

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (6 из 6 прогонов с незакрытым
> сервером в `globalSetup` зависли после отчёта, 4 из 4 контрольных
> завершились за 0,4–3,3 с; Vitest 5.0.5 в клоне и 5.1.0 с
> упакованным mootant; с `--threshold 100` вместо кода 1 — то же зависание);
> скептик: не опроверг и оставил medium — отчёт и вердикт верны, сбой
> fail-closed (внешний таймаут даёт ненулевой код), но CI-джоб висит до своего
> лимита без всякой диагностики, тогда как `vitest --run` на той же утечке
> выходит через ~10 с с предупреждением; попутно скептик нашёл родственный
> fail-open-сценарий (см. «Родственный сценарий»).

## Контекст

С адаптером Vitest в процессе mootant выполняется код проекта: конфиг Vitest,
плагины Vite, `globalSetup`. С любым адаптером там же выполняются
`mootant.config.*` и плагины mootant. Частая ошибка — `globalSetup`, который
поднимает сервер или вотчер и не закрывает его.

Vitest CLI от этого защищён. `start()` после прогона вызывает `ctx.exit()`, а
`exit()` ещё до `await this.close()` взводит таймер на `teardownTimeout` (по
умолчанию 10 000 мс) и снимает его с учёта (`unref()`). Если процесс к этому
времени жив, таймер печатает «close timed out after 10000ms» с подсказкой и
вызывает `process.exit()`. Программный `vitest.close()`, которым пользуется
mootant, выход не форсирует. Значит, за жизнь процесса отвечает сам mootant.
Места в Vitest 5.0.5 (эта версия ставится в клон по `pnpm-lock.yaml`):
`node_modules/vitest/dist/chunks/cac.CLrZKo1g.js:2369`,
`cli-api.De07GUeT.js:13283-13301` (`exit()`), `:13216` (`close()`),
`defaults.B1FCaFfh.js:64` (`teardownTimeout: 1e4`).

mootant закрывает Vitest в `finally` (`core/run-mutants.ts:320-322` →
`close()` в `adapters/vitest/start-vitest-session.ts:175-178` → `closeVitest()`,
`:149-157`). Потом `runMutation` печатает отчёт, при `--html` пишет HTML
(`cli/run-mutation.ts:51-82`) и только выставляет `process.exitCode` (`:74`,
`:93`, `:136`). `bin/mootant.js:5` вызывает `run()` и больше ничего не делает.
Процесс ждёт, пока event loop опустеет сам, а незакрытый сервер из
`globalSetup` держит его вечно. По замеру скептика
`process.getActiveResourcesInfo()` 105 с подряд показывает единственный ресурс
`TCPServerWrap`, воркеров Vitest к этому моменту уже нет.

Отчёт напечатан полностью, но процесс не завершается. В CI джоб висит до
своего лимита (у GitHub Actions по умолчанию 360 минут). Агент ждёт до
таймаута своего инструмента. Код выхода (например, 1 ниже порога) теряется:
вместо него получается код внешнего таймаута. Ложного «зелёного» нет, вердикт
верный.

Сценарий с `globalSetup` касается только `run`: `list` Vitest не запускает
(`core/list-mutants.ts:68-69` → `prepareRun` грузит только конфиг и плагины
mootant). Но `mootant list` тоже висит, если хэндл оставляет код
`mootant.config.*`. Воспроизводящий верификатор это проверил: вывод через
0,52 с, `SIGKILL` через 30 с, контроль завершился за 0,40 с.

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет: файлы ниже создай
сам. В коммит они не входят (см. «Ограничения»). Всё проверялось только на
Linux. Нужны Node.js 22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:22-24`) и pnpm 12: в CI стоит
`latest-12` (`.github/actions/install-tools/action.yml:14`), а
`pnpm-workspace.yaml` использует `configDependencies`. Команды шагов и проверки
из «Критерия готовности» рассчитаны на одну сессию shell. Они используют
переменные `ROOT`, `PACK`, `TGZ`, `FIX`, `MOOTANT` и `VITEST`. Фикстуры те же,
что у верификаторов, и mootant запускается так же, как у них
(`timeout N node …/node_modules/mootant/bin/mootant.js …` из каталога
фикстуры). Но в этой редакции команды целиком не перезапускались.

### Шаг 1. Сборка и упаковка mootant

`bin/mootant.js` импортирует `../dist/cli/index.js`, поэтому нужна сборка.

```bash
# в корне клона azat-io/mootant
ROOT="$PWD"
pnpm install
pnpm build
pnpm pack                          # пишет mootant-<версия>.tgz (на 170ec52 — mootant-0.1.0.tgz)
PACK="$(mktemp -d)"
mv mootant-*.tgz "$PACK/"          # *.tgz нет в .gitignore, не оставляй его в дереве
TGZ="$(ls "$PACK"/mootant-*.tgz)"
```

### Шаг 2. Фикстуры

Одна установка зависимостей в `$FIX` обслуживает все фикстуры-подкаталоги:
Node находит `vitest` и `mootant` в `$FIX/node_modules`, поднимаясь от
фикстуры. Так работал скептик. Ставь `vitest@5` (сейчас это 5.1.0), а не
`vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает с `Cannot read properties
of null (reading 'edgesOut')`. Это баг arborist, не mootant. У каждой фикстуры
свой `package.json` с `"type": "module"`. По опыту верификатора без него
фикстура падает на ESM-импорте.

- `leak` — `globalSetup` поднимает HTTP-сервер и не закрывает его;
- `control` — тот же сервер, но teardown его закрывает;
- `leak-threshold` — как `leak`, но тест слабый: единственный мутант файла
  (`a + b -> a`) выживает, и с `--threshold 100` код выхода должен быть 1;
- `config-leak` — `globalSetup` как в `control`, а сервер открывает
  `mootant.config.js` (сценарий для `mootant list`).

```bash
FIX="$(mktemp -d)"
cd "$FIX"
cat > package.json <<'EOF'
{
  "name": "bug-506-fixtures",
  "private": true
}
EOF
npm i -D vitest@5 "$TGZ"
MOOTANT="$FIX/node_modules/mootant/bin/mootant.js"
VITEST="$FIX/node_modules/.bin/vitest"

mkdir -p leak/src leak/test
cat > leak/package.json <<'EOF'
{
  "name": "bug-506-fixture",
  "private": true,
  "type": "module",
  "scripts": { "test": "vitest --run" }
}
EOF
cat > leak/vitest.config.js <<'EOF'
export default {
  test: {
    include: ['test/**/*.check.js'],
    globalSetup: ['./global-setup.js'],
  },
}
EOF
cat > leak/global-setup.js <<'EOF'
import http from 'node:http'

// A global setup that leaves a server open, a common leak: `vitest --run`
// warns "close timed out after 10000ms" and exits anyway.
export default function setup() {
  http.createServer((request, response) => response.end('ok')).listen(0)
}
EOF
cat > leak/src/add.js <<'EOF'
export function add(a, b) {
  return a + b
}
EOF
cat > leak/test/add.check.js <<'EOF'
import { expect, it } from 'vitest'

import { add } from '../src/add.js'

it('adds', () => {
  expect(add(2, 3)).toBe(5)
})
EOF

cp -r leak control
cat > control/global-setup.js <<'EOF'
import http from 'node:http'

export default function setup() {
  let server = http.createServer((request, response) => response.end('ok')).listen(0)
  return () => new Promise(resolve => server.close(() => resolve()))
}
EOF

cp -r leak leak-threshold
cat > leak-threshold/test/add.check.js <<'EOF'
import { expect, it } from 'vitest'

import { add } from '../src/add.js'

it('adds', () => {
  expect(typeof add(2, 3)).toBe('number')
})
EOF

cp -r control config-leak
cat > config-leak/mootant.config.js <<'EOF'
import http from 'node:http'

http.createServer((request, response) => response.end('ok')).listen(0)

export default {}
EOF
```

### Шаг 3. Прогоны

```bash
cd "$FIX/leak"
time timeout 60 "$VITEST" --run </dev/null; echo "exit=$?"
# тест проходит; через ~10 с «close timed out after 10000ms», exit=0

time timeout 60 node "$MOOTANT" run src --no-cache </dev/null; echo "exit=$?"
# сейчас: полный отчёт через ~2 с, потом тишина и exit=124 через 60 с

timeout 60 node "$MOOTANT" run src --no-cache --json </dev/null >leak.json; echo "exit=$?"
# сейчас: exit=124, хотя JSON в leak.json полный

cd "$FIX/leak-threshold"
timeout 60 node "$MOOTANT" run src --no-cache --threshold 100 </dev/null; echo "exit=$?"
# сейчас: в отчёте «below threshold 100%», потом exit=124 (должен быть 1)

cd "$FIX/control"
time timeout 60 node "$MOOTANT" run src --no-cache </dev/null; echo "exit=$?"
# контроль: exit=0 за ~2 с

cd "$FIX/config-leak"
time timeout 30 node "$MOOTANT" list src </dev/null; echo "exit=$?"
# сейчас: список мутантов через ~0,5 с, потом exit=124 через 30 с
```

Пояснения:

- `--no-cache` нужен, чтобы повторный прогон не взял вердикты прошлого
  (`cli/parse-arguments.ts:44-45`).
- `timeout` без `--preserve-status` возвращает 124, когда время вышло, как бы
  ни завершился сам процесс.
- Числа зависят от нагрузки (верификаторы работали при load average 13–22), а
  само зависание от неё не зависит: хэндл живёт постоянно, и зависли 6 прогонов
  из 6.

### Шаг 4 (необязательно). `run.sh` из анализа внутри клона, без упаковки

Так баг воспроизводили в анализе. Фикстура `leak` лежит в клоне, Vitest 5.0.5
берётся из `node_modules` клона, mootant — из `bin/mootant.js` и `dist/`
клона. Скрипт проверяет только код 124 за 40 с. Он не убеждается, что отчёт
допечатан, не делает контрольного прогона и глушит stderr mootant. На
перегруженной машине медленный, но не зависший прогон дал бы ложное
`REPRODUCED`, поэтому основной способ — шаг 3.

```bash
cd "$ROOT"
mkdir -p test/repros
cp -r "$FIX/leak" test/repros/BUG-506
rm -rf test/repros/BUG-506/node_modules test/repros/BUG-506/leak.json
cat > test/repros/BUG-506/run.sh <<'EOF'
#!/bin/bash
# BUG-506: when something in mootant's own process keeps the event loop alive,
# such as a server a Vitest globalSetup leaves open, `mootant run` prints the
# whole report and never exits; `vitest --run` exits after its teardown
# timeout. Builds dist when it is missing. Exit 1 = reproduced.
set -u
HERE=$(cd "$(dirname "$0")" && pwd)
REPO=$(cd "$HERE/../../.." && pwd)
[ -f "$REPO/dist/cli/index.js" ] || (cd "$REPO" && pnpm run build >/dev/null)
cd "$HERE"
START=$(date +%s)
timeout 40 "$REPO/node_modules/.bin/vitest" --run </dev/null >/dev/null 2>&1
echo "vitest --run: exit $? after $(( $(date +%s) - START )) s"
START=$(date +%s)
timeout 40 node "$REPO/bin/mootant.js" run src --no-cache </dev/null >report.txt 2>/dev/null
CODE=$?
echo "mootant run: exit $CODE after $(( $(date +%s) - START )) s; report lines: $(wc -l <report.txt)"
rm -rf report.txt "$HERE/node_modules"
if [ "$CODE" -eq 124 ]; then
  echo "REPRODUCED: mootant printed its report and did not exit within 40 s"
  exit 1
fi
EOF
chmod +x test/repros/BUG-506/run.sh
test/repros/BUG-506/run.sh; echo "run.sh exit=$?"   # 1 = воспроизведено
```

Перед `pnpm test` и коммитом убери каталог: `rm -rf "$ROOT/test/repros"`.

### Родственный сценарий (вне рамок этого бага)

Скептик нашёл случай, который предложенное исправление не покрывает: teardown
`globalSetup` никогда не завершается, а event loop при этом ничто не держит.
Он проверял две фикстуры. В `hang-teardown` стоял `global-setup.js` ниже и
сильный тест. В `hang-teardown-threshold` был тот же teardown, запись меток в
`marks.txt`, слабый тест и `--threshold 100`. Ниже — вариант со слабым тестом,
без меток.

```bash
cp -r "$FIX/leak-threshold" "$FIX/hang-teardown"
cat > "$FIX/hang-teardown/global-setup.js" <<'EOF'
export default function setup() {
  // teardown that never settles, e.g. waiting for a connection that never ends
  return () => new Promise(() => {})
}
EOF
cd "$FIX/hang-teardown"
timeout 60 node "$MOOTANT" run src --no-cache --threshold 100 </dev/null; echo "exit=$?"
```

У скептика в обеих фикстурах, с `--json` и без, stdout был пуст. В stderr была
только строка вида `+ dry run  1 test in 0.5s`, код выхода 0. Это тихий ложный
«зелёный» (fail-open). Механизм и направление исправления описаны в п. 5
«Подозреваемых мест».

## Ожидаемое поведение

Когда команда напечатала вывод (а `run` ещё и записал HTML-отчёт, если он
запрошен), mootant завершается сам, даже если код проекта оставил открытый
хэндл:

- если процесс не завершился естественно за выбранный таймаут (п. 3
  «Подозреваемых мест»), mootant печатает в stderr предупреждение и выходит с
  кодом, который выставила команда: 0 в `leak`, 1 в `leak-threshold` с
  `--threshold 100`. Предупреждение говорит, что что-то в процессе (например,
  сервер из `globalSetup` или `mootant.config.*`) не даёт ему завершиться,
  сколько mootant ждал и как найти причину;
- stdout не меняется: полный отчёт, а с `--json` — только JSON;
- если процесс ничто не держит (`control`), выход как сейчас: сразу, без
  задержки и предупреждения;
- то же для `mootant list` (`config-leak`).

## Подозреваемые места в коде

- `bin/mootant.js:5` — `run()` вызывается без `await` и без выхода. Строка 1 —
  hashbang `#!/usr/bin/env node` (см. п. 2 ниже).
- `cli/index.ts:12-32` — `run()`, общий вход для `run` и `list`: промис
  завершается, когда команда напечатала вывод.
- `cli/run-mutation.ts:38-95` — `runMutation()`. Отчёт печатается на `:63-72`,
  `process.exitCode = 1` выставляется на `:74` и `:93` и ещё на `:136` в
  `saveHtmlReport` (HTML пишется после отчёта, `:76-82`). JSDoc `:26-28`
  объясняет выбор `exitCode` вместо `process.exit()`: «so piped output is
  never cut».
- `cli/run-list.ts:17-46` — `runList()`: `exitCode` на `:39` и `:44`, та же
  оговорка в JSDoc `:12-13`.
- `core/run-mutants.ts:320-322` — `await session.close()` в `finally`: отчёт
  печатается только после того, как `close()` завершился.
- `adapters/vitest/start-vitest-session.ts:149-157` — `closeVitest()`:
  `await vitest.close()` (`:151`), вызывается через `close()` (`:175-178`).
  Программный `close()` выход не форсирует.
- `cli/terminal/create-spinner.ts:149-152` — комментарий «unicorn/no-process-exit
  allows `process.exit()` only in a handler passed to `process.on()`» неполон
  (п. 2).
- `types/adapter/adapter-session.d.ts:13-70` — в сессии адаптера нет поля с
  таймаутом закрытия (п. 3).
- `test/cli/index.test.ts` — шпион на `process.exit` бросает ошибку
  (`:76-78`), тесты проверяют, что выхода нет (`:101`, `:111`, `:137`, `:155`),
  моки восстанавливаются после каждого теста (`:86`).

Направление исправления (выводы верификаторов и чтения кода):

1. Механизм — как у Vitest CLI. Когда команда допечатала вывод и записала HTML,
   взведи таймер с `unref()`. Если к его срабатыванию процесс ещё жив, напечатай
   предупреждение в stderr и вызови `process.exit()`. Без аргумента Node берёт
   `process.exitCode`, так что код 1 «ниже порога» сохранится. Таймер с
   `unref()` процесс не держит, поэтому обычный прогон завершается так же
   быстро, как сейчас. Выходить сразу после `run()` нельзя (см.
   «Ограничения»).
2. Где взводить таймер. Есть три варианта.
   - `bin/mootant.js` после `await run()` — самое простое место. Правило
     `unicorn/no-process-exit` (в `@azat-io/eslint-config` 2.102.0 оно
     `error`) к этому файлу не применяется. В `eslint-plugin-unicorn` 79.0.0
     (версия из `pnpm-lock.yaml`) `rules/no-process-exit.js:14-18` пропускает
     файлы, которые начинаются с hashbang. Верификатор прогнал ESLint проекта:
     `process.exit()` вне `process.on()` в `bin/mootant.js` даёт 0 ошибок, а
     без hashbang — ошибки `unicorn/no-process-exit` и `node/hashbang`.
     Компромисс: `bin/` нет ни в `coverage.include` (`vitest.config.ts:15`:
     `adapters/**`, `cli/**`, `core/**`), ни в `tsconfig.json:4` (`**/*.ts`,
     `**/*.astro`). Импортирует он собранный `../dist/cli/index.js`, так что
     юнит-тестом это место не покрыть, остаётся сквозная проверка.
   - Логика в `cli/` покрывается тестами и порогом 100%, но правило там
     действует. Оно разрешает `process.exit()` внутри обработчика, переданного
     прямо в вызов `process.on`, `once`, `addListener`, `prependListener` или
     `prependOnceListener` (`rules/no-process-exit.js:28-35,57-67`). Ещё оно
     пропускает файлы с hashbang и файлы, которые импортируют `worker_threads`
     (`:14-18`, `:37-55`, `:84-87`). Комментарий в
     `cli/terminal/create-spinner.ts:149-152` описывает только первый случай.
     Отключение правила с причиной
     (`// eslint-disable-next-line <правило> -- <причина>`) в проекте
     встречается, но для другого правила (`cli/html/client/set-markup.ts:10`).
     Можно и так: функция в `cli/` взводит таймер и печатает предупреждение, а
     сам вызов `process.exit()` ей передаёт `bin/mootant.js`. Этот вариант не
     проверялся.
   - Если таймер взводится внутри `run()` (`cli/index.ts:12-32`), его взведут и
     существующие тесты `test/cli/index.test.ts`, которые много раз зовут
     `run()`. В воркере Vitest 5.0.5 `process.exit` заменён функцией, которая
     бросает `process.exit unexpectedly called with "<code>"`
     (`node_modules/vitest/dist/chunks/base.CzXt2BO_.js:120-123`). Таймер,
     переживший тест, может сработать после восстановления моков и дать
     необработанную ошибку в прогоне. Это вывод из чтения кода, запуском не
     проверялось. Поэтому взводи таймер вне `run()` (например, отдельной
     функцией, которую зовёт `bin/mootant.js` после `await run()`) либо
     используй фейковые таймеры во всех тестах, которые зовут `run()`.
3. Таймаут не определён: выбери его явно и назови в предупреждении. Первый
   вариант — константа mootant (например, 10 с, как `teardownTimeout` Vitest
   по умолчанию). Второй — `teardownTimeout` из конфига Vitest пользователя.
   Для него значение придётся протащить из адаптера в `cli/`, а в
   `AdapterSession` (`types/adapter/adapter-session.d.ts:13-70`, публичный
   тип) такого поля нет. У адаптера node:test аналога нет, а `list` адаптер не
   запускает вовсе. Формулировка «как `vitest --run`» двусмысленна, поэтому в
   коде, тесте и предупреждении нужно конкретное значение.
4. Предупреждение выводи только в stderr: stdout с `--json` должен остаться
   чистым JSON. Образец текста — у Vitest (`cli-api.De07GUeT.js:13287-13293`
   в 5.0.5, вывод 5.1.0 на `leak` приведён в «Фактическом поведении»). Полезно
   назвать, что держит процесс. `process.getActiveResourcesInfo()` у скептика
   показывал только `TCPServerWrap`, а у воспроизводящего верификатора
   (stdout и stderr в pipe) — `["PipeWrap","PipeWrap","TCPServerWrap"]`.
   Подсказка про reporter `hanging-process` годится только для прямого запуска
   Vitest пользователем: в сессии mootant стоят свои репортёры
   (`adapters/vitest/start-vitest-session.ts:97-100`).
5. Родственный сценарий нашёл скептик. Предложенное исправление его не
   покрывает, и скептик рекомендует завести на него отдельный баг.
   - (а) `vitest.close()` не завершается, и при этом ничто не держит event loop
     (teardown `globalSetup` возвращает `new Promise(() => {})`). Тогда event
     loop опустевает прямо внутри `await session.close()`
     (`core/run-mutants.ts:321`), до `progress.finish()`
     (`cli/run-mutation.ts:51`) и печати отчёта. Процесс выходит с кодом 0 и
     пустым stdout. Так происходит даже с `--threshold 100` и выжившим
     мутантом, с `--json` и без. Метки в `marks.txt` показали, что setup и
     teardown выполняются в PID mootant. Vitest в том же случае тоже выходит
     с 0, но результаты он печатает и `exitCode` выставляет до `close()`. У
     mootant же получается тихий ложный «зелёный» (fail-open).
   - (б) `close()` не завершается, а что-то держит loop. Тогда отчёта нет, и
     процесс висит вечно. Таймер «после отчёта» до этого места не дойдёт, а
     Vitest CLI взводит свой таймер до `await this.close()`. Это вывод из
     чтения кода, запуском не проверялось.
   - Таймер с `unref()`, взведённый до `session.close()`, помогает только в
     (б). Для (а) нужен страж на `process.on('exit')` или `'beforeExit'`: если
     команда не завершилась, он печатает ошибку и выставляет код 1. По
     документации Node, если `bin/mootant.js` будет ждать `run()` через
     `await` верхнего уровня, в (а) процесс выйдет с кодом 13 (unsettled
     top-level await) и предупреждением, а не с 0. Это тоже не проверялось.
     Если закрываешь (а) или (б) в этом же PR, добавь на них проверки. Если
     нет — так и напиши в PR.

## Критерий готовности

- Есть автотест механизма выхода.
  - Если логика (кроме, возможно, самого вызова `process.exit()`) живёт в
    `cli/` или `core/`, нужен юнит-тест с фейковыми таймерами
    (`vi.useFakeTimers()`) и моком `process.exit`. Он проверяет четыре вещи.
    (1) До истечения таймаута выхода нет. (2) После него — ровно один вызов с
    сохранённым кодом, в двух случаях: `process.exitCode` не задан и равен 1.
    (3) Предупреждение уходит в stderr, в stdout ничего не пишется. (4) Таймер
    не держит процесс: фейковые таймеры Vitest 5.0.5 возвращают объект с
    `ref`, `unref` и `hasRef`
    (`node_modules/vitest/dist/chunks/index.aTZaPVhf.js:4983-4996`). Тест
    падает до исправления и проходит после, новые ветви покрыты (порог 100%,
    `vitest.config.ts:8-15`). Ни один тест не должен оставлять после себя
    взведённый настоящий таймер выхода (п. 2).
  - Если вся логика в `bin/mootant.js`, юнит-теста не будет (п. 2). Объясни
    это в PR и приложи вывод сквозной проверки ниже.
- Сквозная проверка после пересборки, в той же сессии shell, что шаги 1–3:

  ```bash
  # после исправления
  cd "$ROOT"
  pnpm build && pnpm pack && mv mootant-*.tgz "$PACK/"
  cd "$FIX"
  npm i -D "$TGZ"   # если подхватилась старая сборка: rm -rf node_modules package-lock.json && npm i -D vitest@5 "$TGZ"

  cd "$FIX/leak"
  time timeout 60 node "$MOOTANT" run src --no-cache </dev/null >out.txt 2>err.txt; echo "exit=$?"
  timeout 60 node "$MOOTANT" run src --no-cache --json </dev/null >out.json 2>/dev/null; echo "exit=$?"
  node -e 'JSON.parse(require("node:fs").readFileSync(0, "utf8"))' <out.json && echo "json ok"
  timeout 60 node "$MOOTANT" run src --no-cache --html </dev/null >/dev/null 2>&1; echo "exit=$?"; ls .mootant/report.html

  cd "$FIX/leak-threshold"
  timeout 60 node "$MOOTANT" run src --no-cache --threshold 100 </dev/null >/dev/null 2>&1; echo "exit=$?"

  cd "$FIX/control"
  time timeout 60 node "$MOOTANT" run src --no-cache </dev/null >/dev/null 2>err.txt; echo "exit=$?"

  cd "$FIX/config-leak"
  timeout 60 node "$MOOTANT" list src </dev/null >/dev/null 2>err.txt; echo "exit=$?"
  ```

  Ожидается:
  - `leak`: `exit=0`, а не 124. В `out.txt` полный отчёт со строкой
    `score           100%` и без предупреждения, в `err.txt` есть
    предупреждение. Время — это время до отчёта плюс выбранный таймаут; с 10 с
    это около 12 с. Для этих проверок таймаут должен быть заметно меньше 60 с.
  - `leak --json`: `exit=0` и `json ok`.
  - `leak --html`: `exit=0`, и `.mootant/report.html` записан
    (`docs/content/guide/cli.mdx:50`). Таймер взводится только после записи
    HTML.
  - `leak-threshold`: `exit=1`.
  - `control`: `exit=0`, время того же порядка, что до исправления (у
    верификаторов 2,0–2,1 с), в `err.txt` нет предупреждения.
  - `config-leak`: `exit=0`, а не 124, в `err.txt` есть предупреждение.

  Текст предупреждения приложи к PR.
- Выбранный таймаут назван в предупреждении (п. 3). По желанию опиши поведение

- Родственный сценарий (п. 5) в этот критерий не входит. В PR явно скажи,

- По желанию: `test/repros/BUG-506/run.sh` из шага 4 печатает

- `pnpm test` полностью зелёный (включая 100% coverage, `test:js`,

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  `AdapterSession` (`types/adapter/adapter-session.d.ts`) — публичный тип
  адаптеров. Новое необязательное поле с ним совместимо, но это всё равно
  изменение API, и его нужно описать.
- Не выходи раньше времени. Вызывай `process.exit()` только после того, как
  команда допечатала вывод и записала HTML, и только если процесс сам не
  завершился за таймаут. Node при `process.exit()` не ждёт незавершённых
  асинхронных записей в `process.stdout` и `process.stderr`, а проект
  сознательно выставляет `exitCode`, «so piped output is never cut»
  (`cli/run-mutation.ts:26-28`, `cli/run-list.ts:12-13`). Предупреждение
  выводи только в stderr.
- Тест-воспроизведение из анализа (`run.sh` и фикстуру из шага 4) нельзя
  копировать как есть в `test/repros/` для коммита: регрессионный тест
  перепиши в стиле проекта. Каталог
  `test/repros/` не исключён ни из ESLint, ни из knip, cspell, Vitest и `tsc`.
  Исключён только `test/fixtures/**` (`eslint.config.ts:15`,
  `knip.config.ts:5`, `cspell.config.ts:44`, `vitest.config.ts:18`,
  `tsconfig.json:2`). Строгий ESLint (`@azat-io/eslint-config` с perfectionist
  и vitest, `eslint.config.ts:6-12`) проверяет имена файлов, `describe`/`it` и
  порядок импортов. Фикстуры клади в `test/fixtures/**`. Prettier
  (`test:format`) их проверяет: `.prettierignore` в репозитории нет.
  `test/repros/`, tarball и временные каталоги в коммит не входят.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro` (14 ошибок
  `ts(2322)` в `docs/components/*.astro`). `tsconfig.json:2-4` включает
  `**/*.ts` и не исключает `dist/`. После сборки в программу попадает
  `dist/types/html/inline-script.d.ts` (из `types/html/inline-script.d.ts:1`)
  с `/// <reference types="vite/client" />`, и объявления `*.svg` из Vite
  конфликтуют с SVG-компонентами Astro. В CI джоба Astro пакет не собирает,
  поэтому там она зелёная. После сборки проверяй `test:unit`, `test:js`,
  `test:types` и остальные `test:*` по отдельности, а `test:astro` запускай
  после `rm -rf dist`.
- Есть тесты, которые зависят от окружения; к багу они не относятся. Два теста
  в `test/cli/run-list.test.ts` и два в `test/cli/run-mutation.test.ts` ждут
  Unicode и падают при `TERM=linux` (`cli/terminal/is-unicode-supported.ts:13`),
  поэтому запускай их с `TERM=xterm-256color`. Тест «skips test files it cannot
  read» (`test/adapters/node-test/score-node-test.test.ts:98`) падает под
  root. При заданном `NODE_OPTIONS` покрытие веток меньше 100%
  (`adapters/node-test/start-node-test-session.ts:119,167`), поэтому запускай
  `env -u NODE_OPTIONS pnpm test:unit`.
- Для установки зависимостей нужен pnpm 12 (см. «Воспроизведение»). В
  npm-фикстурах ставь `vitest@5`, не `vitest@5.0.5`: в npm 10.9.9 установка
  5.0.5 падает в arborist (`Cannot read properties of null (reading
  'edgesOut')`).
