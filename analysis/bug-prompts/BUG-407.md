# BUG-407: переустановка той же версии mootant обнуляет кэш вердиктов

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: medium. Статус: подтверждён. Найдено на коммите
> 170ec52.
>
> Перепроверено независимо: воспроизведено (скрипт из ветки репро выходит с
> кодом 1; скептик повторил сценарий 2 из 2 раз на Vitest 5.1.0 без
> `--legacy-peer-deps`: 3 из 3 вердиктов из кэша, после переустановки 0 из 3,
> со старым mtime снова 3 из 3; отдельный агент анализа в эмуляции GitHub
> Actions получил 0 из 67 после `npm ci` с восстановленным кэшем и 67 из 67
> после `touch -d`); скептик: не опровергнуто, но предлагал low — вердикты не
> искажаются, теряется только переиспользование, и нужен кэш, переживший
> переустановку. Координатор оставил medium: в стандартной конфигурации CI с
> `npm ci` кэш вердиктов между прогонами не работает вовсе.

## Контекст

Кэш вердиктов лежит в `node_modules/.cache/mootant`
(`core/cache/get-cache-path.ts:13-21`). Записи в нём ищутся по ключу тестового
файла, и в каждый такой ключ, инкрементальный тоже, входит ключ окружения
(`core/cache/get-test-file-keys.ts:59-65`, вызовы —
`core/cache/prepare-run-cache.ts:176-202`). Ключ окружения
(`core/cache/get-environment-key.ts:70-88`) включает «штамп сборки» — `mtimeMs`
файла самого модуля `prepare-run-cache` (`core/cache/prepare-run-cache.ts:164`:
`build: (await stat(import.meta.filename)).mtimeMs,`; в пакете это
`dist/core/cache/prepare-run-cache.js`). По JSDoc поля штамп нужен, «so a
rebuild of an unreleased version does not reuse verdicts of the previous
build» (`core/cache/get-environment-key.ts:47-50`; тип `build: number` — `:51`,
место в дайджесте — `:76`).

Но npm при установке ставит файлам пакета текущее время, а не время из архива:
в npm 10.9.9 архив распаковывается с `noMtime: true`
(`pacote/lib/fetcher.js:426` в составе npm). По данным скептика, в tarball
время всех файлов нормализовано к 1985-10-26 08:15:00, но npm его не
использует, поэтому после установки из архива штамп — это время установки.
Значит, переустановка тех же байтов меняет ключ, и ни один вердикт не
переиспользуется. Время сравнивается точно: `mtimeMs` — дробное число и
попадает в дайджест через `JSON.stringify` (`core/cache/create-digest.ts:10`).
Поэтому, по коду, ключ меняет и копия, которая сохранила время только с
точностью до секунды.

Где это проявляется:

- CI с npm: `npm ci` на свежем раннере, а каталог `node_modules/.cache/mootant`
  восстановлен из кэша CI. Отдельный агент анализа эмулировал это (`npm ci` →
  прогон → сохранить кэш → `npm ci` → восстановить → прогон) и получил 0 из 67
  вердиктов из кэша. Если после каждого `npm ci` выполнить
  `find node_modules/mootant -exec touch -d '1985-10-26T08:15:00Z' {} +`,
  получается 67 из 67.
- Копия проекта в другой каталог, если у файлов пакета новые mtime (`cp -r`):
  0. Скептик проверил, что в остальном ключ переносим: копия проекта в другом
  каталоге после `npm ci` с восстановленным кэшем дала 0 из 3, а с
  принудительно старым mtime — 3 из 3. Пути в ключах относительные именно ради
  этого: «so the cache file and its keys do not depend on where the project
  lives» (`core/cache/get-portable-path.ts:4-6`). Штамп сводит замысел на нет.
- pnpm. Файлы пакета — жёсткие ссылки на store, поэтому переустановка из того
  же store (`rm -rf node_modules && pnpm install --offline`) mtime не меняет, и
  кэш жив (скептик: 3 из 3). Новый store (другая машина, CI без кэша store)
  даёт новый mtime и сброс кэша, это проверили два агента. Поведение зависит
  от пакетного менеджера.

Не затронуто (проверил скептик). `npm ci` без восстановления кэша: он удаляет
весь `node_modules` вместе с `node_modules/.cache/mootant`. Обычный
`npm install` и добавление другой зависимости: mootant не распаковывается
заново, и mtime прежний. Смена зависимостей и так сбрасывает кэш, потому что
lockfile входит в ключ по замыслу (`core/cache/prepare-run-cache.ts:120-124`).
Скептик также считает, что не страдает CI, который кэширует `node_modules`
целиком, потому что tar сохраняет mtime. Это не проверено; если архив хранит
время с точностью до секунды, ключ, по коду, всё равно сменится.

Последствия касаются только скорости и безопасны: неверных вердиктов нет, все
мутанты просто прогоняются заново, а после одного полного прогона кэш снова
работает. Но промах молчаливый. При попадании в stderr выводится «Reused
cached verdicts for 3 of 3 mutants.» (`core/run-mutants.ts:703-711`), а в
текстовом отчёте — «3 cached» (`cli/report/format-run-text-report.ts:196-199`).
При промахе о кэше не сказано ничего. Документация обещает, что вердикты
кэшируются «between runs» (`readme.md:63`) и переиспользуются, пока «the
mutated file and the files and environment variables its tests read stay the
same» (`docs/content/guide/configuration.mdx:352-355`). Как сохранять кэш
между прогонами CI, она не описывает: раздел про CI
(`docs/content/guide/getting-started.mdx:123-134`) советует только `--since` и
`--threshold`. Документированный способ установки — `npm install -D mootant`
(`readme.md:77`).

## Воспроизведение

Веток `experiment/bug-repros` и `analysis/2026-11` в публичном репозитории нет,
поэтому всё нужное приведено ниже. Проверялось на Linux, Node.js 22.23.4 и
npm 10.9.9. Нужны Node.js 22.12 или новее (этого требует Vitest 5,
`docs/content/guide/compatibility.mdx:23-24`), npm и pnpm 12. В CI стоит
`latest-12` (`.github/actions/install-tools/action.yml`), а
`pnpm-workspace.yaml` использует `configDependencies`; по наблюдениям анализа,
pnpm 10 на этом репозитории зависает. Первая установка в фикстуре идёт из сети,
переустановка — с `--offline`, из npm-кэша.

### Шаг 1. Собрать пакет mootant

`dist/` в git нет (`.gitignore`), а скрипта `prepack` в `package.json` нет, так
что без явной сборки `pnpm pack` упакует пакет без `dist/`.

```bash
# в корне клона azat-io/mootant
pnpm install
pnpm build
pnpm pack                              # пишет mootant-<версия>.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-*.tgz "$PACK/mootant.tgz"   # *.tgz нет в .gitignore, не оставляйте его в дереве
```

### Шаг 2. Скрипт

Сохраните скрипт вне клона как `"$PACK/bug-407.sh"` и запустите
`bash "$PACK/bug-407.sh" "$PACK/mootant.tgz"`. Фикстуру он создаёт во временном
каталоге и удаляет на выходе. Итог — в последней строке вывода; если скрипт
остановился раньше (`bug-407.sh: failed at line …`), это ошибка окружения, а не
результат проверки. Это `test/repros/BUG-407/run.sh` из ветки репро с правками:

- `vitest@5` вместо `vitest@5.0.5 vite@8.3.5 --legacy-peer-deps`. В npm 10.9.9
  установка 5.0.5 падает с `Cannot read properties of null (reading
  'edgesOut')`. Это баг arborist, а не mootant, так что прежний комментарий
  «npm 10 cannot resolve the peer set» был неточен. С 5.1.0 флаг не нужен, и
  скептик воспроизвёл баг так же.
- Файл кэша ищется по шаблону `run-v*.json`. Его имя следует за `CACHE_VERSION`
  (`core/cache/get-cache-path.ts:19`) и после подъёма версии станет
  `run-v4.json`. С жёстко прописанным `run-v3.json` скрипт на исправленной
  версии падал бы на `cp` с тем же кодом выхода 1, что и «баг есть».
- Итоговая строка и необязательный второй аргумент для отрицательного контроля
  (см. «Критерий готовности»). Этот шаг добавлен при редактуре промпта, его
  никто не запускал.

Если исправление переносит или переименовывает `core/cache/prepare-run-cache.ts`,
поправьте путь `stamp` в скрипте.

```bash
#!/usr/bin/env bash
# BUG-407: reinstalling the same mootant package drops every cached verdict.
# Usage: bug-407.sh <mootant tarball> [<dist directory of another build>]
# Exit code: 1 while the bug is present, 0 once a reinstall keeps the verdicts,
# 2 when even an untouched install reuses nothing, 3 when another build of the
# same version still reuses the verdicts.
set -eu
tgz=$(realpath "${1:?path to the tarball from pnpm pack}")
other=${2:+$(realpath "$2")}
work=$(mktemp -d "${TMPDIR:-/tmp}/mootant-bug-407-XXXXXX")
trap 'rm -rf "$work"' EXIT
trap 'echo "bug-407.sh: failed at line $LINENO" >&2' ERR
cd "$work"
cat >package.json <<'JSON'
{ "name": "bug-407", "private": true, "type": "module", "scripts": { "test": "vitest run" } }
JSON
mkdir -p src test
printf 'export function isAdult(age: number): boolean {\n  return age >= 18\n}\n' >src/math.ts
cat >test/math.test.ts <<'TS'
import { expect, it } from 'vitest'

import { isAdult } from '../src/math'

it('isAdult', () => {
  expect(isAdult(30)).toBe(true)
  expect(isAdult(5)).toBe(false)
})
TS
# vitest@5, not 5.0.5: npm 10.9.9 fails on 5.0.5 inside arborist ('edgesOut').
npm i -D --no-audit --no-fund "$tgz" vitest@5 >/dev/null

run() { npx mootant run src --json --all --verbose 2>/dev/null; }
cached() {
  node -e 'let r = JSON.parse(require("fs").readFileSync(0, "utf8")); console.log(r.summary.totalCached ?? 0)'
}

run >/dev/null
cache=$(ls node_modules/.cache/mootant/run-v*.json) # run-v3.json on 170ec52
cp "$cache" saved-cache.json
second=$(run | cached)
echo "same install:   $second cached"

# CI: rm -rf node_modules && npm ci, then node_modules/.cache/mootant is restored.
stamp=node_modules/mootant/dist/core/cache/prepare-run-cache.js
touch -r "$stamp" stamp-reference
rm -rf node_modules/mootant
sleep 1
npm i -D --no-audit --no-fund --offline "$tgz" >/dev/null
mkdir -p "$(dirname "$cache")"
cp saved-cache.json "$cache"
third=$(run | cached)
echo "reinstalled:    $third cached"

# Control: the same files with the old modification time, nanoseconds included.
touch -r stamp-reference "$stamp"
cp saved-cache.json "$cache"
fourth=$(run | cached)
echo "old mtime back: $fourth cached"

if [ -n "$other" ]; then
  # Another build of the same version; package.json and the lockfile stay.
  rm -rf node_modules/mootant/dist
  cp -r "$other" node_modules/mootant/dist
  cp saved-cache.json "$cache"
  fifth=$(run | cached)
  echo "other build:    $fifth cached"
fi

if [ "$second" = 0 ] || [ "$fourth" != "$second" ]; then
  echo "inconclusive: the cache is not reused even without a reinstall"
  exit 2
fi
if [ -n "$other" ] && [ "$fifth" != 0 ]; then
  echo "the key does not change with the code of the package"
  exit 3
fi
if [ "$third" != "$second" ]; then
  echo "BUG-407 reproduced: a reinstall of the same package drops the cache"
  exit 1
fi
echo "BUG-407 not reproduced"
```

## Ожидаемое поведение

Переустановка того же пакета (те же байты) ключ не меняет: строки
`reinstalled` и `old mtime back` показывают столько же вердиктов из кэша,
сколько `same install` (3), последняя строка — `BUG-407 not reproduced`, код
выхода 0. Сборка той же версии с другим кодом ключ меняет: строка
`other build` (если передан второй аргумент) — `0 cached`. Вердикты в обоих
случаях те же, что без кэша.

## Фактическое поведение

Вывод на 170ec52, код выхода 1. Числа в первых трёх строках получены `run.sh`
из ветки репро и скриптом скептика (подписи строк там немного другие). Эта
версия скрипта отличается от них установкой Vitest, шаблоном имени файла кэша
и итоговой строкой; целиком её никто не запускал.

```
same install:   3 cached
reinstalled:    0 cached
old mtime back: 3 cached
BUG-407 reproduced: a reinstall of the same package drops the cache
```

Текстовый отчёт `npx mootant run src` у скептика: промах после `npm ci` с
восстановленным кэшем и попадание в том же каталоге после возврата старого
mtime. При промахе о кэше нет ни слова.

```
# промах
+ dry run  1 test in 0.7s
+ testing 3 mutants  3/3 test runs in 1.0s
...
mutants         3 in 1 file

# попадание
+ dry run  1 test in 1.0s
Reused cached verdicts for 3 of 3 mutants.
...
mutants         3 in 1 file, 3 cached
```

## Подозреваемые места в коде

- `core/cache/prepare-run-cache.ts:164` — `mtimeMs` как идентификатор сборки.
  `prepareRunCache` вызывается один раз за прогон (`core/run-mutants.ts:444`).
- `core/cache/get-environment-key.ts:47-51` — JSDoc поля `build` и его тип
  `number`; `:76` — его место в дайджесте; `:59-69` — JSDoc функции
  («mootant's version and build»).
- `test/core/cache/get-environment-key.test.ts:26` (`build: 1`) и `:56`
  (`['the build', { build: 2 }]`) — единственные места, где проверяется штамп.
  В `test/core/cache/prepare-run-cache.test.ts` штамп не проверяется (прежняя
  версия промпта ошибочно называла этот файл), но его хелперы `prepare` (`:38`)
  и `reuses` (`:104-120`) подходят для теста «вторая подготовка кэша
  переиспользует запись».
- `core/cache/cache-version.ts:6` и тесты, закрепившие версию 3:
  `test/core/cache/cache-version.test.ts:8-9` (`toBe(3)`, `/run-v3\.json$/u`) и
  `test/core/cache/get-cache-path.test.ts:9` (`run-v3.json`). Пример в JSDoc
  `core/cache/get-cache-path.ts:11` уже устарел (`run-v2.json`).
- `vite.config.ts` — если идентификатор вшивает сборка. `preserveModules: true`
  (`:133`): каждый модуль собирается в отдельный файл `dist/`.
  `vitest.config.ts:3-6` подмешивает `vite.config.ts`, так что `define` оттуда
  попадёт и в unit-тесты; как именно Vitest применяет его к исходникам, не
  проверено.
- `core/run/get-package-directory.ts:12-24` — каталог пакета и в сборке, и в
  исходниках; из исходников это корень репозитория.

Направление исправления. Нужен идентификатор, который зависит от байтов кода
пакета, а не от времени файлов: те же байты дают тот же ключ, другие байты
любого модуля — другой.

Что подходит (из исходного анализа и рекомендации агента раздела UX; ни один
вариант не реализован и не проверен):

1. Константа, которую пишет сборка: хэш содержимого (исходников, из которых
   собран `dist/`, или самого результата) либо коммит плюс хэш
   незакоммиченных изменений. Агент раздела UX советует вшивать идентификатор
   через `define`, чтобы не читать файлы `dist/` на каждом прогоне.
2. Хэш байтов модулей пакета, вычисленный один раз за прогон (в
   `prepareRunCache` или с мемоизацией). Для масштаба: в сборке 170ec52,
   сделанной при анализе, в `dist/` было 608 файлов `.js` общим объёмом около
   0,94 МБ, плюс 822 файла `.d.ts`.

Для обоих вариантов решите, каким будет идентификатор при запуске из
исходников. Unit-тесты и сквозные тесты сьюта (например,
`test/adapters/vitest/index.test.ts`) вызывают `core/cache/prepare-run-cache.ts`
напрямую. `getPackageDirectory()` вернёт там корень репозитория, а хэшировать
его целиком, с `node_modules`, нельзя. Если тип поля `build` меняется (хэш —
строка), поправьте `EnvironmentInput` (`core/cache/get-environment-key.ts:51`)
и тесты `test/core/cache/get-environment-key.test.ts:26`, `:56`.

Что не подходит (вывод из кода):

- Убрать `build` из ключа. Версия из `package.json`
  (`core/cache/get-environment-key.ts:75`) одна у всех сборок невыпущенной
  версии, и пересборка переиспользует вердикты прошлой сборки — именно от
  этого поле и защищает.
- Хэшировать только `prepare-run-cache.js` (`import.meta.filename`). Из-за
  `preserveModules` правка адаптера, мутатора или рантайма байты этого файла не
  меняет.
- Любое время файлов пакета: округлённое до секунд, время другого файла
  (например, `package.json`). npm ставит время установки всем файлам.

Первые два варианта ловит отрицательный контроль из «Критерия готовности».

## Критерий готовности

- **Сквозная проверка.** После исправления (новые `pnpm build` и `pnpm pack`)
  скрипт из «Воспроизведения» печатает `3 cached` в строках `same install`,
  `reinstalled` и `old mtime back`, последняя строка — `BUG-407 not
  reproduced`, код выхода 0. На 170ec52 тот же скрипт печатает `BUG-407
  reproduced…` и выходит с кодом 1. Подъём `CACHE_VERSION` скрипту не мешает:
  файл кэша он ищет по шаблону.
- **Отрицательный контроль: другие байты — другой ключ.** Шаг не проверен: его
  добавили при редактуре промпта. После упаковки tarball для сквозной проверки
  временно измените байты модуля вне `core/cache/`, например допишите символ в
  текст «Reused cached verdicts…» (`core/run-mutants.ts:708`). Затем
  `pnpm build` и `cp -r dist "$PACK/dist-other"`, откатите только эту правку и
  снова выполните `pnpm build`. Запуск
  `bash "$PACK/bug-407.sh" "$PACK/mootant.tgz" "$PACK/dist-other"` печатает
  `other build: 0 cached` и выходит с кодом 0. Код 3 значит, что ключ не видит
  код пакета. Если идентификатор хранится вне `dist/`, перенесите в фикстуру и
  его.
- **Unit-тесты.**
  - На источник идентификатора: при тех же байтах и другом mtime (`utimes`)
    идентификатор тот же, при других байтах любого файла — другой. Если он
    вычисляется во время прогона, проверяйте на временном каталоге (`mkdtemp` и
    `utimes`, как в `test/core/cache/find-changed-files.test.ts:1`, `:29`).
    Если идентификатор вычисляет сборка, а код вычисления лежит вне
    `adapters/`, `cli/` и `core/` (покрытие считается только там,
    `vitest.config.ts:15`), напишите в PR, что доказательство — сквозные
    проверки выше.
  - Регрессионный тест, который падает на 170ec52 и проходит после
    исправления: ключ окружения не зависит от mtime модуля. Например, в
    `test/core/cache/prepare-run-cache.test.ts` между двумя вызовами `prepare`
    меняется только mtime, который `stat` возвращает для файла модуля, и
    `reuses(...)` даёт `true`. Подменить `stat` можно через `vi.mock` для
    `node:fs/promises` с пропуском остальных путей (`vi.mock` в проекте уже
    используют, например `test/cli/run-mutation.test.ts:22-24`); этот способ не
    проверен. Mtime исходника в репозитории в тесте не меняйте: до исправления
    от него зависят параллельно идущие тесты кэша, например «reuses every
    verdict of an unchanged project» (`test/adapters/vitest/index.test.ts:1456`).

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
- Если идентификатор пишет сборка, проверь вручную, что после `pnpm build` он
  есть в `dist/` (и в tarball после `pnpm pack`). `test:usage` — это просто
  `knip` (`package.json`, `scripts`): собранный пакет он не проверяет, а
  отдельного скрипта для такой проверки нет. Убедись, что knip
  (`pnpm test:usage`) и `tsc` (`pnpm test:types`) принимают новый код, например
  объявление глобальной константы.
- Скрипт-воспроизведение (в анализе — `test/repros/BUG-407/run.sh`, здесь —
  `bug-407.sh`) не копируй в репозиторий как есть, ни в `test/repros/`, ни
  куда-либо ещё: он ставит пакеты из сети и в сьют не встраивается. Постоянные
  тесты пиши в стиле проекта под строгий ESLint: имена файлов
  (`unicorn/filename-case`), `describe`/`it`
  (`vitest/require-top-level-describe`), порядок импортов
  (`perfectionist/sort-imports`), JSDoc. Каталог `test/repros/` не исключён ни
  из ESLint, ни из knip, cspell или tsc. Исключён только `test/fixtures/**`
  (`eslint.config.ts:15`, `knip.config.ts:5`, `cspell.config.ts:44`,
  `vitest.config.ts:18`, `tsconfig.json:2`), туда и клади фикстуры, если
  понадобятся. Их всё равно проверяет `test:format`: `.prettierignore` в
  репозитории нет.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: 14 ошибок
  `ts(2322)` в `docs/components/*.astro` (см. analysis 00-baseline).
  `tsconfig.json:4` включает `**/*.ts`, а `exclude` (`:2`) не исключает
  `dist/`. После сборки в программу попадает

  остальные скрипты по отдельности, а `test:astro` запускай после
