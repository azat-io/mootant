# BUG-500: `mootant.config.ts` из документации не грузится в CommonJS-пакете на Node ≥ 22.18

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Серьёзность: low (заявлялась medium, итог независимой
> перепроверки — low). Статус: подтверждён. Найдено на коммите 170ec52.
>
> Перепроверено независимо: воспроизведено (`run.sh` из шага 1 — код 1 на
> Node 22.18.0, 22.23.4, 24.22.1, 24.22.2 и 26.13.0, 3 из 3 повторов на
> 22.23.4, и код 0 на 22.12.0 с jiti; с нуля на mootant из tarball в проекте
> после `npm init -y` у npm 11 — то же, причём установленный jiti на 22.18+ не
> помогает); скептик: не опровергнуто, но серьёзность снижена до low, и
> координатор это принял. Сбой громкий и случается до запуска мутантов
> (ложных вердиктов нет), обходится переименованием в `mootant.config.mts` или
> `"type": "module"`, конфиг необязателен, а затронуты только пакеты с явным
> `"type": "commonjs"` (новые проекты npm 11) на Node ≥ 22.18.

## Контекст

Гайд по конфигурации предлагает создать `mootant.config.ts` с
`import { defineConfig } from 'mootant'` и `export default …`
(`docs/content/guide/configuration.mdx:77-91`) и говорит, что TS-конфигу нужен
Node 22.18+ или jiti (`:121-122`, `docs/content/guide/compatibility.mdx:26-28`).
О поле `type` пакета там ничего нет, `.mts` упомянут только в списке
расширений (`configuration.mdx:101`). `loadTypescriptConfig` при
`process.features.typescript` всегда делает нативный `import()`
(`core/config/load-typescript-config.ts:16-18` →
`core/config/import-config.ts:12`), а Node определяет формат `.ts` по полю
`type` ближайшего `package.json`: в пакете `"type": "commonjs"` ESM-синтаксис —
синтаксическая ошибка. jiti, даже установленный, не пробуется: ветка с ним
(`load-typescript-config.ts:19-30`) работает только без type stripping.

npm 11 (идёт с Node 24) пишет `"type": "commonjs"` в `npm init -y` (npm 10 поле
не пишет, а `pnpm init` у pnpm 12 пишет `"type": "module"`). Поэтому новый
npm-проект, который взял пример из гайда, получает ошибку на первом же запуске
с этим конфигом. Первый запуск из getting-started (`npx mootant run src` без
конфига, `docs/content/guide/getting-started.mdx:71-77`) при этом работает. На
Node 22.12 с jiti тот же проект работает, так что обновление Node ломает
конфиг. В пакете без поля `type` конфиг грузится, но каждый запуск печатает
предупреждение Node `MODULE_TYPELESS_PACKAGE_JSON`.

Нативный импорт выбран сознательно (JSDoc
`core/config/load-typescript-config.ts:5-14`), но следствие для примера из
документации не обработано. Ту же ловушку с `type` для тестов под tsx проект
знает и обрабатывает с советом пользователю
(`docs/content/guide/compatibility.mdx:70-72`,
`adapters/node-test/check-typescript.ts:62-73`). Существующий тест нативного
пути (`test/core/config/load-typescript-config.test.ts:33-44`) работает в
модульном раннере Vitest во временном каталоге без `package.json`. Там
`import()` конфига обрабатывает Vite, и тип пакета не важен, поэтому тесты
этот случай не ловят (верификатор проверил на Vitest 5.1.0: тот же `.ts` из
каталога с `"type": "commonjs"` внутри раннера загружается, в дочернем `node` —
`SyntaxError`).

## Воспроизведение

Ветки `experiment/bug-repros` в публичном репозитории нет. В анализе фикстура
лежала в ней, в каталоге `test/repros/BUG-500/`; здесь все файлы создаются
командами ниже. Что нужно:

- Node.js 22.18 или новее для воспроизведения (в анализе — 22.23.4; 24 и 26
  ведут себя так же) и Node 22.12.0 для контроля (без type stripping). Нужные
  версии берите с nodejs.org, например
  `https://nodejs.org/dist/v22.12.0/node-v22.12.0-linux-x64.tar.xz`, и
  сверяйте с `SHASUMS256.txt` из того же каталога (так делал верификатор).
  Запускайте через `PATH=<распакованный каталог>/bin:$PATH`. Дешёвая замена
  22.12 — `node --no-experimental-strip-types` на 22.18+ (проверено на
  22.23.4): `process.features.typescript` становится ложным, и mootant идёт в
  jiti.
- pnpm 12 (`contributing.md:98`; в CI — `latest-12`,
  `.github/actions/install-tools/action.yml:14`). pnpm 10 не читает
  `configDependencies` из `pnpm-workspace.yaml:1-2` и зависает даже на
  `pnpm --version` (наблюдение анализа). Сначала выполните `pnpm install`. В
  анализе `pnpm run build` в свежем экспорте без установки под pnpm 12.16.1
  упал с «Your config dependency called "@pnpm/plugin-trusted-deps" at
  "pnpm.configDependencies" doesn't have an integrity checksum», а
  `pnpm install --frozen-lockfile` и затем `pnpm run build` на 170ec52 прошли.
- `bin/mootant.js` импортирует `../dist/cli/index.js` (`bin/mootant.js:3`),
  поэтому CLI работает только после `pnpm build`.

Шаги 2 и 3 рассчитаны на одну сессию shell: они используют переменные `CLONE`
и `TGZ`.

### Шаг 1. Фикстура в дереве клона (так баг найден)

`run.sh` ставит `node_modules/mootant` фикстуры ссылкой на клон, так что
`import … from 'mootant'` в конфиге берёт собранный `dist`. jiti здесь
доступен из `node_modules` клона (`devDependencies`, `package.json:111`),
поэтому на Node 22.12 скрипт выходит с кодом 0. Каталог временный и в коммит
не входит (см. «Ограничения»). Файлы — дословно из ветки анализа.

```bash
# в корне клона azat-io/mootant
pnpm install
pnpm build
mkdir -p test/repros/BUG-500/src

cat > test/repros/BUG-500/package.json <<'EOF'
{
  "name": "bug-500-fixture",
  "private": true,
  "type": "commonjs"
}
EOF

# пример из docs/content/guide/configuration.mdx:80-90 дословно
cat > test/repros/BUG-500/mootant.config.ts <<'EOF'
import { defineConfig } from 'mootant'

export default defineConfig({
  mutators: {
    'string-literal': 'off',
  },
  run: {
    paths: ['src'],
    threshold: 80,
  },
})
EOF

cat > test/repros/BUG-500/src/add.js <<'EOF'
export function add(a, b) {
  return a + b
}
EOF

cat > test/repros/BUG-500/run.sh <<'EOF'
#!/bin/bash
# BUG-500: the mootant.config.ts of the configuration guide fails to load in a
# package with "type": "commonjs" (what `npm init -y` of npm 11 writes) on
# Node.js 22.18 or later: mootant imports .ts natively whenever Node strips
# types, and Node reads the file as CommonJS. Node 22.12 with jiti loads the
# same file. Builds dist when it is missing. Exit 1 = reproduced.
set -u
HERE=$(cd "$(dirname "$0")" && pwd)
REPO=$(cd "$HERE/../../.." && pwd)
[ -f "$REPO/dist/cli/index.js" ] || (cd "$REPO" && pnpm run build >/dev/null)
mkdir -p "$HERE/node_modules"
ln -sfn "$REPO" "$HERE/node_modules/mootant"
cd "$HERE"
echo "node $(node --version), process.features.typescript=$(node -p 'process.features.typescript')"
node "$REPO/bin/mootant.js" list src </dev/null
CODE=$?
rm -rf "$HERE/node_modules"
[ "$CODE" -eq 0 ] || { echo "REPRODUCED: exit $CODE"; exit 1; }
EOF
chmod +x test/repros/BUG-500/run.sh

node --version                                              # нужен 22.18 или новее
bash test/repros/BUG-500/run.sh; echo "run.sh exit: $?"     # 1 = воспроизведено
```

Вердикт `run.sh` зависит только от кода выхода, и верификатор нашёл в этом
ложные срабатывания:

- без собранного `dist` скрипт пытается собрать его сам. Если сборка падает
  (так было в свежем экспорте без `pnpm install`), `node` даёт
  `ERR_MODULE_NOT_FOUND` для `dist/cli/index.js`, а скрипт печатает
  `REPRODUCED: exit 1` — ложноположительно. На Node < 22.18 без jiti он тоже
  вернёт 1, но по другой причине;
- `dist` пересобирается, только когда его нет. После исправления без нового
  `pnpm build` старый `dist` даст ложное «не исправлено».

Воспроизведение засчитывается, только если в выводе есть «Cannot use import
statement outside a module». Строгая проверка вручную (тот же вызов, что в
`run.sh`; в таком виде в анализе не запускалась):

```bash
# в корне клона, после команд выше
cd test/repros/BUG-500
mkdir -p node_modules && ln -sfn ../../../.. node_modules/mootant
node ../../../bin/mootant.js list src </dev/null >out.txt 2>err.txt
echo "exit=$?"
echo "import-error=$(grep -c 'Cannot use import statement outside a module' err.txt)"
echo "node-warning=$(grep -c 'Failed to load the ES module' err.txt)"
echo "mutants=$(grep -c 'arithmetic-operator' out.txt)"
rm -rf node_modules out.txt err.txt
cd ../../..
```

До исправления на Node ≥ 22.18: `exit=1`, `import-error=1`, `node-warning=1`,
`mutants=0`.

### Шаг 2. Упакованный mootant в npm-проекте (как у верификаторов)

Для `mootant list` Vitest не нужен: у скептика в такой фикстуре стояли только
mootant и jiti. Вместо `package.json` ниже можно взять результат
`npx npm@11 init -y`: npm 11 сам пишет `"type": "commonjs"`, а npm 10 — нет.
Верификатор брал `package.json` от `npm init -y` npm 11.19.1, минимальный
`package.json` с тем же полем был у скептика.

```bash
# в корне клона, после шага 1 (pnpm install и pnpm build уже выполнены)
CLONE="$(pwd)"
pnpm pack                                # пишет mootant-0.1.0.tgz в корень клона
PACK="$(mktemp -d)"
mv mootant-0.1.0.tgz "$PACK/"            # *.tgz нет в .gitignore, не оставляйте его в дереве
TGZ="$PACK/mootant-0.1.0.tgz"
FIX="$(mktemp -d)"
cd "$FIX"
mkdir -p src

cat > package.json <<'EOF'
{ "name": "bug-500-npm", "private": true, "type": "commonjs" }
EOF

cat > mootant.config.ts <<'EOF'
import { defineConfig } from 'mootant'

export default defineConfig({
  mutators: {
    'string-literal': 'off',
  },
  run: {
    paths: ['src'],
    threshold: 80,
  },
})
EOF

cat > src/add.js <<'EOF'
export function add(a, b) {
  return a + b
}
EOF

npm i -D "$TGZ"                          # jiti — необязательный peer (package.json:132,140-142), npm его не ставит
M=node_modules/mootant/bin/mootant.js

# а) без jiti
node "$M" list src; echo "exit=$?"
# б) с jiti
npm i -D jiti@2                          # у верификаторов — 2.7.0
node "$M" list src; echo "exit=$?"
# в) jiti вместо type stripping (проверено на 22.23.4)
node --no-experimental-strip-types "$M" list src; echo "exit=$?"
```

Результаты до исправления (логи верификатора и скептика):

| Вызов | Node 22.12.0 | Node 22.18.0, 22.23.4, 24.22.x, 26.13.0 |
| --- | --- | --- |
| а) без jiti | 1, «Cannot load mootant.config.ts: TypeScript configuration files need Node.js 22.18 or later, or the jiti package.» | 1, предупреждение Node и «Cannot load mootant.config.ts: Cannot use import statement outside a module» |
| б) с jiti | 0, список мутантов | 1, то же, что в а): jiti не пробуется |
| в) `--no-experimental-strip-types`, с jiti | — | 0, список мутантов через jiti (в отчётах названа только 22.23.4, другие версии не указаны) |

Обходы и соседние случаи. Верификатор держал каждый вариант в отдельном
каталоге с теми же `node_modules` (mootant из tarball и jiti 2.7.0); в виде
одного каталога с `npm pkg` команды ниже не запускались.

```bash
# там же, jiti установлен
mv mootant.config.ts mootant.config.mts
node "$M" list src; echo "exit=$?"       # 0 на всех версиях — обход
mv mootant.config.mts mootant.config.ts

npm pkg set type=module
node "$M" list src; echo "exit=$?"       # 0, без предупреждений
npm pkg delete type
node "$M" list src; echo "exit=$?"       # 0, но на Node ≥ 22.18 — [MODULE_TYPELESS_PACKAGE_JSON] Warning
npm pkg set type=commonjs

mv mootant.config.ts config.backup
cat > mootant.config.ts <<'EOF'
export default {
  run: {
    paths: ['src'],
  },
}
EOF
node "$M" list src; echo "exit=$?"       # Node со stripping: 1, «Cannot load mootant.config.ts: Unexpected token 'export'»
mv config.backup mootant.config.ts
cd "$CLONE"
```

### Шаг 3 (необязательно). `mootant run` с Vitest в том же проекте

Сценарий скептика: Vitest грузит `vitest.config.ts` в том же ESM-синтаксисе,
а mootant свой конфиг — нет. Ставьте `vitest@5` (у скептика — 5.1.0), а не
`vitest@5.0.5`: в npm 10.9.9 установка 5.0.5 падает в arborist с `Cannot read
properties of null (reading 'edgesOut')`. Это баг npm, не mootant.
`mootant run` без путей берёт `run.paths` из конфига, а без них падает с
«mootant run needs paths, such as "mootant run src".»
(`core/run-mutants.ts:181-185`), поэтому путь указан явно. С `--no-cache`
mootant не читает и не сохраняет кэш вердиктов (`core/run-mutants.ts:110-114`).
У скептика `package.json` был от `npm init -y` npm 11.19.1 (то же
`"type": "commonjs"`). С минимальным `package.json` эти команды в таком виде не
запускались.

```bash
# в той же сессии shell (нужен TGZ из шага 2), Node 22.18 или новее
RUN="$(mktemp -d)"
cd "$RUN"
mkdir -p src test

cat > package.json <<'EOF'
{ "name": "bug-500-run", "private": true, "type": "commonjs" }
EOF

cat > vitest.config.ts <<'EOF'
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: { include: ['test/**/*.test.ts'] },
})
EOF

cat > src/add.ts <<'EOF'
export function add(a: number, b: number): number {
  return a + b
}
EOF

cat > test/add.test.ts <<'EOF'
import { expect, it } from 'vitest'

import { add } from '../src/add'

it('adds', () => {
  expect(add(2, 3)).toBe(5)
})
EOF

cat > mootant.config.ts <<'EOF'
import { defineConfig } from 'mootant'

export default defineConfig({
  mutators: {
    'string-literal': 'off',
  },
  run: {
    paths: ['src'],
    threshold: 80,
  },
})
EOF

npm i -D vitest@5 "$TGZ"
npx vitest run; echo "vitest exit=$?"                     # проходит
npx mootant run src --no-cache; echo "mootant exit=$?"     # 1, «Cannot load mootant.config.ts: Cannot use import statement outside a module»
mv mootant.config.ts mootant.config.mts
npx mootant run src --no-cache; echo "mootant exit=$?"     # прогон проходит, порог 80 применяется
mv mootant.config.mts mootant.config.ts
cd "$CLONE"
```

## Ожидаемое поведение

- Пакет `"type": "commonjs"`, Node ≥ 22.18, jiti установлен:
  `mootant.config.ts` из гайда загружается так же, как на Node 22.12 с jiti.
  `mootant list src` печатает мутант `src/add.js`, код 0, и в выводе нет
  предупреждения Node «Failed to load the ES module…». Оно сбивает с толку:
  советует `.mjs` или смену `type`, а смена `type` может сломать CommonJS-код
  проекта, про `.mts` же в нём ни слова.
- То же без jiti: либо конфиг всё равно загружается, либо mootant завершается
  с кодом 1 и понятным советом («переименуйте в `mootant.config.mts`, добавьте
  `"type": "module"` или установите jiti»), а не одним «Cannot use import
  statement outside a module».
- Поведение не зависит от текста ошибки Node: конфиг без `import` (только
  `export default {…}`) ведёт себя так же, как пример из гайда.
- Без изменений остаются: `"type": "module"`; `mootant.config.mts` и `.cts`;
  `.js`/`.mjs`/`.cjs`; Node без type stripping (jiti, а без jiti — прежнее
  «TypeScript configuration files need Node.js 22.18 or later, or the jiti
  package.»).
- Вне обязательного объёма (сделайте, если исправление это естественно
  покрывает, и опишите в PR):
  - предупреждение `MODULE_TYPELESS_PACKAGE_JSON` в пакете без `type` (так
    пишет `npm init -y` у npm 10);
  - синтаксис, который Node не умеет стирать (`enum` и т. п.), на Node со
    stripping. Сейчас это «TypeScript enum is not supported in strip-only
    mode» и в ESM-пакетах, а на 22.12 с jiti и с `--no-experimental-strip-types`
    такой конфиг грузится;
  - смежная находка анализа BUG-501, отдельный промпт по которой не
    составлялся: `.cts`-конфиг с `require('mootant')` на Node 22.18+ (22.x)
    падает с «request for './instrument/resolve-switched-text.js' is from a
    module not been linked». По заметкам анализа это баг Node 22 в `import()`
    CommonJS-TypeScript-модуля с require(esm); на Node 24 и 26 его нет.

## Фактическое поведение

`run.sh` из шага 1 на Node 22.23.4 (на 22.18.0, 24.22.1, 24.22.2 и 26.13.0 —
то же; `<pid>` и путь клона меняются):

```
node v22.23.4, process.features.typescript=strip
(node:<pid>) Warning: Failed to load the ES module: <клон>/test/repros/BUG-500/mootant.config.ts. Make sure to set "type": "module" in the nearest package.json file or use the .mjs extension.
(Use `node --trace-warnings ...` to show where the warning was created)
Error: Cannot load mootant.config.ts: Cannot use import statement outside a module
REPRODUCED: exit 1
```

Тот же скрипт на Node 22.12.0, где jiti берётся из `devDependencies` клона.
При `TERM=linux` на машине анализа вывод в ASCII (`*`, `->`), в
Unicode-терминале будут `●` и `→`:

```
node v22.12.0, process.features.typescript=false
* mootant list src                        preset recommended

mutants         1 in 1 file

src/add.js
  2:10  arithmetic-operator  a + b -> a  c8s9
```

Матрица верификаторов: mootant из tarball 170ec52, jiti 2.7.0 рядом, если не
сказано иное; в ячейках — код выхода `mootant list src`.

| Фикстура | Node 22.12.0 (`process.features.typescript=false`) | Node 22.18.0, 22.23.4, 24.22.x, 26.13.0 (`strip`) |
| --- | --- | --- |
| `"type": "commonjs"`, конфиг из гайда | 0, список | 1, предупреждение Node и «Cannot use import statement outside a module» |
| то же без jiti | 1, «…need Node.js 22.18 or later, or the jiti package.» | 1, как строкой выше |
| `"type": "commonjs"`, конфиг только с `export default {…}` | не проверялось | 1, «Cannot load mootant.config.ts: Unexpected token 'export'» (версия Node в отчёте не указана) |
| `"type": "commonjs"`, `mootant.config.mts` | 0 | 0 |
| `"type": "module"` | 0 | 0, без предупреждений |
| без поля `type` | 0 | 0, но каждый запуск — `[MODULE_TYPELESS_PACKAGE_JSON] Warning: Module type of file:///…/mootant.config.ts is not specified and it doesn't parse as CommonJS.` |
| `enum` в конфиге (и в `module`, и в `commonjs`) | 0 (jiti) | 1, «TypeScript enum is not supported in strip-only mode», без предупреждения Node |

Ошибка детерминирована: у скептика 7 из 7 падений на трёх версиях Node, от
нагрузки, root, `TERM` и npm не зависит. Классы ошибок: `SyntaxError` без
`code` («Cannot use import statement…»), `SyntaxError` «Unexpected token
'export'» и `SyntaxError` с `code: 'ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX'`
(`enum`). В шаге 3 `vitest run` проходит, `mootant run src` выходит с кодом 1.
После переименования в `.mts` прогон проходит и порог 80 применяется; без
конфига прогон тоже проходит.

## Подозреваемые места в коде

- `core/config/load-typescript-config.ts:15-31` — при
  `process.features.typescript` (`:16-18`) всегда нативный импорт через
  `importConfig`; jiti пробуется только без type stripping (`:19-30`).
  Направление исправления (уточнено верификатором):
  - формат `.ts` нужно определять до импорта, по `type` ближайшего
    `package.json` (`.mts` — всегда ESM, `.cts` — всегда CommonJS). Схема
    «поймать ошибку и перейти на jiti» оставит в выводе предупреждение Node
    «Failed to load the ES module… Make sure to set "type": "module"…»: Node
    печатает его в момент неудачного `import()`, даже если mootant ошибку
    поймает;
  - запасной путь по тексту сообщения ненадёжен. Форм ошибки как минимум три
    (см. «Фактическое поведение»), и привязка к «Cannot use import statement»
    пропустит конфиг без `import`. Если запасной путь всё же нужен (например,
    для `enum`), смотрите на `type` пакета, класс `SyntaxError` и `code`;
  - не сломайте `.ts` с `module.exports = …` в CommonJS-пакете без jiti. По
    семантике Node он сейчас должен грузиться нативно, но в анализе это не
    проверялось.
- `core/config/import-config.ts:11-17` — нативный `import()` (`:12`). Тот же
  загрузчик у `.js`/`.mjs`/`.cjs` (`core/config/load-config.ts:55-57`), их
  поведение менять не нужно.
- `core/config/load-config.ts:51-60` — карта загрузчиков (`.ts`/`.mts`/`.cts`
  → `loadTypescriptConfig`); `:111-115` — обёртка «Cannot load <файл>:
  <сообщение>» без совета. Совет про `.mts` можно добавить здесь или в самом
  `loadTypescriptConfig`.
- `adapters/node-test/list-package-files.ts:14-30` и
  `adapters/node-test/check-typescript.ts:62-73,84-96` — готовый образец для
  той же ловушки с tsx: поиск ближайшего `package.json` и чтение `type`, совет
  пользователю на `:72`. В `core/` импортов из `adapters/` нет (проверено
  grep), так что хелпер придётся вынести в общее место или написать свой в

## Критерий готовности

- Юнит-тесты в `test/core/config/load-typescript-config.test.ts` (при
  необходимости и в `test/core/config/load-config.test.ts`):
  - хотя бы один падает до исправления и проходит после. Внутри Vitest

    проверяет выбор способа загрузки или текст ошибки, а не только загруженный
    объект. Пример для исправления «jiti для `.ts` вне ESM-пакета» (в анализе

    маркер; модуль импортируется заново после `vi.doMock`, как в `:96-109`.

  - тест на случай без jiti: если исправление в этом случае выдаёт ошибку, в
    ней есть совет с `.mts`. Если исправление сначала пробует нативный импорт,
    сымитируйте его отказ моком `../../../core/config/import-config`

## Ограничения

- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
  jiti остаётся необязательной peer-зависимостью (`package.json:132,140-142`).
- Сообщения коммитов — Conventional Commits (commitlint).
- Фикстуру и `run.sh` из шага 1 нельзя оставлять в `test/repros/` или
  копировать как есть в постоянные тесты. Этот каталог не исключён ни из
  ESLint, ни из knip, cspell или tsc: исключён только `test/fixtures/**`
  (`eslint.config.ts:15`, `knip.config.ts:5`, `cspell.config.ts:44`,
  `vitest.config.ts:18`, `tsconfig.json:2`). Постоянные тесты пишите в стиле
  проекта под строгий ESLint: имена файлов, `describe`/`it`, порядок импортов,
  JSDoc. Если понадобится проект-фикстура, кладите её в `test/fixtures/**`.
  Удалите `test/repros/` до запуска `test:js`, `test:types`, `test:spelling`,
  `test:format` и `test:usage`.
- `pnpm test` после `pnpm build` даёт ложные ошибки `test:astro`: 14 ошибок
  `ts(2322)` в `docs/components/*.astro` (установлено в базовом прогоне
  анализа на 170ec52). Причина в `tsconfig.json:2-4`: он включает `**/*.ts` и
  не исключает `dist/`. После сборки в программу попадает
  `dist/types/html/inline-script.d.ts` (из `types/html/inline-script.d.ts`) с
  `/// <reference types="vite/client" />`, и объявления `*.svg` из Vite
  конфликтуют с SVG-компонентами Astro. В CI джоба Astro пакет не собирает
  (`.github/workflows/test.yml:10-33`), поэтому там она зелёная.
  Воспроизведение требует `pnpm build`, поэтому проверяйте `test:unit`,
  `test:js`, `test:types` и остальные скрипты по отдельности, а `test:astro`
  запускайте после `rm -rf dist`.
- Известные зависимости `test:unit` от окружения, не связанные с этим багом
  (установлено в базовом прогоне анализа):
  - 4 теста в `test/cli/run-list.test.ts` и `test/cli/run-mutation.test.ts`
    ждут Unicode-символы и падают при `TERM=linux`
    (`cli/terminal/is-unicode-supported.ts:13`). Запускайте с
    `TERM=xterm-256color`;
  - тест «skips test files it cannot read»
