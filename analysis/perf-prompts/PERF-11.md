# PERF-11: отсев некомпилирующихся мутантов (исследование)

> Самодостаточный промпт для отдельной сессии Claude Code в репозитории
> azat-io/mootant. Ранг 11 из 12 в `analysis/04-performance.md` §4.4 (ветка
> `analysis/2026-11`). Выигрыш: не измерен (точка `s-tsc` в окно не вошла);
> прогноз анализа — малый: такие мутанты быстро убиваются. Риск для вердиктов:
> низкий (статус некомпилирующихся меняется намеренно, вердикты остальных — нет).
> Трудоёмкость: L. Прототип: нет. Тип: исследование с критерием «делать / не
> делать». Замерено на коммите 170ec52; код сверен с `main` на bd7af11.

## Контекст

Mootant не проверяет типы мутантов: на main `typescript` не импортирует ни
`core/`, ни `cli/`, ни `adapters/`, в `package.json:134` он только devDependency.
Мутаторы опираются на подсказки типов из того же файла (`core/hints/`,
`docs/content/mutators/optional-chaining.md:45-46`); категория пропуска `invalid`
(`types/mutant/skip-category.d.ts:1-16`) — о размещении в файле, не о типах.

Путь мутанта, `core/run-mutants.ts`: переключённые файлы — `:409`, `pending` —
`:429`, dry run — `:436`, вердикты из кэша — `:517`, batch (`--fast`) — `:521`,
isolated-раунды — `:525`. В раунде нерешённый мутант берёт 1, 1, 2, 4, 8…
следующих тест-файлов (`core/run/run-isolated-rounds.ts:66-73`): убитый
останавливается на убившем файле, выживший проходит все покрывающие. `Ignored` и
`Error` в score не входят (`types/run/run-status.d.ts:1-14`,
`core/run/compute-score.ts:4-19`).

**Идея (бывш. 8):** не гонять тесты мутантов, которые не проходят `tsc`. У
Stryker это `@stryker-mutator/typescript-checker`: ошибка даёт `CompileError` вне
score, мутанты несвязанных файлов проверяются группой (раздел 3, §3.5).

**Не путать с фичей «проверка типов выживших»** (`analysis/03-competitors.md`
§6.1, must): её цель — шум в отчёте и у агента, а не скорость. Механизм общий —
применить мутанта в памяти к TS LanguageService по `tsconfig` проекта, сравнить
диагностики файла с исходными, дать статус вне score с кодом ошибки; различаются
место вызова и набор мутантов:

| вариант | когда | кого | цель | цена проверки | что экономит |
|---|---|---|---|---|---|
| §6.1 | после прогона | выживших (по желанию и NoCoverage) | шум | ~62 мс × выживших | ничего |
| PERF-11 (а) | до прогона мутантов | всех, кто пойдёт в прогон | скорость | ~62 мс × мутантов | юниты всех некомпилирующихся |
| PERF-11 (б), гипотеза этого промпта | после первого раунда | ещё не решённых | скорость и шум | меньше, чем у (а) | раунды 2+ некомпилирующихся выживших |

Вариант (б) — проверка §6.1, перенесённая до перепроверки выживших.

**Что изменилось на main с 170ec52.** Задача не сделана, путь тот же (`pending`
— `:401` (170ec52)). У мутанта в отчёте `kind` с новыми `element`/`property`
(`b6142d3`) и кавычечными JSX-атрибутами (`cc84180`): замену применяй по
`types/mutant/mutant-kind.d.ts:1-18`. Jest-адаптер (`bc6adec`) не мешает: проверка — в ядре.

## Что сделать

### Шаг 0. Стенд и инструменты

Сессия на main не видит `analysis/`; нужное — в опубликованной ветке. Нужны
hyperfine 1.18, `/usr/bin/time`, pnpm 12 и сеть (`$A/analysis/bench/README.md`).

````bash
git fetch origin analysis/2026-11
A="$HOME/mootant-analysis"; R="$HOME/r11"; mkdir -p "$A" "$R"
git archive origin/analysis/2026-11 analysis/bench analysis/tools/perf-proto | tar -x -C "$A"
git show origin/analysis/2026-11:analysis/tools/compare-verdicts.mjs > /tmp/compare-verdicts.mjs
pnpm install --frozen-lockfile && pnpm build && pnpm pack && mv mootant-*.tgz "$HOME/mootant-dev.tgz"
export BENCH_PROJECTS="$HOME/bench" MOOTANT_TGZ="$HOME/mootant-dev.tgz"
"$A/analysis/bench/setup.sh" cheerio perfectionist fast-json-stringify
git show origin/analysis/2026-11:analysis/03-competitors.md \
  | awk '/<summary><code>typecheck-mutants.mjs<\/code>/{f=1} f&&/^```js$/{p=1;next} p&&/^```$/{exit} p' \
  > /tmp/typecheck-mutants.mjs   # скрипт §2.5, 120 строк: node … <projectDir> <report.json> <out.json>
````

Под main поправь в скрипте `createRequire` (ищет `typescript` над проектом:
возьми TypeScript проекта или поставь `typescript@5.9` уровнем выше) и текст
мутанта — по `kind`: `expression` в скобках (в кавычечном JSX-атрибуте —
`{(…)}`), `block` в фигурных, `element`/`property` как есть. path-to-regexp — на
TypeScript 7 без JS API (README стенда, «Известные ограничения», п. 7): если его
`tsconfig` не читается TypeScript с JS API, пропусти проект и так и запиши.

### Шаг 1. Разложить базовый прогон (Mootant не меняется)

```bash
for P in cheerio perfectionist; do BENCH_RESULTS=$R/base "$A/analysis/bench/run.sh" $P:m-nocache; done
P=cheerio; cd "$BENCH_PROJECTS/$P"   # затем то же для perfectionist
/usr/bin/time -v node /tmp/typecheck-mutants.mjs "$PWD" "$R/base/$P/m-nocache/run-1.json" "$R/tc-$P.json"
```

Сопоставь по `id` отчёт и `tc-$P.json` (`results[].status === 'CompileError'`):
мутантов; C (некомпилирующиеся) по статусам; R = Σ `duration` у C / Σ `duration`
у всех, отдельно у Killed и Survived; цена проверки T (elapsed и пик RSS по
`time -v`). Сохрани id без `Ignored`: `keep-$P-a.txt` — без C, `keep-$P-b.txt` —
без C ∩ Survived. **Ранний выход:** R < 5 % на обоих проектах — итог «не делать»;
старт процессов поднимет R примерно не больше чем вдвое: в окне старт на юнит
(142–156 мс) не больше загрузки (151–752 мс), а она входит в `duration` (§4.5.3).

### Шаг 2. A/B: верхняя граница выигрыша (Mootant не меняется)

`--mutant` повторяется (`cli/parse-arguments.ts:66`), так что C убирается без
кода: (а) — прогон без C, (б) — без C ∩ Survived (переоценка: первый раунд этих
мутантов в (б) остался бы).

```bash
# в своей копии $A/analysis/bench/run.sh, в define_point рядом с m-nocache:
#   m-keep) CMD=$(mootant_run --no-cache $(sed 's/^/--mutant /' "$KEEP_IDS")) ;;
for v in a b; do for P in cheerio perfectionist; do
  KEEP_IDS=$R/keep-$P-$v.txt BENCH_RESULTS=$R/$v "$A/analysis/bench/run.sh" $P:m-keep
done; done
for d in base a b; do node "$A/analysis/bench/summarize.mjs" "$R/$d"; done
```

Сверь с базой `summary.duration.dryRun` и `summary.runs.dry`: dry run не должен
зависеть от `--mutant`, пока у каждого файла есть мутант. G = wall(base) −
wall(вариант) − T, wall — hyperfine mean ± σ (медиана); числа окна — только
ориентир. Для (б) бери T от (а) — верхняя граница. T — проверка подряд до
прогона; перекрытие с dry run (шаг 3) — бонус, а не основа решения.

**Порог (этого промпта, не из анализа):** G ≥ 10 % wall(base) при
непересекающихся mean ± σ хотя бы на одном TS-проекте и G ≥ 0 на другом —
«делать» вариант с бо́льшим G (при близких — (б): он закрывает и §6.1). Иначе —
«не делать» как ускорение; механизм и числа C уходят фиче §6.1.

### Шаг 3. Итог и, если «делать», реализация

**Итог** — при любом решении, в PR или issue: по проекту мутантов, C по
статусам, R, T, wall base / (а) / (б), G, решение и почему. **Если «делать»:**

- модуль в `core/` (функция — файл); TypeScript — optional peer из проекта, как
  `vitest` и `jest` (`package.json:140-163`), загрузка — как у компиляторов Vue и
  Svelte (`core/run-mutants.ts:409-412`). Нет TypeScript, файл не `.ts`/`.tsx`/
  `.mts`/`.cts`, программа не собралась — без проверки, с диагностикой;
- статус вне score (например `CompileError`) с первой диагностикой в `message`:
  `types/run/run-status.d.ts:13-14`, `core/run/compute-score.ts:4-19`, отчёты,
  HTML; новое значение `status` меняет смысл поля — реши про `schemaVersion`
  (`types/report/run-report.d.ts:293`);
- место вызова: (а) — после `reuseCachedVerdicts` (`core/run-mutants.ts:517`;
  взятых из кэша не проверять), до `:521`; (б) — в `runRound` перед вторым
  раундом, по `next` (`core/run/run-isolated-rounds.ts:66-73`);
- не выкидывай отсеянных из `pending` молча — уйдут в отчёт как `Ignored`
  (`core/run/decide-results.ts:47-64`); оставь их в переключённых файлах (`:409`):
  dry run и ключ снимка PERF-02 не изменятся; исход храни в кэше вердиктов
  (`core/cache/`), иначе тёплый прогон снова платит T;
- сессию раннера ведёт главный процесс (`adapters/vitest/start-vitest-session.ts:91`),
  синхронная проверка блокирует его цикл событий — ставь её в `worker_threads`;
  в окне он простаивал 89–92 % (§4.4), и (а) можно перекрыть с dry run;
- выключатель `typecheck: 'off'` (§6.1).

## Инвариант: вердикты не меняются

У мутантов, которые компилируются, не меняются ни статус, ни убивающий файл.

1. **A/B шага 2.** Оставь в `mutants` базы только id из `keep-$P-*.txt` и сравни
   с вариантом: `node /tmp/compare-verdicts.mjs <база> <вариант/run-k.json>`, и с
   `--strict` — 0 расхождений на каждом прогоне (а) и (б). В окне у Mootant 0 смен
   вердиктов за 3 прогона (§4.5.2): расхождение — находка.
2. **После реализации:** база против изменения, `m-cold` по 3 прогона: у id вне
   C — 0 расхождений (и с `--strict`), у C — новый статус, их число — как в
   шаге 1; изменение score записать.
3. **Выборка и JS:** 20 из 20 отсеянных — ошибки `tsc --noEmit` на файле с
   мутантом (§6.1, «Как проверить»; уже в шаге 1); у fast-json-stringify `m-cold`
   вердикты те же, TypeScript не грузится.
4. **Тесты:** новая диагностика даёт статус, старая — нет; JS-файл; нет
   TypeScript; `typecheck: 'off'`; кэш хранит исход; фикстура с некомпилирующимся
   выжившим (`coupon?.code` → `coupon.code` при `coupon: Coupon | undefined`).

## Как измерить выигрыш

Только если «делать»: база — tarball main, изменение — свой
(`"$A/analysis/tools/perf-proto/use-mootant.sh" <проект> <tgz>`); cheerio и
perfectionist — `m-cold`, `m-warm`, `m-one` по 3 прогона, контроль —
fast-json-stringify `m-cold`. Счётчики — как в окне (§4.5.1): длиннее ~30 с —
hyperfine mean ± σ (медиана), короче — GNU elapsed (`run-k.time`). Запиши wall,
CPU, пик PSS дерева, RSS главного процесса (LanguageService — в нём; в окне до
819 МБ) и T. **Успех:** порог шага 2 на `m-cold`; `m-warm` и `m-one` не
медленнее базы сверх σ (в окне, GNU elapsed, perfectionist / cheerio: 80,4 ± 1,2
/ 5,40 ± 0,56 и 6,91 ± 0,41 / 3,60 ± 0,21 с): сборка программы TS ради одного
мутанта в цикле агента может съесть весь выигрыш. Тихая машина.

## Риски и границы

- **Ложный отсев** мутанта, валидного во время выполнения (`null` от бэкенда при
  типе «не null»; mutmut об этом предупреждает), — `typecheck: 'off'` и причина в отчёте.
- **`tsconfig` не совпадает со сборкой** (`paths`, project references, несколько
  `tsconfig`, TS 7 без JS API): программа не собралась — без отсева. Проверка
  только изменённого файла отсеет меньше — это безопасно; Vue и Svelte
  (`<script lang="ts">`) сначала не проверять.
- **Score меняется:** убитые некомпилирующиеся уходят из score, как у Stryker;
  описать в документации и changelog. Откат — выключатель.

## Связанные промпты

- **Фича §6.1 раздела 3** (не PERF-промпт) — общий механизм; при «не делать» ей
  нужны числа шагов 1–2. **PERF-02** (полный кэш): отсеянные остаются в
  переключённых файлах, исход проверки входит в снимок. **PERF-07** (без барьеров
  раундов): если раунды заменит поток, точка (б) — после первого файла мутанта.
- **PERF-01** (P1): сэкономленное время слотов ближе к wall; если влит — меряй
  поверх. **PERF-09** — на тех же данных: убитые и так дешёвые. **PERF-12**
  (выборка) тоже меняет набор мутантов: порядок отсева и выборки задай явно.

## Критерий готовности

- Итог шага 3 записан при любом решении; если «делать» — тесты из «Инварианта», п. 4.
- Эквивалентность: 0 расхождений вердиктов (и с `--strict`) у компилирующихся
  мутантов на cheerio и perfectionist (`m-cold`, 3 прогона); fast-json-stringify
  без изменений; 20 из 20 отсеянных — ошибки `tsc`.
- Выигрыш: G ≥ 10 % wall `m-cold` хотя бы на одном TS-проекте, 3 прогона,
  mean ± σ; `m-warm` и `m-one` не медленнее базы сверх σ.
- `pnpm test` полностью зелёный (включая 100% coverage, `test:js`,
  `test:types`, `test:usage`, `test:spelling`).

## Ограничения

- Скорость не покупается вердиктами: любое расхождение вердиктов с базой у
  мутантов, которые компилируются, — блокер, а не компромисс.
- Соблюдай стиль проекта: TypeScript, ESM, «одна функция — один файл», JSDoc
  на каждую функцию, `let` вместо `const` там, где так принято в проекте,
  строгий ESLint (`@azat-io/eslint-config`), cspell, knip.
- Не ломай публичный API (`exports` в `package.json`, типы в `types/`, формат
  конфига) без явной необходимости; если без этого нельзя — опиши компромисс.
- Сообщения коммитов — Conventional Commits (commitlint).
