# Прототип: быстрый путь ширины для печатного ASCII (`list` и текстовые отчёты)

- Ветка: `experiment/perf-display-width` (worktree `/home/user/wt/perf-dw`),
  коммит `perf: count printable ascii width without grapheme splitting`.
- Diff: [`perf-display-width-ascii-fast-path.diff`](perf-display-width-ascii-fast-path.diff)
  (12 строк в `cli/terminal/get-display-width.ts`).
- Найдено профилем `mootant list core`: `getDisplayWidth` занимал 38–43%
  CPU-времени (`analysis/tools/prof/top-self.mjs`; независимо — BUG-702 агента
  стенда). Каждая ячейка таблицы режется на графемы через `Intl.Segmenter`, и
  каждая графема проверяется двумя Unicode-регэкспами, хотя почти весь вывод —
  ASCII.

## Изменение

Если текст без ANSI-кодов состоит только из печатного ASCII
(`/^[\u{20}-\u{7E}]*$/u`), ширина равна длине строки. Иначе — прежний путь. Для
каждого символа печатного ASCII старый код и так даёт ширину 1: ни один из
них не входит в `Emoji_Presentation` и не является управляющим символом.

До окна, под нагрузкой, CPU-время `user+sys` по 5 чередующимся прогонам
снизилось с 9,28 до 7,64 с (медианы; `perf-display-width-ab-cpu.txt`).

**Итог:** −19% времени текстового `list` на 16 тысячах мутантов, без риска для
вердиктов: код вывода, не ядро. Трудоёмкость: S. Оставшееся время текстового
`list` против JSON (2,6 с) — это остальное форматирование. Его стоит
профилировать дальше, если текстовый `list` по большим каталогам — частый
сценарий.
